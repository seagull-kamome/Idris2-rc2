# 小さなコンストラクタを値で返す(構造体返却): 設計

(原文: `doc/struct-return.md`。内容が乖離した場合は原文を正とする。)

状態: 2026-09-25から実装済みでデフォルトで有効である(`--directive
nostructreturn`で無効にできる)。「結果」の測定を経て有効にした。
4フィールドまでのコンストラクタには、2026-09-26から対応している。
`TODO.md`の「constructor return values are always heap cells」の項目に
対応する。

## 問題

コンストラクタを返す関数は、呼び出し元が結果に対してcaseを行い、フィー
ルドを取り出すだけの場合でも、必ずヒープセルを作る。代表的なのは、本家の
`Core a = IO (Either Error a)`である。`IO`はすでにIRから消えており
(`dumprcexpr`に`MkIORes`は残らない)、`Core`のアクションは
`Left`/`Right`のセルをそのまま返し、呼び出し元がその場で分解する。

再利用解析は、この問題をすでに和らげている。呼び出し元が同じ大きさの
コンストラクタを組み立て直す場合(`Left e => Left e`、
`Right x => Right (f x)`)、受け取ったばかりのセルの上に組み立てる。この
ため、こうした関数の連鎖では、メモリ確保が最下層で1回、解放が最上層で
1回だけで済み、レベルごとには発生しない。それでも残るコストがある。連鎖
ごとにmalloc/freeの組が1つ残り、各レベルでは、一意性の検査
(`reuseOffer`)、その`dupOnShared`の分岐、セル自体の読み書きが残る。

## 範囲: 4種類の固定C型、フィールドは4つまで

```c
typedef union { IDRIS2RC2_Value *p; int64_t i; double d; } IDRIS2RC2_RetField;

typedef struct { int64_t tag; IDRIS2RC2_RetField f0; } IDRIS2RC2_Ret1;
typedef struct { int64_t tag; IDRIS2RC2_RetField f0, f1; } IDRIS2RC2_Ret2;
/* ... IDRIS2RC2_Ret3, IDRIS2RC2_Ret4 */
```

プログラム全体で使う型は、ランタイムヘッダにある4つだけである。型ごと
のレイアウトは持たず、`CFType`も使わない。`Core.CompileExpr.CFType`は
本家の型であり、その`CFStruct`はどのバックエンドでも「C構造体へのポイ
ンタ」を意味する(Chezは`(* name)`、RefCとrc2は`void *`として扱う)。
コンパイラが生成する値渡しのレイアウトを表すのに使うのは筋違いである。

`IDRIS2RC2_Ret1`は16バイトなので、SysV x86-64 ABIではメモリを経由せ
ずに`rax:rdx`で返る。unionは8バイトのワード1つであり、全体が
INTEGERクラスに分類されるためである。それより大きいものは、呼び出し元が
用意したメモリ経由で返る。それでもmallocよりははるかに安い。コンストラ
クタのフィールド`k`は`fk`に置く。Boxedのフィールドは`fk.p`に置く。
ネイティブのフィールド(`Right 3`など)は、構造体のレイアウトがそう定め
ている場合(「ネイティブフィールド」を参照)、アンボックスのまま、整数型
なら(幅を広げて) `fk.i`に、`Double`なら`fk.d`に置く。コンストラクタ
自身のアリティを超えるフィールドと、引数なしコンストラクタのすべての
フィールドは、0のままにする。

関数の幅は、その関数が返すコンストラクタのうち最も幅の広いものに等しい。
最初はフィールド1つから始めた。測定の結果、幅の広いコンストラクタへの
対応は最優先ではないと判断したためである。のちに対応を加えた(「より幅の
広いコンストラクタ」)。

## 測定

### 静的な件数(idris2-lsp、最終的な`dumprcexpr`、2026-09-25)

セッションのスクラッチパッドに置いた使い捨てのツールで、ダンプを解析して
数えた。フィールド数の上限を`k`として、次の条件を満たす関数を数える。
すべての末尾が、フィールド数`k`以下のコンストラクタか、クラッシュか、
同じ条件を満たす別の関数への末尾呼び出しである(最大不動点。少なくとも
1つのコンストラクタに到達する関数に限る)。そのうえで、これらの関数の
呼び出し箇所を、呼び出し元が結果をどう使うかで分類した。

関数20,864個のうち、どこかでコンストラクタを返して終わるものが9,907
個ある。`let v = call ...; case v of`の組は全部で4,959個ある。

| k | 関数数 | 呼び出し後に`case` | 末尾呼び出し | その他の呼び出し |
|---|---|---|---|---|
| 0 | 66 | 0 | 2 | 3 |
| **1** | **8,039** | **3,648** | **3,688** | 4,782 |
| 2 | 9,539 | 3,896 | 4,170 | 10,831 |
| 3 | 10,124 | 3,949 | 4,232 | 11,991 |

- `k = 1`で、呼び出し後に`case`する組全体の74% をすでにカバーする。
  `k = 2`にするとさらに7% 増えるが、構造体は24バイトになり、メモリ
  経由で返ることになる。
- `case`する3,648箇所のうち2,627箇所(72%)は、それ自身も適格な関数
  の中にある。そのため、構造体は連鎖をさかのぼってもそのまま運ばれる。
- 3,648箇所のうち3,312箇所(91%)は、現状でも受け取ったセルの上に組み
  立て直している(`reuse=`)。上述の再利用解析がすでに節約しているのは、
  この部分である。
- コンストラクタを返す関数が`k = 1`で適格にならない主な理由は2つある。
  2から4フィールドのコンストラクタが末尾にある場合(約2,200関数)と、
  結果の形が分からない`apply`が末尾にある場合(790関数)である。
- 適格な関数どうしの末尾呼び出しには、循環がまったくない(2,711関数が
  そうした辺を3,481本持つが、Kosaraju法で強連結成分も自己辺も見つから
  ない。これらは`Loop`と`MutualLoop`がすでに`goto`に変換している)。
  この事実が重要な理由は、「末尾呼び出し」を参照。

### 実行時間(手書きのモデル)

`step d x`は`d`レベルまで再帰する。各レベルは1つ下のレベルの結果を
caseし、同じ`Either String Int`を組み立て直す。rc2が生成したCをベー
スラインとし、モデルでは`step`とその呼び出し元だけを、手書きの構造体
返却版(結果は同じ)に置き換えた。3回のうちの最良値で、単位は外側の
反復1回(深さ`d + 1`の連鎖1本)あたりのナノ秒である。

| `-O2` | セル + 再利用 | 構造体 | 削減 |
|---|---|---|---|
| 小さなペイロード、d=1 | 129 | 88 | 41 (32%) |
| 小さなペイロード、d=2 | 136 | 95 | 42 (30%) |
| 小さなペイロード、d=4 | 156 | 106 | 50 (32%) |
| 小さなペイロード、d=8 | 188 | 129 | 59 (32%) |
| ヒープ上の`Int`ペイロード、d=1 | 133 | 83 | 50 (38%) |
| ヒープ上の`Int`ペイロード、d=8 | 403 | 334 | 69 (17%) |

連鎖1本あたり約40 ns (malloc/freeの組とセルの初期化)に加えて、レベル
ごとに2〜3 ns (一意性の検査とセルへのアクセス)がかかっている。モデルで
は、呼び出しの周りの`idris2rc2_trampoline`も取り除いており、レベルごと
の差の一部はこれによる。実際のワークロードでの動的な件数は測定していない。

## IRでの表現

`RRet n layout`は新しい`Rep`である。`n`個のフィールドを持つ構造体が
どこにあるかを表す(`layout`は「ネイティブフィールド」で説明する)。構造
体を組み立てるノードも1つ追加する。それ以外はすべて既存のノードで表す。

`RRet`には、消去される証明が2つ付く(`IsSucc n`と`LT n 5`)。これに
より、`n`は`IDRIS2RC2_Ret1`..`Ret4`が存在する幅に限られる。`retLayouts`
が幅を計算する箇所でこれを検査し、計画された関数の幅が条件を満たさなけれ
ば、`applyStructReturn`は内部エラーで停止する。

| 内容 | IR | 新規か |
|---|---|---|
| 関数が構造体を返す | `MkRCFun ... (retRep = RRet n layout)` | Repのみ |
| そのようなワーカーの呼び出し | `RAppNameRep ... (retRep = RRet n layout)` | 既存のノード |
| 結果を保持する | `RLet v (RRet n layout) (callRep ...) body` | 既存のノード |
| 結果で分岐する | `RConCase v alts` (`v`のRepが`RRet`) | 既存のノード |
| そのまま上へ渡す | 末尾位置の`RV v` | 既存のノード |
| **構造体を組み立てる** | **`RRetPack : FC -> (con : Name) -> (tag : Int) -> List RCLocal -> RCExp`** | **新規** |

`RRetPack`が有効なのは、`retRep`が`RRet`である関数の末尾位置だけで
ある。フィールドの参照は、`RCon`の引数と同じ扱いで消費する。引数なしの
コンストラクタには`[]`を渡す(Cではすべてのフィールドが0になる)。
静的な定数コンストラクタが末尾にある場合(`#Left@0([#"neg"])`)は、その
静的な引数をフィールドとする`RRetPack`になる。

組み立てには、末尾位置の`RCon`に第2の意味を持たせずに、専用のノード
を使う。理由は3つある。

1. 置かれた場所によって意味が変わる`RCon`は、パスがそれを末尾の外へ動
   かしたり、Boxedの文脈へコピーしたりしたとき、気づかないうちに意味が
   変わってしまう。これは`RMemoize`が、包括的な節を持つパスに対して仕
   掛けた罠と同じである。
2. `RCon`には`reuse=`とコンストラクタ名の扱いがあるが、構造体には
   どちらも要らない。`RCon`を使えば、すべての読み手(Emitやlint)が
   構造体の場合を例外として扱う必要が出る。
3. ダンプに`retpack`と出ていれば、何も確保していないことが一目で分か
   る。

代償は、`RCExp`を網羅的にマッチするすべての箇所に節が1つずつ増えるこ
とである。DualABIより後に実行されるパスは`DeadCode`、`DupMerge`、
`DeadVars`、最後のdup/drop相殺の4つだけで、それぞれに包括的な節に頼
らず、明示的な節を追加する。

caseは、これまでどおり`RConCase`のままにする。枝はすでに構造体に合っ
ている(コンストラクタ名、タグ、フィールドを持つ)。またEmitはローカル
ごとのRepを保持しているので、スクルティニーが`RRet`であることは、その
`let`から分かる。

`RRet`のローカルは、次の3通りの使い方に限る。

1. 自身の`let`の本体(RCのラッパーを除く)である`RConCase`のスクル
   ティニーとして使う。ほかに読む箇所はないこと。
2. 自身の`retRep`が`RRet`である関数の末尾位置から、そのまま(`RV v`)
   返す。
3. `annotate`が、置き換えるセルに付けたRC操作(`drop`、`free`、
   `reuseOffer`、`releaseReuse`、`reuse=`)の対象に指定される。これらは、
   後述の書き換えで取り除かれるか、フィールドに対する操作に変わる。書き
   換え後にこれらが残ることはない。

それ以外の使い方が1つでもあれば、その呼び出しはBoxedのラッパーのまま
にする。

受け取ったフィールドのまま、照合したコンストラクタを組み立て直す枝
(`Left e => Left e`)は、新しい構造体を詰めずに`v`自体を返す。これは、
現行の`reuse=`に対応する構造体版である。

上の測定で使った`step`モデルは、次のようにダンプされる。

```
def {idris2rc2_worker_Main_step:2}  (fun args= ["v68:Native Int", "v69:Native Int"] ret= Ret1 worker=True)
  case v68 of
    0 ->
      cmp <Int [v69, #0]
      then
        retpack Prelude.Types.Left tag= 0 [#"neg"]
      else
        let v70 : Boxed = ...
        retpack Prelude.Types.Right tag= 1 [v70]
    _ ->
      let v72 : Ret1 =
        callRep {idris2rc2_worker_Main_step:2} ["Native Int", "Native Int"] -> Ret1 [v73, v74]
      case v72 of
        Prelude.Types.Left [datacon] tag= Just 0 args= [v75] ->
          v72
        Prelude.Types.Right [datacon] tag= Just 1 args= [v76] ->
          let v77 : Boxed = ...
          drop [v76]
          retpack Prelude.Types.Right tag= 1 [v77]
```

`dumprcexpr`は、新しいRepを`Ret1`、新しいノードを`retpack`と表示す
る。`.rcexpr`のパーサは`libs/rc2base/src/Language/RCExpr/Parser.idr`に
あり、現在は別のエージェントが編集中である。パーサの変更(Repのトーク
ンと、ノードを1つずつ追加する)は、その作業と調整してから行う必要があ
る。それが済むまで、`rcexpr-lint`はこの形のダンプを読めない。

## パイプライン上の位置: DualABIの新しいステージ

構造体返却は、worker/wrapper分割の一種である。そのため
`Compiler.RC2.DualABI`に置き、その仕組みを再利用する。

- **適格性** (読み取り専用で、DualABIのStage 2と同じ): DualABIがすで
  に見ている`Loop`後の定義に対して、上述の最大不動点を求める。末尾が
  次のいずれかであれば許容する。
  - 引数が4つ以下で、タグが`Just`の`RCon`。
  - フィールドが4つ以下の静的な定数コンストラクタ(`RCConstCon`/
    `RCEmptyCon`)。
  - `RCrash`。
  - 遅延でない`RAppName`、または`RAppNameRep`で、呼び出し先が別の適格
    な関数であるもの。
  - `RV RCNull`。Phase 1はNil/Nothing/Z/MkUnitを`RCNull`に畳み込む。
    いずれもタグは0である。ただし消去された値も`RCNull`になる。その
    ため、このような末尾は許容するが、コンストラクタとしては数えない。

  そのうえで、関数は少なくとも1つの本物のコンストラクタの末尾に到達し
  なければならない。`MutualLoop`が統合した関数と、CAF (`RMemoize`の下に
  ある本体)は除外する。適格な関数どうしの末尾呼び出しの循環に含まれる
  関数も除外する。idris2-lspでは、現時点でこの集合は空だが、この検査に
  よって、「末尾呼び出し」の議論が構造上成り立つことを保証している。
- **ワーカーの合成**: 適格な関数には、`retRep = RRet`のワーカーを作る。
  パラメータは、DualABIのパラメータ解析の結果をそのまま引き継ぐ。その
  ため、ネイティブなパラメータと構造体返却は1つのワーカーの中で組み合
  わさる。ラッパーはBoxedのシグネチャを保ち、セルを組み立てる(後述)。
- **呼び出し箇所の書き換え**: DualABIのStage 4の走査に、場合を1つ追
  加する。`let v = call f ...`の本体が`v`をcaseしている場合(上の使
  い方1)、または別の`RRet`ワーカーの内側にある末尾呼び出しの場合(使
  い方2)は、`f`のワーカー(`retRep = RRet`)を呼ぶように書き換える。
  それ以外の呼び出しは、これまでどおりラッパーを使う。

このステージは、DualABIのほかの部分と同様に、RCアノテーションとReuse
のあとで実行される。そのため、書き換え対象のワーカー本体と呼び出し箇所に
は、すでに`dup`/`drop`/`reuseOffer`が付いている。書き換えでは、それらを
変換する必要がある(次の節)。DualABIより後のパス(`DeadCode`、
`DupMerge`、`DeadVars`、最後のdup/drop相殺)は、Repやスクルティニーを
調べるすべての箇所に`RRet`の場合を持たせる必要がある。

## 構造体のスクルティニーにおけるRC

セルの場合、caseの枝はスクルティニーからフィールドを借用する。枝が自分
用の参照を`dup`で取ってから、セルを解放するように、`annotate`/Reuseが
調整する。構造体の場合は、構造体がBoxedのフィールドを完全に*所有*して
おり、解放や再利用の対象になるセルはない。したがって構造体は常に、単一参
照のセルがあるはずの状態にある。書き換えでは、再利用に関する構成要素のす
べてについて、静的に単一参照の経路を取る。

| セル`v`に対する操作 | 構造体`v`では次のようになる |
|---|---|
| `drop [v]` | `drop [f0, f1, ...]`: 構造体自身が持つ、Boxedフィールドへの参照 |
| `free v` | なし(解放すべき殻がない) |
| `reuseOffer v dupOnShared= ds dropOnUnique= us` | `drop us`。フィールドは構造体の参照を保持する |
| `releaseReuse v` | なし |
| `con C [...] reuse= v` | 新しい`con C [...]`。`RRet`ワーカーの末尾であれば`RRetPack` (同じフィールドで、照合したコンストラクタを組み立て直す場合は`v`自体) |

この`drop`には、枝がまったく読まないフィールドも含めて、すべてのフィー
ルドにローカルが必要である。DualABIは、`DeadVars`が死んだフィールドを
`0`に置き換える前に実行されるので、どのフィールドにもまだローカルがあ
る。`0`のフィールドを持つ枝は、セルのまま残す。その結果、同じフィールド
に`dup f; ...; drop [f]`の組ができることがあるが、これはDupMergeの既
存の相殺処理に任せて取り除く。

セル版にあった共有された場合の経路(`dupOnShared`)は、完全に消える。構
造体が共有されることはないためである。

## コード出力

- `let v : RetN = callRep f ...`は
  `IDRIS2RC2_RetN var_v = worker(...);`と出力する。周りに
  `idris2rc2_trampoline`は付けない。構造体を返すワーカーがサンク
  を返すことはない(次の節)。
- `RRet`のスクルティニーに対する`RConCase`は、`var_v.tag`で分岐す
  る。そのフィールド`k`は`var_v.fk.p`であり、ネイティブのフィールドな
  ら`var_v.fk.i`/`.d`である(「ネイティブフィールド」を参照)。
- `RRet`ワーカーの末尾の値は、その形に応じて出力する。
  - `RRetPack C tag [x, y]`は
    `return (IDRIS2RC2_RetN){ tag, { .p = x }, { .p = y } };`と出力す
    る。ネイティブのフィールドは`.i`/`.d`を使い、コンストラクタのア
    リティを超えるフィールドは0のままにする。
    ワーカーの合成では、関数のコンストラクタの末尾を`RRetPack`に変換
    する。対象は、4フィールド以下の`RCon`と、静的な定数コンストラク
    タである。後者の静的フィールドは不滅なので、dupは要らない。
  - `RRetPack C tag []` (引数なしのコンストラクタ)は`{ tag }`を返す。
  - 別の`RRet`ワーカーへの末尾呼び出しは`return worker(...);`と出力
    する。
  - `RRet`のローカルは`return var_v;`と出力する。
- ラッパーは、ワーカーの結果に対する通常の`RConCase`でセルを組み立て
  る。その枝は普通の`RCon`である。コンストラクタの集合は、関数自身の
  コンストラクタの末尾と、呼び出し先の集合の和集合である。こうすれば、
  `NULL`で表す`NIL`、静的な引数なしコンストラクタ、コンストラクタ名の
  すべてが既存の`RCon`の出力を通るので、ラッパーの出力は、元の関数が
  返していたものと完全に一致する。

## 末尾呼び出し

現状では、`Loop`/`MutualLoop`が`goto`に変換しなかった末尾呼び出しは、
引数が飽和したクロージャとして、呼び出し元のトランポリンに返す形で出力
される(`tryBuildClosureInto`)。このクロージャは別のヒープ確保になる。
これは、深さが分からない末尾呼び出しの連鎖でCスタックが際限なく伸びる
のを防ぐためにある。DualABIが末尾呼び出しを一度も書き換えなかった理由
は、`doc/dual-abi.md`のStage 4の「Scope」を参照。

`RRet`ワーカーはクロージャを返せない。そのため、ほかの`RRet`ワーカー
への末尾呼び出しは、直接のC呼び出しになる。これが安全なのは、適格性の
条件で末尾呼び出しの循環に含まれる関数を除外しているからである。循環がな
ければ、任意の入口から始まる、ネストした直接の末尾呼び出しの連鎖は、適格
な関数からなる非巡回グラフの最長経路より長くならず、静的な上限がある。末
尾でない呼び出しによる再帰は、現状とまったく同じようにCスタックを消費
する。`-O2` (`ff1093d`以降のデフォルト)では、gccがこのような同じシグ
ネチャのreturnをシブリングコールに変換することが多いが、正しさはそれに
頼っていない。

副次的な効果として、適格な関数どうしの3,688回の末尾呼び出しは、もう
クロージャを1つずつ確保しない。

## 実装の順序

1. **適格性のダンプのみ。** `Rep`に`RRet1`を追加し、ランタイムに
   typedefを追加する。適格性を計算して、`--directive dumpdualabi`で出
   力する。idris2-lspで、スクラッチパッドのツールの数値と照合する。挙動
   が変わるコード変更はない。完了: `Compiler.RC2.DualABI`の
   `structReturnEligible`。`.dualabi`ダンプの各行は、適格な関数について
   末尾が` ret1`になる。件数の行はその後ろに出る。idris2-lspでは
   8,005関数が許容される。スクラッチパッドのツールの8,039と違う主な
   理由は、そのツールが関数を表示名で区別するためである。異なる`Name`
   が同じ名前で表示されることがある(16個の別々の定義が
   `Core.Context.full`と表示される)。
2. **ワーカーとラッパー。** `RRet1`のワーカーと、セルを組み立てるラッ
   パーを合成する。呼び出し元は、すべてこれまでどおりラッパーを呼ぶ。
   呼び出し箇所を変えないまま、適格なすべての関数について、ワーカーの
   末尾の出力とラッパーによるセルの組み立てを試せる。完了: Stage 3aの
   ネイティブワーカー合成の直後に置いた、独立したパス
   `applyStructReturn`として実装した。すでにネイティブのワーカーを持つ
   関数は、それをそのまま使い、`retRep`だけを変える。このステップには
   ステップ4を含める必要があった。構造体ワーカーの末尾呼び出しは構造
   体を返さなければならないので、呼び出し先の構造体ワーカーを直接呼ぶ
   ためである。計画では見落としていた点が2つある。
   - `structReturnPlan`は、各関数が返すコンストラクタをタグごとにどう
     組み立てていたかを記録し、ラッパーはその記録のとおりに組み立て直
     す。引数なしの末尾はそのままコピーする(Nothing/Nilの`RCNull`は
     `NULL`のままで、`RCEmptyCon`はタグ付きポインタのままである)。到
     達しうるコンストラクタの組み立て方が、1つのタグについて食い違う関
     数は、対象から外す。
   - ステップ3までは、ネイティブなパラメータを持つ関数は、Stage 4の
     ネイティブな呼び出し箇所を失う。ラッパーが、`workerTable`の探す単
     一呼び出しの形ではなくなるので、呼び出し元が引数を再びボックス化す
     る。ステップ3でこの欠落は解消した。
3. **caseされる呼び出し箇所。** 上のRCの表を使って、使い方1の箇所
   を書き換える。完了: `structSites`として実装し、`packTails`の前に
   すべての本体に対して実行する。構造体がそれ以外の方法で読まれる場合、
   `case`に構造体を参照するデフォルトがある場合、あるいは枝が構造体の持
   つ数より多くのフィールドを持つ場合(呼び出し先が決して返さないコンス
   トラクタである。「より幅の広いコンストラクタ」以降は4を超える場合)
   は、その箇所を書き換えない。このステップは、ステップ2の欠落も解消
   する。ネイティブなパラメータを持つワーカーの呼び出しで、結果をcase
   *しない*ものも、ワーカーに到達する。その場でセルを組み立てるので、引
   数をネイティブのまま渡し続けられる。
4. **ワーカー間の末尾呼び出し。** 使い方2の箇所を直接呼び出しに書き換
   える。
5. **測定。** 2026-09-25に測定した。下記の「結果」を参照。静的な指標、
   新しいベンチマーク、`verify.sh`のすべてを、`nostructreturn`ディレク
   ティブがある場合とない場合で測った(`structreturn`は2026-09-25まで
   オプトインだった。デフォルトになったときにディレクティブの向きを反転
   しており、`directives.md`に記載している)。

## 結果(2026-09-25)

`tests/BenchStructReturn.idr` (4レベルの`Either`の連鎖、500万回の呼び
出し、5回のうちの最良値)では、構造体返却なしが674 ms、ありが
**475 ms** で、約30% 速くなった。出力は同一である。valgrindが数えたメ
モリ確保は、なしが1,000万回、ありが **500万回** で、`Either`のセルは
完全になくなった。呼び出しごとに残る1回の確保は、`mod x 64`がオペラン
ドをボックス化するもので、この作業とは無関係である。

idris2-lspの最終的な`dumprcexpr` (Cの生成までは到達しない。`TODO.md`
を参照)を、デフォルトのパイプラインと比べる。

| | デフォルト | `structreturn` (`prunePlan`導入前) | `structreturn` |
|---|---|---|---|
| 定義数 | 22,522 | 29,609 (ワーカー +7,087) | 22,757 (+235) |
| 構造体ワーカー | 0 | 7,844 | 644 |
| `con` | 53,957 | 49,167 (−8.9%) | **51,175** (−5.2%) |

`prunePlan` (後述)は、利益のある呼び出し箇所をすべて残す。呼び出し元が
caseした、組み立て直しのセル1つにつき1つ数える`reuseOffer`の数は、
変わっていない。取り除かれるのは、誰からも直接呼ばれないワーカーと、その
ラッパーが組み立て直していたセルである。

`rcexpr-lint`は、どちらのダンプにも異常を見つけなかった。`verify.sh`は
valgrindを含むすべてのテストで、構造体返却がある場合もない場合も通る。

idris2-missing-containers (`test/src/Main.idr`、ハッシュマップのベンチマ
ークで、パッケージのルートから実行した。交互に5回ずつ実行し、それぞれ
の最初の1回はウォームアップとして除いた)では、`prunePlan`を入れる前
のウォールクロック時間は、なしが12.13秒、ありが12.29秒(+1.3%)で
あり、プログラム自身が計時する各フェーズも、誤差の範囲か、わずかに遅かっ
た。ここで適格なのは5関数だけで、そのどれも、利益を得る直接の呼び出し
箇所を持たない。これらは`{read:0}`のようなラムダで、クロージャとして渡
されるので、すべての呼び出しが`apply`を通ってラッパーに到達し、呼び出
しが1回余分にかかる上に、セルの組み立て直しも払うことになる。そこで、
構造体ワーカーを作るのは、呼び出し元のどれかが利益を得る場合に限ること
にした(`prunePlan`)。利益を得るのは、結果をすぐにcaseする呼び出し、
または構造体を保持している別の関数からの末尾呼び出しである。ネイティブな
引数だけでは利益と見なさない。Stage 4は、Boxedを返すワーカーに対して
も、すでにネイティブのまま引数を渡しているからである。ある関数を対象か
ら外すと、計画に残っている別の関数が、返す構造体のないその関数を末尾呼び
出ししている状態になりうる。そのため、この絞り込みは変化がなくなるまで
繰り返す。これを入れると、idris2-missing-containersで適格な関数はなく
なり、構造体返却なしの場合と同じ時間になった(12.11秒と12.12秒)。
`BenchStructReturn`は影響を受けない(667 msと468 ms)。

## ネイティブフィールド(2026-09-26)

`RRet n layout`のlayoutには、構造体がネイティブに持つフィールドを含む
タグを列挙する。各タグは`Vect n (Maybe PrimType)`で表し、`ty`として持
つフィールドは`Just ty`、Boxedのフィールド(またはタグ自身のアリティを
超えるフィールド)は`Nothing`とする。ダンプでは、幅の後ろにlayoutを表
示し、`Nothing`は`Boxed`と書く。`Ret1:1=Int`や、`Seg Int Int` (タグ
1)と`Tri Int Int Int` (タグ2)が1つの構造体を共有する
`Ret3:1=Int,Int,Boxed:2=Int,Int,Int`がその例である。フィールドがネイティ
ブになるのは、そのタグを組み立てる末尾のすべてが、同じ固定幅の整数、
`Char`、`Double` (ネイティブなローカルまたはリテラル)をそこに渡す場合に
限る。この条件は、この関数だけでなく、構造体が末尾呼び出しでそのまま通過
するすべての関数に適用される。末尾呼び出しで隣り合う関数は、レイアウトと
幅を共有する(`retLayouts`)。食い違いがあれば、Boxedに合流する。

- 詰める処理では、`rcVarToNativeC`でフィールドを`fk.i`/`fk.d`に格納す
  る。
- 構造体に対する枝は、ネイティブのフィールドをネイティブなCのローカル
  として束縛し、Emitの`RepMap`に記録する。そのためBoxedとしての使用
  は、ほかのネイティブなローカルと同じく、その場でボックス化される。
- 書き換えた呼び出し箇所では、このフィールドは何も所有しない。そのため、
  このフィールドに対する`dup`、`drop`、`postDrop`はすべて取り除かれ
  (`dropOwnership`)、構造体の`drop`からも除外される。
- ラッパーと、その場で組み立てるセルは、通常の`RCon`を通してボックス化
  する。

idris2-lspでは、この条件を満たすものはほとんどない。3,679個のpackの
うち、フィールドがネイティブなローカルなのは5個、整数リテラルなのは73
個である。`Core`は項と名前を返すためである。恩恵を受けるのは数値の連鎖
である。`tests/BenchStructReturnNative.idr` (`BenchStructReturn`のすべて
のペイロードを小整数キャッシュより大きくしたもの)は、構造体返却なしが
1,723 ms、ありが **864 ms** で、メモリ確保はなしが5,000万回、ありが
2,000万回である。ワーカー自体は何も確保しない。残っていた確保は、ベンチ
マーク自身のループにある`i + 1000`が、リテラル`1000`を反復ごとに
`Integer`として組み立てていたものである。これはその後畳み込まれている
(`cast-fold-scope.md`。54 ms、確保35回)。

## より幅の広いコンストラクタ(2026-09-26)

4フィールドまでのコンストラクタが末尾にある関数も、適格になった。
`RRet1`は`RRet n layout`になり、`n`は構造体の幅である
(`IDRIS2RC2_Ret1`から`IDRIS2RC2_Ret4`)。`RRetPack`はフィールドのリスト
を取る。関数の幅は、返すコンストラクタのうち最も幅の広いものに等しい。
末尾呼び出しで隣り合う関数は、それぞれの幅のうち最も広いものを共有す
る。1つの構造体が、そのままの形で両者の間を行き来するからである。
`shapeOf`の3フィールドの構造体で返される`Seg Int Int`は、`f2`を使わ
ない。そのほかの部分は、フィールド1つの設計で1つのフィールドだった箇
所をリストに置き換えたものである。構造体のスクルティニーの`drop`は
Boxedのフィールドをそれぞれdropし、ラッパーはそのすべてからセルを組み
立て直す。

idris2-lspの最終的な`dumprcexpr`を、フィールド1つだけの場合と比べる。

| | フィールド1つ | 4つまで |
|---|---|---|
| 構造体ワーカー | 644 | 727 (+77 `Ret2`、+3 `Ret3`、+3 `Ret4`) |
| `let ... : RetN`、`N > 1` | 0 | 238 (217、14、7) |
| `retpack` | 3,679 | 3,895 |
| `con` | 51,175 | 51,039 |
| `reuseOffer` | 17,865 | 17,768 |

見積もりどおり、対象の箇所が数百増えた。`rcexpr-lint`は異常を見つけな
かった。

idris2-missing-containers (交互に6回実行し、最初の1回を除いて平均を
取った)では、これらの件数から予想される以上に大きな改善が見られた。ハッ
シュ関数が3つ適格になった。SipHashの`round64`/`round32`
(`Ret2:1=Bits64,Boxed`と`Ret2:1=Bits32,Boxed`)と、MurMur3の
`feed8_tick` (`Ret3:0=Bits32,Bits32,Bits32`)である。いずれも、ハッシュ
するバイトごとに、タプルを返し、呼び出し元がそれをすぐに分解する。構造体
返却なし(フィールド1つだけの場合と同じ。そこでは適格な関数がなかっ
た)と、ありを比べる。

| | なし | あり |
|---|---|---|
| ウォールクロック時間 | 9.63 s | **8.15 s** (−15%) |
| MurMur3 | 311 ms | 230 ms (−26%) |
| Sip64 | 474 ms | 405 ms (−15%) |
| Sip32 | 473 ms | 361 ms (−24%) |
| write (ハッシュマップへの挿入) | 6,483 ms | 5,394 ms (−17%) |
| read (ハッシュマップの検索) | 646 ms | 535 ms (−17%) |

出力は、計時を除いて同一である。

## 見つかったバグ: 幅が狭まったワーカーと、より幅の広いcase (2026-09-27)

推移的なクロージャ特殊化のあと、idris2-missing-containersの`IOHashMap`
を使うプログラムがコンパイルに失敗した。
`'IDRIS2RC2_Ret1' has no member named 'f1'`というエラーである。原因は
`IOHashSet.replaceL2`の`case !(notfound) of`だった。

そのアクションの特殊化されたクローンは、フィールド1つのコンストラクタ
しか返さないので、ワーカーは`Ret1`になった。ところが、その結果に対す
る`case`には、2フィールドの`InsertOrReplace`の枝が残っていた。この
枝が一致することはあり得ないが、それでも`.f1`を読んでいた。

`emitConCaseInto`は、スクルティニーの構造体の幅より多くのフィールドを
持つ枝を、すべて出力しないようにした。ワーカーの幅は、返すコンストラク
タのうち最も幅の広いものとちょうど同じなので、そのような枝は到達不能で
ある。小さなテストプログラムでは、この形を再現できなかった。幅が狭まる
前に、Inlineが各部分を畳み込んでしまうからである。再現するのは、
`missing-containers`のベンチマークと同じように、`IOHashMap`の`read`
と`write`を呼ぶプログラムである。
