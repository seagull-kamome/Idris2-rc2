# 循環のない呼び出し先集合への直接の末尾呼び出し

(原文: `doc/leaf-tail-calls.md`。内容が乖離した場合は原文を正とする。)

`Compiler.RC2.LeafTail`。デッド変数の除去の直前に走るパスである。`--directive noleaftail`で無効にできる。

## 問題

末尾位置の`RAppName`は、決してCの呼び出しにならない。`Emit`はそれに対してクロージャを構築し、関数はそのクロージャを返し、末尾でない最も近い呼び出し元が、それを`idris2rc2_trampoline`のループで実行する。そのため、末尾呼び出しの長い連鎖でもCのスタックは一定量で済む(`inlining.md`の "Not even load-bearing")。転送関数は、呼び出しのたびにこのコストを払う。

```
Control.Task.>>=  =  bind          -- returns a closure of bind
```

`Control_Task__gt_gt_eq_Monad_Task`は`bind`のクロージャを確保し、トランポリンがそれを実行し、`bind`はコンストラクタを構築して返す。1回の`>>=`につき、確保が2回、ディスパッチが2回である。

## 直接呼び出しが安全な場合

クロージャがあるのは、末尾呼び出しの連鎖でCのスタックが伸びないようにするためである。直接の末尾呼び出し`f -> g`は、`g`が走っているあいだ、`f`のフレームの上に`g`のフレームを積む。`g`の結果は、`f`がそのまま返す。結果は値であるか、`g`自身の保留中の呼び出しであり、後者は`f`が自分の呼び出し元のトランポリンへ渡す。したがって、スタックが際限なく伸びるのは、*直接の*呼び出しが循環を閉じる場合(`f -> g -> ... -> f`で、どの辺もCの呼び出しである場合)だけである。クロージャのまま残る辺は、決して入れ子にならない。

そこでこのパスは、末尾呼び出しグラフの1つの強連結成分の中にとどまる末尾呼び出しにだけクロージャを残し、それ以外の既知の末尾呼び出しはすべて直接呼び出しにする。こうすると、直接呼び出しの連鎖の深さは成分の数で抑えられる。これはプログラムごとに決まる定数である。

## グラフ

ノードはプログラムの関数である。辺`f -> g`は、`f`の本体の中で`g`を呼ぶ末尾位置である。

- `RAppName`(ボックス化された呼び出し。このパスが直接呼び出しにしうる辺)。
- `RAppNameRep`(ワーカーの呼び出し。すでにCの呼び出しである。ワーカーを通る循環を見落とさないように辺に含める)。
- ループを通るもの: `RLoop`の本体の末尾は、関数の末尾である(`RLoopContinue`は呼び出しではない)。

末尾の`apply`(`RApp`)、force、`RMemoize`は辺ではない。引数1つの末尾の`apply`は保留中の呼び出しを返す。それ以外は、入れ子のCの呼び出しの中でクロージャを実行するが、このパスがその入れ子を深くすることはない。辺になるのは、同じプログラムの中で定義された呼び出し先(`defs`)だけである。インクリメンタルモードでは、別のモジュールへの呼び出しはクロージャのまま残る。

## 書き換え

末尾の`RAppName callee args`は、次のようになる。

```
RAppNameRep callee [RBoxed, ...] RBoxed [] args
```

`Emit`はこれを、末尾位置では`return callee(args)`として(結果はトランポリンにかけない)、それ以外の場所では`idris2rc2_trampoline(callee(args))`として出力する。書き換えるのは、次の条件を満たす場合である。

- `callee`がボックス化されたエントリ(ワーカーではない、ボックス化された結果を返す`MkRCFun`)で、パラメータの数が1から`MaxExtractFunArgs`までであり、呼び出しが渡す引数の数と等しい。
- `callee`と呼び出し元が異なる成分に属する。

自己呼び出しと、ループ変換で除去されなかった循環の中の呼び出しは、クロージャを保つ。書き換えは、ボックス化された結果を返すすべての`MkRCFun`で行う。ボックス化された関数だけでなくワーカーも対象である。

## 以前の葉の規則との関係

このパスは以前、呼び出し先が*葉*である場合にだけ、末尾呼び出しを直接呼び出しにしていた。葉とは、すべての末尾が値か、別の葉の呼び出しである関数である。葉は決して循環に含まれないので、これは上の規則の特別な場合である。葉の規則が取りこぼし、成分の規則が拾うものは次のとおりである。ループで終わる呼び出し先(`tailChildren`は`RLoop`の中に入らなかったので、ループ変換を受けた関数はすべて対象外だった)、ワーカーを末尾呼び出しする呼び出し先、葉でない関数を末尾呼び出しする呼び出し先。

## 測定結果

`rc2`でビルドしたコンパイラによる`libs/prelude`のビルド(callgrind):

| | 葉の規則のみ | 成分の規則 |
|---|---|---|
| 命令数 | 39.14 G | 36.94 G (-5.6%) |
| `idris2rc2_mkClosure`の呼び出し | 25.9 M | 14.7 M |
| `idris2rc2_trampoline`の実行 | 19.6 M | 8.4 M |

Chezでビルドした`idris2-rc2`で`rc2-norepl`をビルドすると、成分の規則で10分3秒、葉の規則のみで10分47秒かかる(それぞれ1回の実行、Cのコンパイルを含む)。以前、葉の規則だけについて測った`TestAsyncHTTPServer`では、飽和して構築されたクロージャが282 -> 176、`Task`の`>>=`のものが45 -> 11になった。

## パスのコスト

成分はプログラムごとに1回計算する(`tarjanSCCs`。`MutualLoop`と共有する)。呼び出しごとに作り直してはならない。最初の版は、グラフをローカル関数の隣の`let`ブロックに置き、末尾呼び出しのたびに計算し直していた。そのためパスの所要時間は、`TestAsyncHTTPServer`で7秒、`rc2-norepl`で30分を超えた。補助関数は、マップを引数として受け取るトップレベルの関数にしてある。

## スタックの深さ

以前は、`L`が`N`を末尾でない位置で呼ぶとき、`N x = L x`は`L`を`N`の呼び出し元のトランポリンに任せていた。いまは`N`が`L`を呼ぶので、このような末尾でない再帰の1周で、Cのフレームが1つ増えうる。深さは依然として、末尾でない再帰の深さである。

測定したのは1つのケースだけである。`nrec n = lstep n`、`lstep n = 1 + nrec (n - 1)`を8 MBのスタックで実行すると、このパスありで100 000段、なし(`--directive noleaftail`)で60 000段の深さまで走った。フレームが小さくなった理由は調べていない。

## やっていないこと

- ネイティブのワーカーを持つ関数への末尾呼び出しは、依然としてボックス化されたラッパを経由する(`TODO.md`)。
- foreignのラッパ(`MkRCForeign`)は呼び出し先にならない。保留中の呼び出しを決して返さないので対象にはできるが、そのエントリには独自の呼び出し規約がある。
- 既知のクロージャに対する末尾の`apply`は調べていない。

## テスト

`Test110Loop/LeafTail`(転送関数と、`MutualLoop`がループに変える相互の循環)、`Test154SccTail`(ループで終わる呼び出し先を直接呼び出す。`--directive nomutualloop --directive noloop`で残した循環はクロージャを保ち、100万回の往復を実行する)。

## 残っているもの (2026-11-13)

さらに先へ進むための案を3つ検討した。計測(使い捨てのパッチで、クロージャのまま残る末尾の`RAppName`それぞれの分類と、実行時の保留中の呼び出しそれぞれの出どころを数えた)の結果、どの案にも得られるものがないことが分かった。

- **成分の中でも直接呼び出しにし、後退辺だけを切る。** 上の規則は、成分の中のすべての辺にクロージャを残す。実際には、各成分の深さ優先探索の後退辺にだけ残せば足りる(どの循環も後退辺を1本含む)。そのとき、直接呼び出しの連鎖の長さは、後退辺を含まない最長の経路で抑えられる。しかし`rc2-norepl`の最終的なIRには、内部に末尾の辺を持つ成分が1つも残っていない。`MutualLoop`と`Loop`が、すべての循環をループに変えている。クロージャのまま残る106個の末尾の`RAppName`の箇所は、どれも直接呼び出しできない関数(ワーカー、アリティが合わないもの)を呼んでいる。
- **保留中の呼び出しに、ヒープ上のクロージャではなくスレッドごとのレジスタを使い**、静的なマーカーとして返す。これを使えるのは、`Emit`が末尾の`RAppName`に対して構築するクロージャだけであり、その数は少ない(下記)。
- **一定の深さまで直接適用する**(深さのカウンタを持ち、上限を超えたら現在と同じく保留中の呼び出しを返す)。対象は未知のクロージャに対する末尾の`apply`だけであり、これは`prelude`のビルドの2400万回のapplyのうち230万回である(下記)。節約できるのは、トランポリン1周分の戻りとループの判定で、ディスパッチ1回あたり約100命令のうち10から20命令である。クロージャの外殻の解放とアリティによるディスパッチは、依然として必要だからである。長いループ(`loop = act >> loop`)は、現在と同じく上限のところで走ることになるので、得をするのは短い連鎖だけである。命令数の0.2%未満である。実施していない。

トランポリンに届く呼び出しの出どころ。`rc2`でビルドしたコンパイラによる`libs/prelude`のビルド(ランタイム内のカウンタと、callgrindのプロファイルでの`idris2rc2_tailcallApplyClosure`の呼び出し元。2026-11-13):

| 出どころ | 回数 |
|---|---|
| 末尾の`RAppName`に対して構築されたクロージャ | 32,394 |
| 生成コードの末尾の`apply`から呼ばれた`idris2rc2_tailcallApplyClosure` | 2.26 M |
| 末尾でない`apply`である`idris2rc2_applyClosure`から呼ばれた`idris2rc2_tailcallApplyClosure`(クロージャを伸ばしてからトランポリンにかける) | 9.58 M |
| (この11.84 Mのうち: 一意なクロージャをその場で伸ばしたもの / コピーしたもの) | 8.78 M / 3.06 M |
| トランポリンのディスパッチ | 8.15 M |

したがって、トランポリンが実行するクロージャのほとんどは、返された保留中の呼び出しではない。通常の(末尾でない)`apply`のクロージャであり、`applyClosure`がアリティまで伸ばして、すぐにディスパッチしたものである。生成コードの末尾の`apply`は、伸ばして実行する事象の5分の1にあたる。適用されるクロージャの出どころと、それらを特殊化するのに何が必要かは、`speculative-closure-specialization.md`の "Where the applies come from" にある。
