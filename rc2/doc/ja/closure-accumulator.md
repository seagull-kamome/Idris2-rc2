# クロージャを値とするループパラメータ

(原文: `doc/closure-accumulator.md`。内容が乖離した場合は原文を正とする。)

状態: 差分リストの形は実装済み(2026-09-26、`Compiler.RC2.ClosureCtx`)。
残りは`TODO.md`の「closure-valued loop parameters」で管理している。
`trmc.md`の議論を前提とし、その`RFill`ノードと`res`/`last`の組を再利用する。

## 問題

`Data.List.sortBy`は、入力を分割するときに差分リストを使う。

```idris
splitRec (_::_::xs) (y::ys) zs = splitRec xs ys (zs . ((::) y))
splitRec _          ys      zs = (ys, zs [])
```

`(.)`をインライン化すると、各ステップでクロージャ
`partial L missing=1 [y, zs]`が1つ作られる。ここで`L x = zs (y :: x)`
である。呼び出し元の`sortBy`は`zs`の初期値を`id`にする。Loop変換は
`splitRec`を`zs`を持ち回るループに変えるが、最後の`zs []`はチェーン
全体を実行する。各`L`が、戻る前に1つ前のクロージャを適用するから
である。つまり要素ごとにスタックを消費する非末尾のC呼び出しが1回
あり、長さnのリストでは深さがn/2になる。100万要素の`sort`では、Cス
タックがあふれる(`KNOWN-BUGS.md`の「deep non-tail recursion」)。

## ループの形

idris2-lspの最終RCExpには、パラメータ`c`を、`c`自身をキャプチャする
部分適用で更新するループが10個ある(`TODO.md`)。そのラムダ`L`(引数
`x`)の本体の形で分類すると次のようになる。

| `L x`の形 | 例 | 個数 |
|---|---|---|
| `c (C .. x ..)`: `c`を、1つのフィールドに`x`を持つコンストラクタに適用する | `sortBy`の`splitRec` | 1 |
| `c (e x)`: `c`を任意の純粋な式に適用する | `Data.Vect.foldr`の`foldrImpl`(`go . f x`) | 1 |
| 継続渡し: `L`が走査をもう一度呼び、その結果を包む | 3つの`treeToList'`、schemeバックエンドの`applyLams` | 6 |
| その他 | `mkClosedElab`、`ProcessData.shaped` | 2 |

本書の設計が扱うのは、1つめの形である差分リストだけである。これは
`sort`のクラッシュの原因になっている書き方であり、`trmc.md`の仕組みに
そのまま対応する。2つめの形は、後述の「今後」で素描する。残りは
対象外である。

## 方針: 差分リストはコンストラクタコンテキストである

ループの出発点となるクロージャを`zs_0 = k`と書き、各ステップ`i`が
それを`(y_i ::)`で拡張するものとする。

```
zs_n v = zs_(n-1) (y_n :: v) = ... = k (y_1 :: y_2 :: ... :: y_n :: v)
```

つまり`zs_n`は、`k`と、チェーン`y_1 :: ... :: y_n :: _`の合成である。
このチェーンは末尾にホールを持ち、TRMCが組み立てるものと同じである。
- `res`は最初のセルである。
- `last`は、末尾がホールになっているセルである。

操作は次のように置き換わる。
- **`(y ::)`による拡張:** `y :: NULL`を確保し、`last`のホールをそれ
  で埋め、それを新しい`last`にする。クロージャ1つの代わりに、O(1)
  でアロケーション1回になる。
- **`v`への適用:** `last`のホールを`v`で埋め、`k res`を計算する。
  n段のネストした呼び出しの代わりに、O(1)でスタックを使わない。

`k`はループ中に変化しない。`k`が`id`(`sortBy`の場合)なら、`k res`は
単なる`res`である。

## 書き換えの形

`trmc.md`と同じ、エントリと対となる関数への分割を使う。このパスは
RCより前に関数`f`を調べ、次をすべて満たすパラメータ`c`を探す。

1. **すべての自己末尾呼び出し**が、`c`を変更せずに渡すか、
   `partial L missing=1 [caps.., c]`として渡す。後者では`c`をちょうど
   1回だけキャプチャする。
2. **`L`の本体**が`let cell = C [..]; apply c' [cell]`である。
   - `c'`は`L`自身のパラメータで、キャプチャされた`c`に束縛される。
   - `L`の引数`x`が、`C`のちょうど1つのフィールド`k`になる。`C`は
     `trmc.md`の適格条件3と同じヒープコンストラクタである。
   - `C`の他のフィールドは、すべてキャプチャか定数である。
   - `C`と`k`は、`c`に対して使われるすべての`L`で同じである。
3. **`f`内の`c`の他の使用**が、すべて飽和した`apply c [v]`である。
   どの経路でも高々1回で、その後に`c`は使われない。`c`は外へ逃げ
   ない。他の関数へ渡されず、格納も返却もされない。

`f`は、エントリと、蓄積版である対の関数`f# = MN "rc2_ctx_<f>"`に
なる。`f#`は`f`のパラメータに`res`と`last`を加えたものを取る。

| 出現 | `f`(エントリ)での形 | `f#`での形 |
|---|---|---|
| `partial L [caps, c]`を渡す自己呼び出し | `let cell = C [caps, NULL@k]; call f# [args', c, cell, cell]` | `let cell = C [caps, NULL@k]; fill last.k := cell; call f# [args', c, res, cell]` |
| `c`を変更せずに渡す自己呼び出し | そのまま | `call f# [args', c, res, last]` |
| `apply c [v]` | そのまま | `fill last.k := v; apply c [res]` |

エントリの時点ではまだチェーンがないので、`apply c [v]`はそのまま
残す。拡張しない呼び出しに追加のコストはかからない。`f#`では、`c`は
どの経路でも変更されずに渡されるので、不変の`k`になる。

`partial L`が1つも残らなくなれば、不要になった`L`の定義はDeadCode
で消える。

## 所有権

議論はすべて`trmc.md`のものを再利用する。
- セルは新しく作られたもので、`apply c [res]`が`res`を`k`に渡すまで
  は、チェーンからしか到達できない。
- `last`は、最新のセルに対する通常の所有参照である。
- `RFill`は値を消費し、セルを借用する。

`res`、`last`、各セル、`c`に対するdupとdropは、すべてRCが配置する。

`c`自体は役割が変わる。書き換え前は、`c`をキャプチャする`partial L`
によって、ステップごとに消費されていた。`f#`では`c`は変更されずに
渡され続け、最後の`apply`で一度だけ消費される。そのため、各クロー
ジャが1つ前のクロージャを保持するクロージャのチェーンはなくなる。
残るのは`k`への参照1つだけで、`sortBy`では`k`は`id`である。

## パイプライン上の位置

このパスはTRMCの直後、RCより前に動く。必要なのは次の2点である。
- `L`の本体が独立した定義として見えること(見える。ラムダリフトが
  そうした)。
- 自己末尾呼び出しがまだループになっていないこと(Loop変換はRCの後
  に動く)。

## `apply id [res]`の畳み込み

`sortBy`では、`k`は定数クロージャ`id`である。設計時には、
`apply c [res]`は`id`の動的な適用として残るものと想定していた。
そのため、すべての`RLoopContinue`が変更せずに戻すループパラメータを、
`resolveConstClosureApps`が保持するようにする計画だった。

実際には、これは不要だった。`sortBy`の最終RCExpでは、不変の`c`は
ループのパラメータに含まれない。Loop変換は、変更されずに戻される
パラメータをループの外に置く。それはループの前で束縛された通常の
ローカルのままなので、LateInlineの定数クロージャ解決が、すでに
`apply c [res]`を直接呼び出しにしている。

## 評価順序

書き換え後は、`L`のセルを、クロージャを作っていた時点で評価する。
適用されるはずだった時点ではない。`L`の他のフィールドはキャプチャか
定数である(条件2)ので、セルの構築には、失敗しうる処理も副作用の
ある処理もない。順序は外から観測できない。

## コストとリスク

- **コードサイズ:** TRMCと同様に、書き換えた関数は2つになる。
- **ステップあたり:** クロージャ1つの代わりに、セル1つ、ストア1回、
  `last`に対する参照カウントの加減算1組になる。`sort`は、n/2段の適用
  のチェーンのコストも払わなくなる。
- **条件3が難しい部分である。** 1つの経路で2回適用される`c`や、適用
  された後で渡される`c`は、拒否しなければならない。チェーンを閉じら
  れるのは1回だけだからである。

## 今後: 任意の`c (e x)`(形2)

`L x = c (e caps x)`で、`e`が単一のコンストラクタでない場合
(`foldrImpl`の`go . f x`)、埋めるべきホールがない。ただし、クロー
ジャのチェーンは、すでにフレームの連結リストになっている。各`L`の
クロージャは、キャプチャした値と1つ前の`c`を保持している。

したがって、適用は反復的に巻き戻せる。`c`が`L`のクロージャである
間、そのキャプチャと内側のクロージャを読み、`v := e caps v`とし、
内側へ進む。最後に、残ったものを適用する。

これには、クロージャの関数を検査してキャプチャを読むIRノードが要る。
つまりクロージャに対する`case`であり、コンストラクタの`case`と同様
に、再利用と所有権の問題が生じる。すべてのパスに影響するので、本書
の設計には含めない。

## 計画

1. 形1に対するパスを、`noctx`ディレクティブ付きで実装する。
2. 次を扱うテストを追加する。
   - `splitRec`そのものと、100万要素の`sort`(加えて、valgrind下で
     動かす、より小さなサイズ)。
   - `id`以外から始まるユーザー定義の差分リスト。
   - 2つの分岐でそれぞれ1回ずつ適用される`c`(受理される)。
   - 1つの経路で2回適用される`c`(条件3が拒否しなければならない)。
3. 次を測定する。
   - rc2での100万要素の`sort`を、Chez(1.23秒)と比較する。
   - idris2-lspでの、`scratchpad`の`trmc`ツールによるクロージャ
     アキュムレータの個数。
   - `--timing 3`によるビルド時間。

## 結果(2026-09-26)

**正しさ。** `Test113DeepRecursion/ClosureCtx.idr`が、Chezの出力と
照らして次を検査する。
- `splitRec`。
- 100万要素の`sort`。
- `\xs => 7 :: xs`から始めた差分リスト。
- 2つの分岐でそれぞれ1回ずつ適用されるコンテキスト。

1つの経路で2回適用されるコンテキスト(`twice`)も検査する。これは
クロージャのまま残り、ダンプにも`partial`が残っている。このテストは
valgrind下でエラーなく動く。

**スタック。** `splitRec`と`sort`は、100万要素と400万要素で動くように
なった。どちらも、以前は100万要素でクラッシュしていた。

**速度。** 10万個の擬似乱数の`Int`の`sort`は0.283秒かかる。
`--directive notrmc --directive noctx`では0.493秒、Chezでは0.157秒で
ある。100万要素では4.17秒で、Chezは1.23秒である。プロファイルの
3分の2は、次が占める。
- TRMC済みの`mergeBy`(35%)。
- `split`(18%)。
- `compare`辞書のクロージャの動的呼び出し。

この差は、このパスが原因ではない。

**idris2-lsp。** 10個のループのうち、この形を持つのは`splitRec`の1つ
で、残りの9つは予想どおり残る。パスの所要時間は0.08秒である。最初の
版は0.54秒かかっていた。パラメータごとに全関数を1回走査していた
ためで、現在は、その関数が拡張子を作るかどうかを先に調べる。
`rcexpr-lint`は異常を検出しなかった。
