# インクリメンタル(モジュール単位)コンパイル

(原文: `doc/incremental-compile.md`。内容が乖離した場合は原文を正とする。)

**ステータス: エンドツーエンドで動作している**(ブランチ`feature/rc2-incremental-compile`)。
`prelude`/`base`/`linear`/`contrib`/`network`(合計272モジュール)は、
`--inc rc2`でインクリメンタルデータの欠落なしにすべて再ビルドできる。
`--cg rc2 --inc rc2`でビルドした実行ファイルも正しく動き、正しい出力を返す。
素の`putStrLn`だけでなく、`Data.List`/`Data.SortedMap`を使うプログラムでも同様である。
ソースファイルを1つ変更して再ビルドすると、再コンパイルされるのはそのファイルだけである。
この間、`rc2/tests/verify.sh`自身のプログラム全体ベースライン(111/0/0)は変わらなかった。
以下の設計の節は、(ほとんど)コードを書く前に書いた当初のまま残してある。
「実装中に見つかったバグ」と「エンドツーエンド検証」は、`incCompileFile`/`incCompile`/`compileExprInc`ができて実コードで試せるようになってから分かったことの記録である。
その一部は、設計の節では予想していなかったものである。

## 動機

rc2自前のプログラム全体パイプライン(`RC2.idr`の`toRCDefs`)は、変更されたソースが1モジュールだけの場合でも、ビルドのたびにプログラム全体の到達可能な定義をすべてゼロから再コンパイルする。
モジュール数の多い実プロジェクトでは、これが編集、コンパイル、実行の待ち時間のほとんどを占める。
上流はこの問題をすでに汎用の形で解決している(`Compiler.Common.Codegen`の`incCompileFile`/`incExt`フィールド。`Idris.ProcessIdr.process`とTTCフォーマットに組み込み済み)。
Chezバックエンドもこれを実装している(`Compiler.Scheme.Chez.incCompile`/`compileExprInc`)。
この文書は、同じ上流の仕組みをrc2のCバックエンドに適用する方法を述べる。

## 上流の仕組み(要約)

- `Codegen.incCompileFile : Maybe (... -> sourcefile -> Core (Maybe (objfile, List extraData)))`と`Codegen.incExt : Maybe String`の2つが、バックエンドがインクリメンタルコンパイルに対応するために埋めるフィールドである。
- `Idris.ProcessIdr.process`は、モジュールのエラボレーションが終わった直後に、`incCompileFile`を**モジュールごとに**1回呼ぶ。
  対象は、`Core.Context`の`toIR : NameMap ()`フィールドに新しく加わった定義である。
  `toIR`へは`addToSave`が登録する。
  `addToSave`は、そのモジュール自身のソースからエラボレートされたトップレベル関数、データコンストラクタ、caseラムダ、PE特殊化のすべてについて呼ばれる。
  つまり`toIR`には、まだ誰からも呼ばれていない定義も含め、そのモジュール自身が定義するものがすべて入る。
  「`toIR`の定義だけをコンパイルする」というデータ収集の段階は、`Compiler.Common.getIncCompileData`がすでに汎用の形で実装している。
  バックエンドの`incCompileFile`は、そのデータをオブジェクトコードにするだけでよい。
- 結果の`(objfile, extraData)`はTTCに保存される(`Core.Context.setIncData`/`incData`フィールド)。
  保存先は、そのモジュール自身のコンパイル済み定義の隣である。
  モジュールをインポートする側は、依存先すべてのincDataを`allIncData`に集める(`Core.Context.addImportedInc`)。
  インポートされたモジュールのうち**1つでも**、有効なコード生成器向けのincDataを持たなければ、そのコード生成器のインクリメンタルサポートはビルド全体で警告なしに放棄される(`missingIncremental`、`Idris.ProcessIdr`)。
  その場合は、プログラム全体の再ビルドにフォールバックする。
  ソース自身と、インポート先のインターフェースハッシュが変わっておらず、有効なコード生成器向けのincDataもすでにあるモジュールは、再処理がまったく省かれる(`processMod`の`sourceUnchanged && ... && incrementalOK`のチェック)。
  コンパイル時間の短縮が実際に生まれるのはここであり、バックエンド側の仕組みによるものではない。
- `Codegen.compileExpr`(従来のプログラム全体向けのエントリポイント)は、実際の`main`の`ClosedTerm`に対して最後に1回だけ呼ばれる。
  最終的な実行ファイルを作るのは、この関数だけである。
  インクリメンタルコンパイルに対応するバックエンドも、これを実装する必要がある。
  Chezの`compileExprInc`は`allIncData`があるかどうかを調べ、あれば小さなルート式だけを新しいファイルにコンパイルする。
  それを、蓄積された全モジュール分の`.so`にリンクする(`load-shared-object`で読み込み、Scheme自身のトップレベル`define`の名前空間で動的に解決する)。
- CLIでは、`--cg rc2 --inc rc2`(`--incremental-cg`/`--inc`、`Idris.CommandLine`)でrc2を有効なコード生成器に選び、同時にインクリメンタルモードを有効にする。
  内部では`setIncrementalCG`が呼ばれ、`incCompileFile`が`Nothing`でないことを確認してから許可する。
  環境変数`IDRIS2_INC_CGS=rc2`でも同じ指定ができる(`docs/source/backends/incremental.rst`)。
  `Idris.Package.installFrom`は、`install`のときに各モジュールのインクリメンタルオブジェクトファイルをすでに汎用的にコピーする。
  コピーの判断は`incExt`だけで決まるので、rc2固有の対応は要らない。

### カスタム/外部バックエンドに追加の対応は要らない

rc2自身が、上流の言う*カスタム*バックエンドである(`docs/source/backends/custom.rst`)。
`Main.idr`は`Idris.Driver.mainWithCodegens [("rc2", codegenRC2)]`を呼んで、独立した`idris2-rc2`実行ファイルを作る。
本体の`idris2`バイナリに組み込みのコード生成器リストへ加える方式ではない。
`docs/source/backends/custom.rst`(バックエンド作成ガイド)と`docs/source/backends/backend-cookbook.rst`(765行)を確認したが、後者にはインクリメンタルコンパイルへの言及がまったくない。
どちらの文書も、`Compiler.Common`/`Idris.ProcessIdr`のソース自身も、この目的に関して`mainWithCodegens`で登録したコード生成器を組み込みのものと区別して扱ってはいない。
`session.codegen`/`incrementalCGs`は`CG`の値で比較する。
カスタムバックエンドには`Other "rc2"`というタグが付く。
`RC2.idr`が既存の`--directive`機構のために`getDirectives (Other "rc2")`と呼んでいるのも、同じ`Other "rc2"`タグである。
インクリメンタルの仕組みはすべて、この値だけで汎用的に動く(TTCへの`incData`の埋め込み、`missingIncremental`による再ビルドのスキップ判定、`installFrom`によるオブジェクトファイルのコピー)。
したがってrc2側で必要なのは`incCompileFile`/`incExt`の実装だけであり、「カスタムバックエンドとしてのパッケージング」を別問題として考える必要はない。

### 実際上の前提条件: rc2自身でインクリメンタルビルドしたprelude/base/contrib/networkが要る

`incremental.rst`の「Building executables incrementally」の節には、次のようにはっきり書かれている。
インポートされるモジュールは、`prelude`/`base`/`contrib`/`network`を含めて推移的に*すべて*が、有効なコード生成器向けのincDataをすでに持っていなければならない。
そうでなければ、ビルド全体が警告なしにプログラム全体のコンパイルへフォールバックする(`missingIncremental`)。
上流は、まさにこれらのパッケージについて、Chez向けのインクリメンタルな成果物をビルド済みで「デフォルトで」配布している。
つまり、各パッケージをChezでインクリメンタルビルドして、できた`.so`を`.ttc`の隣にインストールする作業を、誰かがすでにやったということである。
rc2向けの同じ作業は、これまで誰もやっていない。
現在のセルフビルドのツールチェーンは、通常の(非インクリメンタルな)`.ttc`を1セットだけインストールし、chez、RefC、rc2のどのバックエンドもそれを共用している。
共用できるのは、`.ttc`単体にはバックエンド固有のオブジェクトコードが含まれず、プログラム全体向けのコード生成はどのバックエンドが有効でも毎回その`.ttc`から新しく行うからである。
`--inc rc2`では、この共用が成り立たなくなる。
実プログラムはほぼ必ず少なくとも`prelude`をインポートするので、`prelude`/`base`/`contrib`/`network`を`idris2-rc2 --inc rc2 --install-with-src <pkg>.ipkg`(またはそれに相当するコマンド)で個別に再ビルドし、`.o`ファイルとともに再インストールするまで、rc2のインクリメンタルモードは実プログラムに対してリンクできるものを何も持たない。
これは一度だけ行うツールチェーンのセットアップ作業であり、以下で述べるコンパイラ側の実装作業とは別の課題である。
ただし、依存のない1〜2モジュールの人工的なテスト以外でこの機能を試すときの本当の障害はこれなので、前提として済ませたことにせず、ここに明記しておく。

## rc2にChezの「ルート項を別にコンパイルする」手順が要らない理由

Chezの`compileExprInc`は、ルート項のために小さな動的ロード用のラッパーを合成しなければならない。
Schemeのモジュール間リンクが**動的**だからである。
`.so`のトップレベル`define`は、実行時に`load-shared-object`で生きたSchemeの名前空間へ読み込まれて初めて呼べるようになる。
一方でルート項は、どのモジュールの`toIR`にも含まれないので、どの`incCompileFile`呼び出しからもコンパイルされない。

Cのモジュール間リンクは**静的**(通常のリンカによるシンボル解決)であり、rc2にこのような回り道は要らない。
`main`の本体は、すでに通常のトップレベルIdris定義にすぎない(`Main.main`。Boxedな`%World`トークンを引数にとって呼ばれる)。
この定義は`Main`モジュール自身の`toIR`に入るので、`Main.idr`が定義する他のものと同じ`incCompileFile`呼び出しで`Main.o`にコンパイルされる。
欠けているのは、それを呼び出すCの`int main(void)`というエントリポイントだけである。
これは単なる定型コードで、Chezの`compileExprInc`が必要とする`ClosedTerm`には依存しない。
ただし、プログラム全体向けのフッターが呼ぶ`__mainExpression_0()`は、どのモジュールの`toIR`にも含まれないラッパーの名前である。
そのため`Main`モジュールのフッターは、代わりに`Main.main`を直接呼ばなければならない(`directEntryPoint`。「エンドツーエンドの検証」のバグ3と4を参照)。
このための引数は、`Emit.idr`の`generateCSourceFile`にすでにある。
`%export`をライブラリとして使う場面のために先に追加した`noMain`である(`rc2/doc/export-support.md`の「ライブラリとしてのリンク」)。
インクリメンタルモードはこれをそのまま再利用する。
各モジュール自身の`.c`を生成するとき、`noMain = currentNS coreDefs /= mainNS`を渡す(ファイルパスから導出した名前空間ではなく、`Ctxt`から読み出したモジュール自身の*宣言された*名前空間である。「エンドツーエンドの検証」のバグ1を参照)。
これは、`Main`という名前のモジュール以外のすべてで真になる。
`Idris.ProcessIdr.processMod`が`ns /= nsAsModuleIdent mainNS`のガードで行っているのと同じ判定である。

その結果、インクリメンタルモードでのrc2の最終的なプログラム全体向け`compileExpr`は、Cコード生成を**まったく行わない**。
やることは、`allIncData`に蓄積された`.o`ファイルをリンクするだけになる(`Main.o`に`main()`がすでに含まれている)。
これはChezの最終ステップよりも単純である。

## 既存パスのうち、変更が要るもの、要らないもの

実装に入る前に心配したのは、次の点だった。
`ConstFold`のプログラム全体にわたるCAF不動点計算、`Loop`/`MutualLoop`のcalleeテーブル、`DualABI`のワーカー作成と呼び出し側の書き換えは、どれもプログラム全体が見えることを前提にしている。
そのため、「モジュール境界で安全に動く」ようにするには大きな作り直しが要るのではないかと考えた。
しかし各パスの実装を実際に読むと、これはほとんど当たらなかった。
どのパスも`toRCDefs`が渡す定義リスト以外は見ておらず、calleeがそのリストにない場合に安全に縮退する作りになっている。
この縮退は現在でもすでに起きている。
プログラム全体の`defs`の外にあるforeign、ビルトイン、コンストラクタの呼び出しがすべてそうである。
したがって、インクリメンタルコンパイルでこのリストを1モジュール分の`toIR`に絞るだけで足り、これらのパスにコード変更は要らない。

- **`ConstFold.foldConstProgram`**: `rebuildTable`/`cafValueOf`が参照するのは、渡された定義リストだけである。
  他のモジュールで定義されたCAFの呼び出しにはテーブルエントリがないので、畳み込まれることはない。
  これは安全である(モジュール境界をまたぐ最適化を逃すだけで、正しさのリスクはない)。
  変更は要らない。
- **`MutualLoop.applyMutualLoop`**: ユーザー自身の確認によれば、Idrisはそもそもモジュール境界をまたぐ相互再帰を認めていない(mutualブロックは単一モジュール内の構文である)。
  このパスが見ることになるモジュール間のケースは存在しない。
  変更は要らない。
- **`Loop.buildCalleeTable`/`applyLoop`**: テーブルは、渡された定義リストだけから作られる(`buildCalleeTable`自身のドキュメントコメントに「各エントリは、その1つの定義自身の本体だけから作られ、他のエントリを参照して作られることはない」とある)。
  モジュール外のcalleeにはエントリがなく、テーブルの引き外れは現在でも「対象外」を意味する。
  これは、現在のプログラム全体ビルドで`defs`の外にあるforeignやビルトインの呼び出し先がたどる経路と同じである。
  変更は要らない。
- **`DualABI.applyDualABI`/`applyCallSiteRewrite`**: 関数`n`にネイティブワーカーを合成するかどうかは、`n` *自身の*本体だけで決まる(`paramEligibility`/`returnEligibility`)。
  呼び出し側は関係しないので、モジュール自身の関数は、外部のどのモジュールから呼ばれるかにかかわらず、これまでどおりワーカー最適化される。
  ワーカーのネイティブABIを使うための呼び出し側の*書き換え*は、calleeのワーカーエントリがワーカーテーブルにあるときだけ起きる。
  そのテーブルも、モジュールに絞った同じ定義リストから作られる。
  したがって、モジュールをまたぐ呼び出し側は一致せず、自動的に通常のBoxed呼び出しのまま残る。
  変更は要らない。
- **`Sink`/`DupMerge`/`Reuse`/`ConAltNative`/`RC.normalize`+`annotate`/`Inline`**: もともと定義ごとに閉じているか、すでにモジュール内で完結している(プログラム全体の不変条件を最初から持っていない)。
  変更は要らない。
- **定数のステージング**(`Emit.Util.stageConstCon`/`genConstant`、`ConstDef`/`ConstConDef`): ステージングした値、コンストラクタ、クロージャは、すべてCの`static`として出力される。
  そのため、モジュールごとの翻訳単位にそのまま重複して出力してもシンボルは衝突せず、安全である。
  同一の定数をモジュール間で*共有*することはできなくなる(各モジュールが自分のコピーを出力する)。
  これについては後述の「先送り: モジュール間の定数共有」を参照する。
  正しさのために必要なことは何もない。
- **関数宣言**(`Emit.declarationsOf`): すでに`static`なしで、つまり通常のCの外部リンケージでプロトタイプとして前方宣言されている。
  別々の翻訳単位が互いを呼び合うために必要なものを、すでに満たしている。
  変更は要らない。

## 実際に変更が要るもの

本当に作業が要るのは、`DeadCode.pruneDeadDefs`とトップレベルのドライバ(`Compiler.RC2.RC2`)だけである。

1. **インクリメンタルモードでは、デッドコード除去を完全に省く。**
   `pruneDeadDefs`の「`roots`からの到達可能性」というモデルは、もともとプログラム全体を前提にしている。
   このモジュールが現時点で自分では呼んでいない定義も、あとでコンパイルされるモジュールから(あるいはすでにコンパイル済みのモジュールから、このモジュールに対して)呼ばれるかもしれない。
   `ConstFold`が「定数を返すだけ」に簡約したCAFを削除できないのも、同じ理由による。
   (この文書が置き換えたTODO.mdの記述がこの点を扱っていた。)
   これは別の仕組みではなく、DCEを省いたことの直接の帰結である。
   元の定義は、他の必要な定義と同じように、刈り込まれずに残る。
   `toRCDefs`には、ディレクティブで指定するステージ無効化リストがすでにある(`"nodeadcode"`など。`rc2/doc/directives.md`を参照)。
   A/Bの切り分けのために作ったものである。
   新しい`incCompile`(後述)は、これをそのまま再利用する。
   `toRCDefs`に渡す`disabled`リストに、ユーザーが指定した`--directive noXXX`に加えて、常に`"nodeadcode"`を含める。
   `toRCDefs`自身に新しいパラメータは足さない。

2. **新しい`incCompile`関数**(`Compiler.RC2.RC2`。Chezの`incCompile`に対応する)。
   - `cdata <- getIncCompileData False Lifted` -- プログラム全体パスがすでに使っているのと同じ`UsePhase`である(`toRCDefs`が必要とするのは`LiftedDef`だけで、ANF/VMCodeは使わない)。
   - `namedDefs cdata`が空なら`Just ("", [])`を返す(Chezと同じ)。
     実際の出力がなくても、そのモジュールをインクリメンタルコンパイルしたことは記録しておく必要がある。
     後続の`missingIncremental`のチェックを通すためである。
   - 空でなければ、次の手順で進める。
     まず、`noMain`を、モジュールの宣言された名前空間から判定する(前述)。
     出力パスは、`sourcefile`から求める(`getObjFileName`/`getTTCFileName`)。
     次に、`toRCDefs (nub ("nodeadcode" :: disabledStages))[] (lambdaLifted cdata)`を実行する。
     続いて、`generateCSourceFile`でttcビルドディレクトリ内の`<modpath>.c`に出力し(`getTTCFileName sourcefile "c"`)、それを`compileCObjectFile`で`<modpath>.o`にコンパイルする。
     この段階ではリンクしないので、`compileCFile`は呼ばない。
     最後に`Just (objRelativeName, foreignLibs)`を返す。
     `objRelativeName`は`getObjFileName sourcefile "o"`の結果である。
     これは相対パスで、TTCに保存され、のちに各依存先自身のビルドディレクトリを基準に解決される。
     `foreignLibs`は、このモジュール自身の`generateCSourceFile`が返すforeignライブラリの結果そのものである。
     上流の`extraData : List String`のスロットは、まさにこの用途のためにある(Chezも、モジュールごとのforeignライブラリ名を同じ方法で保存している)。
   - `codegenRC2 = MkCG compileExpr executeExpr (Just incCompile) (Just "o")`。

3. **`compileExpr`のインクリメンタル用の分岐。**
   構造はChez自身の`compileExpr`と同じである(`if not wholeProgram sesh && RC2 elem incrementalCGs sesh then ... else compileExprWhole ...`)。
   まず`allIncData`からRC2の項目を探す。
   あれば、`getCompileDataWith`/`toRCDefs`/`generateCSourceFile`を完全に省略し、蓄積された`.o`をすべてリンクする作業へ直接進む。
   各`.o`は、インポートの`.ttc`と同じ方法で実際のパスに解決する。
   これに、各モジュールの`foreignLibs`の和集合を加えて、`compileCFile`に渡す。
   `allIncData`にRC2の項目がなければ、現在のプログラム全体パスにフォールバックする(Chez自身の「missing incremental compile data, reverting to whole program compilation」というフォールバックメッセージに対応する)。

4. **`CC.compileCFile`のシグネチャ。**
   単一の`objectFile : String`パラメータを`objectFiles : List String`に一般化する。
   `cc`の呼び出しでは同じ位置に置き、位置引数が1つから複数になるだけである。
   呼び出し箇所は`RC2.idr`自身の`compileExpr`だけで、プログラム全体の分岐(常に要素1つのリストで、挙動は変わらない)と、新しいインクリメンタルの分岐(蓄積された`.o`のリスト)の両方がある。

## 実装中に見つかったバグと、その修正

`prelude.ipkg`を`--cg rc2 --inc rc2`で再ビルドして実コードで検証したところ(`incCompile`/`compileExprInc`ができたあと)、上の設計の節では予想していなかった3つの実際の問題が見つかった。
3つとも原因は同じである。
`Emit.idr`の前方宣言の仕組み(`collectDeclarations`/`declarationsOf`)は、`defs`がプログラム*全体*である場合しか動かしたことがなかった。
その場合、参照が必要になりうる名前は、定義上すべて同じリストにすでにある。
`defs`が正当に1モジュール分の部分集合になると、この前提が3か所で崩れる。
(「既存パスのうち、変更が要るもの、要らないもの」の節で心配した`ConstFold`/`MutualLoop`/`Loop`/`DualABI`は、そこでの予想どおり、結局変更が要らなかった。
実際の問題はすべて`Emit`にあった。
`Emit`は、プログラム全体の不動点計算型のパスではないので、その節では扱っていなかった。)

1. **モジュールをまたぐ、タグなしコンストラクタ名の参照。**
   小さな整数タグなしで作られるコンストラクタ(`RCon`の`tag = Nothing`、または`RCConstCon`の相当するもの)は、名前スロットにファイルスコープの`idris2rc2_constr_<name>`という文字列定数を格納する(`constructor-layout.md`、`createCFunctions`の`RCon`の場合、`Emit.Util.boxedConstConExpr`)。
   `declarationsOf`/`collectDeclarations`が前方宣言するのは、*現在の* `defs`リスト自身が定義するコンストラクタに限られる。
   別のモジュールが持つコンストラクタを単に*参照する*だけのモジュールには、宣言がまったく出力されなかった。
   `Prelude.Basics`が`Builtin.Void`を参照して見つかった。
   Cコンパイラは単純に「undeclared identifier」でエラーになる。
   これは、網羅的な走査関数`untaggedConstructorRefsD`(`Emit/ExternRefs.idr`)を新設して直した。
   この関数は、モジュール自身の`defs`からそうした参照をすべて集め、そのモジュールがすでに所有しているものを引き、残りに対して`extern char const idris2rc2_constr_<name>[];`を出力する。
   プログラム全体モードでは何も起きない(所有がすべてなので、引き算の結果は常に空になる)。
   `defs`が絞られたときに初めて効く。
2. **モジュールをまたぐ直接の関数呼び出し。**
   別のモジュールのトップレベル関数に対する`RAppName`/`RUnderApp`/`RCConstClosure`の参照でも、同じことが起きた(`declarationsOf`の`MkRCFun`の場合も、`defs`の内側しか扱わない)。
   `Prelude.Num`が`Prelude.EqOrd`の比較関数を名前で直接呼んでいて見つかった。
   Cの「implicit declaration of function」エラーになる。
   同じ方法で、新しい走査関数`externalFunctionRefsD`を作って直した。
   ただし、1つ注意すべき点があった。
   最初の試みでは、これらの参照をすべて、引数リストを指定しないK&R形式の空括弧(`IDRIS2RC2_Value *name();`)で宣言した。
   伝統的なCの「引数未指定」の意味論により、宣言上のアリティにかかわらず実際の呼び出しが通ることを当てにしたのである。
   これは、実際のツールチェーンが標準でとるCの規格では破綻した。
   C23で変わった点として、この規格では空括弧の`()`が`(void)`と同じに扱われる。
   そのため、そう宣言された名前への実際の2引数呼び出しは、「too many arguments」という致命的エラーになる。
   最終的には、実際の`RAppName`呼び出し箇所から、その名前の正確なアリティを取得して直した。
   飽和した直接呼び出しの引数の数は、必ずcalleeの本当のアリティと一致するので、これが信頼できる唯一の情報源である。
   関数ポインタの値として参照されるだけの名前(`RUnderApp`/`RCConstClosure`)は、アリティ0を使う。
   これらは常に、型消去したシグネチャへの明示的なキャストを経由して使われるので、宣言上のアリティはそもそも問題にならない。
3. **rc2が使える呼び出し規約を持たない`%foreign`宣言。**
   `Prelude.IO.prim__threadWait`は、`%foreign "scheme:blodwen-thread-wait"`しか宣言されていない。
   `"C:..."`/`"RefC:..."`/`"RC2:..."`の呼び出し規約が一切ないのは、必要としたのがChezだけだからである。
   `collectDeclarations`の`MkRCForeign`の場合は、`parseCC`がどれにも一致しないと`InternalError`を投げる。
   プログラム全体モードでは、実際にはここに到達しない。
   既存のどのrc2プログラムも`threadWait`を呼ばないので、`collectDeclarations`が見る前に`DeadCode.pruneDeadDefs`が必ずこの宣言を除去するからである。
   しかしインクリメンタルモードは、意図的に`DeadCode`をまったく実行しない(前述の「実際に変更が要るもの」を参照)。
   そのため、すべてのモジュールの`toIR` *全体*が、使われているか否か、実際の呼び出し規約を持つか否かにかかわらず`collectDeclarations`に届く。
   この宣言は、これまで一度も届いたことがなかっただけである。
   これを実行時にクラッシュするスタブにしないことは決めた。
   それと同時に、よく考えた結果、プログラム全体モードの既存の挙動を緩めることもしないことにした。
   `generateCSourceFile`に`dropUnimplementableForeign : Bool`というパラメータを追加した。
   `compileExprWhole`では`False`にして、現状どおり、問題のIdris関数を名指しするエラー(`InternalError`)をただちに出す。
   こうした宣言がプログラム全体モードで本当に到達可能になった場合は、プログラム中の何かがrc2の実装できない関数を呼んでいるということなので、すぐに明確なエラーにするのが望ましい。
   `incCompile`では`True`にする。
   rc2が使える呼び出し規約を持たない`%foreign`宣言は、前方宣言や定義の生成が走る前に`defs`から取り除かれ、最初から存在しなかったものとして扱われる。
   実際の呼び出し側が(もしあれば)現れた場合は、前述の2番目の問題の仕組みで自動的に処理される。
   つまり「参照されているが、どこにも定義がない」通常の名前になり、単なる`extern`プロトタイプが付く。
   その結果、失敗はコンパイル時の停止でも、先送りされた実行時のクラッシュでもなく、*リンク時*の「undefined reference」として現れる。

この3つはいずれも、実コード(実際の`prelude.ipkg`のインクリメンタル再ビルド)で見つけて直した。
3番目の修正により、`prelude`の14モジュールすべてが`--inc rc2`でエラーなく、「no incremental compile data」の警告もなくビルドできるようになった。

## 既知の制限(仕様として決めたもので、直すべきバグではない): `--inc rc2`ではC構造体サポートが使えない

続いて`base.ipkg`をインクリメンタルに再ビルドした(同じ`--inc rc2`、preludeはすでにクリーン)。
136モジュール中28モジュールまで進んだところで、構造の異なる新しい失敗が起きた。
`System.FFI.idr`の次の定義である。

```idris2
prim__getField : {s : _} -> forall fs, ty . Struct s fs -> (n : String) -> ... -> PrimIO ty

getField : {sn : _} -> (s : Struct sn fs) -> (n : String) -> ...
getField s n = prim__getField s n fieldok
```

`prim__getField`/`prim__setField`(`Compiler.RC2`のC構造体サポートの仕組み。`rc2/doc/c-struct-support.md`)は、構造体名とフィールド名の引数が、*呼び出し箇所で*文字列リテラルであることを要求する。
どのC構造体のどのフィールドを指すのかを知る手段が、ほかにないからである。
これは独自の型宣言を持つ本物のFFI呼び出しではなく、rc2が構文的に認識するプリミティブである。
上の`getField`は、意図的に汎用に作ってある(`n : String`はリテラルではなく、通常の束縛されたパラメータである)。
実プログラムの*実際の*呼び出し箇所は、すべてリテラルを渡す(`getField myStruct "x"`)。
プログラム全体のコンパイルでは、この問題に気づかない。
`Compiler.RC2.InlineCExp`が、これくらい小さい関数を必ずすべての呼び出し箇所にインライン化するからである。
そのため、`prim__getField`が実際に出力される唯一の場所では、その引数はすでに呼び出し側自身のリテラルになっている。
`n`がまだ束縛変数のままの`getField`自身の単独の定義は、そもそもコンパイルされるところまで残らない。
インライン化されなかった版を呼ぶものはなく、`DeadCode`や上流自身の到達可能性解析がそれを先に刈り込むからである。

インクリメンタルコンパイルは、上の3番目の問題と同じ形でこれを壊す。
`DeadCode`を実行しないので、`getField`のモジュールレベルの定義が、リテラルのチェックも含めて実際にコンパイルされてしまうのである。
ただし、3番目の問題とは違って、`getField`は呼び出し規約を持たない`%foreign`宣言のように実装不能なわけではない。
実際の呼び出し箇所に対しては、完全に実際の実装がある。
その実装は、インライン化を通した場合にしか得られない。
そして、単独の再利用可能なオブジェクトファイルとして`getField`をコンパイルすること(インクリメンタルコンパイルの目的そのもの)は、まさにそのインライン化を提供できない。
モジュールをまたぐ呼び出し側には、*自分自身の*モジュールの中で、*自分自身の*リテラル引数に対してインライン化を行う必要がある。
別々にコンパイルされた`getField.o`には、それを後から補う手段が構造上ない。

**それでも実装した。3番目の問題と同じ「取り除く」方針である**(上のトレードオフを説明したうえでの、ユーザー自身の判断)。
`RC.idr`の`normalize`は、2か所のthrow箇所に、自由記述のメッセージの代わりに、専用でgrepしやすいマーカー(`notInlinedStructFieldMarker`)を付ける。
`RC2.idr`の`toRCDefs`には`incremental : Bool`パラメータを追加した。
インクリメンタルモードに限り、`toRCDefPreFold`を1つずつ呼ぶ箇所でこのマーカーだけを捕まえ、その定義1つを結果から取り除く。
プログラム全体モードの`incremental = False`の経路は、まったく変わらない。
上の段落で述べたとおり、この場合は実際には到達しないので、捕捉されない`InternalError`のままである。
構造体に触れないプログラムには、どちらでも影響がない。
構造体を使うプログラムは、3番目の問題と同じリンク時の「undefined reference」になる。
以前は、`getField`を定義しているモジュール(`System.FFI`)が、パッケージ全体のインクリメンタルビルドを巻き込んで失敗していた。
実際に確認した。
`base.ipkg`を`--inc rc2`で最初から全部再ビルドしたところ、この修正のあとは最後まで完了した(`getField`は`base`の一部である`System.FFI`にある)。
以前は`System.FFI`で完全に中断していた。
この再ビルドで次に分かったことは、後述の「1つのモジュールの失敗が、ビルドの残り全体に波及する」の節に書いてある。

先に検討した別案もある。
`prim__getField`/`prim__setField`を包む関数を、`Compiler.RC2.InlineCExp`の通常のサイズや適格性のヒューリスティクスにかかわらず、常に強制的にインライン化する方法である。
これなら、`getField`自身が単独の関数としてどこにもコンパイルされなくても、*呼び出し側*のインクリメンタルコンパイルで、リテラルまでインライン化できる。
この案は採用しなかった。
すでに確立している、より単純な上記の「取り除く」仕組みを選んだ。

**正味の結果として、`--inc rc2`は引き続きC構造体サポートに対応しない**(`Compiler.RC2`の`getField`/`setField`/`Struct`の仕組み。`rc2/doc/c-struct-support.md`)。
`getField`/`setField`を実際に呼ぶプログラムは、インクリメンタルコンパイルすると*リンク*に失敗する。
これは、3番目の問題と同様に取り除かれた他の宣言と同じ扱いである。
変わったのは能力ではなく、影響の範囲である。
以前は、そのようなラッパーをどこかのモジュールで*定義しただけで*(実プログラムが使うかどうかにかかわらず)、そのモジュールのインクリメンタルコンパイル全体が、わかりにくい内部エラーでクラッシュした。
現在はクリーンにコンパイルでき、実際に呼び出しがある場合に限って、リンク時に初めて気づく。
プログラム全体のコンパイル(`compileExprWhole`、デフォルト)には、どちらの場合も影響がない。
後から再発見しなくて済むように、この件は`TODO.md`に、ここへ戻るポインタ付きの項目として記録してある。
以上の作業の間、`rc2/tests/verify.sh`は通常の111/0/0のベースラインを保った。

### 上記に対する改善の候補(未実施。再検討の価値あり)

上の3つの修正は、最小限で局所的に理由づけしやすいものを選んだ。
長期的に最善の形とは限らない。
将来のセッションが、これらのトレードオフをゼロから見つけ直さなくて済むように、ここに残しておく。

- ~~**1番目と2番目の問題は、25ケースある`RCExp`/`RCLocal`の走査を2回重複して持っている。**~~
  対応済み。
  `untaggedConstructorRefsD`と`externalFunctionRefsD`(`Emit/ExternRefs.idr`)、および`Compiler.RC2.DeadCode`自身の`usedFunctionNamesD`は、現在では同じ再帰になっている。
  これは`RCExp.idr`の`foldRCNamesR`/`foldRCNamesD`である。
  `Name`を集める、網羅的でキャッチオールのないfoldで、ノードごとのコールバックを持つ小さな`RCNameFold`レコードでパラメータ化されている。
  `RCExp`/`RCLocal`に新しいコンストラクタを足したときの修正箇所は、3か所ではなく、このfoldの1か所で済む。
- **1番目と2番目の問題が出力する`extern`宣言は、翻訳単位をまたいで型がなく、検査もされない。**
  各モジュールが、外部の名前の形(実際の呼び出しなら正確なアリティ、クロージャとしての参照だけならアリティ0)を独立に推測する。
  呼び出し側の想定と、定義側のモジュールが実際に出力するものとの食い違いを、コンパイラが検出できる共有ヘッダはない。
  これは、ランタイムがクロージャについてすでに受け入れている制限と同じである(`Emit.Util`の、型消去した関数ポインタへのキャストという規約も、コンパイラはアリティを検査できない)。
  したがって新しい種類のリスクではない。
  ただし、インクリメンタルコンパイルによって、それまでこのリスクがなかった*直接*呼び出しにまで広がった。
  より堅牢な設計は、各モジュールが自分の限られた視野からexternを導出する代わりに、実際のモジュールごとのヘッダファイルを生成することである。
  ビルドシステムのレベルで「まずシグネチャをコンパイルし、次に本体をコンパイルする」という段階を持たせる、本物のインクリメンタルなC/C++ ビルドに近い形になる。
  これは規模が大きいので先送りした。
  現在の方法は、ビルドの調整機構を一切新設せずに`Emit.idr`の変更だけで済むという理由で選んだ。
- **3番目の問題のリンク時の失敗は、リンカの「undefined reference」メッセージに、マングルされたCシンボル名(例: `Prelude_IO_prim__threadWait`)しか出さない。**
  元のIdrisの名前も、実装がない*理由*(呼び出し規約がないのか、本当に単なる打ち間違いなのか)も、たどれない。
  よりよい方法は、こうして取り除いた宣言を別のマングル名にすること(例: `idris2rc2_unimplemented_ffi_<name>`というシンボル)である。
  そうすれば、将来のリンカエラーから、少なくともこの仕組みへgrepでたどり着ける。
  あるいは、生成した`.c`の呼び出し箇所ごとに、取り除いたことを示すコメントを出力する方法もある。
  いずれも未実施である。
  2番目の問題の既存の仕組み(extern宣言を出して、あとはリンカに任せる)にそのまま揃えることを優先し、2つ目の並行した仕組みは作らなかった。

## 重大な発見: 1つのモジュールのインクリメンタルデータ欠落は、インポートする側だけでなく、そのビルドの残り全体に波及する

これはrc2のバグではない。
原因は、上流自身の`Core.Context.addImportedInc`にある。
ただしrc2にとっては深刻なので、「既知のギャップ」に含めず、独立した節として扱う。
`base.ipkg`を初めてエンドツーエンドでインクリメンタルに再ビルドしたときに見つけた。
先の`getField`の修正で`System.FFI`を越えられるようになったあとのことである。
ビルドはエラーなしで136モジュールすべてを完了した。
ところが、インストールされたすべての`.ttc`で`rc2`というCGタグを検索したところ(`grep -c rc2`。粗いが有効なincDataの存在確認である)、インクリメンタルデータを持つのは136モジュール中**36個**だけだった。
残りの**100個**には、まったくなかった。
そこには、問題を起こしたモジュールと関係がありそうにない`Data.Vect`、`Control.Monad.State`、`Data.SortedMap`も含まれていた。

原因は、**1つのモジュール(`System.File.Meta`)がオブジェクトファイルの生成に失敗した**ことである。
その理由は、上のどのギャップとも無関係で、有効なはずの`%foreign "C:idris2_fileIsTTY, libidris2_support,idris_file.h"`宣言にあった。
最初は、nixpkgsの古さによるバージョンのずれだと誤診した。
その後、推測せずに確認した。
`idris2_fileIsTTY`は、idris2-src自身の`support/c/idris_file.c`にちゃんと実装されている(`System.File.Meta`の`isTTY`/`prim__fileIsTTY`と同じコミットで追加された)。
ただ、`idris_file.h`に、そのファイルの他の関数すべてにある対応するプロトタイプの行が追加されていなかった。
これはidris2-src自身の現在のソースにある、単発の上流の見落としであり、古さの問題ではない。
`install/idris2-0.8.0/support/c/idris_file.h`(このプロジェクト自身のセルフビルドのコピー)が`idris2-src/support/c/idris_file.h`とバイト単位で同一であることも、`diff`で確認した。
セルフビルドは、idris2-srcのヘッダを上流にあるとおりに忠実に再現していた。
古いnix提供のコピーに戻っていたわけではない。
プログラム全体のコンパイルでも、いずれかのテストが実際に`isTTY`を呼べば、まったく同じ形で失敗する。
これまで呼ばれたことがないだけで、`DeadCode`と上流の到達可能性による取得が、この宣言をいつも先に除外していたためである。
つまり、rc2のインクリメンタルサポート自身の設計や実装のギャップではなく、セルフビルドの問題でもない。
`incCompile`は、この1つのモジュールに対して正しく`Nothing`を返した(モジュールごとの段階的な縮退。設計どおりの動作である)。
しかし、*次に*それをインポートするモジュールで、`addImportedInc`(`Core.Context`)が、そのインポート1つを使えないものとして記録するだけではなく、セッション自身の`incrementalCGs`から`rc2`を*完全に*削除してしまう。
同じ`idris2-rc2`起動内でそれ以降に処理されるすべてのモジュールは、失敗したモジュールとインポート関係があるかどうかにかかわらず、そのパッケージのビルドの残り全体で、インクリメンタルデータを警告なしに持てなくなる。
警告は`rc2`がまだ`incrementalCGs`にある間にしか出ないので、連鎖が始まる瞬間に1度だけ出力される。
その後は、影響が広がり続けているのに、何も表示されなくなる。

したがって、`--inc rc2`(同じ仕組みにより`--inc chez`も)の実際の信頼性は、大きな依存関係順のビルドのどこでも*1つも*モジュールが失敗しないことにかかっている。
`%foreign`宣言が1つでも不正だと、そのビルドで以後に処理されるほとんどすべてに対して、インクリメンタルコンパイルが警告なしに無効になる。
壊れたモジュールに実際に依存するプログラムだけが影響を受けるわけではない。
標準ライブラリ全体をゼロから再ビルドする場合(このセッション自身のユースケース)、これは現実的なリスクである。
`base`だけで136モジュールあり、このセッションでは最初の試行で、独立した2つのモジュールレベルの失敗が見つかった。
`getField`自身のリテラル要件と、`idris2_fileIsTTY`のヘッダのプロトタイプ欠落である(後者はidris2-src自体の1行の上流の見落としで、この文書の関心事とは別に報告、修正している)。
この問題にrc2側で対処する価値があるかどうかは、未解決である。
考えられる対処は、連鎖を検出して、同じ起動内でそれ以降のモジュールのインクリメンタルコンパイルを再試行することなどである。
あるいは、鋭い角として文書に残し、回避して使う方法もある。
たとえば、`IDRIS2_INC_CGS`をパッケージごとに設定する。
あるいは、パッケージ内の最初のモジュールレベルの失敗を直してから、そのパッケージをもう一度ビルドする。
*2回目*の`--install`は、すべてのモジュールを新しく処理し直すので、失敗が再発しない限り`rc2`のincDataを拾うはずである。
どれを選ぶかは、この作業を引き継ぐ人の判断に委ねる。
これは上流自身のインクリメンタルの仕組みの性質であり、`Compiler.RC2`に局所的なものではないので、このセッションでは試していない。

## エンドツーエンド検証: 実際にプログラムを動かして見つかった、さらに5つのバグ

`prelude`/`base`/`linear`/`contrib`/`network`がクリーンに再ビルドできること(前の2つの節)が証明するのは、各*モジュール*が単独で正しい`.o`にコンパイルできることだけである。
それらの`.o`が実際の実行ファイルとして*正しくリンクされ、一緒に動く*ことまでは保証しない。
実際、最初は動かなかった。
簡単な`Hello.idr`(`--cg rc2 --inc rc2`)で、実際のバグが5つ、順に見つかり、1つ直してから次へ進んだ。
`rc2/tests/verify.sh`は、そのたびに111/0/0のままだった。

1. **`noMain`が誤った名前空間を使っていた。**
   `incCompile`は、`ctxtPathToNS sourceFile`で`noMain`を導出していた。
   これは*ファイルパス*から名前空間を推測する(`Hello.idr`なら`Hello`)ので、誤りだった。
   Idris2では、ファイル自身の`module Main`宣言がファイル名と異なってよく、エントリポイントの場合がまさにそれである(`Hello.idr`に`module Main`と書くのはごく普通で、`-o`を指定した呼び出しはすべてそうなる)。
   `Main`自身を含むすべてのモジュールが`noMain = True`でコンパイルされた。
   リンク時に`undefined reference to main`となる(リンカ自身のCランタイム起動コード`_start`は、どこかに本物の`main`シンボルを必ず必要とする)。
   修正では、ファイルパスから再導出する代わりに、`Ctxt`にすでに記録されているモジュール自身の*宣言された*名前空間(`currentNS`)を読むようにした。
2. **`%World`自身のtypecase名の文字列が、どこにも定義されていなかった。**
   `PrimIO.unsafeCreateWorld`の`%MkWorld`の構築は、タグなしコンストラクタ名として`idris2rc2_constr__percentWorld`を参照する。
   1番目の問題の修正は、参照されるすべての場所でこれを正しく`extern`宣言する。
   しかし、これを*定義*するものがどこにもなかった。
   以前の`Int`/`Char`/`(->)`と同様に、プログラム中にこれを支えるトップレベル宣言が一切ないためである。
   リンク時に`undefined reference to idris2rc2_constr__percentWorld`となる。
   `runtime.c`に既存の「事前宣言されるプリミティブtypecase名」のリストがあり、そこに`Int`/`Char`/`(->)`と並べて追加して直した。
   RefC自身の`support/refc/prim.c`にもこの名前がないが、それは別の方法で処理されているからではない。
   rc2を含むプログラム全体のコンパイルは、この形がEmitに届く前に、`unsafeCreateWorld`を唯一の呼び出し側へ必ずインライン化する。
   `PrimIO.idr`を完全に単独でコンパイルしたときにだけ、この問題が表に出る。
3. **ルート項のコード生成がなければ、`main()`を呼ぶものもない。**
   設計では「ルート項を再コンパイルする手順は要らない。`Main.main`は`toIR`の通常のメンバーである」と述べた。
   `Main.main`自身についてはそのとおりである。
   しかし、プログラム全体向けのフッターには、`__mainExpression_0()`の呼び出しがハードコードされている(`getCompileDataWith`(`Compiler.Common`)が毎回新しく作る、`ClosedTerm`由来のラッパー)。
   インクリメンタルモードでは、これが呼ぶ先がない。
   この名前はどのモジュールの`toIR`にも含まれないからである。
   `Emit.idr`の`generateCSourceFile`に、`directEntryPoint : Maybe String`パラメータを追加した。
   `Nothing`なら、現在のプログラム全体向けフッターをそのまま使う。
   `Just call`なら(`incCompile`の`Main`モジュールの場合のみ)、完全な呼び出し式をそのまま埋め込む。
   この式は、`incCompile`自身が見つけたものから組み立てる。
4. **`Main.main`の実際のアリティは、必ずしも1ではない。**
   3番目の問題への最初の対処では、`"\{cname}(idris2rc2_freshWorld())"`をハードコードした。
   これは、新しい`%World`トークンを1つ作り、それで`Main.main`を呼ぶ。
   `idris2rc2_freshWorld()`は新しく作った小さなランタイムヘルパーで、`createCFunctions`が通常のタグなしアリティ0の`RCon`に対してインラインで出力するのと同じ構築を行う。
   素の`putStrLn`では動いた(`Main.main`はアリティ1でコンパイルされ、本物の`%World`パラメータを受け取る)。
   しかし、もう少し大きなプログラム(最初の本物の`IO`アクションより前に、`let`束縛した純粋な値がある)では、何も出力しない実行ファイルができた。
   動いているように見えたので、すぐには気づけなかった。
   `--directive dumprcexpr`で理由が分かった。
   その`Main.main`はアリティ0でコンパイルされており、本体は、まだ`%World`引数を待っている`RUnderApp`型のクロージャ(`partial Main.{main:31} missing=1 [v0]`)を作っていた。
   これを引数ゼロで呼んでも、*そのクロージャを作って返す*だけで、何も実行されない。
   「すでに解決済み」なのではなく、同じ関数の代わりをするCAFだったのである。
   修正では、`defs`にある`Main.main`自身の実際の`MkRCFun`のアリティで分岐するようにした(`incCompile`では分かるが、`Emit.idr`自身は意図的にこれを知らない)。
   アリティ0なら、呼び出しをさらに`idris2rc2_applyClosure(..., idris2rc2_freshWorld())`で包む。
   これは、プログラム内のアリティ不足のクロージャが*すべて*通る汎用のランタイム関数である。
   プログラム全体モードの`PrimIO.unsafeCreateWorld`の本体(`apply v0 v1`)も、これとまったく同じ理由で同じことをしている。
   アリティが1以上なら、以前の直接呼び出しを維持する(これはもともと正しい。そこの`%World`トークンは型付きの本物のCパラメータなので、直接呼び出しで`apply`に相当することがすでに行われる)。
   壊れた1つの形だけでなく、両方の形で再テストして確認した。
5. **複数モジュールの実プログラムをリンクして見つかった、さらに3つのモジュール間リンクの落とし穴**
   (小さなプログラムで`Data.List`/`Data.SortedMap`を使った。素の`putStrLn`ではなく、あえてそうした。`base`の136モジュールのクリーンな再ビルドが証明するのは、各モジュールが単独でコンパイルできることだけで、複数が正しくリンクされて動くことではない)。
   - **`.o`を丸ごとリンクすると、3番目の問題の「取り除いて、リンク時に失敗する」仕組みが働かなくなる。**
     `compileExprInc`の最終リンクステップは、蓄積されたすべての`.o`をリンカのコマンドラインに直接並べていた。
     しかし、そのように名前で指定した`.o`は、アーカイブのメンバーとは違って*常に*丸ごとリンクされる(アーカイブのメンバーは、未解決のシンボルがそこにある場合に限って取り込まれる)。
     `base`の`Prelude.IO.threadWait`(意図的に取り除かれた`prim__threadWait`を呼ぶ)は、`putStrLn`自身とまったく同じ`.o`にある。
     そのため`putStrLn`を呼ぶプログラム、つまりすべてのプログラムが、`threadWait`を呼ぶかどうかにかかわらず、`threadWait`の宙に浮いた参照まで取り込んでしまっていた。
     新設した`CC.archiveObjectFiles`(`ar rcs`)で、蓄積されたすべての`.o`を1つの静的アーカイブにまとめてからリンクするようにして直した。
     これで、モジュールごとの選択が実際に働くようになった。
   - **同じ問題が、1段階細かい粒度で起きた。**
     アーカイブ化だけでは足りなかった。
     `putStrLn`と`threadWait`は*同じモジュール*(`Prelude.IO`)にあるので、片方が必要なだけで、*ファイル*単位のアーカイブ選択にかかわらず、`.o`全体が、つまりもう一方も取り込まれてしまう。
     コンパイル時の`-ffunction-sections -fdata-sections`と、リンク時の`-Wl,--gc-sections`で直した(`CC.idr`。どちらのモードでも無条件に適用する。純粋なデッドコード除去であり、挙動は変わらない)。
     これでリンカは、オブジェクトファイル全体ではなく、*セクション*の粒度で個々の未使用関数を捨てられる。
   - **名前の新規生成カウンタが、プログラム全体での一意性を前提にしていた。**
     `Compiler.RC2.MutualLoop`が合成するディスパッチャの名前(`MN "rc2_mutualLoop" i`)の`i`は、コンパイルごとに新しく始まるカウンタから振られる。
     プログラム全体モードでは(カウンタが1つ共有されるので)グローバルに一意になる。
     しかし別々のインクリメンタルコンパイルでは、それぞれがカウンタを0から始めるので、一意にならない。
     `Data.List`/`Data.SortedMap.Dependent`/`Prelude.Types`をリンクしたときに、`multiple definition of rc2_mutualLoop_0`となった。
     無関係な3つのモジュールが、それぞれ1つずつこれを必要としたのである。
     `fnSignature`が、`isMutualLoopMerged`に認識される名前(`Compiler.RC2.Util`。他のパスからこれらを除外するためにすでに使われている)に`static`を出力するようにして直した。
     このディスパッチャは、プログラム全体モードでもインクリメンタルモードでも、生成された自分自身の`.c`の外から参照されることを最初から想定していない。
     したがって、無条件に適用しても安全である。

## 先送り: モジュール間の定数共有

この文書が置き換えたTODO.mdの記述には、次の提案もあった。
翻訳単位が分かれると、定数の重複排除はもともとモジュール単位のものになり、各モジュールが必要な定数を自分でステージングするようになる。
そこで、定数のCシンボル名を、その*値*から決定的に導出し(たとえばコンテンツハッシュ)、`static`ではなく`__attribute__((weak))`で宣言してはどうか。
そうすれば、別々のモジュールが出力した、バイト単位で同一のコピーを、リンカがリンク時に1つにまとめられる。
これは実際にある手法(weakシンボルのマージ)で、どちらにしても正しさには影響しない(影響するのは、staticによる重複したメモリだけである)。
後続の課題としての価値はあるが、この機能の最初の動くバージョンの範囲外とした。
そのためには、モジュールをまたいで同じソース値が出現するたびに、生成される初期化子のテキストがバイト単位で同一になることを、証明可能にする必要がある(フィールドの出力順序、浮動小数点の書式など)。
現在の連番による命名(`constcon_0`、`constcon_1`、...)は、それを保証する必要がない。

**再検討したが、今のところは見送ると決めた。**
`Emit/Util.idr`の`ConstDef`の命名のうち、プレーンなリテラルの場合(`genConstant`)を確認した。
`Int`/`Int64`/`Bits64`/`Double`の定数は、実はすでに自分自身の値から命名されている(カウンタではなく、`cCleanString (show x)`など)。
そのため、これらだけを`static`の代わりに`weak`にするのは低リスクである(命名を変える必要がまったくない)。
しかし、得られる効果は小さい。
節約できるのは、複数のモジュールで構築されたバイト単位で同一の定数の、重複した静的ストレージだけで、1つあたりわずか数バイトである。
実行時の性能向上にはまったくならない。
`Str`定数は、通常のカウンタ(`getNextCounter`)のままである。
任意の文字列の*内容*に`cCleanString`を流用する(本来の用途は識別子のテキストである)のは、見た目が悪いだけでなく、実際に安全でないと分かった。
`cCleanString`は`' '`と`'_'`の両方を同じ`"_"`に写す。
また、表示不能文字のエスケープ(`"u" ++ hex`)が、そのエスケープ列そのものをASCIIで綴った文字列リテラルと衝突する。
たとえば、リテラルのテキスト`"u3042"`と、単一の文字U+3042は、どちらも`u3042`にマングルされる。
本当に異なる2つの文字列値が、同じ`weak`シンボル名に衝突し、リンカは、たまたま先にリンクした方を警告なしに採用してしまう。
安全にするには、本物のコンテンツハッシュ(たとえばUTF-8バイト列に対する64ビットのFNV-1a)が必要で、それをゼロから書かなければならない(使える既存のハッシュユーティリティはない)。
数値側の効果もすでに小さく、文字列側にはハッシュ衝突に対する安全性が重要な新しいコードが必要なのに、得られる効果はやはり小さい。
そのため、今はリスクにも実装コストにも見合わないと判断した。
調べた内容も含めて、ここに残してある。
再び話題になったときに、ゼロから調べ直す必要はない。

## 検証: 2つのステップとも完了

Idrisプログラムはすべて、暗黙のうちに`prelude`をインポートする(`addPrelude`、`Idris.ProcessIdr.processMod`)。
「依存のない」フィクスチャというものは存在しない。
そのため、本物のエンドツーエンドのインクリメンタルなラウンドトリップは、上のprelude/base/linear/contrib/networkの再ビルドが実際に成功するまで、実施できなかった。
以下の2つのステップは、計画だけでなく、どちらも実施済みである。

1. **ブートストラップ前の、穏当なフォールバック。**
   標準パッケージのどれもrc2のincDataを持っていなかった早い段階で確認した。
   通常のrc2テストを`--cg rc2 --inc rc2`でビルドすると、警告なしに、正しくプログラム全体のコンパイルへフォールバックした(`prelude`自身のincDataがないために`missingIncremental`が働いた。設計の予想どおりである)。
   クラッシュも、途中までスキップされた中途半端なビルドもなかった。
2. **ブートストラップ後の、本物のインクリメンタルなラウンドトリップ。**
   `prelude`/`base`/`linear`/`contrib`/`network`をすべてクリーンに再ビルドした状態(272モジュール、incDataの欠落なし。上の「エンドツーエンド検証」)で、2つの使い捨てプログラムを試した。
   素の`putStrLn`だけの`Hello.idr`と、`Data.List.sort`/`Data.SortedMap`を使う2つ目のプログラムである。
   どちらも`--cg rc2 --inc rc2`でビルドでき、正しい出力で動いた。
   `Hello.idr`のメッセージを編集して再ビルドすると、再コンパイルされたのは`Hello`自身だけだった(出力に`prelude`/`base`の再処理は見えない。`missingIncremental`の`sourceUnchanged && ... && incrementalOK`によるスキップが、設計どおり働いている)。
   そのあとで再リンクが行われた。

`rc2/tests/verify.sh`は、上記のすべての修正を通じて、通常の111/0/0というプログラム全体のベースラインを保った。
インクリメンタル専用のコードパスには、`--inc rc2`なしでは到達できないからである。
