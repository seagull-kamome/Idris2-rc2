# インクリメンタル(モジュール単位)コンパイル

(原文: `doc/incremental-compile.md`。内容が乖離した場合は原文を正とする。)

**ステータス: エンドツーエンドで動作**、ブランチ
`feature/rc2-incremental-compile` 上。
`prelude`/`base`/`linear`/`contrib`/`network`(合計 272 モジュール)
はすべて `--inc rc2` の下でインクリメンタルデータの欠落ゼロで
クリーンに再ビルドされる; `--cg rc2 --inc rc2` でビルドされた
実際の実行ファイル(素の `putStrLn` だけでなく
`Data.List`/`Data.SortedMap` を使うものを含む)は実行され正しい
出力を生成し、1 つのソースファイルに触れて再ビルドすると
そのファイルだけが再コンパイルされる(`rc2/tests/verify.sh` 自身の
111/0/0 の全プログラムベースラインは全体を通して影響なし)。
下記の設計セクションは(ほとんど)コードより前に書かれ、当初の
まま保たれている; "実装中に見つかったバグ" と "エンドツーエンド
検証" は、`incCompileFile`/`incCompile`/`compileExprInc` が実コード
に対して試せるようになって実際に判明したことを記録し、そのいくつか
は下記の設計セクションが予期していなかった。

## 動機

rc2 自身の全プログラムパイプライン(`RC2.idr` の `toRCDefs`)は、
1 つのモジュールのソースだけが変わったときでも、毎ビルド、
プログラム全体のすべての到達可能な定義をゼロから再コンパイルする。
多数のモジュールを持つ実プロジェクトでは、これが
編集-コンパイル-実行のターンアラウンドを支配する。上流は既に
これを汎用的に解決しており(`Compiler.Common.Codegen` の
`incCompileFile`/`incExt` フィールド、`Idris.ProcessIdr.process` と
TTC フォーマットに配線されている)、Chez がそれを実装している
(`Compiler.Scheme.Chez.incCompile`/`compileExprInc`)-- この文書は
その同じ上流機構を rc2 の C バックエンドに適応させる。

## 上流機構(要約)

- `Codegen.incCompileFile : Maybe (... -> sourcefile -> Core (Maybe (objfile, List extraData)))`
  と `Codegen.incExt : Maybe String` が、バックエンドが
  インクリメンタルサポートを選択するために埋める 2 つの
  フィールドである。
- `Idris.ProcessIdr.process` は、そのモジュールがエラボレートを
  終えた直後に、そのモジュール自身のソースからエラボレートされた
  すべてのトップレベル関数/データコンストラクタ/case ラムダ/
  PE 特殊化に対して呼ばれる `addToSave` によって投入される
  `Core.Context` の `toIR : NameMap ()` フィールドに新たに追加
  された定義に対してちょうど、**モジュールごとに** 1 回
  `incCompileFile` を呼ぶ(つまり「このモジュール自身が定義する
  すべて」、まだ何かがそれを呼ぶかどうかにかかわらず)。
  `Compiler.Common.getIncCompileData` は既に汎用の
  「`toIR` の定義だけをコンパイルする」データ収集ステップを実装
  している; バックエンドの `incCompileFile` はそれをオブジェクト
  コードに変えるだけでよい。
- 結果 `(objfile, extraData)` はモジュール自身のコンパイル済み
  定義と並んで TTC(`Core.Context.setIncData`/`incData` フィールド)
  に格納される。インポートするモジュールはすべての依存の incData
  を `allIncData`(`Core.Context.addImportedInc`)に蓄積する --
  *いずれか*のインポートされたモジュールがアクティブなコード生成の
  incData を欠いていたら、そのビルド全体でそのコード生成の
  インクリメンタルサポートは静かに放棄され(`missingIncremental`、
  `Idris.ProcessIdr`)、全プログラム再ビルドにフォールバックする。
  自身のソースとインポートのインタフェースハッシュが変わっておらず、
  アクティブなコード生成の incData を既に持つモジュールは、
  再処理を完全にスキップする(`processMod` の
  `sourceUnchanged && ... && incrementalOK` チェック)-- ここが
  実際のコンパイル時の勝ちが来る場所であり、バックエンド側の
  何かからではない。
- `Codegen.compileExpr`(既存の全プログラムエントリポイント、
  最後に、実際の `main` `ClosedTerm` に対してちょうど 1 回呼ばれる)
  が、最終実行ファイルを生成する唯一の場所である。インクリメンタル
  コンパイルをサポートするバックエンドもこれを実装する -- Chez の
  `compileExprInc` は `allIncData` を検査し、あれば、その小さな
  ルート式*だけ*を新しいファイルにコンパイルし、蓄積された
  モジュールごとの `.so`(`load-shared-object` 経由でロードされ、
  Scheme 自身のトップレベル `define` 名前空間で動的に解決される)
  すべてに対してリンクする。
- CLI: `--cg rc2 --inc rc2`(`--incremental-cg`/`--inc`、
  `Idris.CommandLine`)は rc2 をアクティブなコード生成として選択し、
  それをインクリメンタルモードに入れる(`setIncrementalCG`、これ
  自体がこれを許す前に `incCompileFile` が `Nothing` でないことを
  検査する); 同等に `IDRIS2_INC_CGS=rc2`
  (`docs/source/backends/incremental.rst`)。
  `Idris.Package.installFrom` は既に、`incExt` だけをキーとして、
  各モジュールのインクリメンタルオブジェクトファイルを `install`
  時に汎用的にコピーする -- そこに rc2 固有のものは何も要らない。

### カスタム/外部バックエンドは追加のものを何も必要としない

rc2 自体が上流自身の意味でのカスタムバックエンドである
(`docs/source/backends/custom.rst`): `Main.idr` が
`Idris.Driver.mainWithCodegens [("rc2", codegenRC2)]` を呼んで、
メインの `idris2` バイナリ自身の組み込みコード生成リストに折り
込まれるのではなく、スタンドアロンの `idris2-rc2` 実行ファイルを
生成する。`docs/source/backends/custom.rst`(バックエンド作成
ガイド)と `docs/source/backends/backend-cookbook.rst`(765 行、
その中にインクリメンタルコンパイルへの言及ゼロ)の両方を確認した
-- どちらの文書も、`Compiler.Common`/`Idris.ProcessIdr` 自身の
ソースも、この目的のために `mainWithCodegens` 登録のコード生成を
組み込みのものと少しも違う扱いにしない。
`session.codegen`/`incrementalCGs` は `CG` 値で比較する(カスタム
バックエンドは `Other "rc2"` とタグ付けされる。`RC2.idr` 自身の
`getDirectives (Other "rc2")` 呼び出しが既存の `--directive` 機構
のために他の場所で既に依拠する同じ `Other "rc2"` タグ)。そして
インクリメンタル機構のすべての部分(TTC `incData` 埋め込み、
`missingIncremental` の再ビルドスキップチェック、`installFrom` の
オブジェクトファイルコピー)がその値を汎用的にキーとする。
よって: rc2 側で `incCompileFile`/`incExt` 自体を実装する以外に
追加の配管は不要 -- 「カスタムバックエンド」パッケージングは別個の
懸念ではない。

### 実際の実用上の前提条件: rc2 は自身のインクリメンタルビルドされた prelude/base/contrib/network を必要とする

`incremental.rst` の "Building executables incrementally" セクション
は明示的である: *すべての*インポートされたモジュール -- 推移的に、
`prelude`/`base`/`contrib`/`network` を含む -- がアクティブな
コード生成の incData を既に持っていなければならない。さもなくば
ビルド全体が静かに全プログラムコンパイルにフォールバックする
(`missingIncremental`)。上流はまさにそれらのパッケージの事前
ビルドされた Chez インクリメンタルアーティファクトを
「デフォルトで」出荷する -- つまり誰かが既に各々のインクリメンタル
Chez ビルドを実行し、結果の `.so` サイドカーをその `.ttc` の隣に
インストールした。誰も rc2 の相当物をやったことがない: 今日の
自己ビルドツールチェーンは、すべてのバックエンド -- chez、RefC、
rc2 -- が交換可能に共有する 1 セットの通常の(非インクリメンタル)
`.ttc` をインストールする。まさに `.ttc` 単体が
バックエンド固有のオブジェクトコードを一切運ばず、どのバックエンド
がアクティブかにかかわらず全プログラムコード生成が毎回それから
新しく再生成されるからである。その交換可能性こそが `--inc rc2`
の下で壊れる: 実プログラムはほぼ常に少なくとも `prelude` を
インポートするので、rc2 自身のインクリメンタルモードは、
`prelude`/`base`/`contrib`/`network` が各々別途
`idris2-rc2 --inc rc2 --install-with-src <pkg>.ipkg`(または同等)
で再ビルドされて自身の `.o` サイドカーとともに再インストールされる
まで、どの実プログラムに対してもリンクする有用なものを持たない。
これは下記のコンパイラ側の実装作業と直交する一度きりの
ツールチェーンセットアップタスクだが、依存のない合成の 1/2
モジュールフィクスチャを越える何かでこの機能を試す実際の障壁で
ある -- 仮定で片付けるのではなくここで追跡する。

## なぜ rc2 は Chez の「ルート項を別途再コンパイル」ステップを必要としないか

Chez の `compileExprInc` は、Scheme のクロスモジュールリンケージが
**動的**なので、ルート項のために小さな動的ロードラッパを合成
しなければならない: `.so` のトップレベル `define` は、実行時に
ライブの Scheme 名前空間に `load-shared-object` されて初めて
呼び出し可能になり、ルート項自体はどのモジュール自身の `toIR` の
一部でもなかったので、どの `incCompileFile` 呼び出しによっても
コンパイルされなかった。

C のクロスモジュールリンケージは**静的**(通常のリンカシンボル
解決)であり、rc2 は相当する回り道を必要としない: `main` 自身の
本体は既に、他のどの定義とも同じく `Main` モジュール自身の `toIR`
に着地する通常のトップレベル Idris 定義(`Main.main`、ボックス化
された `%World` トークンで呼ばれる)である -- それは `Main.idr` が
定義する他のすべてとまったく同じモジュールごとの `incCompileFile`
呼び出しによって `Main.o` にコンパイルされる。欠けている唯一の
ものは、それを呼ぶ文字通りの C `int main(void)` エントリポイント
であり、それは Chez の `compileExprInc` が必要とする `ClosedTerm`
に依存しない純粋なボイラープレートである。`Emit.idr` の
`generateCSourceFile` は既にこれを制御するパラメータをちょうど
持っている: `noMain`、`%export`-as-library シナリオのために以前
追加された(`rc2/doc/export-support.md`、"ライブラリとしてリンク")。
インクリメンタルモードはそれをそのまま再利用する: モジュール自身の
`.c` を生成するとき `noMain = (moduleNS /= nsAsModuleIdent mainNS)`
を渡す -- 文字通り `Main` と名付けられた 1 つを除くすべての
モジュールで真(`Idris.ProcessIdr.processMod` が自身の
`ns /= nsAsModuleIdent mainNS` ガードで既に行うのと同じチェック)。

帰結: rc2 の最終的な全プログラム `compileExpr` は、インクリメンタル
モードでは **C コード生成を一切しない** -- `allIncData` の蓄積
された `.o` ファイル(`Main.o` は既に `main()` を含む)に対する
純粋なリンクステップに退化する。これは Chez 自身の最終ステップより
単純である。

## どの既存パスが変わる必要があるか -- そしてどれが必要ないか

入るときの素朴な心配は、`ConstFold` の全プログラム CAF 不動点、
`Loop`/`MutualLoop` の被呼び出しテーブル、`DualABI` のワーカー/
呼び出し箇所書き換えがすべて全プログラム可視性を仮定しており、
「モジュール境界安全」になるには本物の作り直しが必要だろう、
というものだった。各々の実際の実装を読むと、これはほとんど真では
ないと分かる -- それらは `toRCDefs` が渡す def リスト*以外*を
与えられたことがなく、被呼び出しがそのリストにないときは既に今日
安全に劣化する(まさに今も、全プログラム `defs` の外にある
すべての foreign/builtin/コンストラクタ呼び出しに対して真)。
したがって、そのリストをインクリメンタルコンパイルのために 1 つの
モジュール自身の `toIR` スコープに制限することだけで、それ自体で
十分である -- これらのパスにコード変更は不要:

- **`ConstFold.foldConstProgram`**: `rebuildTable`/`cafValueOf` は
  渡された def リストしか参照しない。別のモジュールで定義された
  CAF への呼び出しは単にテーブルエントリを持たないので、決して
  fold されない -- 安全(モジュール境界を越えた見逃した最適化で
  あって、正しさのリスクではない)。変更なし。
- **`MutualLoop.applyMutualLoop`**: ユーザー自身の確認によれば、
  Idris はそもそもモジュール境界を越えた相互再帰を許さない
  (相互ブロックは単一モジュールの構文的構成物)-- このパスが
  見るクロスモジュールケースは存在しない。変更なし。
- **`Loop.buildCalleeTable`/`applyLoop`**: テーブルは渡された def
  リストだけから構築される(`buildCalleeTable` 自身の doc コメント:
  「各エントリはその 1 つの定義自身の本体だけから来る ... 決して
  他のエントリを参照しない」)。モジュール外の被呼び出しは
  エントリを持たず、テーブルルックアップミスは既に今日
  「適格でない」を意味する(これはまさに、現在の全プログラム
  ビルドで `defs` の外のすべての foreign/builtin 呼び出しターゲット
  が既に通る同じ経路)。変更なし。
- **`DualABI.applyDualABI`/`applyCallSiteRewrite`**: 関数 `n` が
  ネイティブワーカーを合成されるかは `n` の*自身の*本体だけから
  決定される(`paramEligibility`/`returnEligibility`)、決して
  その呼び出し側からではない -- なのでモジュール自身の関数は、
  外部から誰が呼ぼうと今もワーカー最適化される。ワーカーの
  ネイティブ ABI を使う呼び出し箇所*書き換え*は、被呼び出しの
  ワーカーエントリが、同じモジュール制限された def リストから
  構築されるワーカーテーブルに存在するときだけ発火する --
  クロスモジュール呼び出し箇所は単にマッチせず、自動的に通常の
  ボックス化呼び出しのままである。変更なし。
- **`Sink`/`DupMerge`/`Reuse`/`ConAltNative`/`RC.normalize`+`annotate`/
  `Inline`**: 既に純粋に定義ごと、あるいは既に今日モジュール
  ローカル(そもそも全プログラム不変条件を保持していなかった)。
  変更なし。
- **定数ステージング**(`Emit.Util.stageConstCon`/`genConstant`、
  `ConstDef`/`ConstConDef`): 既にすべてのステージ化された値/
  コンストラクタ/クロージャを C `static` として出力する --
  シンボル衝突なしにモジュールごとの翻訳単位間でそのまま複製して
  安全。同一定数のクロスモジュール*共有*は失われる(各モジュール
  が今や自身のコピーを出力する)-- 下記
  "遅延: クロスモジュール定数共有" を参照。正しさのために必要な
  ものはない。
- **関数宣言**(`Emit.declarationsOf`): 既に `static` 修飾子
  なしで出力される、つまり既に通常の外部 C リンケージで、
  プロトタイプとして前方宣言される。互いを呼ぶ別々の翻訳単位が
  必要とするものそのもの。変更なし。

## 実際に変わる必要があるもの

`DeadCode.pruneDeadDefs` とトップレベルドライバ
(`Compiler.RC2.RC2`)だけが本物の作業を必要とする:

1. **インクリメンタルモードではデッドコード除去を完全にスキップ
   する。** `pruneDeadDefs` の `roots` からの到達可能性モデルは
   本質的に全プログラムである -- このモジュールが現在自身では
   呼ばない定義も、後でコンパイルされる(あるいは既にこれから
   コンパイルされた)モジュールから呼ばれるかもしれない。これは
   `ConstFold` が「単に定数を返す」に簡約した CAF も drop できない
   *理由*でもある(この文書が置き換える TODO.md の注記)-- それは
   別個の機構ではなく、DCE スキップの直接の帰結である: 元の定義は
   単に、他のすべてのまだ必要な定義とまったく同じく、prune
   されずに生き残る。`toRCDefs` は既に A/B 分離のために作られた
   ディレクティブ駆動のステージ無効化リスト(`"nodeadcode"` を
   含む、`rc2/doc/directives.md` を参照)を持つ -- 新しい
   `incCompile`(下記)は、ユーザーが供給した
   `--directive noXXX` フラグの上に、`toRCDefs` に渡す `disabled`
   リストに `"nodeadcode"` を無条件に含めることで、それをそのまま
   再利用する。`toRCDefs` 自体に新しいパラメータはなし。

2. **新しい `incCompile` 関数**(`Compiler.RC2.RC2`、Chez の
   `incCompile` を反映):
   - `cdata <- getIncCompileData False Lifted` -- 全プログラム経路
     が既に使うのと同じ `UsePhase`(`toRCDefs` は `LiftedDef`
     しか必要とせず、ANF/VMCode は決して必要としない)。
   - `namedDefs cdata` が空なら: `Just ("", [])` を返す(Chez に
     一致 -- モジュールが実際の出力なしでインクリメンタルに
     コンパイルされたことを記録、後の `missingIncremental` の
     チェックが通るために今も必要)。
   - そうでなければ: `sourcefile` からモジュール自身の
     `ModuleIdent` を導出し(`ctxtPathToNS`、
     `getObjFileName`/`getTTCFileName` が既に使う同じヘルパ)、
     `noMain`(上記参照)を決めて出力パスを計算する;
     `toRCDefs (nub ("nodeadcode" :: disabledStages)) [] (lambdaLifted cdata)`
     を実行する; ttc ビルドディレクトリ自身の `<modpath>.c`
     (`getTTCFileName sourcefile "c"`)に `generateCSourceFile`;
     それを `<modpath>.o` に `compileCObjectFile` する
     (`compileCFile` はスキップ -- この段階でリンクなし);
     `Just (objRelativeName, foreignLibs)` を返す。ここで
     `objRelativeName` は `getObjFileName sourcefile "o"`(相対、
     TTC に格納され後で各依存自身のビルドディレクトリに対して
     解決される形式)、`foreignLibs` はまさにこのモジュール自身の
     `generateCSourceFile` foreign-library 結果 -- 上流自身の
     `extraData : List String` スロットがまさにこのために存在する
     (Chez は自身のモジュールごとの foreign lib 名を同じやり方で
     格納する)。
   - `codegenRC2 = MkCG compileExpr executeExpr (Just incCompile) (Just "o")`。

3. **`compileExpr` のインクリメンタル分岐。** Chez 自身の
   `compileExpr` と同じ形状
   (`if not wholeProgram sesh && RC2 elem incrementalCGs sesh then ... else compileExprWhole ...`):
   `RC2` の `allIncData` を検索する; あれば、
   `getCompileDataWith`/`toRCDefs`/`generateCSourceFile` を完全に
   スキップし、蓄積されたすべての `.o`(各々、インポートの `.ttc`
   が解決されるのと同じやり方でその実パスに解決される)と、
   すべてのモジュール自身の `foreignLibs` の和集合を、
   `compileCFile` 経由でリンクすることに直接進む。`allIncData` が
   RC2 のエントリを欠いていたら今日の全プログラム経路に
   フォールバックする(Chez 自身の "missing incremental compile
   data, reverting to whole program compilation" フォールバック
   メッセージを反映)。

4. **`CC.compileCFile` シグネチャ**: その単一の
   `objectFile : String` パラメータを `objectFiles : List String`
   に一般化する(`cc` 呼び出しに同じやり方で、ただ 1 つではなく
   複数の位置引数として置かれる)-- 唯一の呼び出し箇所は
   `RC2.idr` 自身の `compileExpr` で、全プログラム分岐(常に
   1 要素リスト、振る舞い無変更)と新しいインクリメンタル分岐
   (蓄積された `.o` リスト)の両方。

## 実装中に見つかったバグ(と各々どう修正したか)

実コード(`incCompile`/`compileExprInc` が存在してからの
`--cg rc2 --inc rc2` での `prelude.ipkg` 再ビルド)に対する検証は、
上記設計セクションが予測しなかった 3 つの本物のギャップを浮かび
上がらせた -- 3 つとも同じ根本原因を共有する: `Emit.idr` の前方
宣言機構(`collectDeclarations`/`declarationsOf`)は、参照し得る
すべての名前が構築上その同じリストに既に存在する*全*プログラム
である `defs` でしか行使されたことがなかった。`defs` が正当に
1 つのモジュール自身の部分集合になると、その仮定は 3 つの異なる
場所で壊れる。(`ConstFold`/`MutualLoop`/`Loop`/`DualABI` -- 上記
"どの既存パスが変わる必要があるか" セクションが心配したパス --
は結局、そこで予測された通り、変更を必要としなかった; 本物の
ギャップはすべて `Emit` にあり、それは全プログラム不動点スタイル
のパスの 1 つでないのでそのセクションがカバーしなかった。)

1. **モジュールを越えたタグなしコンストラクタ名参照。** 小整数
   タグなしで構築されたコンストラクタ(`RCon` 自身の
   `tag = Nothing`、または `RCConstCon` の同等物)は、その
   ランタイム `->name` フィールドをファイルスコープの
   `idris2rc2_constr_<name>` 文字列定数に設定する
   (`createCFunctions` 自身の `RCon` ケース;
   `Emit.Util.boxedConstConExpr` の `nameField`)。
   `declarationsOf`/`collectDeclarations` は、*現在の* `defs`
   リスト自身が定義するコンストラクタに対してのみこれを前方宣言
   する -- 別のモジュールが所有するものを単に*参照する*だけの
   モジュール(`Prelude.Basics` が `Builtin.Void` を参照するのを
   通じて発見)は宣言を一切得なかった: 素の
   "undeclared identifier" C エラー。新しい網羅的ウォーカー
   `untaggedConstructorRefsD`(`Emit/ExternRefs.idr`)で修正。
   モジュール自身の `defs` にわたってそのような参照をすべて収集し、
   そのモジュールが既に所有するものを引き、残りに対して
   `extern char const idris2rc2_constr_<name>[];` を出力する --
   全プログラムモードでは no-op(所有権が全なので、そこでは
   引き算が常に集合を空にする)、`defs` が狭まると本物になる。
2. **直接のクロスモジュール関数呼び出し。** 別のモジュール自身の
   トップレベル関数への `RAppName`/`RUnderApp`/`RCConstClosure`
   参照についてまったく同じ話(`declarationsOf` の `MkRCFun`
   ケースも等しく `defs` ローカルのみ)-- `Prelude.Num` が
   `Prelude.EqOrd` 自身の比較関数を名前で直接呼ぶのを通じて発見:
   C の "implicit declaration of function" エラー。同じやり方で
   修正、新しいウォーカー `externalFunctionRefsD`、1 つの追加の
   微妙さとともに: 最初の試みはそのような参照をすべて、
   仕様不定の K&R スタイルの空括弧パラメータリスト
   (`IDRIS2RC2_Value *name();`)で宣言し、伝統的 C の
   「仕様不定の引数」意味論が宣言されたアリティにかかわらず実際の
   呼び出しを通すことを信頼した -- これは実際のツールチェーン自身
   の C 標準デフォルト(C23 が導入した本物の違い)、素の `()` を
   `(void)` と同じに扱うもの、で壊れた: そのように宣言された名前へ
   の本物の 2 引数呼び出しはハードな "too many arguments" エラー
   である。その名前への任意の本物の `RAppName` 呼び出し箇所から
   正確なアリティを追跡する(飽和した直接呼び出し自身の引数数は
   常に被呼び出しの実アリティに一致するので、本物の権威ある
   アリティ)ことで本物に修正し、関数ポインタ値としてのみ参照
   される名前(`RUnderApp`/`RCConstClosure`、既に常に明示的な
   消去シグネチャキャストを通して消費されるので、そこでの宣言
   アリティは無意味)に対してのみアリティ 0 にフォールバックする。
3. **rc2 が使える呼び出し規約のない `%foreign` 宣言。**
   `Prelude.IO.prim__threadWait` は `%foreign "scheme:blodwen-thread-wait"`
   だけで宣言される -- `"C:..."`/`"RefC:..."`/`"RC2:..."` 規約が
   それに一切存在しない、Chez だけがそれを必要としたので。
   `collectDeclarations` 自身の `MkRCForeign` ケースは `parseCC`
   が何もマッチしないときハードな `InternalError` を投げる --
   全プログラムモードではこれは実際上到達不能(既存のどの rc2
   プログラムも `threadWait` を呼ばないので、`DeadCode.pruneDeadDefs`
   が `collectDeclarations` が見る前に常に宣言を除去する)だが、
   インクリメンタルモードは意図的に `DeadCode` を一切実行しない
   (上記 "実際に変わる必要があるもの" を参照)-- すべての
   モジュールの*全* `toIR` が、使われるか否か、本物の規約か否か、
   にかかわらず `collectDeclarations` に到達し、これは単に以前
   到達されたことがなかった。これをランタイムクラッシュスタブに
   変えないことにした -- が、熟考して、全プログラムモード自身の
   既存の振る舞いを緩めることもしなかった: `generateCSourceFile`
   は `dropUnimplementableForeign : Bool` パラメータを得た、
   `compileExprWhole` に対して `False`(今日のハードで即座に責任を
   追える、正確な Idris 関数を名指しする `InternalError` を保つ
   -- そのような宣言がそこで本当に到達可能なら、プログラムの何かが
   rc2 が実装できない関数を本当に呼んでおり、即座に曖昧さなく失敗
   する価値がある)、`incCompile` に対して `True`(rc2 が使える
   規約のない `%foreign` 宣言は、前方宣言または定義生成のどちらが
   走る前にも、`defs` から完全に drop され、単に存在しなかったかの
   ように扱われる)。本物の呼び出し側(もしいつか現れれば)は
   その後、上記ギャップ #2 自身の機構から自動的に外れる -- 通常の
   「参照されるがどこにも定義されない」名前 -- ので、それは今も
   素の `extern` プロトタイプを得て、失敗はコンパイル時の停止でも
   遅延されたランタイムクラッシュでもなく、そこでの*リンク時*の
   "undefined reference" として現れる。

これら 3 つの各々は実コード(本物の `prelude.ipkg` インクリメンタル
再ビルド)で見つかり修正された -- 修正 #3 が入って、14 個すべての
`prelude` モジュールが `--inc rc2` の下でエラーゼロ、
"no incremental compile data" 警告ゼロでクリーンにビルドされる。

## 既知の制限(決定済み、修正すべきバグではない): `--inc rc2` の下では C 構造体サポートなし

次に `base.ipkg` をインクリメンタルに再ビルドすると(同じ
`--inc rc2`、prelude は既にクリーン)、新しい構造的に異なる失敗の
前に 136 モジュール中 28 まで進んだ: `System.FFI.idr` 自身の

```idris2
prim__getField : {s : _} -> forall fs, ty . Struct s fs -> (n : String) -> ... -> PrimIO ty

getField : {sn : _} -> (s : Struct sn fs) -> (n : String) -> ...
getField s n = prim__getField s n fieldok
```

`prim__getField`/`prim__setField`(`Compiler.RC2` 自身の C 構造体
サポート機構、`rc2/doc/c-struct-support.md`)は、自身の
struct 名/field 名引数が*呼び出し箇所で*リテラル文字列であること
を要求する -- 呼び出しがどの C 構造体/フィールドを意味するか知る
他の方法がないからである。これは自身の宣言された型を持つ本物の
FFI 呼び出しではなく、rc2 が構造的に認識するプリミティブである。
上記の `getField` は意図的に汎用である(`n : String` はリテラル
ではなく通常の束縛パラメータ)-- 実プログラムのすべての*本物の*
呼び出し箇所はリテラルを供給し(`getField myStruct "x"`)、
全プログラムコンパイルはこれに気づかない。`Compiler.RC2.Inline`
がこんなに小さい関数を常にすべての呼び出し箇所にインライン化する
ので、`prim__getField` 自身の引数は、それが実際に出力される唯一の
場所で既に呼び出し側自身のリテラルであるからである; `getField`
自身のスタンドアロン定義(`n` がまだ素の束縛変数)は、インライン
化されていない版を何も呼ばず、`DeadCode`/上流自身の到達可能性が
それを先に prune するので、コンパイルされるまで生き残ることは
決してない。

インクリメンタルコンパイルは、上記ギャップ #3 と同じ一般的な
やり方でこれを壊す(`DeadCode` を決して実行しないので、`getField`
自身のモジュールレベル定義が本物にコンパイルされる、リテラル
チェック込みで)。ただしギャップ #3 と違い、`getField` は、規約
なし `%foreign` 宣言のように実際に実装不能なのではない: すべての
本物の呼び出し箇所に対して完全に本物の実装を持ち、*インライン化を
通じてのみ*到達可能で、それはまさに、それをスタンドアロンの
再利用可能なオブジェクトファイルとしてコンパイルすること
(インクリメンタルコンパイルの要点そのもの)が提供できないもので
ある -- クロスモジュール呼び出し側は、このインライン化が*自身の*
モジュールで、*自身の*リテラル引数に対して起きる必要があり、
別途コンパイルされた `getField.o` は構造的にそれを遡って供給
できない。

**それでも実装、ギャップ #3 と同じ「drop する」動き**(上のトレード
オフが提示された後の、ユーザー自身の判断): `RC.idr` の
`normalize` は両方の throw 箇所を、フリーテキストメッセージでは
なく専用の grep 可能なマーカー(`notInlinedStructFieldMarker`)で
タグ付けする; `RC2.idr` の `toRCDefs` は `incremental : Bool`
パラメータを得て、インクリメンタルモードでのみ、各個の
`toRCDefPreFold` 呼び出しの周りでちょうどそのマーカーを catch し、
その 1 つの定義を結果から drop する(全プログラムモード自身の
`incremental = False` 経路は完全に無変更 -- 上の段落の通り、
そのケースはそこで実際上到達不能なので、今も catch されない
`InternalError`)。構造体に決して触れないプログラムはどちらの道でも
影響なし; 触れるものは今、`getField` 自身の定義モジュール
(`System.FFI`)がパッケージ全体のインクリメンタルビルドを道連れに
するのではなく、ギャップ #3 と同じリンク時 "undefined reference"
の結果を得る。本物に検証済み: `base.ipkg` の完全な `--inc rc2`
再ビルド(`getField` は `base` の一部である `System.FFI` にある)
がその後エンドツーエンドで完了した、以前は `System.FFI` で完全に
中断していた場所で -- その再ビルドがその後明らかにしたものは下記
"1 つの欠落/失敗したモジュールのカスケード的脆弱性" を参照。

以前に浮かんだ無条件インライン化を強制する代替案
(`prim__getField`/`prim__setField` を包む関数を
`Compiler.RC2.Inline` の通常のサイズ/適格性ヒューリスティクスに
かかわらず常にインライン化させ、*呼び出し側*自身のインクリメンタル
コンパイルが、`getField` 自体がどこでもスタンドアロン関数として
コンパイルされなくてもそれらをリテラルまでインライン化するように
する)は、上のより単純で既に確立された「drop する」機構を優先して
追求されなかった。

**正味の効果: `--inc rc2` は今も C 構造体サポートをサポートしない**
(`Compiler.RC2` の `getField`/`setField`/`Struct` 機構、
`rc2/doc/c-struct-support.md`)-- 実際に `getField`/`setField` を
呼ぶプログラムは、他のどのギャップ #3 スタイルの drop とも同じく、
インクリメンタルにコンパイルされると*リンク*に失敗する。変わった
のは能力ではなく波及範囲である: 以前は、モジュールのどこかで
そのようなラッパを単に*定義する*だけ(実プログラムがそれを使うか
否かにかかわらず)で、そのモジュールのインクリメンタルコンパイル
全体を紛らわしい内部エラーでクラッシュさせた; 今はクリーンに
コンパイルされ、本物の呼び出し側だけがリンク時に気づく。
全プログラムコンパイル(`compileExprWhole`、デフォルト)はどちらの
道でも完全に影響なし。静かなギャップではなく、ここに戻ってくる
`TODO.md` エントリとして追跡され、ゼロから再発見されないように
する。`rc2/tests/verify.sh` は上記すべてを通じて通常の 111/0/0
ベースラインに留まった。

### 上記への可能な追随改善(未実施、再考の価値あり)

上の 3 つの修正は、必ずしも最良の長期形状ではなく、最小で局所的に
論理立てられるよう選ばれた。将来のセッションがこれらのトレード
オフをゼロから再発見しなくてよいようここに残す:

- ~~**ギャップ #1/#2 は完全な 25 ケースの `RCExp`/`RCLocal` 歩きを
  二度重複する。**~~ 完了。`untaggedConstructorRefsD` と
  `externalFunctionRefsD`(`Emit/ExternRefs.idr`)、および
  `Compiler.RC2.DeadCode` 自身の `usedFunctionNamesD` は今や同じ
  再帰 -- `RCExp.idr` の `foldRCNamesR`/`foldRCNamesD`、網羅的で
  catch-all のない `Name` 収集 fold -- を、ノードごとのコールバック
  の小さな `RCNameFold` レコードでパラメータ化したものである。
  新しい `RCExp`/`RCLocal` コンストラクタは、その fold の 1 箇所の
  更新を強制する、3 箇所ではない。
- **ギャップ #1/#2 が出力する `extern` 宣言は翻訳単位間で
  型なし/チェックなし**である -- 各モジュールが外部名の形状に
  ついて自身の推測を独立に導出し(本物の呼び出しは正確なアリティ、
  クロージャのみの参照はアリティ 0)、呼び出し側が仮定するものと
  定義側自身のモジュールが実際に出力するものの間の本物の不一致を
  コンパイラが捕捉できる共有ヘッダはない。これはランタイムが
  クロージャに対して既に受け入れている制限を反映する
  (`Emit.Util` 自身の消去された関数ポインタキャスト規約も
  コンパイラによってアリティチェックできない)ので、新しい
  カテゴリのリスクではないが、インクリメンタルコンパイルが以前は
  この露出を持たなかった*直接*呼び出しにも新たに拡張するものでは
  ある。より堅牢な設計は、各モジュールが自身の限られたビューから
  extern を再導出するのではなく、本物のモジュールごとのヘッダ
  ファイル(適切なビルドシステムレベルの「まずシグネチャを、
  次に本体をコンパイル」フェーズ、本物のインクリメンタル C/C++
  ビルドがどう動くかに近い)を生成するだろう -- より大きく、
  遅延された; 現在のアプローチは、新しいビルドオーケストレーション
  機構を一切必要とせず `Emit.idr` の変更だけで済むので選ばれた。
- **ギャップ #3 のリンク時失敗は、リンカ自身の "undefined
  reference" メッセージに mangle された C シンボル名だけ**(例えば
  `Prelude_IO_prim__threadWait`)を表面化し、元の Idris 名や、
  *なぜ*実装がないか(規約の欠落 vs 本物のタイポ)への追跡がない。
  より良い版は、これらの特定の drop を明確に別に name-mangle し
  (例えば `idris2rc2_unimplemented_ffi_<name>` シンボル)、将来の
  リンカエラーが少なくともこの正確な機構まで grep 可能にするか、
  すべての呼び出し箇所で drop を注記するコメントを生成 `.c` に
  出力できる。未実施 -- 素のアプローチが、2 つ目の並行するものを
  発明するのではなく、ギャップ #2 自身の既存の「単に extern 宣言
  してリンカに任せる」機構にちょうど一致するよう選ばれた。

## 主要な発見: 1 つのモジュールの欠落したインクリメンタルデータは、その importer だけでなく*そのビルドの残り*にカスケードする

rc2 のバグではない -- これは完全に上流自身の
`Core.Context.addImportedInc` にある -- が、rc2 自身の目的にとって
"既知のギャップ" に折り込むより自身のセクションに値するほど深刻
である。上記 `getField` 修正が `System.FFI` を通過させた後、初めて
`base.ipkg` をエンドツーエンドでインクリメンタルに再ビルドして
発見: ビルドは 136 モジュールすべてをエラーゼロで完了したが、
その後すべてのインストール済み `.ttc` を `rc2` CG タグについて
スキャンする(`grep -c rc2` -- 粗いが効果的な incData 存在チェック)
と、136 中**36 モジュール**だけが実際にインクリメンタルデータを
運んでいた。他の**100** -- これをトリガーしたものと妥当な関係の
ない `Data.Vect`、`Control.Monad.State`、`Data.SortedMap` のような
モジュールを含む -- は一切持っていなかった。

原因: **1 つのモジュール(`System.File.Meta`)がオブジェクト
ファイルの生成に失敗した**、上記どのギャップとも関係のない理由で
-- 本物の、他の点では有効な `%foreign "C:idris2_fileIsTTY,
libidris2_support,idris_file.h"` 宣言。当初は古い nixpkgs の
バージョンずれ問題と誤診断された; 代わりに適切に確認した
(推測せず検証する): `idris2_fileIsTTY` は*実装されている*、
まさに idris2-src 自身の `support/c/idris_file.c` に
(`System.File.Meta` 自身の `isTTY`/`prim__fileIsTTY` と同じ
コミットで追加された)-- `idris_file.h` が、そのファイルの他の
すべての関数が持つ対応するプロトタイプ行を単に得なかっただけ、
idris2-src 自身の現在のソースの孤立した上流の見落としであって、
古さではない。バイト単位の `diff` で、
`install/idris2-0.8.0/support/c/idris_file.h`(このプロジェクト
自身の自己ビルドコピー)が `idris2-src/support/c/idris_file.h` と
同一であることを確認した -- 自己ビルドは idris2-src 自身のヘッダを
上流のそのままに忠実に再現した; 何も古い nix 提供のコピーに
フォールバックしなかった。どのテストも実際に `isTTY` を呼んだら
(単に呼んだことがないだけ、なので `DeadCode`/上流自身の到達可能性
fetch がこれが表面化する前に常に宣言を除外する)全プログラム
コンパイルもまったく同じように失敗するだろう -- rc2 自身の
インクリメンタルサポートの設計や実装のギャップでは全くなく、
自己ビルドの問題でもない。`incCompile` はその 1 つのモジュールに
対して正しく `Nothing` を返す(モジュールごとの優雅な劣化、設計
通りに動作)-- が、それをインポートする*次の*モジュール
(`addImportedInc`、`Core.Context`)は、その 1 つのインポートを
使えないと注記するだけでなく、セッション自身の `incrementalCGs`
から `rc2` を*完全に*削除することで反応する。その同じ
`idris2-rc2` 呼び出しでその後処理されるすべてのモジュール --
*そのパッケージのビルドの残り*について、失敗したモジュールと
インポート関係があるかどうかにかかわらず -- も静かに
インクリメンタルデータを得ず、それ以上の警告は印字されない
(警告自体は `rc2` がまだ `incrementalCGs` にある間だけ発火する
ので、カスケードが始まるまさにそのとき、ちょうど 1 回印字され、
その後、効果が広がり続けても静かになる)。

これは `--inc rc2`(あるいは、この同じ機構で `--inc chez`)の
実用上の信頼性が、大きな依存順のビルドのどこでも*ゼロ*個の
モジュールが失敗することに懸かっていることを意味する -- 1 つの
悪い `%foreign` 宣言が、どこであれ、その同じ呼び出しでその後
処理されるほとんどすべてのインクリメンタルコンパイルを静かに
無効にする、壊れたモジュールに実際に依存するプログラムだけで
なく。標準ライブラリ全体のゼロからの再ビルド(このセッション
自身のユースケース)にとって、それは本物のリスクである: `base`
だけで 136 モジュールあり、このセッションはまさに最初の試みで
2 つの独立したモジュールレベルの失敗(`getField` 自身のリテラル
要件、`idris2_fileIsTTY` 自身の欠落したヘッダプロトタイプ --
idris2-src 自体の 1 行の上流の見落とし、この文書自身の懸念とは
別に報告/修正)を見つけた。これを rc2 自身の側で回避する価値が
あるか(例えばカスケードを検出し、同じ呼び出し内でその後の
モジュールのインクリメンタルコンパイルを再試行する、あるいは
他の緩和)、あるいは単に文書化して回避する鋭いエッジか(例えば
パッケージごとの `IDRIS2_INC_CGS`、パッケージ自身の最初の
モジュールレベルの失敗が修正されたらそのパッケージを 2 回目に
再ビルドする。*2 回目*の `--install` 実行はすべてのモジュールを
新しく再処理し、失敗が再発しないところではどこでも `rc2` incData
を拾うから)は、これを再開する人への未解決の問いである -- この
セッションでは試みなかった、それが上流自身のインクリメンタル機構
の性質であって `Compiler.RC2` にローカルな何かではないので。

## エンドツーエンド検証: 実際にプログラムを実行してさらに 5 つのバグが見つかった

`prelude`/`base`/`linear`/`contrib`/`network` をクリーンに
再ビルドさせること(前の 2 セクション)は、各*モジュール*が
単独で有効な `.o` にコンパイルされることを証明するだけである --
それらの `.o` が実際に実行ファイルとして*一緒に正しくリンクして
実行される*かは何も言わない。最初は実行されなかった: 自明な
`Hello.idr`(`--cg rc2 --inc rc2`)がさらに 5 つの本物のバグを、
順に、各々次に移る前に修正されて、浮かび上がらせた。
`rc2/tests/verify.sh` は各々の後 111/0/0 に留まった。

1. **`noMain` が誤った名前空間を使った。** `incCompile` はそれを
   `ctxtPathToNS sourceFile` 経由で導出し、それは*ファイルパス*
   から名前空間を推測する(`Hello.idr` -> `Hello`)-- 誤り、
   Idris2 はまさにエントリポイントのケースのために、ファイル自身の
   `module Main` 宣言がそのファイル名と異なることを許すからである
   (`module Main` を含む `Hello.idr` は完全に通常で、すべての
   `-o` 呼び出しが行うことそのもの)。すべてのモジュールが
   `noMain = True` でコンパイルされた、`Main` 自体を含めて --
   リンク時に `undefined reference to main`(リンカ自身の C
   ランタイム起動コード `_start` は常にどこかから本物の `main`
   シンボルを必要とする)。ファイルパスから何かを再導出するのでは
   なく、`Ctxt` からモジュール自身の既に記録された*宣言された*
   名前空間(`currentNS`)を読むことで修正。
2. **`%World` 自身の typecase 名文字列がどこにも定義されて
   いなかった。** `PrimIO.unsafeCreateWorld` の `%MkWorld` 構築は
   `idris2rc2_constr__percentWorld` をタグなしコンストラクタ名として
   参照する -- ギャップ #1 自身の修正は参照される場所ではどこでも
   それを正しく `extern` 宣言するが、どこにも一切それを*定義*する
   ものがない、(その前の `Int`/`Char`/`(->)` のように)プログラム
   に裏付けとなるトップレベル宣言が一切ないからである。リンク時に
   `undefined reference to idris2rc2_constr__percentWorld`。
   `runtime.c` 自身の既存の「事前宣言されたプリミティブ typecase
   名」リストにそれらの隣に追加することで修正(同じリスト、RefC
   自身の `support/refc/prim.c` もこれを持たない -- そこで違う
   扱いだからではなく、全プログラムコンパイル、rc2 自身のものを
   含む、が常に `unsafeCreateWorld` を Emit に届く前に自身の唯一の
   呼び出し側にインライン化するから; `PrimIO.idr` を完全に単独で
   コンパイルすることだけがそれを露出する)。
3. **ルート項コード生成がないことは `main()` 呼び出し側もない
   ことを意味する。** 設計は「別のルート項再コンパイルステップは
   不要、`Main.main` はただの別の `toIR` メンバー」と言った --
   `Main.main` 自体には真だが、全プログラムフッタ自身のハード
   コードされた `__mainExpression_0()`(`getCompileDataWith` が
   毎回新しく構築する `ClosedTerm` 合成ラッパ、`Compiler.Common`)
   への呼び出しは、インクリメンタルモードで呼ぶものが何もない --
   その名前はどのモジュール自身の `toIR` のメンバーでも一切ない。
   `Emit.idr` の `generateCSourceFile` は
   `directEntryPoint : Maybe String` パラメータを得た: `Nothing`
   は今日の全プログラムフッタをそのまま保つ; `Just call`
   (`incCompile` 自身の `Main` モジュールケースのみ)は代わりに、
   `incCompile` 自身が見つけたものから構築した完全な呼び出し式を
   継ぎ足す。
4. **`Main.main` 自身の実アリティは信頼できるほど 1 ではない。**
   (3) の最初の試みは `"\{cname}(idris2rc2_freshWorld())"` を
   ハードコードした(1 つの新しい `%World` トークンを構築 --
   小さな新しい `idris2rc2_freshWorld()` ランタイムヘルパ、
   `createCFunctions` が通常のタグなし 0 アリティ `RCon` にインラ
   インで出力するのと同じ構築 -- し、それで `Main.main` を呼ぶ)。
   素の `putStrLn` には動いた(`Main.main` はアリティ 1 で
   コンパイルされ、本物の `%World` パラメータを取る)-- そして
   少し大きいプログラム(最初の本物の `IO` アクションの前に
   `let` 束縛された純粋な値)に対して*何も*印字しない動いて見える
   実行ファイルを静かに生成した。`--directive dumprcexpr` が理由を
   示した: その `Main.main` はアリティ 0 でコンパイルされ、自身の
   本体は `%World` 引数をまだ欠いた `RUnderApp` スタイルの
   クロージャ(`partial Main.{main:31} missing=1 [v0]`)を構築
   していた -- ゼロ引数でそれを呼ぶのは*そのクロージャを構築*して
   返すだけで、何も実行しない。「既に解決済み」ではなく、同じ関数
   を代理する CAF。`defs` の `Main.main` 自身の実 `MkRCFun`
   アリティで分岐する(`incCompile` で利用可能、これについて意図的
   に何も知らない `Emit.idr` 自体と違い)ことで修正: アリティ 0 は
   加えて呼び出しを `idris2rc2_applyClosure(..., idris2rc2_freshWorld())`
   で包む -- プログラム全体の*すべての*他の未飽和クロージャが常に
   通される同じ汎用ランタイム関数、まさに全プログラムモード自身の
   `PrimIO.unsafeCreateWorld` 本体(`apply v0 v1`)がこの同一の
   理由で既に行うこと; アリティ >=1 は以前からの直接呼び出しを
   保つ(既に正しい -- そこの `%World` トークンは本物の型付き C
   パラメータなので、直接呼び出しは既に無料で同等の `apply` を
   行う)。その後、壊れた 1 つに対して再テストするだけでなく、
   両方の形状に対して検証。
5. **さらに 2 つのクロスリンキング危険、実マルチモジュール
   プログラムをリンクして発見**(`Data.List`/`Data.SortedMap` を
   使う小さなプログラム、意図的に素の `putStrLn` だけでない --
   `base` 自身の 136 モジュールクリーン再ビルドは、各モジュールが
   単独でコンパイルされることだけを証明し、それらのいくつかが
   一緒にリンクして正しく実行されることを証明しない):
   - **`.o` 全体のリンクがギャップ #3 自身の「drop して、リンク時
     に失敗」機構を打ち負かす。** `compileExprInc` 自身の最終
     リンクステップは、蓄積されたすべての `.o` をリンカコマンド
     ラインに直接列挙した -- が、そのように名付けられた素の `.o`
     は*常に*丸ごとリンクされる、アーカイブメンバー(まだ未解決の
     何かがそれが提供するシンボルを実際に必要とするときだけ引き
     込まれる)と違い。`base` 自身の `Prelude.IO.threadWait`
     (意図的に drop された `prim__threadWait` を呼ぶ)が
     `putStrLn` 自体とまさに同じ `.o` にあるので、`putStrLn` を
     呼ぶ任意のプログラム -- つまりすべてのプログラム -- が、
     `threadWait` を呼んだかどうかにかかわらず `threadWait` 自身の
     ダングリング参照も引き込んだ。新しい `CC.archiveObjectFiles`
     (`ar rcs`)で、リンク前に蓄積されたすべての `.o` を 1 つの
     静的アーカイブに束ねて修正、本物のモジュールごとの選択を
     回復。
   - **同じ問題、1 レベル細かく。** アーカイブだけでは不十分
     だった: `putStrLn` と `threadWait` は両方とも*同じモジュール*
     (`Prelude.IO`)にあるので、一方が必要でもモジュール*ファイル*
     ごとのアーカイブ選択にかかわらず `.o` 全体を(ゆえに他方を)
     引きずり込む。コンパイル時の
     `-ffunction-sections -fdata-sections` に加えてリンク時の
     `-Wl,--gc-sections`(`CC.idr`、無条件、両モード -- 純粋な
     デッドコード除去、決して振る舞いを変えない)で修正、リンカが
     個々の未使用関数を、オブジェクトファイル全体ではなく
     *セクション*粒度で捨てられるようにする。
   - **全プログラムの一意性を仮定した名前 freshening カウンタ。**
     `Compiler.RC2.MutualLoop` 自身の合成されたディスパッチャ名
     (`MN "rc2_mutualLoop" i`)は `i` を fresh-per-compile
     カウンタから採番する -- 全プログラムモードではグローバルに
     一意(1 つの共有カウンタ)だが、別々のインクリメンタル
     コンパイル間では*そうでない*、各々が自身のカウンタを 0 で
     再開する。`Data.List`/`Data.SortedMap.Dependent`/`Prelude.Types`
     (各々たまたま 1 つを必要とした 3 つの無関係なモジュール)を
     一緒にリンクして `multiple definition of rc2_mutualLoop_0`。
     `isMutualLoopMerged` が認識する任意の名前に対して
     `fnSignature` が `static` を出力するようにして修正
     (`Compiler.RC2.Util`、これらを他のパスから除外するために
     既に他の場所で使われている)-- 無条件で安全、このディスパッチ
     ャはそもそも自身の生成 `.c` の外から参照される意図がない、
     全プログラムであれインクリメンタルであれ。

## 遅延: クロスモジュール定数共有

この文書が置き換える TODO.md の注記はこうも提起した: 各モジュール
が今や必要な定数の自身のコピーをステージするので(翻訳単位が
分かれると定数 dedup は本質的にモジュールスコープになる)、定数
自身の C シンボル名をその*値*から決定論的に導出し(例えば内容
ハッシュ)、`static` の代わりに `__attribute__((weak))` と宣言
して、リンカが別々のモジュールが出力したバイト同一のコピーを
リンク時に 1 つに折り畳めないか? これは本物の技法(weak シンボル
マージ)であり、どちらの道でも正しさに影響しない(static のメモリ
重複だけ)-- 追随の価値があるが、この機能の最初の動作版のスコープ
外である: モジュール間で同じソース値の任意の 2 出現に対して生成
された初期化子テキストが証明可能にバイト同一であること(フィールド
出力順、float フォーマット、等)が必要で、現在の逐次カウンタ命名
(`constcon_0`、`constcon_1`、...)は今日それを保証する必要がない。

**再訪、今のところ見送りを決定。** `Emit/Util.idr` 自身の素の
リテラルケース(`genConstant`)の `ConstDef` 命名を確認した --
`Int`/`Int64`/`Bits64`/`Double` 定数は*既に*自身の値から命名
されている(`cCleanString (show x)` 等、カウンタではない)と
判明したので、それらだけを `static` の代わりに `weak` にするのは
低リスク(命名変更は一切不要)だろう -- が、実際の見返りは
限界的である: それは、複数のモジュールで構築されるバイト同一の
定数のために重複した静的ストレージ、各々数バイト、を節約するだけ
で、いかなる種類のランタイム性能の勝ちでもない。`Str` 定数は
今も素のカウンタ(`getNextCounter`)を使い、任意の文字列*内容*
(識別子テキスト、その実際の仕事、と対照的に)のために
`cCleanString` を再利用するのは、単に不整然なだけでなく本当に
安全でないと判明する: `cCleanString` は `' '` と `'_'` の両方を
同じ `"_"` にマップし、その非印字文字エスケープ(`"u" ++ hex`)は、
その正確なエスケープシーケンスを素の ASCII で綴るリテラル文字列
(例えばリテラルテキスト `"u3042"` と単一文字 U+3042 は両方とも
`u3042` に mangle される)と衝突する -- 本当に異なる 2 つの文字列
値が同じ `weak` シンボル名に衝突し、リンカはたまたま最初に
リンクした方を静かに保つだろう。安全な版は代わりに本物の内容
ハッシュ(例えば UTF-8 バイトに対する 64 ビット FNV-1a)を、
ゼロから書く(スコープ内に既存のハッシュユーティリティなし)必要
がある。数値の半分自身の利益が既に限界的で、文字列の半分も
限界的な利益のために新しいハッシュ衝突安全性が重要なコードを必要
とすることを考えると、今それはリスクにも実装コストにも値しないと
決めた -- 発見のすべてとともにここに残し、また出てきたらゼロから
再調査しないようにする。

  `validateExport`/`emitExportWrapper` 経路)はここで扱われて

  ライブラリターゲットビルドをサポートする前に、エクスポート

  yes、その 1 つの名前自身のシグネチャだけを必要とする)自身の
  検討が必要。
- `%cg rc2 extraRuntime=<path>`/`inlineRuntime=<code>` ディレク
  ティブ(`rc2/doc/directives.md`)は今日、生の C を単一の
  全プログラムファイルに継ぎ足す; モジュールごとモードでどの
  モジュールがそれらを受け取るべきか(外部リンケージを必要とする

- まだテストされていない: 自身がインクリメンタルにコンパイル

  `network` はすべて、どの実プログラムが恩恵を受けられる前にも

## 検証: 完了、両ステップ

すべての Idris プログラムは暗黙に `prelude` をインポートする
(`addPrelude`、`Idris.ProcessIdr.processMod`)-- 「依存なし」
フィクスチャなどというものは存在しないので、本物のエンドツーエンド
インクリメンタル往復は、その再ビルドが実際に成功するまで、上記の
prelude/base/linear/contrib/network 再ビルドでブロックされていた。
下の両ステップは今や完了、計画されただけでない:

1. **優雅なフォールバック、ブートストラップが存在する前。**
   標準パッケージのどれもまだ rc2 incData を持っていなかった
   早い段階で確認: 通常の rc2 テストを `--cg rc2 --inc rc2` で
   ビルドすると、静かに、正しく、全プログラムコンパイルに
   フォールバックした(`prelude` 自身の欠落した incData で
   `missingIncremental` が発火、設計が予測した通り)-- クラッシュ
   なし、静かに半分スキップされたビルドなし。
2. **本物のインクリメンタル往復、ブートストラップの後。**
   `prelude`/`base`/`linear`/`contrib`/`network` がすべてクリーン
   に再ビルドされた(272 モジュール、欠落 incData ゼロ -- 上記
   "エンドツーエンド検証")状態で、2 つの使い捨てプログラム
   (`Hello.idr`、素の `putStrLn`; と `Data.List.sort`/
   `Data.SortedMap` を使う 2 つ目)が両方とも `--cg rc2 --inc rc2`
   でビルドされ正しい出力で実行され、`Hello.idr` 自身の
   メッセージを編集して再ビルドすると `Hello` 自体だけが再
   コンパイルされた(出力に `prelude`/`base` の再処理が見えない
   -- `missingIncremental` 自身の
   `sourceUnchanged && ... && incrementalOK` スキップ、設計通りに
   動作)、再リンクの前に。

`rc2/tests/verify.sh` は上記すべての修正を通じて通常の 111/0/0
全プログラムベースラインに留まった -- インクリメンタルのみの
コード経路はどれも `--inc rc2` なしでは到達不能である。
