# コンストラクタ、クロージャ、Stringセルのレイアウト

(原文: `doc/constructor-layout.md`。内容が乖離した場合は原文を正とする。)

## コンストラクタ

| バイト | フィールド |
|---|---|
| 0..4 | ヘッダ(参照カウント、値タグ、予約) |
| 4..6 | アリティ(`uint16_t`) |
| 6..8 | タグ(`int16_t`。なければ -1) |
| 8.. | `args[arity]` |
| 8 + 8·arity | 名前(**タグが -1 の場合のみ**) |

consセルは24バイトである。`idris2rc2_newConstructor`は、`tag < 0`のときだけ名前用のスロットを確保する。`idris2rc2_conName`と`idris2rc2_setConName`は、これを`args[arity]`として読み書きする。

定数コンストラクタ(`RCConstCon`、`doc/const-con-fold.md`)も同じレイアウトになる。タグ付きのものは`IDRIS2RC2_ConstConstructor<n>`を使い、タグなしのものは、名前用のスロットを1つ余分に持つ無名構造体を使う。

## 理由

2026-09 までのレイアウトは次のとおりだった。

| バイト | フィールド |
|---|---|
| 0..4 | ヘッダ |
| 4..8 | アリティ(`int32_t`) |
| 8..12 | タグ(`int32_t`) |
| 12..16 | パディング |
| 16..24 | 名前 |
| 24.. | args |

consセルは40バイトで、glibcのチャンクとしては48バイトだった。Chezでは16バイトである。`name`を読むのは、タグなしコンストラクタに対する`strcmp`によるマッチと`%World`だけである。タグ付きコンストラクタ(リスト、`Maybe`、タプル、レコード)は、すべて使わない名前を持ち歩いていた。

ヘッダは4バイトだが、`args`は8バイト境界に置く必要があるので、ヘッダの後ろの4バイトはもともとパディングだった。16 ビットのフィールド2つが、ちょうどこの隙間に収まる。隙間はフィールドの並べ方で埋めており、`__attribute__((packed))`は使わない。使ってもこれ以上は得られないためである。
- packed構造体では、`_Atomic`な参照カウントのアラインメントが保証されない。
- ボックス化した`Int64`/`Double`は16バイトから12バイトに縮むが、アロケータはどのみち16バイトを返す。ペイロードのアラインメントが崩れるだけである。

`name`を8バイト目に動かし、すべてのセルに残す案では32バイトになる。しかしglibcのチャンクは48バイトのままである。そこで名前をフィールドの後ろへ移し、タグなしのセルにだけ置くことにした。

## 上限

アリティは最大65535、タグは最大32767である。エミッタは両方を検査し(`Emit/Util.idr`の`checkConLayout`)、切り詰めずにコンパイルを失敗させる。実在するデータ型で、この上限に近いものはない。

## 結果 (2026-09-26)

`Data.List.sort`、`Int` 100万個(`TODO.md`、「`sort` against Chez」):

| | 変更前 | 変更後 |
|---|---|---|
| 時間 | 3.237s | 3.117s (-3.7%) |
| 時間、mimalloc | 2.457s | 2.400s |
| max RSS | 81.4MB | 65.8MB (-19%) |
| cache-misses | 118M | 104M (-12%) |
| L1-dcache-load-misses | 85.7M | 73.6M |

命令数は変わらないので、短縮された時間はすべてメモリトラフィックによるものである。改善幅は小さい。リストのセルを読み込むときのストールは、主にセルがヒープ上に散らばっていることと、ボックス化された`Int`ごとにたどるポインタが1つ増えることに由来する。セルの大きさによるところは小さい。

## クロージャ

`IDRIS2RC2_Closure`にも、同じ隙間があった。`fn`がヘッダの直後にあり、`arity`/`filled`(各1バイト)はその後ろだった。

| | 変更前 | 変更後 |
|---|---|---|
| ヘッダ | 0..4 | 0..4 |
| `arity`, `filled` | 16..18 | 4..6 |
| `fn` | 8..16 | 8..16 |
| `args` | 24.. | 16.. |

ヒープ上のクロージャは、常にアリティ全体分の領域を持つ。そのため 16 + 8·arityバイトになり、従来より8バイト小さい。`IDRIS2RC2_ConstClosure`(まだ何も充填されていないクロージャの静的な形)も、先頭のフィールドは同じである。その初期化子(`boxedConstClosureExpr`)はこれらのフィールドを名前で指定するようになったので、並び順には依存しない。

この8バイトが得になるかどうかは、アロケータ次第である。glibcは16バイト刻みでチャンクを払い出し、チャンクごとに8バイトのオーバーヘッドがある。このため、アリティが偶数ならチャンクの大きさは変わらず、奇数のときだけ1段小さくなる。100万個のクロージャの構築と畳み込みを20回繰り返して測定した(2026-09-26、同じ生成Cを、2つのランタイムのそれぞれにリンクした)。

| クロージャ | アロケータ | 変更前 | 変更後 |
|---|---|---|---|
| アリティ 3 | glibc | 3.89s, 128MB | 3.71s, 112MB |
| アリティ 3 | mimalloc | 3.46s, 134MB | 3.15s, 102MB |
| アリティ 2 | glibc | 3.70s, 112MB | 3.73s, 112MB |

アリティ 2 の測定では、確保バイト数が 8% 減る(valgrind)。しかしglibcでもmimallocでも、時間とRSSは変わらなかった。`sort`は比較関数のクロージャを1回しか作らないので、影響を受けない。

## String

```c
typedef struct {
  IDRIS2RC2_Header header;
  uint32_t len; // str の内容のバイト長(終端文字を含まない)
  char *str;    // NUL 終端の UTF-8 バイト列。途中に NUL バイトを
                // 含みうる。添字はバイト単位
} IDRIS2RC2_String;
```

これも16バイトである(`idris2rc2_datatypes.h`で`_Static_assert`により検査している)。`len`は、上のコンストラクタとクロージャのレイアウトが追加フィールドに使っているのと同じ、ヘッダのアラインメント用パディングの4バイトに置かれ、`str`の直前に位置する。

`len`は文字列のバイト長であり、コードポイント数ではない。`String`がAPIレベルではコードポイントで添字付けされるのに、`len`自体はバイトを数える理由は、README.mdの「Deliberate differences from upstream RefC」を参照。`len`があるので、`strlen`と違って`String`は途中にNULバイトを含められる。文字列の範囲を必要とするプリミティブ(比較、`++`、`pack`/`unpack`、リテラルとのパターンマッチ)は、終端文字ではなく`len`を読む。

`str`自体は、通常の`char *`としてCに渡せるようにするためだけに、常にNUL終端のままである。この境界を越える場合(FFIの引数、`%export`された戻り値、`String`から数値へのキャスト)は、途中の最初のNULで切れる。これは許容された制限であり、`rc2/doc/fastpack-fix.md`とREADME.mdに記載がある。

バイト長が`len`の`uint32_t`に収まらない結果(4 GiB超)は、それを構築する時点でabortする(`idris2rc2_checkedStrLen`、`idris2rc2_memory.h`)。気づかないうちに桁あふれし、短すぎる壊れた`len`になることはない。

## 落とし穴: ランタイムの`Makefile`

`rc2/support/rc2/Makefile`には、以前はヘッダへの依存関係がなかった。レイアウトを変更したあと、`make`は自分自身が変更された`.c`ファイルしか再ビルドしなかった。`idris2rc2_strings.o`は古いレイアウトのままで、確保したすべてのセルの範囲外へ書き込んだ(`malloc(): corrupted top size`、`verify.sh`で30件の失敗)。現在は、すべてのオブジェクトがすべてのヘッダに依存する。
