# `Compiler.RC2.DeadVars`: どこからも参照されない束縛の消去

(原文: `doc/dead-vars.md`。内容が乖離した場合は原文を正とする。)

## 動機

大規模な実プログラムである`idris2-lsp`で、実際の`--directive dumprcexpr`の出力を見ると、単一の呼び出し元しか持たない小さな`Compiler.RC2.SpecClosure`のクローンが繰り返し現れていた。同じ出力には、ごく普通の`RConAlt`(`case`のaltが分解したコンストラクタのフィールド)も数多く含まれ、その束縛変数はalt自身の本体のどこでも読まれていない。使われないだけでなく、dropもされない。

こうした束縛にもコストはある。`Compiler.RC2.Emit`は、それに対して実際のCローカル変数を宣言する(`IDRIS2RC2_Value *var_N = sc->args[k];`)。`dumprcexpr`のダンプを読む人間も、頭の中で読み飛ばすノイズを1つ余分に抱えることになる。

ただし、Cの宣言をEmitで省くだけでは根本的な解決にならない。それでは、前段のどのパスにも、ダンプ自体にも、フィールドが未使用であることが見えない。得られるのは、生成されるCの1行分にすぎない。それも最終的にはやる価値があるが、本当に得たいのは、最終段で宣言を1つ飛ばすことではなく、*IR* の上で「このフィールドは使われない」と表すことである。

## 「参照されない」の意味

`RConAlt`が分解するフィールド(`MkRConAlt`の`args : List Int`)は単なる変数idであり、マッチしたコンストラクタの実際のフィールドと、位置で1対1に対応する。`Compiler.RC2.Emit`の`emitConAltBody`は位置で`sc->args[k]`を引くので、リストから要素を削除すると、後続のフィールドの添字がすべてずれてしまう。

「参照されない」とは、そのaltの本体に対する`Compiler.RC2.RCExp.freeLocalsR`の結果に、そのidが一切含まれないことをいう。`freeLocalsR`は、`RDrop`/`RFree`/`RReleaseReuse`の対象も本物の参照として数える(`Compiler.RC2.Sink`の`genuinelyUsedR`は、意図的にこれと異なる扱いをする)。したがってこれは、通常の意味での「未使用」より厳密に狭い、保守的な基準である。このパスが消すフィールドは、最終的な本体のどこでも、解放する必要すらないものに限られる。

## 実際には当初の想定より対象が広い理由

当初は、このパスが捕まえるのは次のようなフィールドだけだと考えていた。*native* に分類され(`Compiler.RC2.RC`の`definitionNatives`。dropの追跡対象にそもそもならない)、唯一の使用が後段のパスによる最適化で消えたものである。Boxedのフィールドで未使用のものには、`annotate`(`Compiler.RC2.RC`の所有権注釈パス)がすでに明示的な`RDrop`を付けるので、それが参照として数えられるはずだった。

これは過小評価だった。再利用の対象にならない通常のマッチでは、`Compiler.RC2.DeadVars`に届くIRは次のような形をしている(3フィールドのレコードから1つだけを使う実例)。

```
case v9453 of
  Prelude.Interfaces.MkApplicative [record] tag=Just 0 args=[v9455, v9457, v9456] ->
    dup v9457
    drop [v9453]
    apply v9457 [...]
```

実際に使うフィールド(`v9457`)には、明示的な`dup`が付く。一方、スクルーティニー全体(`v9453`)には、最後に単純な`drop`が1回付くだけである。`dup`されなかったフィールドはすべて、このdropの再帰的な解体で解放される。`annotate`が未使用の2フィールドのために合成した個別の`RDrop`は、この形では残らない。この形を作るのがどの後段の処理であれ、`annotate`が付けたフィールドごとの参照が`Emit`まで生き残る必要はない。このためこのパスは、当初想定した限定的なnativeのケースだけでなく、「レコードのパターンマッチで一部のフィールドしか使わない」というありふれたケースにも効く。`idris2-lsp`を`--directive dumprcexpr`付きでコンパイルして測ったところ、この方法で19000を超えるフィールドが消えた。

正しさには影響しない。`freeLocalsR`による判定は、フィールドが最終的な本体で参照されなくなった理由を問わず、参照されているかどうかだけを見る。変わるのは、このパスがどれだけ効くかの見積もりだけである。

## 構造的な「束縛なし」マーカーではなく`0`を使う理由

`args : List Int`の型を変えず、たとえば`List (Maybe Int)`にしなかったのは、このパスの影響範囲を小さくするための意図的な選択である。`RConAlt.args`は、パイプラインのほぼすべてのパス(`ConstFold`、`ConAltNative`、`DualABI`、`Sink`、`Loop`/`MutualLoop`、`LateInline`、`SpecClosure`、`Reuse`、`Pretty`、`DupMerge`)を通過する。それらの大多数は、altの本体を再帰的にたどるために`args`を中身に触れず素通しするだけである。型を変えると、各フィールドに実際の束縛があるかどうかを知る必要のないそれらの箇所すべてで、少なくとも型の再検査が必要になる。得るものは何もない。

通常の`Int`の範囲をそのまま使う場合、健全性のために守るべき不変条件はプログラム全体で1つだけである。`0`が実在の変数idにならないことである。`Compiler.RC2.Util`の共有`VarId`カウンタは、パイプライン全体の新規idの唯一の供給元であり、`Compiler.RC2.RC`のトップレベルパラメータや`RConAlt`のフィールドのidもここから採番される。このカウンタを`0`ではなく`1`から始めることで、走査なしに、この不変条件を全体にわたって保証している。

## `Compiler.RC2.DupMerge`より厳密に後ろに置く理由

リネームしても、「このidがどこかで参照されるか」という構造的な性質は変わらない。id `x`が`freeLocalsR body`に現れないなら、部分木全体を一貫して`x -> y`とリネームした後でも、`y`はリネーム後の本体の`freeLocalsR`に現れない。したがって、このパスが置いた`0`は、後段のパスが新しい「本物らしい」idにリネームしたとしても、動作上は無害なままである。それでも、この性質に頼る理由はない。変数idをリネームまたは新規採番するパスは、すべてこのパスより前に走る(`Compiler.RC2.Loop`/`MutualLoop`の末尾ループ変換、`Compiler.RC2.LateInline`のスプライス、`Compiler.RC2.SpecClosure`のクローン作成、`Compiler.RC2.DualABI`のワーカー/ラッパー分割)。このため`0`は、このパスだけが一度置き、`Compiler.RC2.Emit`が読むまで一切触られない。`--directive nodeadvars`で無効にできる。

## `Emit.idr`での扱い

`emitConAltBody`のフィールドごとのループは、`0`のエントリではCの宣言を完全に省く。altの本体のどこからも参照されえないことが、`0`を与えた理由だからである。ただし、フィールド添字のカウンタはそのエントリでも進める。`0`のフィールドも、マッチしたコンストラクタのそのオフセットには実在する記憶域であり、このaltが名前を付ける必要がないだけだからである。
