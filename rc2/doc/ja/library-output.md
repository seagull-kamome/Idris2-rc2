# ライブラリ: `--directive staticlib`と`sharedlib`

(原文: `doc/library-output.md`。内容が乖離した場合は原文を正とする。)

プログラムの`%export`された関数(`export-support.md`)を、実行ファイルではなくライブラリとしてビルドする。`-o foo`を指定すると、`build/exec/`の下に次のファイルを書き出す。

| ディレクティブ | 書き出すファイル                                               |
|-------------|----------------------------------------------------------------|
| `staticlib` | `libfoo.a`、`foo.h`、`foo.link`                                  |
| `sharedlib` | `libfoo.so`、`foo.h`、`foo.link`                                 |

(名前がすでに`lib`で始まる場合は、`lib`をさらに付けることはしない。)2つのディレクティブは同時に指定できない。どちらも`nomain`を含意するが、プログラムには依然として`main`が必要である(`-o`がそれを要求する)。その`main`が実行されることはない。ライブラリをビルドするのはプログラム全体のコンパイルだけである。インクリメンタルモード(`incremental-compile.md`)が有効な場合、これらのディレクティブは`compileExpr`にプログラム全体の経路を取らせる。

`foo.h`には、エクスポートされた各関数のプロトタイプを、ラッパ(`Emit.Foreign.emitExportWrapper`)が定義する形で収める。`foo.link`には、ホストがリンク行のライブラリの後ろに加えるフラグを収める。ランタイム、サポートライブラリ、依存パッケージの検索パス、`-lgmp -lm -lpthread`、そしてプログラムの`%foreign`ライブラリである。`$(cat foo.link)`の形で使う。

## ランタイムはホストが持つ

ライブラリはロード時に何もせず、ランタイムも持ち込まない。ホストは、Cであれrc2であれ、ライブラリを最初に呼ぶ前に`idris2rc2_rtInit()`を1回呼び、最後に`idris2rc2_rtFinish()`を呼ぶ。2つ目のスレッドを始める前には`idris2rc2_enableMultiThreading()`を呼ぶ(`idris2rc2_runtime.h`、`runtime-lifecycle.md`、`hybrid-refcount.md`)。ホスト自身がrc2のコードであれば、これはすべてすでに行われている。ライブラリも同じことをすれば、二重に行うことになる。同じ理由で、1つのプロセスの中にランタイムのコピーは1つだけである。ランタイムの状態(セルプールのスレッドローカルなヒープ、マルチスレッドのフラグ、メモ化したCAFのレジストリ)は、2つのコピーで共有できるものではない。また、ライブラリからホストへ渡った値は、最後にそれをdropした側が解放する。

## シンボル

ライブラリのコードは、すべて1つのCファイルになる。ライブラリモードでは、`%export`のラッパを除き、その中の関数と定数をすべて`static`にする。そのため、`libfoo.a`や`libfoo.so`のシンボルはエクスポートだけになる(`nm -g --defined-only`で確認でき、`tests/library/run.sh`がこれを検査する)。したがって、1つのプログラムから作った2つのライブラリや、ライブラリとrc2でビルドしたホストは、同じ内部名(番号付きの`Main_add_123`や同じPreludeの関数)を、異なる本体で定義できる。静的にリンクしても衝突せず、共有ライブラリとしてロードしてもシンボルの横取り(interposition)は起きない。

## 静的ライブラリ

ホストは、ほかのCライブラリと同じように、`libfoo.a`とランタイムのアーカイブをリンクする。

```sh
gcc -I$RT -Ibuild/exec host.c build/exec/libfoo.a $(cat build/exec/foo.link) -o host
```

(`$RT`は`$(idris2 --libdir)/support/rc2`で、`idris2rc2_runtime.h`はそこにある。)1つのホストに複数の静的ライブラリを入れられる。ランタイムは、従来どおりアーカイブから来る。

## 共有ライブラリ

`libfoo.so`は`-fPIC -ftls-model=initial-exec`でコンパイルし、`-shared`だけでリンクする。ランタイムはその中で未定義のまま残り、ロード時に解決される。ランタイムは、プロセス全体で1つの共有オブジェクトでなければならない。それが`shared/libidris2rc2.so`である(`support/rc2/Makefile`。`-fPIC`でビルドし、`libidris2rc2.a`の隣にインストールする。素の`-lidris2rc2`が引き続きアーカイブを見つけるように、専用のディレクトリに置く)。共有ライブラリの`foo.link`は、これを`-rpath`付きで指定する。したがって次のようになる。

```sh
gcc -I$RT -Ibuild/exec host.c -Lbuild/exec -lfoo $(cat build/exec/foo.link) -Wl,-rpath,$PWD/build/exec -o host
```

rc2で書いたホストは、`--directive sharedruntime`で同じことを指定する。これは、実行ファイルをアーカイブではなく`libidris2rc2.so`に対してリンクする。ライブラリは`%foreign "C:name,libfoo,foo.h"`(`ffi-cexpr.md`)でリンクし、`IDRIS2_CFLAGS=-I<dir>`と`IDRIS2_LDFLAGS="-L<dir> -Wl,-rpath,<dir>"`を指定する。`tests/library/Host.idr`は、同じ定義から作った2つのライブラリを、この方法で呼ぶ。

ホストにアーカイブを入れない理由は次のとおりである。リンカは、リンク対象の何かが必要とするアーカイブのメンバしか取り込まない。そのため、`idris2rc2_strAppend`を使わないホストには、ライブラリが探すそのシンボルがなく、ライブラリの`dlopen`が失敗する(`undefined symbol: idris2rc2_strAppend`。`idris2rc2_rtInit`だけを呼ぶCのホストで観測した)。共有ランタイムなら、ホストが何を使うかにかかわらず、すべての関数がそろっている。また、複数のライブラリをロードするプロセスは、1つの状態を共有する。

`-ftls-model=initial-exec`により、プールの高速経路(`idris2rc2_memory.h`からインライン化される、スレッドローカルなヒープの読み取り)は、`__tls_get_addr`の呼び出しではなく、スレッドポインタからの1回のロードで済む。これには、ランタイムがホストと一緒にロードされている必要がある(`foo.link`がそうするようにホストの`DT_NEEDED`エントリになっているか、ホスト自身のコピーである)。後から`dlopen`されるランタイムでは失敗する。

## 共有ライブラリの探索

`libfoo.so`には、何がどこにあるかの情報を一切埋め込まない。soname(そのファイル名)を持ち、rpathも`DT_NEEDED`も持たない。ローダの通常の規則で決まるので、次のようになる。

- **ライブラリ自体。** `foo.link`はそのディレクトリを指定しない。それをリンクするホスト(`-L<dir> -lfoo`)は`libfoo.so`を`DT_NEEDED`として記録し、実行時には、自身の`RUNPATH`(`-Wl,-rpath,<dir>`、または隣にインストールしたライブラリなら`$ORIGIN`)、`LD_LIBRARY_PATH`、システムのキャッシュを通じて見つける。それを`dlopen`するホストは、パスを自分で指定する。決めるのはホストをビルドする側であり、ビルドディレクトリを指す絶対パスのrpathを代わりに入れることはしない。
- **ランタイム。** 共有ライブラリの`foo.link`には`-L<dir>/shared -Wl,-rpath,<dir>/shared -lidris2rc2`が入る。`<dir>`は、ライブラリをビルドしたツールチェーンのサポートディレクトリ(`$(idris2 --libdir)/support/rc2`)である。この絶対パスはホストの`RUNPATH`に入る。ホストを別のマシンへ移す場合は、それを置き換えるか、ローダが探す場所に`libidris2rc2.so`をインストールする。
- **ライブラリ自身のランタイムへの依存。** `libfoo.so`は、ランタイムのシンボルを未定義のまま残し、`DT_NEEDED libidris2rc2.so`を意図的に持たない。ランタイムはホストが、共有オブジェクトとして、またはエクスポートする静的なコピーとして提供する。ライブラリに`DT_NEEDED`があると、自身のランタイムを持つホストの横に2つ目のコピーをロードし、ランタイムの状態が二重になる。その代償として、ランタイムをロードしていないプロセスが`dlopen`したライブラリは`undefined symbol`で失敗する(`tests/library/dl.c`のホストは、ランタイムを`foo.link`から得ている)。

## パッケージのコードはコピーされる

ライブラリはプログラム全体から生成されるので、使用するパッケージ(`prelude`、`base`、...)の定義のうちエクスポートから到達できるものは、`static`関数としてライブラリの一部になる(`Data.List.sort`を呼ぶライブラリは、`sortBy`、`mergeBy`とその補助関数を持つ)。ホストは、自分が使うもののコピーを別に持つ。コピーされるのはコードだけではない。Idrisのコードのグローバルな状態も一緒にコピーされる。トップレベルの定数や、`unsafePerformIO`で作ったグローバルな`IORef`(メモ化したCAF)は、ホストに1つ、それに到達する各ライブラリに1つずつ存在し、それらのコピーは共有されない。値も共有できない。`%export`を通るのはスカラー、`String`、ポインタ、`Integer`であり、データ構造は通らない。そのため、レイアウトの異なるコピーどうしが出会うことはない。ネイティブコード(`%foreign`ライブラリ)はコピーされず、ホストが1回だけリンクする。パッケージのIdrisコードを共有するには、モジュールごとのコンパイルと、全体で同じパッケージのバージョンが必要になる(`KNOWN-BUGS.md`)。

## 対象外のこと

- 依存パッケージのネイティブライブラリ(`libidris2rc2base.a`、...)は、`.link`ファイルの列挙に従ってホストがリンクする。これらは`-fPIC`でビルドしていないので`.so`に入れられない。また、ネイティブ部分が状態を持つパッケージも、コピーが1つである必要がある。
- インクリメンタル(モジュールごと)のコンパイルではライブラリをビルドしない。
- ライブラリ内の深い非末尾再帰は、呼び出し元スレッドのスタック上で走る(`KNOWN-BUGS.md`)。

## テスト

`tests/library/run.sh`(`tests/verify.sh`から呼ばれる)は次を検査する。`AddLib.idr`と`Add2Lib.idr`(同じ定義で、エクスポート名だけが異なる)から作った静的ライブラリと共有ライブラリで、それぞれのシンボルがエクスポートだけであること。両方の静的ライブラリを1つのCホスト(`host.c`)に入れること。両方の共有ライブラリを1つのCホストに入れること。ライブラリを`dlopen`するホスト(`dl.c`)。`sharedruntime`を使うrc2のホスト(`Host.idr`)で、そのリンクに`libidris2rc2.so`が含まれていること。
