# コンストラクタとクロージャのためのセルアロケータ

(原文: `doc/small-object-allocator.md`。内容が乖離した場合は原文を正とする。)

状態: ステージ0、1a、1b、1c、2を実装済みである(`idris2rc2_pool.c`、`idris2rc2_pool.h`、`idris2rc2_memory.[ch]`)。ステージ3は測定した結果、実施しない予定である(「ステージ3の測定」を参照)。2026-11-10にランタイムと突き合わせてレビューし、その指摘を以下に反映してある。測定結果は末尾の「結果」にある。

## 問題

コンストラクタ、クロージャ、ボックスは、すべて`idris2rc2_alloc`を通る。これは`malloc`である。rc2でビルドしたコンパイラで`libs/prelude`をビルドしたときの測定(`stage1`のcallgrindの呼び出し回数、36.9 G命令、2026-11-10、1ブロックの`String`レイアウトより前)は次のとおりである。

| 割り当て元 | 呼び出し回数 | `malloc`呼び出しに占める割合 |
|---|---|---|
| `idris2rc2_newConstructor` | 53.2 M | 72.1% |
| `idris2rc2_mkClosure` | 14.4 M | 19.5% |
| `idris2rc2_mkLazy`(`Lazy`のセル) | 2.6 M | 3.6% |
| `Data.IORef.newIORef` | 0.3 M | 0.4% |
| 文字列(1.6 M個のオブジェクト、それぞれ2ブロック) | 3.2 M | 4.3% |

6.6秒のビルドで73.9 M回の割り当てがあり、毎秒約11 M回である。サイズ別(8バイト単位に切り上げ)では、16バイトが25.4%、24バイトが31.2%、32バイトが16.3%、40バイトが13.6%、48バイトが5.9%である。48バイト以下が合計で93.3%、128バイト以下が98.8%である。24バイトのセルは、フィールドが2つのコンストラクタ(`::`、ペアなど)である。

コストは、`rc2-norepl`のビルドのcallgrindプロファイル(`self-hosting.md`の項目7)では、`malloc`/`free`が命令の27%、参照カウントが26%、割り当てのラッパーが8%である。`LD_PRELOAD`でmimallocに差し替えると、`base`のビルドが13.5%短くなり(84.0秒から72.7秒。`BENCHMARKS.md`。同じ差し替えを以前に測定したときは5.1%だったので、効果はランタイムによって変わる)、リストを多用する`map`/`filter`は6倍速くなった(`TODO.md`)。原因は主に局所性である。リストを解体すると、そのセルがglibcのLIFOのfastbinへばらばらの順序で積まれ、次の割り当てがその順序で取り出す。取り出すたびにキャッシュミスになる。

## 範囲: セルのみ

このアロケータが扱うのは、サイズがタグと引数の数(arity)から決まるオブジェクトである。

| セル | バイト数 |
|---|---|
| `Constructor` | `8 + 8 * (arity + (tag < 0 ? 1 : 0))` |
| `Closure` | `16 + 8 * arity`(作るときに、arityの全体分の領域を確保する) |
| `IORef`、および`Lazy`のセル | 16 |
| ボックス化された`Int64`/`Bits64`/`Double` | 16 |
| `GCPointer` | 24 |

これらは上の`malloc`呼び出しの95.6%を占め、`String`が1ブロックになった後では約97.7%である(3.2 M回ではなく1.6 M回)。扱わず、`malloc`のままのものは、`String`(オブジェクトの約2%、可変長)、`Integer`(`mpz`)、`Array`、`Buffer`、`ThreadID`、`Mutex`/`Condition`/`Semaphore`/`Barrier`/`JoinHandle`/`Channel`と、チャネルのノードである。文字列のサイズは`16 + len + 1`なので、後で加えることはできる。以下のどこも、文字列を除外していることには依存しない。

### まず入口を分ける(ステージ0)

`idris2rc2_alloc(size)`は、現在すべての型の唯一の入口なので、同じサイズの2つの型(`IORef`と`Buffer`、`GCPointer`と`Array`)をサイズで区別できない。ステージ0は`idris2rc2_cellAlloc`を加え、セルの型だけをちょうどそこへ移す。挙動は変えない(まだ`malloc`を呼ぶ)。

| 割り当て箇所 | セルか |
|---|---|
| `newConstructor`、`mkClosure`、`mkDouble`、`mkInt64`、`mkBits64`(`memory.c`) | はい |
| `newIORef`(`ioprims.c:15`)、`mkLazy`(`rt.c:541`)、`mkGCPointer` | はい |
| `mkInteger`、`mkArray`、`mkBuffer`、`mkThreadID`、`cast Integer String`の`String`(`numeric.c:443`)、`allocString` | いいえ |
| `libs/rc2base`の`Mutex`/`Condition`/`Semaphore`/`Barrier`/`JoinHandle`/`Channel`(`concurrency_util.c`) | いいえ |

解放側もタグで分ける。`idris2rc2_teardown`は最後に`idris2rc2_cellFreeInline`を呼ぶ。これは`idris2rc2_cellPooled`(タグとarityによる、割り当てと同じ判定)に問い合わせ、プールのセルでないものを`free()`へ送る。`idris2rc2_trampoline`と`idris2rc2_applyClosureN`(`rt.c`)、`idris2rc2_releaseReuse`(`rt.h`)が解放するクロージャの殻はセルである。チャネルのノード(`concurrency_util.c`)とスレッドのプリミティブはセルではなく、移してはならない。ランタイムの外でセルを解放するものはない。`%export`の結果は別のコピーである。

### どのクラスか

1つの関数`idris2rc2_poolClass(size)`が、サイズをクラス(`16..128`、8刻みで15クラス)か、「大きすぎるので`malloc`を使う」に対応づける。arityが定数の割り当て箇所では、クラスは定数になり、分岐は消える。`malloc`に回るのは、引数が14個を超えるクロージャと、フィールドが15個(名前スロットがあれば14個)を超えるコンストラクタだけである。解放箇所は、同じタグとarityから同じ判定をするので、アドレスを見なくても両者は一致する。プールにあるセルは、その後でページを通して見つける。

## レイアウト

- **セグメント。** 4 MiBで、4 MiBにアラインされる(2倍のサイズを`mmap`して切り詰める)。64 KiBのページ64個からなる。ページ0は**セグメントヘッダ**を保持する。ページ記述子と、どのヒープも保持していないページのビットマップ`freeMask`である。残りの63ページがセルを保持する。セグメントは**決してunmapしない**。セルを解放したスレッドは、セルが`thread_free`に載った後でページ記述子(`owner`、`inPending`)を見る。その時点では、所有者がすでにそれを回収し、ページを空にして返しているかもしれないからである。返されたページのメモリはOSへ戻す(`madvise`)。常駐し続けるのは、セグメントのヘッダページだけである。
- **ページ記述子**(128バイト、2キャッシュライン。ページをOSへ返しても消えないように、セグメントヘッダの中にある)。1本目のラインは所有者だけが使う。`free`(フリーリスト)、`used`、クラス、状態、`bump`と`end`(ページのうち、まだセルに切り分けていない部分)、`base`、およびヒープのクラスごとのリストのリンクである。2本目は、ほかのスレッドが書き込む。`thread_free`(ほかのスレッドが解放したセルのアトミックなスタック)、`owner`、`inPending`、`pendingNext`である。
- **ヒープ。** スレッドごとに1つあり、`__thread`のポインタを通して見つける。このポインタは、静的な*空のヒープ*を指した状態で始まる。空のヒープの`direct[k]`は、すべて空のフリーリストを持つダミーのページを指す。そのため、高速パスはNULLを検査しない。まだヒープを持たないスレッドは低速パスに落ち、そこでヒープを作り、スレッド終了時のフックを登録する。`%export`関数を呼ぶCのスレッドも、これで扱える。ヒープは、クラスごとに`direct`(割り当て中のページ)、`avail`(空きのあるほかのページ)、`full`を持つ。さらに、空のページのリストと、`pending`を持つ。`pending`は、`thread_free`にセルが待っているページのスタックで、専用のキャッシュラインに置く。
- **フリーリストのリンク。** 空きセルは、次へのポインタを、ヘッダではなく**2番目のワード**(オフセット8)に保持する。そのため、ヘッダ(参照カウント、タグ)は、チェックモードと`isUnique`のために読める状態のまま残る。

```c
// allocate: heap -> current page -> head of its free list
pg = tl_heap->direct[k]; c = pg->free;
if (likely(c)) { pg->free = c->next; pg->used++; return c; }
return slow_path(k);

// release: the page is found through the segment header
seg = p & ~(SEG - 1); pg = &seg->pages[(p - seg) / PAGE];
if (atomic_load_relaxed(&pg->owner) == tl_heap) {   // own page: plain
  c->next = pg->free; pg->free = c; --pg->used;
  if (pg->state != ACTIVE || (pg->used == 0 && pg != tl_heap->direct[pg->klass])) page_after(pg); }
else push_remote(pg, c);                            // anything else: remote
```

- **低速パス**は、次の順序で処理する。(1) ページのバンプポインタから次の64セルをアドレス順に切り出し、`free`を延ばす。こうすると、新しいページは使われるにつれて触れられ、そのセルは順番に出てくるので、高速パスは1回のpopのままである。(2) `pending`を処理し、ページの`thread_free`を(`atomic_exchange`で)`free`へ取り込む。(3) ページを使い切ったら、それを`full`リストに入れ、別のページを取る。順に、`avail`のページ、ヒープの空のページ、そのクラスの放棄されたページ(引き取る)であり、それでもなければ新しいページを取る。新しいページを取る前に、`thread_free`に何かがある、全クラスの放棄されたページを掃引する。そうすることで、生産者と消費者が、ヒープを大きくする代わりに、消費者が解放したものを再利用する。
- **満杯のページ**は、そのクラスのリストを離れ、*full*リストに入る。満杯のページへの最初の解放で、そのページは`avail`に戻る。
- **`used`**は、ページのセルのうち、生きているもの**または`thread_free`にまだ載っているもの**を数える。これを変えるのは所有者だけである。局所的な解放は`--used`を行い、`thread_free`の回収は`used -= n`を行う。そのため、`used == 0`のページの`thread_free`には何も残っておらず、そのときに限ってページを空にしてよい。リモートのpushは`used`に決して触れない。
- **`pending`とのハンドシェイク。** pushする側は、セルを`thread_free`へpushし(compare-and-swap)、次にページの`inPending`フラグを立てる(フラグがすでに立っていれば交換を省く)。フラグが立っていなかった場合は、ページを所有者の`pending`へpushする。所有者は`pending`のスタック全体を`atomic_exchange`で取り、各ページについて、`thread_free`を回収する*前に*フラグを下ろす。フラグを下ろした後に来たpushは、フラグが下りているのを見て、ページを再びキューに入れる。下ろす前に来たpushは回収される。これはすべて`seq_cst`であり、フラグを下ろした後の回収は無条件に行う。ほかの箇所で使っている、relaxedの「何かあるか」という事前検査をここで使うと、フラグが立っているのを見たpushする側と、`thread_free`が空なのを見た回収する側が、どちらも何もせずに去りうるからである。
- **古いエントリ。** ページのエントリが、まだ古い所有者の`pending`に載っているうちに、そのページが空になって返されることがある(pushする側の2つの手順はアトミックではない)。`pageReturn`は、ページが再び取られる前に`owner`を番兵`abandonedHeap`にし、`pageInit`は新しい所有者を最後に公開する。そのため、そのエントリについては、古いヒープの`owner == h`の検査が失敗し、古いヒープはそのページに触れない。ヒープは、`inPending`が立っている空のページを返さない。しかし、遅れてきたpushする側が、すでに返されたページにフラグを立てることはまだありうる。その場合の害は、古いヒープが次に`pending`を処理するまで、新しい所有者のページの`inPending`が立ったままになることだけである。そのため、そのページへのリモート解放は、キューからは来ない回収を待つことになる。新しい所有者は、directページの空きを使い切ったときか、新しいページを取る前に最初の数個の満杯のページを見るときに、それらを見つける。パージはそれらをすべて見つける。遅れてきたpushする側のヒープが、その時点ですでに再利用されている場合も同じである。エントリは新しいスレッドのヒープの`pending`に載り、そのヒープの`processPending`がフラグを下ろしてページを飛ばす(自分のページではないからである)。ページの本当の所有者は、その処理以降に初めてフラグが下りているのを見る。
- *放棄された*ページのセルも、同じリモートの経路で解放される。`owner`は番兵`abandonedHeap`で、その`pending`は`POOL_DEAD`である。所有者の検査はアトミックなloadなので、ヒープを失ったばかりのスレッドが、そのページを自分のものと取り違えることはない。

## コンストラクタと短命なリストにもたらすもの

- **LIFOの再利用。** あるページで解放されたセルは、そのページが次に渡すセルであり、まだキャッシュにある。`::`を作って1ステップ後に解放するループは、ほんの数本のキャッシュラインの中で走る。
- **1つのリストのセルがまとまって並ぶ。** 新しいページはアドレス順に使われるので、一度に構築されたリストのセル(TRMCのループは前から後ろへ埋める)は隣り合う。走査ではセルごとにミスするのではなく、ハードウェアプリフェッチャが働く。
- **定数のサイズ。** `newConstructor(2, 1)`は、フリーリストのpop1回と、定数の8バイトのヘッダワード1つ(参照カウント1、タグ、`arity`、`tag`)のstoreになる。
- **解体。** リストは、すでにその末尾をたどるループで解放している。なくなるのは`free`の呼び出しとその管理処理である。タグに対する`switch`と子の走査は残る(`teardown`は現在オブジェクトあたり約47命令かかり、`free`はその一部であって、すべてではない)。
- **リモート解放はバッチ化する。** ほかのスレッドが解放するセルの連鎖は、たいてい1つのページにある。スレッドはバッチを1つ保持し(ページと、そのページに対して解放したセル。リンクされているが、まだ`thread_free`には載っていない)、64セルになったとき、次のセルが別のページにあるとき、割り当ての低速パスを通るとき、`idris2rc2_poolPurge()`の中、およびスレッド終了時のフックの毎回の呼び出しで、それを1回のcompare-and-swapでpushする。解放だけするスレッド(消費者)は、そのフックのために、最初のリモート解放でヒープを得る。バッチのセルは、ページの`used`に数えられたままなので、ページがその下で空にされることはない。代償として、ブロックしたスレッドは、再び走るまで最大63セルと、それらがあるページを抱えたままになる。また、スレッド自身のデストラクタの最後の呼び出しより後に走るキーのデストラクタが解放したセルは、バッチに残る。
- **インラインの割り当て。** `idris2rc2_newConstructor`と`idris2rc2_mkClosure`は、`memory.h`の中で`static inline`である。arityが定数ならクラスは定数になり、割り当てはフリーリストのpopになり、ヘッダ(参照カウント、タグ、arity、コンストラクタのタグ)は8バイトのstore 1回になる。解放はインライン化しない。`dup`/`drop`のインライン化を強制したときは、コンパイラが15 MBから38 MBに増えた。インラインの割り当てで増えるのは3%である。
- **最初のステージには入れない候補: 割り当て時の再利用(recycle at allocation)。**連鎖の先頭が最後に解放されたとき、それを解放せずに保持し、その子を割り当てのたびに1つずつ解体して、空になったばかりのセルを次の割り当てに渡す。解放と割り当ての組が1ステップになり、長いリストの解体が分散される。代償は、子の参照カウントが下がるのが遅くなることである。`isUnique`(クロージャのその場での拡張、`reuse=`)は、共有されたセルをより長く見ることになり、`GCPointer`の`onCollect`は遅れて走る。入れる前に、`isUnique`がどれだけの頻度で失敗するかを測る必要がある。

## スレッド

このアロケータは`idris2rc2_threaded`を見ない。ヒープは最初からスレッドごとにあるので、後からマルチスレッドになるプログラムも、最初からそうであるプログラム(`multithreaded`)も、同じ経路を使う。数少ない大域構造(セグメントのリストと`freeMask`、放棄されたページ)は専用のロックを持つ。`idris2rc2_spin_lock`はそれではない。あちらは、プログラムがシングルスレッドの間は何もしないからである。

- **自分のページ。** `owner == tl_heap`: 通常の操作で、アトミック操作はない。
- **ほかのスレッドのページ。** セルはページの`thread_free`へpushされる(先頭に対するcompare-and-swap)。そのスタックを取る唯一の消費者は、ページの所有者(または、ページを引き取ったばかりのもの)であり、`atomic_exchange`で全体を取る。そのため、pushする側が古い先頭をリンクに入れてしまうことはない(ABAは起きない)。
- **スレッドが終わる。** `rc2base`の`pthread_key`(`concurrency_util.c`)は、そのデストラクタでスレッドのデータを解放する。そのデストラクタはIdrisのコード(`GCPointer`の`onCollect`)を走らせることがあり、それがセルを割り当て、解放する。glibcはデストラクタの順序を定めないので、アロケータ自身のデストラクタは、最初の何ラウンドかは自分自身を再設定し(`pthread_setspecific`)、最後のラウンドではなく、その1つ前のラウンドでヒープを手放す。ThreadSanitizerは最後のラウンドでスレッドを終了させ、その後に取られたmutexで失敗するからである。ヒープを手放す手順は次のとおりである。
  1. `pending`を`POOL_DEAD`と交換し、そこにあったエントリを処理する。こうして、どのスレッドもこのヒープへ二度とpushしなくなる。`POOL_DEAD`を見つけたpushする側は、自分が立てたフラグを下ろし、その時点でページに新しい所有者がいれば、そちらのキューに入れる。
  2. 生きているセルを持つすべてのページは`owner = abandonedHeap`になり、そのクラスの大域リストに入る。それ以外のページは返す。
  3. `tl_heap`は静的な空のヒープに戻るので、その後の割り当ては再びヒープを取る。終了したスレッドのヒープ構造体は、次にヒープを必要とするスレッドのためにリスト(`retiredHeaps`)に入り、そのメモリは決して返さない。ほかのスレッドがまだそのアドレスを保持しているかもしれないからである。スレッドが終わる直前にページの所有者を読んだpushする側は、その`pending`へpushする。そこで見つけるのは`POOL_DEAD`か、ヒープが再利用された後なら、そのページを所有しない生きたヒープのスタックである。後者の`processPending`はそのエントリを飛ばす(「古いエントリ」を参照)。知らせるはずだったセルは、そのページを引き取ったものが回収する。ヒープが再利用されるのは、どのページもそのヒープを所有者としていないときだけである。空のページは、`inPending`の値にかかわらず返される。死んだヒープのキューには、もう何も入らないからである。したがって、ヒープの数は、同時に生きていたスレッドの最大数に、デストラクタの中にまだいるスレッドのヒープと、`KNOWN-BUGS.md`の遅れて作られたヒープを加えたものになる。
- **引き取り(adopt)。** あるクラスのページを使い切ったスレッドは、そのクラスの放棄されたページを引き取る。`owner`を設定し、`thread_free`を取る。所有者の変更と競合する解放は`thread_free`へpushされる(解放するヒープ以外の`owner`の値はすべて、そこへ送る)ので、失われるものはない。
- **セルがすべてリモートで解放されたページ**は、回収されるまで`used > 0`のままである。回収するのは、その所有者、引き取ったもの、新しいページを取る前にスレッドが行う掃引、または`idris2rc2_poolPurge()`である。
- **メインスレッド**はキーのデストラクタを走らせないので、そのヒープは決して放棄されない。ほかのスレッドは、そのセルを`thread_free`へ解放する。
- **最後のラウンドより後に作られたヒープ**(遅れて走ったデストラクタの中での割り当て)は、決して放棄されない。そのページはそのヒープに残る。
- **`fork(2)`**を呼ぶのは`popen2`だけであり、子プロセスではすぐに`exec`する。これに対しては何もしない。
- **参照カウントは変わらない。** 通常の操作とアトミック操作の切り分けは、そのままである(`hybrid-refcount.md`)。

## メモリを返す

- `used`が0になったページは、クラスが割り当て中のページを除き、そのヒープの空のページのリスト(新しいものが先頭)に入る。そのリストに触れるのは所有者だけである。そこからは、どのクラスのためにもページを取れる。
- ヒープは、64ページ(4 MiB)と、保持するページの1/8の大きいほうまで、空のページを保持する。それより4分の1多くなって初めて返し始める。返すのは古いものからである。ページに`madvise(MADV_DONTNEED)`を行い、常駐サイズを実際に下げ、それから(大域ロックの下で)そのセグメントの`freeMask`でページを空きとして印を付ける。新しいページは、空きページを持つ最初のセグメントから取るので、メモリは少数のセグメントにとどまる。クラスの`direct`ページは、これで手放すことは決してない。そのため、割り当てと解放を交互に行うループが、ページを返してはまた取ることはない。
- **`idris2rc2_poolPurge()`**は、その時点で空のものを返す。呼び出したヒープを空にし(生きたセルのない`direct`ページと、すべての空のページ)、放棄されたページを掃引する。ほかの走っているスレッドのページには触れない(触れてよいのは、そのスレッドだけである)。テストと、長時間走るプログラムのためのものである。
- クラスに収まらない大きさのセルは`malloc`のものであり、`malloc`が自分の大きなブロックを返す。
- Transparent huge pagesのために、64 KiBの`MADV_DONTNEED`で常駐サイズが下がらないことがありうる。測定していない。

## 検査

- **チェックモード、`IDRIS2RC2_POOL_CHECK`**(コンパイル時)。解放したセルは、`rc`と`reserved`にパターンが設定され、本体の残り(リンクより後)が`0xDD`で埋められる。割り当ては、本体がまだすべて`0xDD`であること(解放後の書き込みがないこと)と、ページのクラスが要求されたものであることを検査する。セルの二重解放や、ページのセル境界上にないポインタは、abortする。`filled`が`arity`を超えるクロージャもabortする。プールのセルには余裕がない。`malloc`は32バイトの要求を40バイトに切り上げるので、はみ出しが隠れていたが、ここでは次のセルのヘッダを上書きしてしまう。エミッタが`idris2rc2_tailcallApplyClosure`を連鎖の最後のホップに限っているのは、このためである(`Emit.idr`の、`applyChain`の上のコメント)。
- **プールを無効にする。** `IDRIS2RC2_POOL=0`(環境変数。ほかのどのコンストラクタよりも前に読む)または`-DIDRIS2RC2_NO_POOL`(コンパイル時)で、すべてのセルが`malloc`のブロックになる。`cellAlloc`と`idris2rc2_cellPooled`は`idris2rc2_poolOn`を検査する。予測しやすい分岐である。`verify.sh`は、valgrindで走らせるとき(`LEAK_SENSITIVE_TESTS`)にこれを設定する。4 MiBの`mmap`セグメントのプールは、リーク、二重解放、解放後の使用をすべてvalgrindから隠すので、それらのテストは何も検査せずに通ってしまうからである。ASanにも同じ切り替えを使う。
- **`rc2/tests/pool/run.sh`**は`verify.sh`から実行され、`poolstress.c`を3通り(出荷時のまま、チェックモード、ThreadSanitizerの下)にビルドして走らせる。内容は、別々のスレッドの生産者と消費者。4つのスレッドの輪で、それぞれが1つ前のスレッドのセルを割り当て、解放するもの。短命な400の生産者と、そのセルを解放する長命な1つの消費者、および生きたセルを持ったまま終わる300のスレッド(使用中のページ数の最大値は小さいままでなければならない。終わったスレッドのページは引き取られるか、掃引される)。かき混ぜた順序での局所的な割り当てと解放の繰り返し。そして大きなヒープを構築して解放するもので、その後に常駐サイズが下がらなければならない(ThreadSanitizerの下では、そのシャドウメモリが常駐するので、これは求めない)。古い`pending`のエントリがあるうちのクラスをまたいだページの再利用と、多数のスレッドが同時に1つのページへ解放する場合は、扱っていない。

## ステージと、それぞれを決めるもの(0、1a、1b、1c、2は完了)

| ステージ | 内容 | 比較の対象 |
|---|---|---|
| 0 | `cellAlloc`/`cellFree`、上の監査表、`args[filled]`への書き込みの検査、プールを無効にした`verify.sh`のvalgrind実行。まだ`malloc`で、挙動は変わらない | `verify.sh`が変わらないこと |
| 1a | セグメント、ページ、ヒープ、局所的な解放、リモート解放、低速パス、fullリスト。`newConstructor`/`mkClosure`はまだインラインでない呼び出し | `stage1`(CCは`gcc`に固定)による`base`のビルド、リストの`map`/`filter`、`sort`。glibcおよび`LD_PRELOAD`によるmimallocと、**同じセッションで**比較する。合格: 「結果」を参照 |
| 1b | 放棄と引き取り、スレッド終了のプロトコル、それらのテスト | 並行性のテスト、`tsan` |
| 1c | OSへの返却、`idris2rc2_poolPurge()`、メモリのテスト | 大きなリストのテストの後の常駐サイズ |
| 2 | 定数のクラスとヘッダワードによる`newConstructor`と`mkClosure`のインライン化。バッチ化したリモート解放 | `stage1`の命令数(callgrind)、時間、実行ファイルのサイズとコンパイラのビルド時間 |
| 3 | `mp_set_memory_functions`を通した`Integer`。測定が支持すれば、割り当て時の再利用 | `Integer`を多用するベンチマーク。`isUnique`が失敗する頻度。測定済みで、実施しない: 「ステージ3の測定」を参照 |

関門はステージ1aで、難しい部分(1b、1c)を書く前に置く。mimallocが与える効果に近づかなければ、独自のアロケータを抱える理由はほとんどなく、mimallocを依存として同梱することを改めて検討しなければならない。この比較は厳密ではない。`LD_PRELOAD`は、プールが`malloc`に任せている文字列、`Integer`、バッファの割り当ても置き換えるからである。独自のアロケータがmimallocにはできないこととして加えられるのは、インラインの高速パス、ヘッダの1回のstore、バッチ化したリモート解放であり、これらがステージ2である。

ステージ2は以前の結果とぶつかる。`dup`/`drop`のインライン化を強制すると、命令数が7.1%、時間が5%減ったが、コンパイラのビルドに10分ではなく40分かかり、実行ファイルが15 MBから38 MBに増えた(`self-hosting.md`の項目7)。そのため、インライン化するのは割り当てだけである。`cellFree`と`idris2rc2_releaseReuse`(idris2-lspで10,739箇所、`reuse-analysis.md`)は、短いインラインでない関数のままにし、実行ファイルのサイズとビルド時間をそれとあわせて測定する。

ステージ3の`mp_set_memory_functions`は、プロセス全体の設定である。ライブラリのすべての`mpz`も支配し、その関数は同じ設計によってスレッドセーフであり、GMPは解放時にサイズを渡すが、プールはそれを必要としない。

## リスク

- 1回のレビューには多いコードである。ページ、ヒープ、放棄、返却の方針は、それぞれ、スレッドの下でだけ現れるバグの温床になりうる。チェックモード、`tsan`、上のストレステストは、後回しではなくステージの一部であり、難しい部分は関門の後ろにある。
- ある規則では小さく、別の規則では大きいセルは、一方のアロケータで割り当てられ、もう一方で解放されてしまう。判定するのは1つの関数で、その呼び出し元は割り当てと解放の箇所であり、チェックモードが不一致を捕らえる。ステージ0は2つの一覧を明示する。
- 生きたデータが多数のページに薄く散らばるプログラムでは、常駐サイズがglibcより大きくなりうる(生きたセルが1つあるページは残る)。ページのコンパクションは行わない。
- セルのアラインメントは16バイトではなく8バイトなので、24バイトのセルがキャッシュラインをまたぐことがある。16バイトのアラインメントに依存するものはない。ポインタのタグはビット0だけである(`idris2rc2_is_unboxed`)。

## 結果(2026-11-10、ステージ0から1c)

`idris2-src/libs`の`base`と`prelude`を、同じ`stage1`(rc2でビルドし、`gcc`でコンパイルしたコンパイラ)でビルドした。各3回で、単位は秒である。

| アロケータ | `prelude` | `base` |
|---|---|---|
| セルプール | 5.55 | 71.0 |
| `malloc`(`IDRIS2RC2_POOL=0`) | 6.84 | 87.3 |
| mimallocをpreloadした`malloc` | 5.97 | 75.5 |

`base`では、プールは`malloc`より18.7%、mimallocより6.0%速い。同じコンパイラをプールのコードなしで(ステージ0より前の状態で)ビルドしたものは84.0秒かかったので、そのビルドに対する改善は15.5%である。`POOL=0`の実行がそのビルドより遅いのは、解放の経路にある、プールか`malloc`かの検査の分である。

リストを多用するプログラム(ステージ1a、3回の最良値、秒): 300000要素のリストの構築、map、filter、解放を50回行うもの(`BenchListChurn`)は、プールで1.98、`malloc`で3.01、mimallocで2.47である。100万個の`Int`の`Data.List.sort`(`BenchListSort`)は、0.72、0.86、0.72である。

ステージ2(2026-11-10): 同じ`base`のビルドは、割り当てをインライン化して69.5秒(以前は71.0秒)かかる。コンパイラの実行ファイルは15.27 MBから15.78 MBに増え(+3%)、コンパイラ自身のビルドは611秒から624秒になる(+2%)。バッチ化したリモート解放: 割り当てたのとは別のスレッドが解放する400万個のセル(`poolstress`)は、31 msかかる。セルごとにcompare-and-swapを行う場合は125 msである。

残っていること: 計画しているものはない。ステージ3については次の節を参照。

## 解放の経路(2026-11-10)

rc2でビルドしたコンパイラで`base`をビルドしたときのcallgrindプロファイル(439.6 G命令)では、セルの解放が全命令の9.7%を占め、割り当ての3倍だった。`idris2rc2_poolFree`は1回あたり約39命令かかっていた。まれな場合(ページの状態の変化、ほかのヒープのページのセル)がそこへインライン化され、毎回の呼び出しで6つのレジスタを退避していたからである。`idris2rc2_cellFree`は約22命令かかっていた。プールか`malloc`かを決めるためだけに、タグからセルのサイズを計算していたからである。現在の解放は`idris2rc2_poolFreeInline`(所有者の検査、フリーリストへのpush、`used--`、状態の検査1回)であり、まれな場合はインラインでない関数(`idris2rc2_poolAfter`、`idris2rc2_poolFreeRemote`)にある。`idris2rc2_cellPooled`は、割り当てが使うのと同じサイズのマクロ(`IDRIS2RC2_CON_BYTES`、`IDRIS2RC2_CLOSURE_BYTES`)で、タグとarityからプールか`malloc`かを決める。`teardown`とランタイムのクロージャの殻の解放はそれをインライン化する。生成されたCは引き続き`idris2rc2_cellFree`を呼ぶので、10,739箇所の`releaseReuse`は大きくならない。

`prelude`で測定すると、解放(`poolFree`、`cellFree`)の命令数は3.2 Gから0.4 Gに下がるが、その大半はそれをインライン化する呼び出し元(`teardown`、`trampoline`)へ移るので、合計は31.5 Gから31.0 G(-1.6%)になる。プロファイルから予想した3から5%には届かない。同じ1時間のうちに測った`base`のビルド時間は、73.4秒から71.7秒(-2.3%)、`prelude`は5.87秒から5.65秒(-3.7%)である。

## ステージ3の測定: 実施する価値はない

ステージ3は、GMPの割り当てをプールに通し(`mp_set_memory_functions`)、割り当て時の再利用を行うものだった。現状のコード(すべての実行でステージ2のセルプールあり)で、2026-11-10に測定した。

- **rc2でビルドしたコンパイラによる`libs/prelude`のビルド**: GMPの割り当ては439回で、全体の73.9 M回(callgrindの呼び出し回数)に対して0.0006%である。62ビットに収まる`Integer`は即値であり、GMPには決して届かない。
- **プールの外のすべての割り当て(文字列、`Integer`、配列、バッファ)の上限**: 同じ`stage1`で、プールの上にさらにmimallocをpreloadし、各3回測定した。`base`は69.15秒対69.00秒(-0.2%)、`prelude`は5.52秒対5.43秒(-1.6%)である。文字列と`Integer`のプールが得られるのは、これ以上ではない。
- **大きな`Integer`を実際に使うプログラム**: 2から3リムの数(約2^70から2^140)に対するループ(300万回の反復、それぞれ`Integer`の演算3回、すべての結果がリム配列を持つボックス化された`Integer`)は、プールで1.51秒、`malloc`で1.50秒、mimalloc(GMPの割り当ても置き換える)で1.49秒かかる。時間はGMPの算術に費やされており、`Integer`のセルとリムのためのプールで得られるのは、多くても1%である。

したがって、`Integer`のセルとGMPは`malloc`のままにする。割り当て時の再利用(「コンストラクタと短命なリストにもたらすもの」の候補)は測定しておらず、計画もしていない。それが狙う効果、つまりセルの割り当てと解放を安くすることは、今はプールが行っている。そして、その代償(参照カウントの遅れ、`onCollect`の遅れ)が、まず測定を必要とした理由だった。既知の制限: 最後のデストラクタのラウンドより後に作られたヒープは、決して手放されない(`KNOWN-BUGS.md`)。もう走っていないヒープに残った古いエントリは、ほかのヒープのページに解放されたセルの回収を遅らせる(「古いエントリ」を参照)。
