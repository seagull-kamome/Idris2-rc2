# `Int`、`Int64`、`Bits64`、`Integer`の即値表現

(原文: `doc/immediate-ints.md`。内容が乖離した場合は原文を正とする。)

状態: 実装済み(2026-09-27)。

## 問題

ボックス化された値は`IDRIS2RC2_Value *`である。32ビット以下の型
(`Int32`、`Bits32`、`Char`など)は、すでにポインタのワード自体に値を
収めていた。一方`Int`、`Int64`、`Bits64`はヒープセルで表現されており、
0..99だけは静的キャッシュを指していた。

rc2は、可能な限り`Int`を関数内でネイティブ(`int64_t`)のまま扱う。
したがって、このボックス化が問題になるのは、値が`Value *`でなければ
ならない場面に限られる。

- コンストラクタのフィールド(`List Int`のセル)
- クロージャが捕捉する引数
- 多相コード(`apply`経由で呼ばれる比較関数など)

こうした場面では、次のコストがかかっていた。

- 結果を作るたびのメモリ確保
- `dup`/`drop`のたびの参照カウント操作
- 読み出しのたびのポインタ参照

`sort`のプロファイルでは、比較関数が1回の比較ごとに2つのボックスの
参照カウントを触っていた(`TODO.md`の「`sort` against Chez」)。

## 表現

値のワードは、ビット0が立っていれば即値であり、それ以外であればヒープ
オブジェクトまたは`NULL`である。タグが示すのはそこまでで、型は示さない。
どの読み出し箇所でも値の型は静的に分かっており、レイアウトは型で決まる
ためである。

| 型 | 即値のレイアウト | 即値で表せる範囲 |
|---|---|---|
| `Int`、`Int64` | value << 1 \| 1 | [-2^62, 2^62) |
| `Bits64` | value << 1 \| 1 | [0, 2^63) |
| 32ビット以下(`Int32`、`Bits32`、`Char`など) | value << 32 \| 1 | 全範囲(変更なし) |

この範囲を外れる値は、従来どおりヒープ上の`IDRIS2RC2_Int64`または
`IDRIS2RC2_Bits64`に置く。そのため、各型の64ビットの意味はそのまま
保たれる。

- 演算は`int64_t` / `uint64_t`で行い、結果の表現だけを選ぶので、
  オーバーフロー時のラップアラウンドも従来と同じである。
- 外部関数呼び出しには、これまでどおり完全な`int64_t` / `uint64_t`を
  渡す。

Chezも同じ方式である。fixnumは約61ビットで、それを超える値はbignum
になり、64ビットに切り詰め直される。

### 設計の経緯

最初の版では2ビットのタグを使っていた。32ビットのスカラーが`01`、
`Int`/`Int64`が`10`、`Bits64`が`11`で、ペイロードは62ビットである。
しかし読み出し側は型を知っているので、2種類の64ビット型どうしや、
64ビット型と32ビット型を区別しても得るものがない。タグを1ビットに
すると、2つの64ビット型の範囲がどちらも1ビット広がる。これはハッシュ
で効く。64ビットのハッシュが2^62未満になるのは4回に1回だが、
2^63未満なら2回に1回になる。`missing-containers`は6.51秒から
6.33秒になった。

32ビット型も同じシフト形式のレイアウトに揃える案も試したが、測定できる
ほどの遅さは出なかった(`Char`リストのベンチマークで5.71秒に対して
5.73秒)。それでも32ビット型は上位半分に値を置くレイアウトを維持して
いる。このレイアウトなら、シフトなしでメモリから直接ロードして読めるため
である。

## ランタイム

- **`idris2rc2_mkInt64`、`idris2rc2_mkBits64`** は、値が範囲に収まれば
  即値を返し、収まらなければヒープ上のボックスを返す。0..99の静的
  キャッシュは廃止した。
- **`idris2rc2_to_i64`、`idris2rc2_to_u64`** はビット0を調べてから、
  シフトするかボックスを読む。
- **`dup`/`drop`** は、ビット0が立っている値をすべて素通しする
  (`idris2rc2_is_unboxed`)。即値にはここでのコストがかからない。
- **`idris2rc2_isUnique`** は、即値に対しては常にfalseを返す。数値
  プリミティブは、単一参照の`Int64`/`Bits64`ボックスを結果の格納先に
  再利用する(`rop-reuse.md`)。即値には書き込めないため、この判定が必要
  である。
- **`idris2rc2_extractInt`** は型が分からない値を受け取るので、即値は
  すべて符号付き63ビット値として読む。したがって`Int`と`Int64`専用
  である。それ以外の整数型に対する`RConstCase`は、その型のアクセサで
  スクルティニーを読む(`extractIntExpr`)。

## コード生成

`boxedConstExpr` (`Emit/Util.idr`)は、範囲内のリテラルを
`IDRIS2RC2_IMM_INT64(...)` / `IDRIS2RC2_IMM_BITS64(...)`として出力する。
整数定数をポインタにキャストしたものなので、畳み込まれた定数コンスト
ラクタのフィールドなど、静的初期化子にも書ける。範囲外のリテラルは、従来
どおり静的なボックスを使う。

## `Integer`

`Integer` (およびそれにコンパイルされる`Nat`)も、`Int64`と同じ即値
表現`value << 1 | 1` (範囲 [-2^62, 2^62))を使う。これは、
`IDRIS2RC2_Integer`セルの0..99の静的キャッシュを置き換えるものである。

### 正規形

範囲内の`Integer`は*必ず*即値で表し、ボックス化されたmpzには範囲外の
値だけを入れる。どの演算も結果を正規化する
(`idris2rc2_integerNormalize`、`idris2rc2_mkIntegerI64`)。その結果、次の
ことが成り立つ。

- 即値との等値比較は1回のワード比較で済む。即値がボックス化された値と
  等しくなることはない。
- 範囲内の`Integer`定数に対する`RConstCase`の枝は、ワード比較になる
  (`integerAltCond`)。範囲外の定数はGMPで比較する
  (`idris2rc2_integerEqualsLiteral`)。
- 範囲内のリテラルはCの定数なので、`let`が要らず(`bindOne`)、畳み
  込まれた定数コンストラクタにも置ける(`isConstLocalProof`)。

### 演算

- 両オペランドが即値の場合は`int64_t`で計算する。63ビットのオペランド
  どうしの加減算は64ビットをあふれないが、乗算は
  `__builtin_mul_overflow`で検査する。範囲内の値に対する
  `and`/`or`/`xor`は範囲内に収まる。`mod`、`div` (ユークリッド除算)と
  シフトはGMPの意味論に従う(`mpz_mod`、`mpz_fdiv_q_2exp`)。
- それ以外は、`numeric.c`のGMPによる低速経路を通る。即値のオペランド
  は`idris2rc2_integerView`で読み取り専用のmpzとして扱う。この関数は
  `mpz_roinit_n`をスタック上の1リムに向けるだけなので、メモリを確保
  しない。単一参照のボックス化オペランドは、従来どおり結果の格納先に
  再利用する(`rop-reuse.md`)。

GMP自身の混合型関数(`mpz_add_ui`、`mpz_mul_si`など)を使っても、この
ビューに比べて得られるものは小さい。低速経路に入るのは2^62を超える値
のときだけで、そこではGMPが本物の計算をするからである。

### 外部関数呼び出し

- `Integer`の引数は
  `idris2rc2_integerView(x, &(IDRIS2RC2_IntegerView){0})`の形で渡す。
  複合リテラルは、それを含むブロックの終わりまで生存する。呼び出しは
  このブロックの中にある。呼び出された側が読み取りしかしてはならない点
  は、従来と同じである。
- `Integer`の戻り値は、従来どおり新しい`IDRIS2RC2_Integer`のmpzに
  書き込み(GMPの`rop`を先頭に取る規約)、そのあとで正規化する
  (`packCFType CFInteger`)。
- `%export`は、入ってきたmpzを`idris2rc2_mkIntegerFromMpz`でコピー
  する。この関数も正規化を行う。

### 作業中に見つかった問題

- ボックス化された`Integer`に対する`cast {to = Double}`は
  `mpz_get_d`を使っていたが、これは切り捨てるので、2^63 - 1が
  2^63 - 1024になっていた。Chezでは2^63に丸められる。現在は、
  `String -> Double`と同じ補助関数を通して最近接丸めを行う。
- `Integer`に対する`RConstCase`は、スクルティニーを`mpz_get_si`で
  読んでいた。これは下位ビットしか保持しないため、2^64 + 5が枝`5`に
  一致してしまっていた。

`Test112Numeric/ImmediateInteger.idr`は、±2^62、±2^63、±2^64の両側で、
すべての演算、キャスト、caseを、負のオペランドと除数も含めてChezと
比較する。

### 結果(2026-09-27)

変更前はHEADの生成CをHEADのランタイムで実行したもの、変更後は
今回の変更である。3回のうちの最良値で、どのプログラムも出力は変わって
いない。

| | 変更前 | 変更後 | Chez |
|---|---|---|---|
| `Nat`のfib 30、300kまでのCollatz、200万要素の`Nat`リスト | 10.65s | 1.70s | 1.94s |
| `sort`、100万個の`Int` | 1.12s | 1.13s | |
| map/filter | 3.32s | 3.31s | |
| クロージャ | 1.87s | 1.82s | |
| `Char`リスト | 5.86s | 5.90s | |
| `idris2-missing-containers` | 5.63s | 5.67s | |

`Integer`を使わないプログラムは、誤差の範囲に収まっている。

## テスト

`Test112Numeric/ImmediateInts.idr`は、`Int`、`Int64`、`Bits64`の値を
リストに入れてボックス化された形で保持させ、次の各境界の両側を調べる。

- `Int`と`Int64`について ±2^61と ±2^62
- `Bits64`について2^62と2^63
- 64ビットの両端

それぞれの値に対して、算術、シフト、ビット演算、比較、キャストを実行
し、Chezの出力と比較する。

このテストは、以前からあった別のバグも見つけた。`String`から`Bits64`
への`cast {to = Bits64}`が`atoll`を使っており、`INT64_MAX`で止まって
いた。現在は`strtoull`を使う。

## 結果(2026-09-27)

測定したのは最初の2ビット版である。変更前はそれ以前の生成Cをそれ以前
のランタイムで実行したもの、変更後はその版が生成したCをそのランタイム
で実行したものである。1ビット版は、`sort`と`missing-containers`で
さらに数パーセント速い(「設計の経緯」を参照)。3回のうちの最良値で、
どのプログラムも出力は変わっていない。

| | 変更前 | 変更後 |
|---|---|---|
| `sort`、100万個の`Int` | 2.44s | 1.59s (-35%) |
| map/filter、300k x 50 | 6.64s | 3.36s (-49%) |
| クロージャ、100万x 20 | 2.55s | 1.86s (-27%) |
| BenchKnownCon | 0.54s | 0.27s |
| BenchPushCon | 0.22s | 0.08s |
| BenchArityRaise | 0.59s | 0.41s |
| `idris2-missing-containers` | 6.49s | 6.54s |

`missing-containers`の大部分は文字列と64ビットのハッシュである。ハッシュ
は`Bits64`の全範囲に散らばるので、2^62未満で即値になるのは4分の1
程度にとどまる。
