# プログラム全体のインライン展開: `Compiler.RC2.InlineCExp`

(原文: `doc/inlining.md`。内容が乖離した場合は原文を正とする。)

基準A、基準B、およびcase-of-caseの畳み込みは、ラムダリフトの前の、名前付きcase tree上で動く(`Compiler.RC2.InlineCExp`)。2026-09-29までは、これらは`Lifted`上で`Compiler.RC2.Inline`として動いていた。移行の内容は、後述の「case tree上のインライン展開」を参照。

## 動機

`Compiler.RC2.RC`の`tryFuseCompare`は、2分岐のBoolマッチがすぐに消費する*直接の*プリミティブ比較を、ネイティブな`RCmpCase` 1つに融合する。ボックス化された`Bool`は一切作られず、分岐はオペランドをネイティブに読む。ただしこれが働くのは、比較がマッチのすぐ隣にある、裸の`NmOp`である場合に限る。比較がインターフェースのメソッド呼び出しを経由して現れる場合、融合は単独では働かない。たとえば`Ord Int`の`<=`を通した`acc <= 0`がそうである。この`<=`は、静的に解決される本物のトップレベル関数で、辞書をパラメータに取るものではない(そもそもネイティブにできるのは固定幅のスカラー型だけである)。比較は`<=`自身の別の定義の中にあり、呼び出し元の融合解析からは見えない。

インライン展開は、小さく、呼び出しを含まない呼び出し先の本体を、呼び出し箇所へ直接差し込むことで、この隙間を埋める。実行は`Compiler.RC2.RC`のPhase 1(`normalize`)がプログラムを見るより前に1回だけで、`RC.idr`から見れば、その呼び出しは最初から存在しなかったことになる。動機となった正確な形と、それを`--directive dumprcexpr`や`--directive noinline`で確認する方法は、`rc2/tests/Test114Inline/CompareFusionThroughCall.idr`を参照。

## パイプライン上の位置

```
NamedCExp (upstream, phase Cases)
  -> Compiler.RC2.InlineCExp      (基準AとB、case-of-caseの畳み込み、NamedCExp -> NamedCExp)
  -> Compiler.RC2.RC.normalize    (ラムダリフトとPhase 1を1回の走査で実施、doc/lambda-lifting.md)
  -> Compiler.RC2.RC.annotate     (Phase 2: 所有権 -- RDup/RDrop/RFree)
  -> Compiler.RC2.Reuse           (コンストラクタのその場再利用)
  -> Compiler.RC2.ConAltNative    (ネイティブシャドウによるフィールドのキャッシュ)
  -> Compiler.RC2.MutualLoop      (相互末尾再帰 -> 1つに統合した関数)
  -> Compiler.RC2.Loop            (自己末尾呼び出し -> RLoop/RLoopContinue、
                                    加えてネイティブシャドウの昇格)
  -> Compiler.RC2.DualABI         (ワーカー/ラッパーの合成、呼び出し箇所の書き換え)
  -> Compiler.RC2.Emit            (RCExp -> C。機械的な変換のみ)
```

インライン展開は、ラムダリフトの前に、`compileExpr`と`incCompile`の中で走る。`--directive noinline`で飛ばすことができる。これは、`noloop`や`noconaltnative`などがすでに提供している、A/Bで回帰を切り分けるための手段と同じ種類のものである(`RC2.idr`の`toRCDefs`のモジュールノートを参照)。

## 適格性: 基準A

呼び出し先は、次の3つをすべて満たすとき、そのすべての呼び出し箇所でインライン展開される。

- トップレベルの関数定義である(`MkNmFun args body`)。ラムダリフトはまだ走っていないので、本体が参照するのは、自身の`args`と、本体の内側の束縛だけである。捕捉された変数は、そもそも存在しない。引数のない定義(CAF)も同じ条件で対象になり、その裸の参照箇所ごとに差し込まれる。
- 本体が*呼び出しを含まない*(`isCallFree`)。本体に現れてよいノードは、`NmLocal`、`NmLet`、`NmCon`、`NmOp`、`NmConCase`、`NmConstCase`、`NmPrimVal`、`NmErased`、`NmCrash`だけである。ラムダリフトが呼び出し、クロージャ、適用に変えるもの(`NmRef`、`NmApp`、`NmLam`、`NmDelay`、`NmForce`、`NmExtPrim`)が1つでもあれば、その本体は対象外になる。したがって、呼び出しを含まない本体は、リフトしても自分自身に等しい。
- 本体が小さい(`sizeOf body <= smallBodyThreshold`。現在は24)。`sizeOf`は、ノード1つにつき1を数え、`let`、コンストラクタ、演算子、`case`(scrutinee、alt、default)では、その部分式も数える。構造上のノード数による粗い指標で、生成されるCのサイズに対して較正したものではない。

呼び出しがインライン展開されるのは、ちょうど飽和しているときだけである。つまり、引数の数が呼び出し先のパラメータ数に等しい場合である(`NmRef`への`NmApp`、またはパラメータのない呼び出し先への裸の`NmRef`)。部分適用や過剰適用の呼び出しはそのまま残る。`allLiteralArgs`が拒否する呼び出し(次の節)も同様である。

この条件は、「小さい関数を一般にインライン展開する」パスより、意図的に狭くしてある。呼び出しを含まないことを要求するので、適格な呼び出し先自身が、さらにインライン展開すべき呼び出しを含むことはない。したがって、定義1つの書き換えは、不動点まで反復せず、1パスで済む。呼び出しを含まない本体を差し込んでも、差し込んだ部分の内側に新しいインライン展開の機会は生じないからである。機会が生じうるのは、呼び出し自身の*引数*の中だけで、その引数は、呼び出し自身を検討する前に、ボトムアップで処理される。

基準B(呼び出し箇所が1つで、ループを含まない呼び出し先)は、同じパスの中で動き、同じ表へ呼び出し先を追加していく。後述の「基準B: ループを含まず、呼び出し元が1つの呼び出し先」を参照。その呼び出しグラフは、`Compiler.RC2.MutualLoop`の`Graph`/`tarjanSCCs`を再利用する。

## `allLiteralArgs`ガード

引数がすべて裸の`NmPrimVal`リテラルで、そのうち少なくとも1つが`Double`である呼び出し(`ConstFold.safeConst`が`False`になるのは`Db`だけ)は、ほかの条件を満たしていても、インライン展開しない。すべてのオペランドがコンパイル時定数の状態で差し込むと、浮動小数点の式の連鎖が、gccへ定数式として届き、gccが`-Werror=overflow`の下で拒否しうるからである。リテラルの中に`Double`がなければ、ふつうにインライン展開する。引数のない呼び出しは、決して止められない(畳み込む対象がない)。このガードは、基準Bの差し込みにも効く。どちらも同じ`callTo`を通るからである。

## case tree上のインライン展開(2026-09-29)

基準Aは、`Lifted`から、upstreamの名前付きcase tree(`NamedCExp`)の上へ移った。rc2自身のラムダリフト(`lambda-lifting.md`)の前である。規則は変わらない。ただし、リフトがそのcase treeから作る木に対して読む。

- 「呼び出しを含まない」は、リフトが呼び出し、クロージャ、適用に変えるものをすべて除く。`NmRef`(裸のものも)、`NmApp`、`NmLam`、`NmDelay`、`NmForce`、`NmExtPrim`である。したがって、呼び出しを含まない本体は、リフトしても自分自身のままであり、`sizeOf`の数える対象は`Lifted`上と同じである。
- 裸の`NmRef f`と`Force f`は、リフトによって、それぞれ引数なしの`f`の呼び出しと、erasedな引数を1つ渡す`f`の呼び出しになる。そのため、どちらもそれらの呼び出しとしてインライン展開する。
- アトミックでない引数は、従来どおり、先に`let`で束縛する。

de Bruijn indexの代わりに名前を使うので、差し込みでは、コピーするすべての束縛(`let`とcase altの引数)を、新しい`MN "rc2inl" i`に付け替える。この`i`は、プログラム全体で1回ずつ数える。リフトは、名前を最も内側の束縛に解決する。したがって、名前が捕捉されても失敗にはならず、間違った変数を読むことになる。

出力の変化は次のとおりである。捕捉の解析が、差し込みの後で走るようになった。そのため、基準Aの呼び出し先が引数を1つ捨てていた場合、その呼び出しを含むラムダは、その引数を捕捉しなくなった。idris2-lspでは、47個のリフト済み定義の引数が減り、それらの呼び出し元と、それらから特殊化された複製もそれに従った。`rcexpr-lint`は異常を検出していない。`partial`が17個、`dup`の増分が511個、`drop`の減分が675個、それぞれ減った。変数を番号付けし直せば、ほかの定義はすべて同一である。インライン展開に要する時間は、以前と同程度である(今回は、case tree上で0.25秒、`Lifted`上で1.35秒。以前は1.56秒)。

基準Bも、同じパスの中で続けて移った。定義は、呼び出し先を先に書き換える(プログラム全体でTarjan順)。呼び出されるのが1回で、どの循環にも属さない呼び出し先は、自身の呼び出しのインライン展開が済んだ時点で、差し込む呼び出し先に加える。`Lifted`上との違いは次の2点である。

- **呼び出しグラフ。** 定義の中のすべての`NmRef`が、その定義の呼び出しである。ラムダの中のものも含む。`Lifted`上では、ラムダは別の定義であり、その親からはラムダへの辺がなかった。そのため、クロージャを通した再帰(`f`のラムダが`g`を呼び、`g`が`f`を呼ぶ)は、そこでは循環にならず、ここでは循環になる。idris2-lspでは、差し込まれる呼び出し先は、2,813個ではなく2,744個になる。
- **差し込みがコピーするもの。** 基準Bの本体はラムダを含むことがあり、それらは呼び出し元へコピーされて、そこでリフトされる。呼び出しがなくなった呼び出し先自身も、各ラムダをもう1回ずつリフトするので、`DeadCode`までのすべての段階が、それらを余分に持つことになる。そこで、プログラム全体のコンパイルでは、`%export`されていなければ、リフトの前に呼び出し先を捨てる。インクリメンタルコンパイルでは、ほかのモジュールが呼ぶ可能性があるので、残す。

idris2-lspでの結果は次のとおりである。`rcexpr-lint`は異常を検出していない。基準Aだけの段階と比べて、定義が225個、`partial`が256個、`apply`が45個、`con`が348個、それぞれ減った。値で返されるコンストラクタが331個、増えた。`dup`の増分は1,174個、`drop`の減分は2,595個、減った(融合された比較は2個減って、473個のうち471個)。インライン展開は1.34秒、畳み込みは0.11秒かかる。DualABIまでのすべての段階が速くなり(Early inlineは6.21秒から5.48秒)、全体で約1.5秒短くなる。

## IRの配管: case tree上での名前の付け替え

インライン展開は名前付きcase treeの上で動くので、差し込みは名前で置換する。各パラメータは、引数(ローカル変数、リテラル、erasedな値のいずれか)か、アトミックでない引数に対して束縛された`let`に対応づける。コピーが新しく導入するすべての束縛(ラムダ、`let`、altの引数)には、新しい`MN "rc2inl" i`を付ける。この`i`は、プログラム全体で1回ずつ数える。衝突したときだけでなく、すべての束縛を付け替えることで、捕捉が起きないようにしている。リフトは名前を最も内側の束縛に解決するので、捕捉が起きても失敗にはならず、間違った変数を読むことになる。

case-of-caseの畳み込みは、外側のaltを、内側のaltの束縛の下へ移す。名前を使っているので、番号の付け直しは要らず、捕捉も起きない。それらの束縛は、その位置のスコープにあるどの名前とも異なり、外側のaltが参照できるのは、そのスコープにある名前だけだからである。`Lifted`上では、これに`Core.TT.Term`から移植したde Bruijnの弱化と置換、および`believe_me`を使った`FreelyEmbeddable Lifted`が必要だった。それらはすべて不要になった。


## case-of-caseの畳み込み

呼び出しの、scrutineeの形をした引数を`case`の位置へ置換すると、「case of case」(`case (case x of ...) of ...`)ができる。`tryFuseCompare`は、これを単独では認識しない。`collapse`は、upstreamの`Compiler.CaseOpts`の`doCaseOfCase`/`doCaseOfConstCase`/`tryCaseOfCase`(case-of-caseの半分だけ)を、名前付きcase treeへ移植したもので、各定義をインライン展開した直後に、ボトムアップで適用する。upstreamは、自身のインライナーが残したネストをすでに畳み込んでいる。したがって、残っているのは、rc2の差し込みが作ったネストである。コピーが加えるサイズには、ラムダの本体も数える(`treeSize`)。case treeでは、altをコピーするとそのラムダもコピーされ、それぞれが別々にリフトされるからである。`Lifted`上では、ラムダは参照1つだった。idris2-lspでは、これによる測定可能な変化はない。融合された比較は同じ471個で、`let`が1つ減るだけである。大きな外側のcaseを、すべての内側の分岐へ複製する危険を抑えるため、畳み込みが働くのは、内側のcaseのaltがすべてコンストラクタ頭である場合(または、altが1つだけで、デフォルトがない場合)に限る。これは、upstreamの`canCaseOfCase`と同じ制限である。

### サイズの予算

上の形の制限が抑えているのは、畳み込みの*対象*であり、*量*ではない。畳み込み(`tryCaseOfCase`)は、外側の`alts`/`def`の全体を、内側の分岐ごとに1つずつ複製する。そして、`alts`/`def`自身のサイズには、制限がなかった。呼び出しを含まず、caseを返す小さな関数が連なる場合を考える。これは、まさに基準Aの対象とする形である。たとえば、`if pI x then ... else ...`というガードが並び、各`pI`が小さな列挙型の述語であるような場合である。これらを、scrutineeの位置へ次々に差し込むと、増加が*乗算的*に積み重なる。各段が、下の段の畳み込み済みの結果を、自分のすべての分岐へ複製するからである。

同じ`CaseOpts`のコードにupstreamがさらされる状況とは、構造が異なる(上の「case-of-caseの畳み込み」を参照)。upstreamの自動インライン展開の既定のヒューリスティック(`Compiler.Opts.InlineHeuristics`の`simple`)は、本体自身が`CConCase`/`CConstCase`である呼び出し先を、明示的に除外する。そのため、upstreamの`caseOfCase`が畳み込むのは、ソースにもともとあったネストだけである。自身のインライナーが作ったばかりのネストを畳み込むことはない。このパスは、意図的にその逆の形を狙う。caseを返す小さな呼び出し先をscrutineeの位置へインライン展開することが、このパスの存在理由そのものだからである(上の「動機」を参照)。したがって、upstreamの「case型の本体はインライン展開しない」というガードは、採用できない。採用すれば、このパス自身の存在理由が失われる。upstreamのやり方は、ここには移せない。

これは、合成したNレベルのガードの連鎖で、実際に確認した。`if pI x then ... else ...`の連鎖で、`pI : Tri -> Bool`は3つのaltを持つ列挙型の述語である(生成スクリプトは、リポジトリには入れていない)。生成されたCの行数は、1段増えるごとにおよそ*倍*になった。N=5/10/11/12で、1,185/19,041/37,473/74,337行である。これに対して、同じN=10のソースを`--directive noinline`でコンパイルすると1,044行だった(Nが増えても増加しない。scrutineeの位置へ差し込まれるものが、そもそもないからである)。N=15のあたりで、メモリが完全に尽きた。重要なのは、`--timing 2`で`rc2: Inline`自体が約0msで終わっていたことである。肥大した木を作っている最中でもそうだった(すでに作ったノードを複製するのは、安いメモリ割り当てで済む)。実時間のコストが見えるようになるのは、肥大した木に対して、ノードごとの本格的な処理を行う次の段階で、`rc2: RC normalize`がN=10で0.378秒かかった。つまり、「インライン展開の段階」のせいとして、実時間やメモリの観測で見えるハングや遅さは、サイズの肥大がそこで生じていても、`rc2: Inline (before lifting)`の計時の行より下流に現れることがある。

**修正**: `tryCaseOfCase`の2つの節は、さらに`copies * outerSize <= caseOfCaseSizeBudget`(`caseOfCaseSizeBudget = 200`)を要求する。`outerSize`は、外側の`alts`/`def`に`treeSize`を適用した値である。これは基準Aの`sizeOf`と同じ構造上のノード数だが、ラムダの本体も数える点が異なる。`copies`は、それらをコピーする箇所の数である(`length xalts`、`xdef`があればさらに1)。畳み込みを飛ばしても、意味の上では常に安全である。結果は、畳み込む前の`case (case ...) of ...`のままで、正しいが、その先では融合されないだけである。検査は、`alts`/`def`の*すでに実現された*サイズに対して、ボトムアップで行われる。このサイズには、木の下のほうの畳み込みによる複製がすでに反映されている。そのため、放っておけば積み重なって増え続ける連鎖が、累積のサイズが予算を超える最初の段で、上限に達する。それより上の段は、すでに予算に達しているか超えている入力を見て、飛ばし続ける。乗算が再開することはない。

修正後に、同じ合成の生成スクリプトを再実行した。生成されたCの行数は、おおよそ*線形*に増えた。N=5/10/12/15/20で、729/822/862/922/1,022行(1段増えるごとに約20行)である。回帰スイート全体(87/87。`Test114Inline/CompareFusionThroughCall.idr`を、機能面と`valgrind`の両方で含む)は、通ったままだった。この予算が、このパスの動機となったケースを、実際に現れる大きさでは妨げないことを確認できた。

### サイズの管理: 再走査せず、受け渡す

上の合成Nレベルの連鎖のベンチマークは、もうクラッシュしない。しかし、このガード自身の*測定*コストは、一度も試されていなかった。測定とは、`outerSize`を、候補となるすべての箇所で、`alts`/`def`に対する新しいトップダウンの`treeSize`の走査で計算することである。実際の大きなプログラムでは、この走査のコストが、`rc2: Inline`の実時間をまるごと支配した。ある大きな実プログラムで144秒かかった。畳み込みによる*複製*そのものは、上の予算によって、すでに正しく抑えられていたにもかかわらずである。見分けがつく兆候は、直後の`rc2: RC normalize`が、同じプログラムで`--directive noinline`とデフォルトとのあいだに、測定可能な差を示さなかったこと(0.20秒と0.24秒)である。つまりコストは、`rc2: Inline`の*内側*にあり、下流にはなかった。これは、先の合成Nレベルの連鎖の場合とは異なる。あの場合は、サイズの肥大は本物だったが、Inline自身の`collapse`は高速に終わり、より大きくなった木を処理する`rc2: RC normalize`が、見える実時間のコストを引き受けていた。大きな実プログラムには、病的な連鎖が1つあるのではなく、case-of-caseの候補の箇所が散らばって多数ある。それぞれが、自分を囲むaltsやdefの、上限のない大きさのものを、毎回最初から走査し直す。実質的に、O(候補の箇所の数 × 囲んでいる文脈の平均の大きさ)である。

**修正**: `collapse`は、木そのものではなく、`Sized`のペア(`szOf`/`valOf`)を返すようになった。これにより、各ノードのサイズは、木を作っていたボトムアップの畳み込みの副産物として、増分的に、ちょうど1回だけ計算される。別の走査で再導出することはない。`caseOfCaseHere`の再試行ループ(1つの木の位置で最大5回まで試す)は、木そのものではなく`Collapse`(`totalSize`、`branchesSize`、つまり`outerSize`と木そのもの)を受け渡す。したがって、1つの位置で畳み込みが連続して起きる場合も、再走査しない。`tryCaseOfCase`は、結果から再導出する代わりに、閉じた式で両方のサイズを更新する。

```
newBranchesSize = size(xalts) + size(xdef) + copies * (1 + outerSize)
```

(複製した`alts`/`def`のコピーのノード数は、入力の`outerSize`とちょうど等しい。名前付きcase tree上では、番号の付け直しは要らない。`copies`個のコピーはそれぞれ、周りに作られるラッパーの`case`ノードを1つ得る。そのため、コピーごとに`+ 1`がある。)`xalts`と`xdef`(*内側*の、差し込まれたばかりの側)は、スレッドを通さない、ふつうの`treeSize`(`conAltsSize`/`constAltsSize`)で、引き続き新しく走査する。それらが基準Aの差し込みに由来する場合は、プログラムの大きさにかかわらず、`smallBodyThreshold`で上限が決まる。逆に、もともとあった本物の大きなネストしたソースの`case`に由来する場合(このパスの`collapse`は、インライン展開されたかどうかにかかわらず、*すべての*定義に対して走る)、この走査は、この管理の仕組みができる前から、まったく同じだけ高価だった。この側で、新しいコストが生じたわけではない。

再検証した結果、同じ合成生成スクリプトで、上と同じ線形の行数の増加になった(サイズを受け渡すのは、純粋な性能の変更であり、挙動の変更ではない)。回帰スイート全体(87/87。`Test114Inline/CompareFusionThroughCall.idr`を含む)も、通ったままだった。

この調査の中で、別の、無関係なコストも見つかった。同じ合成生成スクリプトのN=25は、upstream自身の「Elaborating」の段階で5.6秒かかった(rc2とは無関係。`rc2:`で始まる段階は、すべて0.000秒のままだった)。26段にネストした`if`-`then`-`else`の式を1つ、そのままelaborateするのは、upstream自身のelaboratorにとって、おそらく高価である。`--directive noinline`を付けても変わらない。これ以上は調べていない。実際のソースコードで、この深さの単一行の`if`の連鎖を手で書くことは、まずないからである(合成生成スクリプトは、case-of-caseの形を切り出すために、あえてそう書いた)。ただし、再び現れたときに、このパス自身の挙動と取り違えないよう、記しておく。

## リテラル引数自身のRep(`buildSplice`の定数の節)

`buildSplice`の`RCLoc`の節は、呼び出し先がそのパラメータをネイティブに読むかどうかを、以前から`nativeEligible`に問い合わせ、読む場合は新しい`RLet`を`RNative ty`で束縛していた。一方、*定数*の節は、この問い合わせを完全に飛ばして、常に`RBoxed`で束縛していた。定数の節とは、`Compiler.RC2.ConstFold`がすでに`RCConst`/`RCEmptyCon`/`RCConstCon`/`RCConstClosure`に畳み込んだ引数を受け取る節である。

ネイティブにできるリテラル(`Types.litRep`)では、新しいボックスを作り、直後の文でそれをアンボックスし直していた。典型的な使い手は`RLoop`自身のネイティブな`initial=`スロットで、ループ変換された呼び出し先を、唯一の呼び出し元へ差し込んだ後に残る。

```
let v402 : Boxed = #0
let v401 : Boxed = #100000
loop ["v400:Native Int64", "v399:Native Int64"] initial= [v401, v402] prologueDrop= [v401, v402]
```

```c
IDRIS2RC2_Value * var_401 = idris2rc2_mkInt64(INT64_C(100000));
int64_t var_400 = (var_401 == NULL) ? 0 : (idris2rc2_to_i64(var_401));
```

この節は、`RCLoc`の節と同じ問い合わせをするようになった。`RNative`で束縛されたリテラルは、`Compiler.RC2.Emit`の`declareLet`の`(RNative _, RPrimVal _ c)`の場合に到達して、そのまま`InlineMap`に入る。C変数は宣言されず、リテラルは唯一の使用箇所にインラインで出力される。リテラルでない定数にはネイティブな表現がなく、`RBoxed`のままである。`litRep`は、そのような定数に対して`Nothing`を返す。

これが働くようになるためには、共有しているネイティブ読み取りの解析に、2つの対応する修正が必要だった。`RLoop`自身の`initial=`スロットと、定数`case`のscrutineeは、どちらも、`Compiler.RC2.Loop`の`nativeArgTypes`でネイティブな読み取りとして数えられる必要があり、`hasNonNativeUse`では、不適格にする使い方として数えられてはならなかった。後者は、同じ共有の`nativeSlotTy`と`constAltsNativeType`に対して判定するので、両者が食い違うことはない。2つの修正と、その測定結果は、`doc/dual-abi.md`の「Extending the promotion to `case` scrutinees」を参照。

## 基準B: ループを含まず、呼び出し元が1つの呼び出し先(2026-09-25。2026-09-29からcase tree上)

2つ目の基準は、上で、決め手にならないとして見送ったが、ConstFoldの既知のコンストラクタの畳み込みと`Compiler.RC2.PushCon`(`constructor-escape-analysis.md`)ができたことで、決め手になった。呼び出し先が、唯一の呼び出し元がすぐにマッチするコンストラクタを返す場合、コンストラクタの構築と`case`が1つの関数の中に並ぶのは、インライン展開した後だけである。`LateInline`もインライン展開するが、それはRCの注釈の後で、これらの畳み込みが届かない。`LateInline`をそれほど後ろで走らせる必要があるのは、`Loop`が変換するまで再帰している呼び出し先だけである。もともと再帰していない呼び出し先は、待たなくてよい。

呼び出し先は、次の条件を満たすとき、唯一の呼び出し箇所でここでインライン展開される。

- 引数が少なくとも1つある`MkNmFun`である(引数が0個の定義はCAFで、何回参照されても評価は1回である)。
- プログラム全体で、その名前の出現(`NmRef`)がちょうど1回である。
- 呼び出しグラフのどの循環にも含まれない。自己呼び出しも含む(`NmRef`のグラフに対する`MutualLoop`の`tarjanSCCs`)。

呼び出し元はCAFでもよい。最初の版は、CAFの呼び出し元を除外していた。`main`のメモ化された本体に差し込んだコードが、最適化されない状態になったためである。実際の原因は、DualABIとSinkが`RMemoize`の中へまったく入っていなかったことである(`caf-memoization.md`の「Limitations」)。これは修正済みで、除外は取り除いた。

定義は、呼び出し先を先に処理する(`tarjanSCCs`の順序の逆で、`LateInline`と同じ)。適格な呼び出し先は、処理済みの形でマップに入るので、連鎖`A -> B -> C`は1パスで畳み込まれる。`LateInline`と同じく、サイズの上限はない。呼び出し箇所が1つであれば、コピーが増えることはない。`%noinline`は参照しない。基準Aと`LateInline`も、これを参照しない。

**引数は、置換するのではなく、束縛するようになった。** 差し込みは、各引数の式を、そのパラメータのすべての出現へ置換していた。そのため、2回使われるパラメータは引数を2回評価し、使われないパラメータは引数を一度も評価しなかった。`sq x = x * x`を`sq (expensive y)`にインライン展開すると、`expensive y`が2回計算された。基準Aは、書かれた当初から、この動作だった。基準Bの本体は任意なので、Bが同じ差し込みを使えるようにする前に、これを直す必要があった。`splice`は、アトミックでない引数(ローカル変数、リテラル、erasedな値以外のすべて)を、先に`NmLet`で束縛し、置換するのはその3つだけにする。この修正は、2つの基準の両方に及ぶ。

ConstFoldの既知のpartialの畳み込み(`constructor-escape-analysis.md`)とあわせて、どちらも入れる前のビルドと比較し、idris2-lspで測定した結果は次のとおりである。`apply`は11,326から10,039、`partial`は16,448から15,788、割り当てを行う`con`は39,741から38,257、IRの行数は-1.2%、コンパイル時間は27.9秒から29.3秒になった。パスがまだ`Lifted`上で動いていた時点で適格だった呼び出し先は3,158個であり、`LateInline`の差し込みは約11,800個である。その大半は、ConstFoldとSpecClosureがクロージャの適用を直接呼び出しに変えた後で、初めて呼び出し元が1つになる(RCの注釈の直前で8,126個が適格)。そのため、`LateInline`自身の差し込みも、そこで「Early inline」の段階として1回走る(`constructor-escape-analysis.md`の「Early inline」)。

## 基準B、再訪: `Compiler.RC2.LateInline`

「呼び出し箇所が1つで、プログラム全体の」基準は、`RCExp`上にも、別のパス`Compiler.RC2.LateInline`としてある。このパスは、名前付きcase treeではなく`RCExp`を対象にし、上の`Compiler.RC2.InlineCExp`より、パイプラインのずっと後ろで走る。`--directive nolateinline`で無効にできる。

### 動機

`Compiler.RC2.SpecClosure`は、クロージャ引数を取る関数について、呼び出し箇所ごとに特殊化した複製を作る(`rc2/doc/speculative-closure-specialization.md`を参照)。元の関数が自己再帰していれば、SpecClosureが作った時点で、その複製も自己再帰している。基準Aは呼び出しを含まないことを要求する(この文書の「適格性」の節)ので、この自己再帰のせいで、複製は一律に拒否されていた。自分自身への呼び出しでも、呼び出しである以上、呼び出しを含まないとは言えない。

`Compiler.RC2.Loop`(と`MutualLoop`)は、ふつうの自己再帰(と相互末尾再帰)を、すでに`RLoop`/`RLoopContinue`に畳み込んでいる。これはgotoに基づくループで、元の名前への関数呼び出しがもう残らない。呼び出しグラフがLoopの変換の*前*には再帰して見えた複製は、*後*では、完全にふつうの、再帰しない、ほかのどの関数とも同じようにインライン展開できる関数に見える。SpecClosureの複製は、構成上、ちょうど1つの呼び出し箇所のために作られる。そのため、Loopの変換が済んだ時点で、無条件に、呼び出し元が1つの場合の適格性を持つ。こうして、基準Bの呼び出し元1つの基準に、初めて、具体的で決め手となる動機のケースができた。先の調査では、そのようなケースは見つからなかった。

### パイプライン上の位置

```
  -> Compiler.RC2.MutualLoop      (相互末尾再帰 -> 1つに統合した関数)
  -> Compiler.RC2.Loop            (自己末尾呼び出し -> RLoop/RLoopContinue、
                                    加えてネイティブシャドウの昇格)
  -> Compiler.RC2.LateInline      (このパス -- プログラム全体のインライン展開、RCExp -> RCExp)
  -> Compiler.RC2.Sink            (分岐局所へのlet値の沈め込み)
  -> Compiler.RC2.DualABI         (ワーカー/ラッパーの合成、呼び出し箇所の書き換え)
  -> Compiler.RC2.DeadCode        (プログラム全体の到達可能性による枝刈り)
  -> Compiler.RC2.DupMerge
  -> Compiler.RC2.Emit            (RCExp -> C。機械的な変換のみ)
```

Loop/MutualLoopの変換より、厳密に後に走る。これより前に走らせると、このパスが届くべきまさにその複製を拒否することになる(理由は「動機」を参照)。Sinkより、厳密に前に走る。このパスが差し込んだばかりの値(たとえばループ全体が、1つの分岐の`RLet`の値になったもの)に、Sinkの分岐局所の配置の判断を、引き続き適用できるようにするためである。DualABIより、厳密に前に置く。この選択の実際の帰結は、後述の「修正済み: DualABI自身のネイティブ適格性の解析が、関数ごとに`RLoop`が1つだと仮定していた」を参照。それでも順序を逆にしなかった理由も、そこにある。

インライン展開された元の定義は、ここでは明示的に削除しない。ほかに何も到達しなくなれば、パイプラインの後ろにある`Compiler.RC2.DeadCode`が、到達できないほかの定義と同じように、自動的に枝刈りする。ただし、*ほかの*何かがまだその定義を参照している場合(たとえば直接呼び出しではなく、保存されたクロージャ値の`RUnderApp`/`RCConstClosure`として)は、正しく残る。このパスが取り除くのは、唯一だと証明できる1つの呼び出し箇所だけで、定義自身を取り除くことはない。

### 適格性: これは採算判定でもある

呼び出し先は、プログラム全体で次の条件を満たすとき、その呼び出し箇所でインライン展開される。

- `RAppName`の出現が、どこにもちょうど*1つ*だけである(`analyse`の`callCounts`。独自の走査ではなく、`RCExp.idr`の汎用の`foldRCNamesD`/`RCNameFold`の仕組みで作る)。
- 本物の`MkRCFun`である(`RCCon`/`RCForeign`/`RCError`ではない)。
- `callsBack`が、呼び出し先は呼び出し元を直接呼び返さないと判定する。この検査は、個々の差し込みの判断のたびに新しく行う。最初に出荷した版のように、プログラム全体の循環への所属を、先に除外して済ませるのではない。この、より弱く、局所的な、1ホップの検査で足りる理由は、後述の「より大きな循環の一部でも安全である理由」を参照。

基準Aと違って、サイズの閾値は別に設けない。呼び出し元が1つの場合のインライン展開は、それ自体が*無条件に*採算に合うと見なして、安全である。呼び出し先の呼び出し箇所はちょうど1つなので、そこに差し込んでも、プログラム内のそのコードのコピーが増えることはない。最悪でもサイズは変わらない(呼び出しのオーバーヘッド自体が消えるので、実際には常に得になる)。サイズの上限が意味を持つのは、適格性が「小さく、呼び出し元が複数」の呼び出し先(基準A自身の形)へ広げられるときだけである。ここではそこまで試みていない。

処理は、`defs`の偶然の順序ではなく、`tarjanSCCs`の逆順、つまり呼び出し先が呼び出し元より先になる順序で進む(`Compiler.RC2.MutualLoop`の`Graph`/`tarjanSCCs`を、そのまま再利用している。このために、そちらで`public export`にした)。`C`の唯一の呼び出し元が`B`で、`B`の唯一の呼び出し元が`A`であれば、`C`を`B`へ処理してから、`B`を`A`へ処理する。そのため、`A`は、`C`がすでにインライン展開された`B`を、完全に畳み込まれた形で、1パスで受け取る。連鎖全体を畳み込むための再実行は、要らない。

### より大きな循環の一部でも安全である理由

これは、構成した例ではなく、実際のビルドで見つかった。`idris2-lsp`を`--directive dumprcexpr`でコンパイルすると、`rc2_specClosure_Prelude_IO_map_Functor_IO:4852`が見つかった。これは`Compiler.RC2.SpecClosure`の複製で、呼び出し箇所がちょうど1つで、3行しかないのに、インライン展開されなかった。プログラム全体の`RAppName`グラフを、手で追跡した。定義ごとに、ダンプを`call NAME [`でgrepした。その結果、この複製は、実際の循環の上にあることが分かった。

```
:4852 -> rewriteSub:33 -> rewriteCExp -> rewriteSub
       -> rc2_specClosure_Core_Core__lt_star_gt:183 -> rewriteSub:36
       -> rc2_specClosure_Core_Core__lt_star_gt:181 -> rewriteSub:34 -> :4852
```

`Compiler.Opts.Constructor.rewriteCExp`/`rewriteSub`は、典型的な再帰的な式木の書き換え器である。`SpecClosure`は、その同じ再帰構造の*内側*の、複数の別々の箇所で、それぞれ別のクロージャの対象のために複製を作った。そのため、複製自身が循環に織り込まれていた。もとのプログラム全体の循環SCCの除外は、それらすべてを、正しく捕まえていた(ただし、乱暴すぎた)。

**絞り込んだ基準。** 呼び出し元`a`から1つだけ呼ばれる呼び出し先`b`は、`b`が`a`を*直接*呼び返さない限り、`a`に差し込んでも安全である。この検査は、局所的に、1ホップで、差し込みの判断のたびに新しく行う(`callsBack`)。`b`が、はるかに大きな循環のどこかに位置しているだけで、その循環を閉じることに直接は関わっていない場合まで除外する方式は、とらない。

**証明。** 不変条件 **I** を固定する。「プログラム全体の呼び出しグラフで、どの関数も、自分自身への直接の辺を持たない」。差し込みは、呼び出し自身の対象`Name`を付け替えない(付け替えるのは、呼び出し先の内部の`Int`の変数idだけである。後述の「すべてのidを付け替える」を参照)。したがって、`b`を`a`に差し込んだ後は、次が成り立つ。

$$\text{outEdges}'(a) = \big(\text{outEdges}(a) \setminus \{a \to b\}\big) \cup \text{outEdges}(b)$$

`a`の出辺の集合に新しく加わる辺は、`b`のもとの出辺だけである。`callsBack`は $a \notin \text{outEdges}(b)$ を要求するので、この和集合は、やはり $a \to a$ を含まない。この差し込みで、ほかの定義の本体は、触られない。したがって、差し込みの前に **I** が成り立っていれば、差し込みの後も成り立つ。帰納法により、これらの差し込みを何回、どの順序で行っても、不動点まででも、そうでなくても、成り立つ。(**I** は、最初に成り立つ。`Compiler.RC2.Loop`/`MutualLoop`は、このパスが走る前に、末尾の自己再帰を`RLoop`へすでに取り除いている。そして、本物の非末尾の自己呼び出しは、自身の`RAppName`の出現によって、`callCounts`を1より大きくする。これだけで、`eligible`から除外される。)

**`a -> b -> c -> a`の場合をたどる。** `b`は`a`を呼び返さない(呼び返すのは`c`だけである)。したがって、`b`を`a`に差し込むことは許される。グラフは`a -> c -> a`に縮み、2サイクルになるが、自己ループは生じない。次に、`c`は呼び出し元が(`a`の)1つだけだが、`a`を直接呼び返す。`callsBack`は、差し込みを正しく拒否する。連鎖は、差し込みが文字どおりの自己ループを作ったはずの、まさにその位置で止まる。それより前で止まることはない。

**実行時の正しさには、そもそも決め手にならない。** `Emit.idr`の`emitRC`は、`InTailPosition`の`RAppName`を、本物の呼び出しとして出力することが、そもそもない。`tryBuildClosureInto`が、それをクロージャの構築に変える。そのクロージャは、`NotInTailPosition`である祖先の呼び出し箇所まで返される。その祖先が、呼び出しを`idris2rc2_trampoline(...)`で包む。この関数は、そのクロージャ(と、それをディスパッチして生じる、さらなるクロージャ)を、平坦な`while`ループでディスパッチする。何回反復しても、Cスタックの深さはO(1)である。これは完全に汎用であり、出力される`RAppName`が、このパスが走る前からあったか、`c`を`a`に差し込んだ直後にできたばかりかは、問わない。したがって、`callsBack`が今も拒否する唯一のケースを許したとしても、実行時には安全なはずである。そのケースとは、`c`が`a`を呼び返すもので、差し込んだ後の`a`に、新しい直接の末尾の自己呼び出しが残る。`a`の新しい末尾位置は、ほかと同じくクロージャの構築になり、`a`を外から呼んだ呼び出し元がディスパッチする。それでも`callsBack`が禁じているのは、純粋に、`applyLateInline`の不動点ループが、ラウンドの途中で一時的に新しい自己ループを持つ関数について、考えなくて済むようにするためである。そのような関数は、プログラム全体の`callCounts`により、次のラウンドで、どのみち再び`eligible`から外される(新しい自己参照が、出現として数えられる)。したがって、その回り道を省いても、失うものはない。自己ループが*非*末尾の位置に生じる場合も(`c`の本体のどこに`a`への呼び出しがあったかによって、起こりうる)、トランポリンはまったく適用されない。しかし、これも新しい危険ではない。直接の非末尾の自己呼び出しは、ふつうのCコールスタックを通って再帰するだけで、非末尾再帰の関数が、インライン展開と無関係に、すでに持っているコストとまったく同じである。

**未解決の問い: ネイティブ型の末尾位置は、確認していない。** 上の議論は、このパスが見る唯一のものである`RAppName`に関するものである。`Compiler.RC2.LateInline`は、`Compiler.RC2.DualABI`より厳密に前に走る。そのため、ここには`RAppNameRep`はまだなく、関係するすべての戻り値の型は、一様に`RBoxed`のままである。しかし、差し込みは、`DualABI`が後で見る*形*を変えうる。この、緩めた循環の除外によって、呼び出し先の末尾位置を得た呼び出し元`a`は、差し込みの後で、`DualABI`のネイティブワーカー適格性の解析(`tailValueReps`/`uniformTailType`)に対して、`a`単独だったときとは異なる末尾位置の組み合わせを見せるかもしれない。その解析が、`a`を、上述のトランポリンの扱いが構造上なおも必要な末尾位置(`RLoop`変換の残りで、まだクロージャ構築のフォールバックに頼るもの)の上で、*ネイティブ*を返すワーカーに昇格させたとすると、それを遅延させる手段が残らない。ネイティブのスカラーは「あとで戻ってくる」を表現できず、それを表現できるのは`RBoxed`だけである。`tailValueReps`の「すべての末尾の出口が同じ型で一致する」という一様性の検査が、本当に混ざったケースを捕らえて、昇格を拒否するのだろう。後述の「関数ごとの複数のループ」がすでに汎用に処理されていたのと同様である。しかし、この特定の相互作用(緩めた循環のインライン展開が、`DualABI`のネイティブワーカーの昇格に入ってくる)は、上のボックス化/トランポリンのケースのようには、実際には追跡も試験もされていない。誰かが確認するまでは、確認済みではなく未検証として扱う。

### 不動点まで反復し、ラウンドごとにデッドコードを枝刈りする

当初は、プログラム全体を1パスで処理するだけだった。`analyse`の`eligible`の集合は、このパスが始まった時点の`defs`から、1回だけ計算していた。このパスが走った*後*で初めて呼び出し元が1つになる呼び出し先は、検出されないままだった。1ラウンドの中では、`callCounts`を導出し直す者がいないからである。現在の`applyLateInline`は、1ラウンド分のロジック(`applyLateInlineOnce`)をループで包んでいる。毎回、更新したばかりの`defs`に対して、`analyse`を最初からやり直す。ループは、枝刈りも差し込みも残らないラウンドに達するか、`maxLateInlineIterations`(4。`RC2.idr`の`maxConstFoldIterations`と同じ値で、理由も同じ)に達するまで続く。

不動点のループだけでは、新しく生じる機会の、*狭い*種類にしか届かない。届くのは、*このパス自身の*差し込みが変えたことによって、初めて生じる機会だけである。一見、より魅力的に思える別のケースは、対象にならない。呼び出し先に2つの呼び出し箇所があり、`analyse`が走るあるラウンドで、その一方が、同じラウンドに到達不能な不要物へ書き換えられる定義の中にある場合である。*インライン展開そのもの*は、`defs`から定義を削除しない。古い呼び出し箇所は物理的に残る。`analyse`の`callCounts`(`RAppName`の出現を、ただ数えるもの)は、「まだ呼ばれている」と「もう何も到達しないコードからだけ呼ばれている」を区別できない。そのため、呼び出し先は、その後に何ラウンド回しても、「呼び出し元が複数」のままに見える。

これは、`applyLateInlineOnce`が、毎ラウンドの最初、`analyse`が何かを数える前に、`Compiler.RC2.DeadCode.pruneDeadDefs roots`を呼び出すことで直した。`Compiler.RC2.DeadCode`自身が呼ぶのと、まったく同じ使い方である。`roots`は、`applyLateInlineOnce`と`applyLateInline`の両方の新しいパラメータとして渡す。`DualABI`の後にある、別の`pruneDeadDefs roots`の呼び出しは、意図的に、落とす理由にしていない。`DualABI`はこのパスより完全に後で走り、それ自身の新しい不要物(たとえば使われないワーカー/ラッパーの分割)を作りうる。それは、このパスからは見えない。したがって、その呼び出しは、元の位置にそのまま残る。また、このパス自身の適格性のグラフと、`pruneDeadDefs`の到達可能性のグラフを、1つのグラフに統合することも、意図的にしていない。`pruneDeadDefs`の`usedFunctionNamesD`は、`RAppName`/`RAppNameRep`に加えて、`RUnderApp`/`RCConstClosure`による参照(クロージャとして保存されるだけで、`RAppName`では呼ばれない値)も、本物の使用として数える。そのようにしてのみ到達できる関数が、生き残るようにするためである。一方、`analyse`の`calleesOf`/`callOccurrencesOf`は、数えない。保存されたクロージャへの参照は、このパスがインライン展開できるものではないからである。その、より狭いグラフを、到達可能性に再利用すると、クロージャ値としてだけ生きている関数を、誤って枝刈りしてしまう。

### すべてのidを付け替える: 呼び出し先自身の内部のidも含む

差し込みは、呼び出し自身の、引数からパラメータへのトップレベルの束縛を、引数ごとの`RLet`に置き換える。そして、差し込む本体の全体で、呼び出し先のパラメータidの出現を、その新しい`RLet`自身のidへ付け替える(`Compiler.RC2.Loop`の`Renaming`/`renameRCExp`を、そのまま再利用している)。これには、見かけほど自明でない点が2つあり、どちらも、実装中に本物のバグとして見つかった。

1. **すべての引数が*新しい*idを得る。呼び出し元ですでに裸の`RCLoc`である引数も同じである。** 実引数がすでに`RCLoc j`であれば、`RLet`を飛ばして、パラメータidを直接`j`に付け替えたくなる。しかし、この近道は、ふつうの(インライン展開されない)呼び出しが、何もしなくても与える分離を壊す。ループ変換された呼び出し先の`RLoop`は、自身のトップレベルのパラメータのidを、ループ間で運ばれる*可変*の変数として再利用することが多い(`Compiler.RC2.Loop`の「自身のidを再利用する」場合と、`Emit.idr`の`declareLoopParam`)。そのidを呼び出し元の`j`へ直接エイリアスすると、差し込まれたループが、呼び出し元自身の変数を、その場で再代入できてしまう。**見つかった経緯**: 同じ`xs`に対する`map (*2) xs`の直後の`filter p xs`で、どちらも呼び出し元が1つで適格であり、同じ呼び出し元へ続けて差し込まれた。両方が、まったく同じidへ付け替えられていたので、`map`のループが、共有された`xs`の変数を`NIL`まで書き換えてから、`filter`のループが読む番になった。`printLn (filter p xs)`は、正しい結果ではなく`[]`を出力した。
2. **呼び出し先の*内部の*idも、トップレベルのパラメータだけでなく、付け替える必要がある。** `Compiler.RC2.Util`の`VarId`のカウンターは、すべてのidを、最初に割り当てた時点から、プログラム全体で一意にしている(`rc2/doc/...` -- そのモジュールのドキュメントコメントを参照)。それにもかかわらず、付け替えが必要である。例外は`Compiler.RC2.SpecClosure`である。これは、共有された1つの元の本体から、*複数の*複製を作る。そのとき、各複製自身の適用の連鎖と自己呼び出しだけを書き換え、本体の残りは、内部のidも含めて、*すべての*複製へそのままコピーする。したがって、そのような2つの複製は、正当に、内部のidを共有する。それぞれが別のC関数のままである限り、害はない(Cは、ローカル変数を関数ごとにスコープ付けするので、無関係な2つの関数が、それぞれ別の`var_301`を持っても、衝突しない)。そのような2つの複製を、*同じ*呼び出し元へ差し込むと、この分離が壊れる。**見つかった経緯**: 同じ元の`String -> ... -> Boxed`のヘルパーの、2つのSpecClosureの複製(それぞれ呼び出し箇所は1つ)が、共有された元から、まったく同じ形で引き継いだ、無関係な`let v301 = call Data.String.Iterator.fromString [...]`を含んでいた。両方を同じ呼び出し元へ差し込むと、1つの関数の中に`var_301`のC宣言が2つできた(`error: redefinition of 'var_301'`)。

`collectBoundIds`(このモジュール自身のコピー。`RLet`の`var`、`RConAlt`の分解された`args`、`RLoop`の`loopParams`を対象とする。これらは、このセッションの`VarId`の統一によって不要になる前の、`Compiler.RC2.Loop`と`Compiler.RC2.MutualLoop`が、それぞれ持っていたコピーが扱っていたのと同じノードの形である)が、呼び出し先の内部のidをすべて見つける。それぞれに、`Compiler.RC2.Util`の`freshVarId`で新しいidを与え、パラメータの置換が使うのと同じ`Renaming`へ統合する。

### 関数ごとの複数のループ

呼び出し元がすでに自身の`RLoop`(自身の自己再帰を、このパスが走る前に変換したもの)を持ち、そこへ、*別の*、独立にループ変換された呼び出し先を差し込むと、`rc2/doc/loop-conversion.md`の「Multiple loops per function」の節が`Emit.idr`に正しく扱わせた、まさにその「1つの関数に`RLoop`が複数ある」形ができる。ここで特別な処理は要らない。`emitInto`は、`RLoop`を、任意の`sink`/`TailPositionStatus`に対して汎用にディスパッチする。したがって、ループを含む呼び出し先を、ふつうの`RLet`の値として差し込む場合(このパス自身の既定の形。上の「すべてのidを付け替える」を参照)は、兄弟でも入れ子でも、すでに正しくlowerされる。

### 修正済み: DualABI自身のネイティブ適格性の解析が、関数ごとに`RLoop`が1つだと仮定していた

`Compiler.RC2.DualABI`の`findLoopThroughLets`と`paramEligibility`(パラメータをネイティブに昇格させるかどうかの判断)は、「関数ごとに`RLoop`は1つ」という仮定の下で書かれていた。この仮定は、このパスができるまでは、どこでも真だった。`findLoopThroughLets`は、純粋な`RLet`の前置きを通って到達できる最初の`RLoop`しか見つけず、その本体の中のさらなるループを探さずに止まっていた。また、`Loop.idr`の`nativeArgTypesFor`/`nativeArgTypes`には、`RLoop`の場合がまったくなく、`RLoop`の本体へ再帰することがなかった。これは、前置きから到達できるループがそもそもないときに、`paramEligibility`が使うフォールバックである。たとえば、本体の根とループのあいだに`case`があるときがそうで、このパスが、ループ変換された呼び出し先を、根に限らずどこにでも差し込めるようになると、これが一般的な形になる。

このパスが、ループ変換された呼び出し先を、すでに自身のループを持つかもしれない呼び出し元へ差し込める以上(上の「関数ごとの複数のループ」を参照)、その内側にネストされたものでも、`case`の先でしか到達できないものでも、差し込まれたループの*内側で*ネイティブにだけ使われるトップレベルのパラメータは、`paramEligibility`の2つの経路のどちらからも見えなかった。そして、ネイティブなワーカー引数へ昇格されなかった。これは、`DualABI.idr`と`Loop.idr`を直接たどって、仮説ではなく本物であることを確認した。

**修正**: `nativeArgTypesFor`/`nativeArgTypes`(`Loop.idr`)は、`RLoop`の`body`へ、ほかのラッパーノードと同じように再帰するようになった(`loopParams`/`initial`/`prologueDrop`はメタデータであり、走査する操作ではない)。これだけで、差し込み後の一般的な形の隙間は塞がる。`findLoopThroughLets`が`Nothing`を返す場合(純粋な`RLet`の前置きにループが続く形以外のすべて)は、すでにこのフォールバックへ回されていたからである。`findLoopThroughLets`(`DualABI.idr`)も、見つけたループの`body`へ再帰して、さらに*本当にネストした*ループを探すようになり、各レベルの`loopParams`を統合する。これは、`paramEligibility`が`Just`の枝を今も通る場合を、カバーする。本当の*兄弟*のループ(ネストではなく、最初のループの後で、別の方法で到達されるもの)は、この修正をしても、この方法では見つけられない。`RLoop`には、続きへ進むための「その後」のフィールドがないからである。ただし、その形は、もともと`findLoopThroughLets`の`Just`の枝ではなく、(今は修正された)フォールバックへ回されていた。回帰スイート全体(85/0、16/16)で再検証した。ゴールデン出力の再生成は不要だった。つまり、現在のスイートで、この修正が塞いだ隙間を実際に突くものはない。この修正は、`Compiler.RC2.LateInline`が有効になって新しく到達できるようになった形を、対象にしている。

### 修正済み: 差し込みがネイティブRepを伝えず、ネイティブだと証明できる値を、ボックス化してすぐアンボックス化していた

のちのセッションで`rc2/BENCHMARKS.md`を更新しているときに見つかった。`BenchChain`(自己再帰する数値のループが、反復ごとに、小さな再帰しないヘルパーを1回呼ぶ)と`BenchLoopCallArg`(FFIで条件づけられたヘルパーの呼び出しで、その結果がループ自身の蓄積変数に渡る)が、`LateInline`より前のベースラインと比べて、約20倍から50倍遅くなっていた。上のすべての適格性の検査を満たしており、差し込み自体も、正しい出力を出していたにもかかわらずである。同じ根本原因の、3つの別々の、重なり合った現れがあり、それぞれ、`--directive dumprcexpr`と、`--directive nolateinline`のビルドを正解として行った直接の`time`比較で見つかった。

**層1 -- 呼び出し先自身の、置換されたパラメータ。** `buildSplice`は、各実引数を、新しい`RLet`で束縛する。その`Rep`は、`argRep`が*呼び出し元の*現在の`reps`環境から選ぶ(呼び出し元がすでにネイティブにしていなければ`RBoxed`)。ところが、呼び出し先自身の本体には、このパスが走る前に(Phase 2で)、呼び出し先のトップレベルのパラメータが常に`RBoxed`だという仮定で、*Boxed*なパラメータのための`RDup`/`RDrop`/postDropの管理が、すでに注釈されている。この管理を取り除かずに、新しいidを`RNative`と宣言すると、本物のCのコンパイルエラーになる(`idris2rc2_drop`に生の`int64_t`が渡される)。修正前の動作のように、`RBoxed`のままにすると、呼び出し先自身の本体がネイティブな文脈(`ROp`/`RCmpCase`のオペランド)でしか読まない引数を、ボックス化することになる。使うたびに、ボックス化してすぐアンボックス化する往復が強制される。

### 修正済み: 定数クロージャとループパラメータ(2026-09-26)

`buildSplice`は、定数クロージャ(`RCConstClosure`)である引数を、すべて`ConstClosureArgs`に記録する。`resolveConstClosureApps`は、差し込んだ本体の中の、そのidの`apply`を、直接呼び出しに書き換える。ところが、そのidは、呼び出し先のループパラメータの1つでもありうる。その場合、定数は、ループの*初期値*にすぎず、`RLoopContinue`のたびに再束縛される。

`Data.List.sort`が、まさにこれに当たった。その`splitRec`は、自己末尾ループになり、差分リスト`zs`(`zs . ((::) y)`)を運び、`id`から始まる。`splitRec`を`sortBy`へ差し込むと、その呼び出しは`id`をリテラルとして渡すので、基底ケースの`zs []`が、`id`への呼び出しに書き換えられた。これは、ループが集めた要素ではなく`[]`を返した。そのため、`sort [5, 3, 0, 9]`が`[9]`になった。

この書き換えは、ループの境界で止まらなければならない。`resolveConstClosureApps`の`RLoop`の場合はすべて、本体を歩く前に、そのループ自身の`loopParams`を、マップから取り除くようになった。ループの`initial`のリストには手を触れない。それは最初の反復の前に読まれるからである。

ほかの段階を無効にしてもバグが隠れた理由は、次のとおりである。`noloop`はループを残さない。`noconstfold`では、引数が畳み込まれた定数クロージャにならない。回帰テストは`Test110Loop/LoopConstClosureParam.idr`である。

### 検証の方法

1. ビルド全体とテストスイート全体: `rc2/tests/verify.sh`(85/0)と`libs/rc2base/tests/verify.sh`(16/16)。どちらも`valgrind`を含む。
2. 手書きの再現コード: `go`/`mkTarget`の形をした、自己再帰する高階関数を、SpecClosureが2つの呼び出し箇所で特殊化する。`--directive dumprcexpr`で、2つの複製の両方が`main`に直接差し込まれ(別々のトップレベル定義としては残らず)、それぞれが、生成されたCの中で、自身の`RLoop`/`loop_N:`ラベルを持つことを確認した。出力は変わらず、正しい。
3. `rc2/tests/refc-suite/callingConvention`のゴールデン出力は、このセッションのほかの変更も引き起こした、`var_N`/`tmp_N`の番号の見た目だけの変化に*加えて*、別の理由でも、再生成が必要だった。このパスが、`Compiler.RC2.DualABI`がワーカーを合成するより前に、`sumLoop`/`eligibleAdd`/`tailAbs`をインライン展開して消してしまうので、それらのワーカー関数が、別のC関数としては、実際に存在しなくなった。プログラム自身の標準出力が変わらないことを、再生成を受け入れる前に確認した(バイナリを直接実行して確認した。テスト自身のCソースの構造に関する検証とは別である)。インライン展開が、呼び出しの境界を取り除いた。`DualABI`の最適化は、その境界のコストを狭めるためのものだった。したがって、これらの特定の関数に対して、その、より狭い最適化が要らなくなるのは、想定どおりであり、退行ではない。
