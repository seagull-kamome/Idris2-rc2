# `Lazy`と`Inf`のメモ化

(原文: `doc/lazy-memoization.md`。内容が乖離した場合は原文を正とする。)

**ステータス: 2段階に分けて実装済み。** `RDelay`/`RForce`は独立した`RCExp`ノードであり、遅延セル(`IDRIS2RC2_TAG_LAZY`)にコンパイルされる。セルに最初に格納された結果は、`idris2rc2_force`によって以後のすべての強制評価で共有される。同じセルを2つのスレッドが同時に強制評価するとサンクが2回走ることがあるが、保持されるのは最初に格納された結果だけである(後述の「`Force`」を参照)。何も計算しない`Delay`(定数、ラムダ、アトムだけのコンストラクタ)は、セルを作らずにその値そのものに置き換える。

`Compiler.RC2.LazyCaf`は、引数0個のトップレベルの`Delay`定義に専用のセルを与えず、既存のCAFメモ化に載せる。`Compiler.RC2.LazyFold`は、ちょうど1回だけ強制評価されるローカルの遅延を、そのサンクの直接呼び出しに変える。何が変わり、どう検証したかは、後述の「計測」と「検証」を参照。

## 規模

どちらの段階も入る前に、upstreamの`NamedCExp`(`--dumpcases`、2026-10-01)で数えた。

| | rc2自身 | idris2-lsp |
|---|---|---|
| 定義 | 11,027 | 10,289 |
| `%delay Lazy` | 2,645 | 2,526 |
| `%delay Inf` | 925 | 748 |
| `%force Lazy` | 4,352 | 4,190 |
| `%force Inf` | 19 | 35 |
| 本体全体が`%delay`である、トップレベルの引数0個の定義 | 218 | 214 |
| `%force (%delay ...)` | 0 | 0 |

rc2自身で何が遅延されているかは次のとおりである(idris2-lspもほぼ同じ)。

| `Lazy`の本体 | 個数 | `Inf`の本体 | 個数 |
|---|---|---|---|
| コンストラクタ | 673 | ラムダ | 469 |
| 呼び出し | 648 | コンストラクタ | 369 |
| 定数 | 605 | 呼び出し | 74 |
| ラムダ | 494 | | |
| 変数 | 141 | | |

4,352個の`%force Lazy`のうち4,219個は、呼び出しの結果を強制評価している。その大半は、CSE済みのトップレベル定数`({csegen:N} [])`であり、その本体が`%delay`になっている。

rc2のパスを通した後も、delayのリフトで生じた定義(rc2が3,583個、idris2-lspが3,287個)のうち、約2,800個(rc2)と約2,670個(idris2-lsp)が最終的なIRに残る。数値は概数である(`.lifts`の名前は`show`で、ダンプは`dumpName`で出力されるため)。rc2自身では、残った定義のうち1,281個が捕捉を持つクロージャとして実行時に構築され、1,369個が静的な定数クロージャで、93個が直接呼び出しに畳み込まれた。これらの本体のうち、1,499個がアロケーションを行い、621個が定数を返し、693個はそれ以外の処理をする。

`{csegen:17}`のサンクは静的な定数を返す。`{csegen:189}`のサンクは、強制評価のたびに`Foldable`レコードと3つのクロージャを作り直す。メモ化の効果が出るのは後者の形である。

## Chezの場合

すべてのSchemeバックエンドは`LazyReason`を無視する。

- デフォルト: `Delay e`は`(lambda () e)`、`Force t`は`(t)`になる。メモ化はされない。
- 本体が`Delay e`である、トップレベルの引数0個の定義は、Schemeの`(delay e)`になる。その定義の呼び出しを`Force`したものは`(force ...)`になり、どちらも1回だけ評価される。
- `--directive lazy=weakMemo`は、すべての`Delay`をweak pairでメモ化する。キャッシュされた値はGCで回収されることがあり、回収されると再計算される。

rc2は`Lazy`と`Inf`を区別せず、どちらもメモ化する。参照カウント方式にはweak参照がない。セルとその値は、セルを参照するものがなくなった時点で解放される。ストリームの評価済みの先頭部分は、call-by-needと同じく、その先頭を保持しているものがある間だけ生き続ける。

## 計測

rc2自身をコンパイルしたときの、最終的なIR(`--directive dumprcexpr`)での数を示す。

- 遅延セルがまったくなかった時点(`Delay`/`Force`をただのラムダとその適用にコンパイルしていた): 定義19,797個、クロージャ適用3,993個(ダンプの`apply`)。
- 段階1(すべての`Delay`にセルを付ける): 定義21,546個、`delay`が3,765個、`force`が5,073個。
- 段階2(定数・ラムダ・アトムのコンストラクタの`Delay`はセルを持たず、`LazyCaf`と`LazyFold`を適用): 定義19,616個、`delay`が1,731個、`force`が202個、クロージャ適用3,454個。

idris2-lspを段階2でコンパイルすると、定義18,048個、`delay`が1,676個、`force`が227個になる。

## ランタイム上の表現

遅延セルは、専用のタグ`IDRIS2RC2_TAG_LAZY`を持つ`IDRIS2RC2_IORef`である。これにより、`Lazy (IORef a)`をセルと取り違えることも、その逆も起きない。セルの中身はIORefの`v`と同じワードにあり、構造体のアトミックなメンバ`av`(`v`とのunion)を通して読み書きする。セルは`av`だけで、IORefは`v`だけで読み書きする。

- **未評価**: `v`は、サンク関数とその捕捉に対する飽和したクロージャ(`filled == arity`)である。
- **評価済み**: `v`は値そのものである。値が飽和したクロージャになることはない。`idris2rc2_trampoline`は`filled < arity`になるまでディスパッチを続けるので、`v`にある飽和したクロージャは、必ず「まだ評価されていない」ことを意味する。
- 捕捉のないサンクは、引数0個のクロージャである。`idris2rc2_dispatchFn`はすでにアリティ0を扱える。
- 値を格納すると、`header.reserved`が1になる。セルが評価済みかどうかは、`v`を見ずにこのフラグで決める。未評価の`v`は、別のスレッドがいつでも解放しうるクロージャだからである。セルの大きさはIORefと同じままである。

## `Force`

`idris2rc2_force(v)`は`v`を借用する。処理は次の3つの場合に分かれる。

1. セルでない(タグが`LAZY`でない)場合: `v`自身をdupして返す。遅延された値がただの値であってよいのは、このためである(後述)。
2. 評価済みのセルの場合(`reserved`のacquire loadが1を読む): ロックを取らずに、`v`をdupして返す。値は1回だけ書き込まれ、セルが生きている間は置き換えられない。
3. `v`が飽和したクロージャであるセルの場合は、次の順に処理する。
   - このセルがこのスレッドの評価中セルのスタックにあれば、stderrに「idris2rc2: a lazy value forces itself」と出力し、終了ステータス1で止まる。スタックを探索するのは、評価に入る直前のここだけである。評価そのものの方がはるかにコストが高いので、この探索は問題にならない。
   - そうでなければ、ロックを取って`v`を読み直す。まだクロージャであれば、クロージャ自身をdupする(捕捉だけではない。ロックを手放した後は、別のスレッドが結果を格納して、セルが持つクロージャへの参照をいつ落としてもおかしくないため)。ロックを解放し、このスレッドのスタックにセルを積んで、dupした参照を通して評価する。具体的には、捕捉をdupして関数を呼び、トランポリンを回し、最後にその参照をdropする。共有されたクロージャに対する`idris2rc2_dispatchWithExtra`と同じ手順である。クロージャはセルに残るので、別のスレッドが同時に評価することもできる。
   - スタックからセルを降ろし、ロックを取る。`reserved`がまだ0なら、結果を1回dupして格納する。これでセルと呼び出し元がそれぞれ1つずつ参照を所有する。続けて`reserved`を立て(release store)、セルが持つクロージャへの参照をdropする。別のスレッドが先に格納していた場合は、今回の結果をdropし、格納済みの値をdupして返す。2つのスレッドが同時に強制評価すると、サンクが2回以上走ることがあるが、これは許容する。
   - 評価をロックの下で行うことは決してない。別のセルや、このセル自身を強制評価するサンクがあると、デッドロックするからである。

## `Delay`

- **すでに値である場合**: 定数、ラムダ、あるいはフィールドがすべて変数か定数であるコンストラクタの`Delay`は、セルを作らずにその値に置き換える。`Force`はそれをそのまま返す(上の場合1)。これらは評価しても何も計算しない。フィールドに呼び出しや`force`を含むコンストラクタは、遅延されたまま残す。早く評価すると、無限の構造で発散するおそれがあるためである。
- **変数**は遅延されたまま残す。変数自身が遅延値(`Lazy (Lazy a)`)であることがあり、その場合`Force`は強制評価せず、そのまま返さなければならない。
- **それ以外**はすべて、飽和したクロージャを持つセルを確保する。
- **本体が`Delay`である、トップレベルの引数0個の定義**(218個/214個)にはセルを付けない。非定数のCAFはすでにすべてメモ化されている(`RMemoize`、`RC2.idr`の`insertMemoize`、`caf-memoization.md`)ので、セルを付けると同じ値を二重にメモ化してしまうためである。

  この書き換えは`Compiler.RC2.LazyCaf`(`applyLazyCaf`)が、リフトの前にプログラム全体に対して一度だけ行う。呼び出しは`RC2.idr`の`compileExpr`にある。モジュールごとの処理にしないのは、モジュール単位だと、同じ定義を指す別のモジュールの参照が実行時点では見えないからである。`NamedCExp`に対する書き換えは次のとおり。

  - `x = Delay e`は`x = e`になる(メモ化されるか、定数に畳み込まれる)。
  - `Force (x [])`は`x []`になる。
  - それ以外の`x []`への参照(強制評価されずに渡される遅延値)は、`Delay (x [])`になる。これにより、何かが強制評価するまで`e`は評価されない。この`Delay`はメモ化済みのCAFを呼ぶだけであり、`x`が定数に畳み込まれる場合はただの値になる。
- **捕捉のないサンク**は引数0個の定義だが、CAFとしてメモ化することはない。`insertMemoize`は、`LiftInfo`が`Delay`からのリフトと記録している名前をすべて飛ばす。メモ化はセルが行う。つまり、セルごとに1回、セルと一緒に解放される。CAFにすると、その`Delay`から作られたすべてのセルで1つの値を共有し、それを実行終了まで保持することになってしまう。

## 所有権

- **セル。** `RForce`はセルを借用する。強制評価がセルの最後の使用である場合は、呼び出しの後にセルをdropする(`ROp`と同じ`postDrop`)。これでセルが解放されるなら、セルが持つ値への参照も一緒に解放される。呼び出し元自身の参照は残る。
- **値。** 強制評価の後は、セルと呼び出し元がそれぞれ1つずつ参照を所有する。したがって、強制評価された値は、セルが生きている間は共有される。強制評価がセルの最後の使用で、セルが解放された場合を除き、その値へのコンストラクタのその場での再利用は失敗する。ただし、一意性は実行時に検査されるので、失われるのは速度だけである(TODO.mdの「skip reuse analysis on values whose cell outlives the force」を参照)。
- **クロージャ。** 結果が格納されるまで、クロージャはセルが所有する。評価中のスレッドは、(ロックの下で取得した)自分自身の参照を持っているので、評価の途中でセルがクロージャへの参照をdropしても問題ない。
- **末尾呼び出し。** `idris2rc2_force`は、サンクが返った後でその結果を格納する必要がある。このため`Emit.idr`は、`RForce`を通常の末尾呼び出しが使うクロージャディスパッチのトランポリン経由にはせず、`idris2rc2_force(v)`というただのC呼び出しにコンパイルする。`Force`が末尾呼び出しになることはない。次のサンクを強制評価するサンクが長く連なっていると、1つ連なるごとにCスタックが1フレームずつ伸びる。これは許容する。
- **解放。** セルは、コンストラクタのフィールドと同じ方法で解体される(`idris2rc2_teardown`のループで遅延される)。そのため、強制評価済みの長いストリームを解放するときも、要素ごとに再帰することはない。
- **循環。** 値が自分自身のセルを指すセルは、参照カウントでは解放できない。サンクの捕捉は、そのセルより先に存在しており、Idrisには再帰的な`let`もない。したがって、そのような循環が生じうるのはトップレベルの定義を通した場合に限られ、これはもともと解放されない。自分自身のセルを強制評価するサンクは、プログラムを停止させる(`Force`の3)。

## IR

- `RDelay fc lr thunk captures`は`captures`を消費して、セルを構築する。`RForce fc lr v`は`v`を借用する。どちらもダンプに出力され(`delay`、`force`)、`Language.RCExpr.Parser`(`libs/rc2base`)が読み戻す。
- リフト: 本体がまだ値でない`Delay`は、自身の束縛パラメータなしで、`RC.idr`の`lift`を直接呼ぶ(origin は`FromDelay lr`)。したがって生成されるサンクが取るのは捕捉だけであり、中にあるラムダとは決して統合されない。本体がラムダである`Delay`は、上の「すでに値である場合」の1つにあたる。これは、そのラムダを単独でリフトしたときとまったく同じ方法でリフトされる。`lambda`を通り、`lambda`がラムダ自身のパラメータを蓄積してから`lift`を呼ぶ(origin は`FromLambda`)。それがかつて`Delay`であったことを示すものは、`LiftInfo`には何も残らない。
- `children`/`mapChildren`/`traverseChildren`(`RCExp.idr`)から見ると、`RDelay`/`RForce`は葉であり、再帰して降りていく`RCExp`の子がない。したがって、木をこの3つだけでたどるパスには、専用の節は要らない。

  ただし、`captures`と`v`はローカル変数であり、ローカル変数の読み取り、名前の付け替え、置換を行う処理には、葉であっても明示的な節が要る。`RCExp.idr`の`freeLocalsR`、`countUsesR`、`mentionedLocalsAcc`、`directReads`と、`ConstFold`自身の`foldConst`の置換が、それぞれ節を持っている。包括的な節を持つパスでこれらのどれかを書き忘れると、`RDelay`/`RForce`が気づかれないまま飛ばされる。これは、`caf-memoization.md`の「制限」の節が`RMemoize`について記載している、気づかないうちに取りこぼす形と同じである。

## `ConstFold`

`Compiler.RC2.ConstFold.foldConst`自身は、`Delay`に対する`Force`を畳み込まない。`RDelay`/`RForce`の節は、`captures`/`v`を、`resolveLocal`がすでに知っているもの(エイリアスや畳み込み済みの定数)に解決するだけで、他のオペランドと扱いは変わらない。

`Force`と`Delay`の組を畳み込むのは`Compiler.RC2.LazyFold`の仕事である。これは、Earlyインライン展開の直後に走る(`RC2.idr`の`rc2: Lazy fold`で、`--timing 2`がこのパスについて出力する行)。インライン展開によって、`Delay`とそれに対する1回の`Force`が同じ関数に入る機会があった後、という位置である。

`foldSingleForce`は、`let v = delay thunk caps`であり、本体が`v`を`Force`のオペランドとしてちょうど1回だけ、ほかのどこにも使わないものを見つけ、`let`と本体の全体を、`caps`に対する`thunk`の直接呼び出しに置き換える。セルは一度も構築されない。このパスはRCアノテーションの前(まだ乱す所有権がない)、およびループ変換の前に走る。ループ変換の後だと、ループの中の`Force`が、1つの束縛に対して何度も実行されるおそれがあるためである。

## 既知の制限

- 遅延されたまま残る値(上の`Delay`の「すでに値である場合」でも、`LazyFold`でも畳み込まれなかったもの)は、アロケーションが1回ではなく2回かかる。セルと、最初に強制評価されるまでそのセルが保持するクロージャである。
- `idris2rc2_force`の最初の検査は「セルでない」である(上の「`Force`」を参照)。そのため、`Delay`を通して構築されていない値(`believe_me`された`Lazy`/`Inf`や、どちらかの型を含む`%foreign`シグネチャ)を強制評価しても、クラッシュせず、そのまま返す。upstreamの`base`/`contrib`にあるそうした値のすべてが、このように`force`に渡して安全かどうかは、確認していない。

## 既知のupstreamの挙動

Idris2のコンパイラ自身が、rc2のパイプラインに入る前に、いくつかの箇所で`Lazy`を消去している。確認できたのは2つの形で、型引数の中にネストした`Lazy`(例: `IORef (Lazy Int)`)と、`main`に直接束縛された一度きりの`delay`である。どちらも、`Delay`/`Force`ノードはrc2にまったく届かないので、本書の内容は当てはまらない。消去を行うupstreamのパスが具体的にどれかは、それ以上追っていない。

## 検証

`rc2/tests/Test125LazyMemo`は次を確認する。

- 共有された束縛を通して2回強制評価された値の副作用は、1回しか実行されない。
- `Inf`のストリームの各テールは、同じストリームに対する別々の2回の`take`を通して、それぞれ1回しか評価されない。
- 強制評価済みの長いストリーム(`iterate`/`index`)は、要素ごとに再帰することなく解体される。
- 複数のスレッド(`forkJoin`)が同じセルを同時に強制評価しても、すべてが同じ値を読み戻す(競合の下での一貫性を検査するものであり、サンクが何回走ったかを数えるものではない。テストは自身の副作用が何回発火したかを読まない)。

`rc2/tests/Test126LazySelfForce`は、評価に自分自身を必要とする値が停止することを確認する。この値のトップレベルの`Delay`はCAFになる(`LazyCaf`)ので、循環を見つけて「a top-level value depends on itself」で停止させるのは、CAFメモ化である(caf-memoization.md)。セルが自分自身を強制評価した場合は「a lazy value forces itself」で停止する(上の「`Force`」を参照)。ただしLazyCafがあると、自己参照が生じうるのはトップレベルの定義を通した場合だけなので、これに到達するテストプログラムはない。

`rc2/tests/Test122LiftOrigin`の`check.sh`は、リフトを確認する。値でない`Delay`のサンクは自身の捕捉だけを取る(`.lifts`のダンプで`delay Lazy`/`delay Inf`、`params 0`)。ラムダの`Delay`は、そのラムダとしてリフトされ、サンクもセルも作られない(同じダンプで、`delay`ではなく`lambda`)。

すべてのテストが通り、`bench.sh`でも、この作業による性能の後退は見られない。
