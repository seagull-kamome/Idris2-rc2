2つ以上の関数にまたがる相互末尾再帰、そしてその両方の上に積み重ねた
ネイティブ表現への昇格について。将来のセッション(あるいは将来の
自分)が、設計を再導出したり、既に発見・修正済みのバグを再発見したり

## この最適化群と、それぞれが存在する理由

Idris2自身のコンパイル済みIRは*あらゆる*呼び出しを一様に表現する:
クロージャを構築し、それをトランポリンで駆動する。再帰関数にとって
これは、たとえ末尾再帰関数の「次の反復」が意味的には「自分の
パラメータを再代入して先頭へジャンプする」以上の何物でもないとして
も、反復のたびにクロージャを1つ確保し、その引数スロットを埋め、
汎用のディスパッチループを経由して戻ることを意味する。

これを攻略する2つの重ねられた最適化があり、構築された順に:

1. **末尾呼び出し→`goto`**(本書の主題): 自己再帰の末尾呼び出し、
   または2つ以上の関数が相互に末尾呼び出しし合うサイクル内の末尾
   呼び出しは、Cのパラメータ変数の再代入と、関数自身の先頭への
   単純な`goto`にコンパイルされる -- 反復あたり、クロージャ確保も
   トランポリンのディスパッチも一切ない。
2. **ループ内蓄積パラメータのネイティブ表現化**((1)の直接の上に
   構築される。後述の独自の節を参照): ループ本体の*どこか*で
   ネイティブコンテキストの数値オペランドとして読まれるループ
   パラメータは、`goto`のたびに新しいヒープ値へ再box化され、次の
   反復の先頭で即座に再unbox化される代わりに、ループ突入時に
   ちょうど一度だけunbox化される。

どちらも純粋なコードの形/表現の変更であり -- どちらも独自の所有権
判断を一切下さない。両方とも、変換前の元の呼び出しについて
`Compiler.RC2.RC`の`annotate`(Phase 2)が既に決定したことをそのまま
再利用する。この再利用こそが、両パスをそれぞれ小さく保っている理由:
所有権を*正しく*決めるという仕事は既に一度、より上流で解決済みで
あり、ここでの仕事は純粋に「呼び出しの形を変えながら、それを乱さ
ない」ことだけである。

## パイプライン上の位置

```
Lifted (Compiler.LambdaLift)
  -> Compiler.RC2.RC.normalize      (Phase 1: ANF風、ネイティブ型推論)
  -> Compiler.RC2.RC.annotate       (Phase 2: 所有権 -- RDup/RDrop/RFree)
  -> Compiler.RC2.Reuse             (コンストラクタのin-place再利用)
  -> Compiler.RC2.MutualLoop        (相互末尾再帰 -> 1つの合成関数へ)
  -> Compiler.RC2.Loop              (自己末尾呼び出し、MutualLoop自身の
                                      合成関数も含む -> RLoop/RLoopContinue、
                                      加えてネイティブshadow昇格)
  -> Compiler.RC2.Emit              (純粋に機械的なRCExp -> C)
```

`MutualLoop`は`Loop`の*後*ではなく*前*に実行される。この順序は
`MutualLoop`の設計全体の核心である(下記のその自身の節参照): `Loop`
が`MutualLoop`によってマージされた関数を初めて目にする時点で、その
内部遷移(メンバー内・メンバー間問わず)は既に全て*自分自身*への
通常の末尾呼び出しになっている -- `Loop`から見れば、手書きの
自己再帰関数と見分けがつかない。`MutualLoop`自身の出力を変換する
ためだけに`Loop`側で必要となった特別扱いはゼロだった。これは偶然
ではなく、`MutualLoop`がまさにその性質を生み出すよう設計されている
からである。

## IRの形: `RLoop` / `RLoopContinue`

```idris
RLoop         : FC -> (loopParams : List (Int, Rep)) -> (initial : List RCLocal) -> RCExp -> RCExp
RLoopContinue : FC -> List RCLocal -> RCExp
```

`RLoop`は末尾再帰ループ全体をラップする: `loopParams`はこのループ
自身が保持するローカルであり、それぞれが*独自の*`Rep`を持つ
(*外側の関数*自身のトップレベルパラメータが使う表現 -- 外部呼び出し
規約により常にBoxed -- とは独立している)。`initial`が各パラメータの
開始値を与える(同じ順序、同じ長さ)。ループそのものが初めて実行
される前に、*外側の*スコープで一度だけ評価される。`body`はその後
繰り返し評価される -- そこから末尾位置で到達可能な`RLoopContinue`が
次の反復のための新しい値を与えて先頭へジャンプし、それ以外の末尾
位置の値はループを抜けて`RLoop`ノード自身の結果になる。
`Compiler.RC2.Loop`のみが生成する。`RC.idr`自身のPhase 1/2はどちらも
一切構築しない。

### なぜこの形なのか、もっと単純な形ではだめだったのか

以前の設計の反復では、`MkRCFun`にフラットな`isLoop : Bool`フィールド
を持たせ、変換された各呼び出しの代わりに散在する`RSelfTailCall`
ノードを置く方式だった -- つまり「これがループである」という明示的な
境界は一切なく、関数自身へのフラグと、各ジャンプバック箇所の
マーカーだけだった。この設計で表現できるのは「関数本体全体はBoxed
で、一部の末尾呼び出しが`goto`になる」ということまでで、「*この特定
のループパラメータ*は、関数自身の呼び出し規約とは別個の独自の表現を
持つ」とは言いようがなかった -- なぜなら外側の関数から切り離された
「ループ」というものをそれ自身のアイデンティティを持つものとして
扱うIRレベルの概念が存在しなかったから。

ネイティブshadow昇格(次節)にはまさにそれが必要になる: ループ内
蓄積パラメータの*ネイティブ*表現は、制御がループ内にとどまっている
間だけ有効である -- 関数自身の入口(外部からの呼び出し)と出口(ループ
自身の最終的な値)は、どちらも依然として通常のBoxed値を必要とする。
`RLoop`/`RLoopContinue`に落ち着く前に、これを表現する方法として
2つの設計が検討された:

1. **関数入口で一度だけunboxし、以降ネイティブのまま保持し、shadow化
   された変数のIDを使われている場所すべてでリネームする。** 却下:
   `RCLoc p -> RCLoc shadowId`を関数本体全体にわたって何も考えずに
   置換すると、それ以外は何も触らない限り、`annotate`が`p`について
   既に計算していた*既存の*所有権注釈(その自身の`postDrop`エントリ、
   独立した`RDrop`/`RDup`ノード -- どれも「複数の*Boxed*コンテキスト
   の箇所から読まれる値」を前提にサイズと配置が決まっている。置換
   だけではこの前提は直らない)を破壊してしまう -- しかもそれは
   サイレントに起きる。型検査は通り、しばしばそのまま動きさえする
   コードが生成されるが、特定の入力の下ではリークするか二重解放
   する。(これは仮説上のリスクではなく、実際に発現したリスク
   だった -- 下記「発見したバグ」参照: 本書が記述する、この書き換え
   のもっと*狭く*、きちんとスコープ限定された版でさえ、正しく行う
   ためには専用の所有権除去ステップが必要だった。)
2. **box/unboxを`ROp`のような通常のオペランド消費/生成ノードとして
   明示的なIRノードにし、Phase 2の既存の`annotate`機構に、他の
   あらゆるものと同じ方法でその所有権を決めさせる。** これは
   アーキテクチャ的に魅力的である(新しい所有権ロジックがどこにも
   一切不要)が、この決定を`annotate`が実行される*前*、つまりPhase 1
   の最中に下す必要がある -- そしてPhase 1には「これはループである」
   という概念が一切ない(ループ検出は末尾位置の構造的な性質であり、
   ANF正規化とは意図的に切り離された、*後の*専用パスによって発見
   される)。これを正しく行うにはループ検出そのものをPhase 1へ
   畳み込む必要があり、他の作業よりはるかに大きなリストラクチャリング
   になるため、この反復のスコープ外として棚上げされた
   (`TODO.md`の「デュアル呼び出し規約」参照 -- 「ネイティブ表現が
   境界を越えられるようにする」の一般版(任意の呼び出し境界)は、
   まさにこの種の理由により依然として未実装のまま)。

`RLoop`/`RLoopContinue`の分割は、どちらのコストも払うことなくこれを
解決する: 「一度だけ実行される」(`initial`。*外側の*スコープで
評価され、依然として元のBoxedなパラメータについて語っている)と
「繰り返す」(`body`。ループ自身のパラメータについて語っており、
それぞれ独自の`Rep`を持つ)が、IR自体の中で構造的に異なる2つの位置
になる。これにより後段のパス(本書の対象そのもの)は、`annotate`が
*既に*実行し終えた*後*に昇格の決定を下すことができ、正しさは、
Phase 1にループについて何も知らせる必要のない、よくスコープ限定
された機械的な2ステップ -- 木全体のリネームと、狙いを定めた所有権
の除去 -- に帰着する。この2ステップが正確にどう機能し、なぜそれで
十分なのかは下記「ネイティブshadow昇格」参照。

## `Compiler.RC2.Loop`: 自己末尾呼び出しの変換

### `mapTailAppNames` -- 共有される末尾位置の走査

```idris
mapTailAppNames : (FC -> Name -> List RCLocal -> Maybe RCExp) -> RCExp -> (Bool, RCExp)
```

`f fc n args`が`Just e'`を返すような、末尾位置にある、遅延でない
`RAppName fc Nothing n args`の葉すべてを`e'`へ書き換える。ここでの
「末尾位置」は、`Compiler.RC2.Emit`自身の`TailPositionStatus`スレッド
がCへの下ろし込みの際に既に訪れている構造的な集合と*まったく同じ*
である: `RLet`の本体、`RDup`/`RDrop`/`RFree`/`RReleaseReuse`/
`RReuseOffer`の継続、`RCmpCase`の2つの分岐、`RConCase`/`RConstCase`
の枝とデフォルト。オペランドの位置(`RCon`の引数、`ROp`のオペランド、
`RApp`自身の関数部/引数部、`RAppName`自身の引数、...)は一切訪れ
ない -- そこにある呼び出しは末尾位置ではなく、`f`が何を言おうと
通常の呼び出し規約をそのまま通らなければならない。

`Loop.idr`に一度だけ定義され、`Compiler.RC2.Loop`自身(`f`は外側の
関数自身の名前だけに一致する)と`Compiler.RC2.MutualLoop`(`f`は相互
再帰グループ全体のどのメンバーにも一致する)で共有される。この共有は
単なる重複排除ではなく、正しさの要件そのものである: もし2つのパス
自身の「末尾位置」の捉え方が食い違えば、一方のパスが、もう一方の
パスの`TailPositionStatus`駆動の発行ロジックが末尾位置だと同意
しないような呼び出しを変換(あるいはスキップ)してしまい、サイレント
に誤コンパイルする恐れがある。

### `applyLoop` -- ラップするかどうかの決定

```idris
applyLoop : Name -> RCDef -> RCDef
```

定義自身の名前(`RC.idr`はPhase 1/2を通じて定義自身の名前を一切
運ばないので、`RC2.idr`の`toRCDefs`が明示的にスレッドする)を受け
取り: `mapTailAppNames`を実行し、`self`をターゲットとする呼び出し
だけを`RLoopContinue fc args'`へ置換する。何も見つからなければ本体は
変更なしで素通りする。1つでも見つかれば、(書き換え済みの)本体
全体が1つの`RLoop`でラップされる -- そしてここが、次に説明する
ネイティブshadow昇格が起きる場所でもある。

スコープは`mapTailAppNames`自身の制限と同じ: 自己のみ(相互再帰は
`MutualLoop`の仕事、下記参照)、`LazyReason`下の呼び出しは除外
(保守的に、それ以上は調査しない)。*ラップすること自体*の所有権は
完全に不変である -- `annotate`は、このパスが実行される前に既に
`RAppName`自身の引数について正しいdup/move挙動を、他の関数への
呼び出しの場合とまったく同様に決定済みである。呼び出しの*形*を
変えることは、そのオペランドに何が起きるべきかを変えない。
`RAppName`をラップする`RDup`/`RDrop`/`RFree`/`RReleaseReuse`は
そのまま残される。置き換えられるのは末端の`RAppName`ノードだけ。

### ネイティブshadow昇格

`applyLoop`の後半: 関数自身のトップレベルパラメータそれぞれについて、
`RBoxed`から新しいネイティブshadowへ昇格させる価値があるかを判断し、
あればそれに応じてループ本体を書き換える。

**適格性(`nativeArgType`/`nativeArgTypes`)**: あるパラメータ`p`は、
(既に末尾呼び出しの書き換えが済んだ)本体が、それを*一貫してただ
1つの`PrimType`で*ネイティブコンテキストのオペランドとして読んで
いれば適格である -- 具体的には、融合された`RCmpCase`のオペランド
としてか(文脈によらず常にネイティブ)、あるいは自身の`Rep`が
`RNative`/`RInlineNative`である`RLet`束縛の`ROp`のオペランドとして
(Boxedな*結果*を返す`ROp`自身のオペランドも、`emitRC`自身の`ROp`
ケース経由でBoxedとして読まれる -- これらはカウントされない)。この
2つが、`Compiler.RC2.Emit`が`rcVarToBoxedC`ではなく`rcVarToNativeC`
経由でオペランドを読む*唯一*の場所である。適格性の走査は、Emitが
実際に行っていることと決して食い違わないよう、意図的にこの2つの
言葉だけで定義されている。`nativeArgTypes`は(タイル位置だけでなく)
*木全体*を歩いて、そのような型すべてを`SortedSet`へ集める --
オペランドはどこにでも出現しうるため。`nativeArgType`は*単一元*の
結果のみを受理する(一度もネイティブに読まれない、または食い違う
型で読まれる、どちらの場合もパラメータは保守的に`RBoxed`のまま)。

`opNativeUsesThrough`が存在する理由は、`RLet`自身の`value`が常に
裸の`ROp`とは限らないから -- `annotate`(Phase 2)は、複数回使われる
オペランドの値を、先頭に`RDup`(あるいはそれほど多くないが`RDrop`/
`RFree`/`RReleaseReuse`)でラップすることを日常的に行う。これは
`Emit.idr`自身の`emitNativeValue`が実際の演算にたどり着く前に透過
しなければならないのとまったく同じ形である。**これは開発中に実際に
起きたバグであり、仮説ではない**: 適格性走査の初期バージョンは
`value`を`ROp`へ直接パターンマッチしており、自分自身の算術演算の
使用より前に`dup`されていた(つまり1回より多く使われる)パラメータを
すべて見逃していた -- どう診断されたかは下記「発見したバグ」参照。

**書き換え(適格な`(p, ty)`ペアの集合が分かったら)**:

1. `assignShadowIds`が、適格なパラメータごとに1つずつ新規IDを発行
   する。開始値は、この定義のどこかで既に使われている最大のID
   (`args`に加え、書き換え後の本体中のすべての`RLet`/`RConAlt`束縛
   ID、`collectBoundIds`経由)より1大きい値 -- `Core`でスレッドされる
   カウンタではなく単純な算術的最大値である。このパス全体が、1つの
   定義だけを対象にした純粋関数のままだから(`MutualLoop`自身の
   `FreshId`と対照的 -- あちらはプログラム全体をまたいで本当に
   スレッドされる必要がある)。
2. `renameRCExp`(下記参照)が、昇格された各パラメータの元のIDの
   出現すべてを、対応する新規shadow IDへ、本体全体にわたって一様に
   置換する -- ネイティブコンテキストの読み取りの中だけでなく
   **すべての**出現。Boxedコンテキストでの使用(コンストラクタの
   フィールド、呼び出しの引数、ループ自身の最終的な戻り値)も
   リダイレクトされ、それは正しい: ネイティブRepのローカルに対する
   `rcVarToBoxedC`はその場で新しくbox化するので、リダイレクトされた
   Boxedコンテキストの読み取りも正しい*値*を生成する。ただし元の
   オブジェクトのアイデンティティを共有するのではなく新規確保
   経由になる(現実的だが許容できるトレードオフであり、正しさの
   問題ではない)。
3. `stripOwnership`(下記参照)が、`annotate`が*元の*パラメータに
   ついて計算していた、今や古くなった所有権の帳簿付けを、*shadow*
   ID(リネーム後)をキーにして除去する。
4. `loopParams`は関数自身の`args`をマップして構築される: 適格な
   パラメータは`(shadowId, RNative ty)`を寄与する。それ以外の
   パラメータは`(p, RBoxed)`を変更なしで寄与する(自身のIDをそのまま
   使う -- これにより`Compiler.RC2.Emit`の`declareLoopParam`はそれを
   宣言することすら完全にスキップできる、下記参照)。`initial`は
   どちらにせよ*常に*`map RCLoc args`である -- どのループパラメータの
   開始値も、真に元の、常にBoxedなパラメータを読むことから来る。
   `Compiler.RC2.Emit`の`declareLoopParam`が(変更のない`RBoxed`
   パラメータについてはスキップされる)unbox変換を行う。

#### `renameRCExp` -- 木全体の置換

```idris
public export
Renaming : Type
Renaming = SortedMap Int Int

export
renameRCExp : Renaming -> RCExp -> RCExp
```

木の中の*あらゆる*`RCLocal`の出現、あらゆる束縛IDに対する、純粋で
意味を保存する置換(`mapTailAppNames`とは異なり、末尾位置に限定
されない -- 束縛IDや読み取りはどこにでも出現しうる)。`RDup`/
`RDrop`/`RFree`/`RReleaseReuse`/再利用関連のノードを追加も削除も
一切しない、それらの(そしてあらゆる読み取りの)参照先をリラベルする
だけ -- 既存の所有権ノードは、自身のターゲットとともに新しいIDへ
そのまま移動する。`Renaming`が`public export`なのは、別のモジュール
の呼び出し元が、不透明な型の単一化失敗を起こすことなく、その実際の
基底型に対して直接`SortedMap Int Int`の値を書けるようにするため
(このポイント -- `export`だけでは不十分だった -- が正確にどんな
コンパイルエラーを生んだかは下記「発見したバグ」参照)。

元々は`Compiler.RC2.MutualLoop`(自身のメンバーごとのIDリネームで
これを必要とする、下記参照)にプライベートだったものを、この
モジュール自身のネイティブshadow書き換えと`MutualLoop`の両方が
手で同期させた2つのコピーではなく1つの定義を共有できるよう、
ここへ移設した。`MutualLoop.idr`は(`mapTailAppNames`のために)既に
`Compiler.RC2.Loop`をimportしていたので、これは新しいモジュール
依存を一切導入していない -- 既に存在していた辺に沿って既存のコードを
移動させただけである。

`collectBoundIds : RCExp -> List Int`も同じ理由でそのすぐ隣に
置かれている(`MutualLoop`自身の`buildGroup`は「ある本体でローカルに
束縛されているすべてのID」を、あるメンバー自身のトップレベル
パラメータとは別に、どの内部IDに新しい名前が必要かを知るために
必要とする。このモジュール自身の`applyLoop`は、既にスコープにある
ものと衝突しえない新規shadow IDの開始点を選ぶために必要とする)。

#### `stripOwnership` -- 昇格されたパラメータの古い帳簿付けを除去する

```idris
stripOwnership : SortedSet Int -> RCExp -> RCExp
```

`ids`(*shadow*ID、リネーム後 -- 元のパラメータIDではない。このパス
が実行される時点で、値を読むあらゆる出現は既にshadowへリダイレクト
済みだから)のいずれかを名指しするあらゆる`RDup`/`RDrop`/`RFree`の
対象、およびあらゆる`ROp`/`RCmpCase`の`postDrop`エントリを除去する。
ネイティブ値は参照カウントの帳簿付けを一切必要としない -- 生のCの
スカラーには`idris2rc2_dup`/`idris2rc2_drop`/`idris2rc2_free`に渡す
参照カウントヘッダなど存在しないので、`annotate`が元々*元の*、依然
Boxedだったパラメータ自身のdup/drop生存期間について決めていたこと
(ループ本体中の複数のBoxedコンテキストの箇所から読まれていた頃の
決定)は、もはや適用されず、単に残しておくのではなく完全に除去
しなければならない。

**なぜこれが安全か**: 昇格されたパラメータの*他の*あらゆる出現が、
これより前に実行される付随の`renameRCExp`呼び出しによって既に
そのshadowへリダイレクトされているから、まさにその一点による。除去
されようとしているdropをまだ必要としている、生き残ったBoxedな読み
取りは木のどこにも存在しない -- もし存在すればこのステップは不健全
になる。この順序(先にリネーム、次に除去、両方とも同じshadow ID
集合をキーにする)こそが、この2つのステップが組み合わさって正しい
全体になる理由である。

**なぜ`RCon`自身のフィールド引数、`RConCase`/`RConstCase`のスクル
ティニー、`RReuseOffer`自身の`sc`/`dupOnShared`が意図的に触られない
のか**(`renameRCExp`はそれらの中のIDも他の場所と同様に置換する --
それらの*所有権*の帳簿付けだけが、この関数の仕事とは別の関心事): 
ネイティブshadow化に適格なパラメータ(`ROp`/`RCmpCase`のオペランド、
つまり数値型)と、コンストラクタとしてパターンマッチまたは再利用
チェックされるパラメータは、*Idrisの型レベルで*互いに排他的である
-- 単一のIdrisレベルの値が、ネイティブ対応のスカラーであると同時に
コンストラクタディスパッチの対象となるADTでもあることはできない
-- なのでshadow化されたIDがそもそもそれらのいずれかになることは
ない。そしてshadow化されたIDがコンストラクタのフィールドへ格納
される場合、`rcVarToBoxedC`によってその場で新しくbox化されるだけで
正しく、除去すべき自身の帳簿付けノードも存在しない。

とはいえ`RConstCase`のスクルティニーはもう一度見直す価値がある。
なぜなら(コンストラクタ/ADT形状しか照合しない`RConCase`とは異なり)
これは実際にネイティブ対応の数値型でありうるから -- ループカウンタ
をリテラルと照合する(`case n of 0 => ...`)のはまさにこの形であり、
まさに`BenchLoop.idr`自身の`sumTo`が突き当たるケースである。
`stripOwnership`はこれを正しく手つかずのままにする(スクルティニーの
位置自体に除去すべき所有権ノードは付いていない)が、これがまさに
実際の発行側のバグを生んだ隙間でもある -- 下記「発見したバグ」参照。

## `Compiler.RC2.MutualLoop`: 相互末尾再帰

### `RLoop`/`RLoopContinue`だけでは解決しない問題

`Compiler.RC2.Loop`が認識するのは*外側の関数自身*をターゲットと
する末尾呼び出しだけである。サイクルの中で互いに末尾呼び出しし合う
2つ(以上)の関数 -- 教科書的な例が`isEven`/`isOdd` -- には、そのような
自己呼び出しはどこにもない。各々の末尾呼び出しは*別の*関数をターゲット
にする。`RLoop`/`RLoopContinue`を何とか複数の名前付き関数にまたがる
よう拡張することも検討されたが、根本的にはコード生成時の変換に
すぎないものに対して、コアIRの形をあまりに大きく変更することになる
として見送られた。

### 設計: サイクルを1つの関数へマージする

新しいIRを発明する代わりに、このパスは互いに末尾呼び出しし合う
`>= 2`個の関数の各グループについて、小さな整数タグで分岐する単純な
`RConCase`を本体に持つ、1つの新しい合成関数を合成する -- 元のグループ
メンバーごとに1つの枝 -- そしてグループ内の*あらゆる*末尾呼び出し
(自己・メンバー間問わず)を、対象の持つタグと(パディングされた)引数を
添えて、その合成関数自身への通常の末尾呼び出しへ書き換える。合成
関数自身の視点からは、これらのどれもが今や単なる自己末尾呼び出しに
過ぎない -- (直後に実行される)`Compiler.RC2.Loop`が既に`goto`へ変換
する方法を知っている、まさにその形である。これこそが`MutualLoop`が
`Loop`の後ではなく*前*に、あるいはその一部として統合された形では
なく実行される理由のすべてである: `Loop`は合成された相互再帰も扱う
ために**まったく**新しいロジックを必要としない。なぜなら`Loop`が
合成関数を目にする時点で、`Loop`が解いている問題は、それが既に解いて
いるものとまったく同一だから。

各元のメンバー自身のトップレベル名は、通常の、独立に呼び出し可能な
関数として動作し続ける(外部の呼び出し元のため、そして*末尾でない*
あらゆる使用 -- 例えばクロージャとして受け渡されること。
`Test10MutualLoop.idr`がまさにこれを行使する -- のため)。それは合成
関数を、自身のタグと引数を添えて一度だけ呼び出し、返ってきたものを
そのまま返す薄いラッパーになる。

rc2自身の呼び出し規約は一様に`Value*`であるため、合成関数の
パラメータは単に`tag, slot_0 .. slot_k`(`k`=グループのメンバーの
中で最大のアリティ)である -- ごく普通の`RCLocal`であり、バックエンド
固有の要素は何もない。アリティが小さいメンバーは自身の未使用の末尾
スロットを単に一切参照せず、あらゆる呼び出し元(ラッパーであれ
グループ内の遷移であれ)は常にそれらを`RCNull`でパディングする。

### サイクル検出: 直接のペアだけでなくTarjanのSCC

`tailCallTargets`(`Loop.idr`自身の`mapTailAppNames`の読み取り専用の
姉妹関数で、*同じ*末尾位置の構造的な概念に基づく -- 上で議論した
のと同じ正しさの要件、この2つは決して食い違ってはならない)は、
単一の定義について、末尾呼び出しがターゲットとする名前の集合を
集める。`buildGraph`はこれを`Graph = SortedMap Name (SortedSet
Name)`へ変換し、このパス自身が検討している定義(すなわち`MkRCFun`
のみ)間の辺に制限する。`tarjanSCCs`は、その辺の上で、Tarjanの強
連結成分アルゴリズムを、明示的な状態(`TState`)を使った反復版
(素朴な再帰版のTarjanではなく、Idris2自身の全域性/スタックの制約
内に収まるように)で実装したものである。直接のペアだけを探すのでは
なくSCCを使うことで、`applyMutualLoop`は*間接的な*サイクル
(`A -> B -> C -> A`、単なる`A -> B -> A`だけでなく)も見つけられる
-- `Test10MutualLoop.idr`自身の`cycleA`/`cycleB`/`cycleC`グループが
まさにこれを行使する。サイズ`>= 2`の成分だけがマージされる。サイズ
1の成分は単なる通常の(自己再帰であるかもしれない)関数であり、既に
`Compiler.RC2.Loop`の仕事であり、このパスは完全に手をつけない。

### `buildGroup` -- 1つの合成関数を合成する

1つのSCC(`groupNames`)について:

1. メンバーを決定論的に順序付ける(`SortedSet.toList`、`Ord Name`で
   ソート済み)。これによりタグの割り当てがSCC探索の順序に依存
   しなくなる -- 再現可能な出力のために重要な安定性であって、
   正しさの問題ではない。
2. `maxArity` = グループのメンバーの中で最大のアリティ。
   `tagOf : SortedMap Name Int`が各メンバーに小さな整数タグ
   `0..length members - 1`を割り当てる。
3. 新しい合成関数名(`freshName`、プログラム全体に既に存在する名前
   との衝突を回避)、およびタグパラメータ(`tagId`)と共有の引数
   スロットそれぞれ(`slotIds`、`maxArity`個)のための新規IDを発行
   する。
4. 各メンバーについて、それ自身の`RConstAlt`を構築する:
   - `collectBoundIds`がメンバー自身の本体が内部で束縛するすべての
     ID(自身のトップレベルパラメータは除く、下記で別途扱う)を
     見つけ、`freshId`がそのようなIDそれぞれに1つの新規置換を発行
     する。
   - `Renaming`が、メンバー自身のトップレベルパラメータを*共有の*
     `slotIds`(任意の新規IDではなく -- あれらこそが今や合成関数の
     本当のパラメータだから)へ、そしてすべての内部IDをそれ自身の
     新規置換へマップする。
   - `renameRCExp`がその置換をメンバー自身の本体へ適用する。
   - `rewriteGroupTailCalls`が、*リネーム後の*本体自身の末尾位置を
     (共有の`mapTailAppNames`経由で)歩き、グループの*どの*メンバー
     をターゲットとする末尾呼び出しも(`tagOf`で引かれる。ターゲット
     が同じメンバー自身であるか別のメンバーであるかを問わず)、合成
     関数自身への通常の末尾呼び出しへ置き換え、ターゲット自身のタグ
     を先頭に加え、引数リストを`maxArity`まで`RCNull`でパディング
     する。
5. 合成された本体は`RConstCase EmptyFC (RCLoc tagId) alts (Just
   crash)` -- クラッシュのデフォルトは実際には到達不能である
   (`tagId`は`alts`のいずれかが生成した値しか持ちえない)。防御的な
   `RCrash`として保持され、チェックなしの部分マッチにはしない。
6. 各元のメンバーは薄いラッパーになる: `MkRCFun args_i
   (RAppName ... mergedName (tag :: padded args))`。

### 所有権: 新規決定ではなく純粋なリネーム

`Compiler.RC2.RC`の`annotate`(Phase 2)は、このパスが実行される
*前に*、各メンバー自身の元の引数とローカルについてのdup/drop/move
挙動を既に決定済みである -- マージはそれを一切変更せず、変更する
のは*末尾呼び出しがどこへ着地するか*だけである。`renameRCExp`自身の
保証(純粋な置換であり、既存の`RDup`/`RDrop`/`RFree`ノードは自身の
ターゲットとともに新しいIDへそのまま移動する)こそが、上記のステップ
4を、このパスが所有権について一切考える必要なしに健全にしている
理由である。

このパスが自力で正しく行う必要がある唯一のことは、それが
`annotate`を一切経由していない、本当に新しい木の形を構築している
ことに由来する: アリティパディングの不変条件である: ある遷移が
メンバー`j`へ入る際、`< arity(j)`のスロットは常に`j`のための本物の、
新しく供給された値を保持し、`>= arity(j)`のスロットは常に`RCNull`
である。これは*帰納的に*成り立つ -- *あらゆる*遷移(ラッパー呼び出し
であれグループ内の末尾呼び出しであれ)が未使用の末尾スロットを
`RCNull`でパディングし続ける限り。これは`rewriteGroupTailCalls`/
ラッパーの構築が常に行っていることである。この不変条件のもとでは、
メンバー自身の本体は、常にそうしてきたのとまったく同じように自身の
`[0, arity)`スロットだけを考慮すればよい(それはまさに`annotate`が
その元の、マージ前の引数リストについて既に決定したことそのもの)。
それを超えるものは一切読まれないので、それを超えるものについて、
このパスが発明しなければならない追加のdropも一切ない。リテラルの
`NULL`に対する`idris2rc2_drop`/`idris2rc2_dup`/`idris2rc2_free`は
どれもランタイムのno-opである(この作業中に`support/rc2/memory.c`に
対して確認済み)ので、たとえパディングスロットを対象にした防御的な
dropがあったとしても無害だっただろう -- しかしこの不変条件のおかげで
そもそも一切生成されない。

**この不変条件には、本書のもう1つのパスとの、実際に発生した記録済み
の相互作用が1つある**: 直後に`Compiler.RC2.Loop`で実行される
ネイティブshadow昇格は、どのスロットが「一部の呼び出し元にとって
常に`RCNull`」であるかについて一切の可視性を持たない -- その自身の
視点からは、他のどの関数のトップレベルパラメータとも同じように、
合成関数自身のトップレベルパラメータを見ているだけである。もし
*別の*グループメンバーが自身の同じ位置のスロットをネイティブに
読んでいれば、そのスロット全体がグループ全体で昇格されてしまう
(`RCNull`も含めて)。これは実際のクラッシュを生んだ -- 下記
「発見したバグ」参照。

## 発行(`Compiler.RC2.Emit`)

上記の両パスは決定を下すだけであり、`RLoop`/`RLoopContinue`をCへ
下ろすことは完全に機械的であり、`Emit.idr`に存在する。

- **`declareLoopParam`**: 1つのループパラメータを宣言(かつ初期化)
  する。`initVal`が文字どおり自分自身のIDである、変更のない`RBoxed`
  パラメータ(よくあるケース -- 昇格されなかったすべてのパラメータ、
  および`MutualLoop`によってマージされた関数自身の共有スロットの
  通常経路)については、自身の`Rep`を記録すること以外は完全な
  no-opである -- `var_N`は既に存在し、既にちょうどこの値をC関数
  パラメータとして保持している。再宣言はC上の再宣言エラーになる
  だけで、単なる無駄ではない。本当に新規のパラメータ(どんな
  ネイティブshadowでも、あるいは別のIDを持つBoxedなもの -- 後者は
  現在どちらのパスも生成しないが全域性のために保持されている)に
  ついては、`declareLet`/`declareNative`を経由するのではなく
  `initVal`を`rcVarToNativeC`/`rcVarToBoxedC`で直接読む: それらは
  評価すべきANF形の計算レシピ(`ROp`/`RPrimVal`/...)を期待して
  おり、`emitNativeValue`には裸の既存ローカル読み取り(`RV`)の
  ケースが一切存在しない -- `declareLet`を経由しようとした初期の
  試みは、まさにこの隙間に`InternalError`として突き当たった。これが
  この関数がその機構を完全に迂回する理由であり、`RV`を
  `emitNativeValue`が一般的に理解する新しいケースにしようとする
  代わりに(そこで汎用的な修正がなぜ間違った形になるかは「発見した
  バグ」参照 -- `emitNativeValue`の既存ケースが`postDrop`/所有権
  文脈経由で答えている「この読み取りにdropが必要か」という問いに、
  裸の`RV`が答えるための情報を一切運んでいないから)。

  このネイティブshadow宣言はまた、関数全体を通じて、元の、依然
  Boxedなパラメータのこのループパラメータにとって*最後の*使用でも
  ある(`Compiler.RC2.Loop`自身の書き換えが既に他のあらゆる参照を
  新しいshadowへリダイレクト済み) -- なのでこの時点で`initVal`が
  まだBoxedであれば、ちょうどここで一度だけdropされる。この drop、
  およびその直前のunbox読み取りは、どちらも実行時の`NULL`チェック
  (`(initValName == NULL) ? 0 : (...)`)でガードされている -- この
  ガードがなぜ存在し、なぜ`MutualLoop`によってマージされた関数
  だけに限定しようとするより無条件に適用する方が安上がりなのかは
  「発見したバグ」参照。

- **`emitLoopInto`**: `RLoop`自体を下ろす -- すべてのループパラメータ
  を宣言し(上記の`declareLoopParam`、よくあるケースではno-op)、
  `loop:;`ラベルを発行し、ループ自身のパラメータリストを
  `Ref LoopParams (List (Int, Rep))`(ループへ実際に入るまでは空、
  下記の`tryEmitLoopContinue`だけが参照する)に記録し、それから
  このモジュールの他のあらゆる構文と同じ`Sink`/`TailPositionStatus`
  対応の`emitInto`経由で`body`へ再帰する。

- **`tryEmitLoopContinue`**: `RLoopContinue`を下ろす -- それぞれの
  新しい値について、まず一時変数へスナップショットし(例えば
  `f x y = f y x`のようなエイリアシングに対する、単純な同時代入の
  安全策 -- ここに所有権の判断は一切含まれない、`annotate`は
  `Compiler.RC2.Loop`が実行される前に既にすべての引数のdup/move
  を決定済み)、`rcVarToBoxedC`または`rcVarToNativeC ty`で(その
  具体的なループパラメータ自身の`Rep`ごとに、`LoopParams`から
  読み戻したうえで)レンダリングする -- `RBoxed`/`RNative`/
  `RInlineNative`にわたって既に完全に汎用的であり、これはネイティブ
  shadow化専用に後付けされたのではなく、最初からこう書かれていた
  ため。それから各ループパラメータ変数を自身の一時変数から再代入
  し、`goto loop;`を発行する。

## 発見・修正したバグ(時系列)

1. **`Renaming`の可視性(`export` vs. `public export`)。**
   `Renaming`/`renameRCExp`/`collectBoundIds`を`MutualLoop.idr`
   (単一モジュールにプライベートな定義)から`Loop.idr`へ、*共有*の
   モジュールをまたぐユーティリティとして移設する際、最初はただの
   `export`を使っていた。`MutualLoop.idr`自身の`buildGroup`
   (`let ren : Renaming = SortedMap.fromList (...)`)は
   `Can't solve constraint between: SortedMap Int Int and Renaming`
   というエラーで型検査に失敗した -- `export`はモジュール境界を
   またいで名前の*型シグネチャ*を公開するが*定義*は公開しないため、
   `Renaming`はただの型エイリアスであるにもかかわらず、
   `Loop.idr`の外側での単一化にとって不透明なままだった。エイリアス
   を`public export`にすることで修正した。
2. **`RDup`でラップされた`ROp`の適格性見逃し。** 上記「ネイティブ
   shadow昇格」で説明したとおり: 適格性走査の最初のバージョンは
   `RLet`自身の`value`を`ROp`へ直接パターンマッチしており、
   (`annotate`が共有オペランドの値を先頭の`RDup`でラップするため)
   1回より多く使われるパラメータをすべて見逃していた。`applyLoop`
   内の適格性チェックの直前に、(一時的にexportした
   `Compiler.RC2.Pretty.prettyExp`経由でレンダリングした
   `doc/reading-the-ir.md`参照)候補のループ本体を一時的な
   `Debug.Trace.trace`でダンプし、`BenchLoop.idr`自身の`sumTo`に
   ついて走査が*本来*見つけるべきものと実際に見つけたものを比較
   することで診断した -- 食い違いが未対応の`RDup`ラッパーを直接
   指し示した。`opNativeUsesThrough`で修正した。`ROp`をチェックする
   前に`RDup`/`RDrop`/`RFree`/`RReleaseReuse`を剥がす、`Emit.idr`
   自身の`emitNativeValue`の剥がし方をそのまま鏡映しにしたもの。
3. **`RConstCase`のスクルティニーが常にBoxedだと仮定されていた。**
   `emitConstCaseInto`(整数スイッチの高速経路 -- `idris2rc2_extractInt`
   風の抽出を使う -- と、`Db`/`Str`の枝についてBoxedな
   `IDRIS2RC2_Double`/`IDRIS2RC2_String`構造体のフィールドを参照
   する文字列/double等値チェインの経路の両方)は、自身のスクル
   ティニー`sc`を裸の`varName sc`で読んでおり、常に本物の
   `IDRIS2RC2_Value*`だと仮定していた -- `RC.idr`自身のPhase 1/2が
   単独で生成するあらゆるcaseについては真だった。caseのスクル
   ティニーが通常の関数引数やBoxedな中間値以外の何かになったことが
   それまで一度もなかったから。ループパラメータがリテラル定数と
   照合される(カウントダウン自身の`0`チェック -- まさに
   `BenchLoop.idr`自身の`sumTo`)ことでネイティブshadowになりうる
   ようになった途端、この仮定は崩れた: 生成されたCは
   `idris2rc2_extractInt`が`IDRIS2RC2_Value *`を期待している場所へ
   生の`int64_t`を渡そうとし、ネイティブshadow昇格が着地した直後の
   最初のエンドツーエンドテストで即座に`-Wint-conversion`コンパイル
   エラーとして捕捉された。両方の経路を`Rep`対応にすることで修正
   した: `scRep <- repOfLocal sc`とし、それから`sc`を裸の`varName`
   ではなく`rcVarToNativeC`/`rcVarToBoxedC`で適宜読む。
4. **`MutualLoop`の`RCNull`アリティパディングがネイティブshadow化
   されたスロットへ到達する -- 2つの独立したクラッシュ箇所、2つの
   独立した修正。** 上記`MutualLoop`自身の節で説明したとおり: 合成
   関数の共有スロットは、*どこかの*グループメンバーがそれをネイティブ
   に読むために`RNative`へ昇格されうるが、*他の*メンバーはそこで
   常に`RCNull`しか受け取らない(自身のアリティが小さいため)。
   `Test10MutualLoop.idr`自身のアリティが異なる`stepA`/`stepB`
   グループ(`stepA : Nat -> Int -> Int -> Int`、
   `stepB : Nat -> Int -> Int`)で発見された。ネイティブshadow昇格が
   着地した後、他のすべてのテストはパスしているのにこれだけが
   セグフォルトした。
   - **箇所1 -- ループ中、`RLoopContinue`経由**: `tryEmitLoopContinue`
     は、ネイティブRepのループパラメータの新しい値に対して無条件に
     `rcVarToNativeC ty v`を呼び出し、`rcVarToNativeC`自身の
     `RBoxed`分岐(`nativeUnbox ty (varName l)`)は`RCNull`を特別
     扱いしていなかった -- リテラルの`NULL`に対して、これは
     `idris2rc2_to_i64(NULL)`を生成してしまい、ランタイムのアクセサ
     内でのnullポインタ参照になっていた。一般ケースより前に専用の
     `rcVarToNativeC _ RCNull = pure "0"`節を追加して修正した:
     ここでの`RCNull`は実際に読まれる値では決してない --
     `MutualLoop`自身の不変条件(アリティの小さいメンバーは自身の
     未使用の末尾スロットを一切参照しない)が、この特定の値がそれを
     受け取るパス上では死んでいることを保証しているので、*どんな*
     値でも安全であり、`"0"`はこれがなりうるあらゆるネイティブC型
     (`int64_t`、`double`、符号なし幅、いずれも裸の`0`を受け付ける)
     にとって有効なリテラルである。
   - **箇所2 -- ループ突入時、`declareLoopParam`経由**: 最初の修正
     (箇所1のみ)ではクラッシュは完全には解消しなかった --
     `Test10MutualLoop.idr`は依然セグフォルトした。実際のクラッシュ
     はもう1段階前にあった: `declareLoopParam`自身の`initial`の値の
     unbox化(合成関数自身のトップレベルパラメータを、まさに関数
     入口で、ループのタグディスパッチが実行される*前に*読む)は
     無条件である -- `Main.stepB`自身の薄いラッパーが、自身の未使用
     の末尾スロットをリテラル`NULL`でパディングして合成関数を呼び
     出すとき、その`NULL`は実際にどのタグが渡されたかに関わらず
     `declareLoopParam`の`RNative`分岐に到達する。そして
     (既にパッチ済みの)`rcVarToNativeC`の`RCNull`節はここには適用
     されない -- IRレベルではこれは通常の`RCLoc`であり、その
     *実行時*の値がたまたま`NULL`であるだけで、静的に既知の
     `RCNull`定数ではない。`Compiler.RC2.Loop`は`MutualLoop`自身の
     パディングの仕組みについて一切の可視性を持たない(設計上 --
     上記のパイプライン上の位置の議論参照)ので、そもそもこのケース
     を適格性から除外できない。実際にそれが必要な唯一の場所での
     実行時ガードで修正した: `declareLoopParam`自身のunbox化(と
     その直後のdrop)を`(initValName == NULL) ? 0 : (...)`で
     ラップする。コスト: 1回の比較、関数の*入口*ごとに一度
     (反復ごとではない)。なので(`MutualLoop`によってマージされた
     関数だけに限定しようとするのではなく)無条件に適用しても、
     それが証明可能に不要な圧倒的多数の呼び出しにとってすら、意味の
     あるリグレッションにはならない。

   両方の修正は、フルマトリクスに対して再度検証済み: 19/19
   refc-suite、全スモークテスト(`Test1Basics.idr`〜
   `Test10MutualLoop.idr`)、全ベンチマーク、いずれも
   `idris2 --cg refc`とバイト完全一致/クラッシュなし。

## 既知の限界: ネイティブshadowの適格性は裸のトップレベルスカラーどまり

実際のサードパーティパッケージ(`idris2-missing-containers`のハッシュ
アルゴリズム群 -- 完全な数値は`rc2/BENCHMARKS.md`の2026-08-14付の
エントリ参照)に対して計測したところ、あるループパラメータが昇格
されるのは、それ*自身*がネイティブ対応型のローカルとして`ROp`/
`RCmpCase`のオペランドに直接読まれている場合のみである。これが完全
に見逃す一般的な実世界のパターンが、単一フィールドの`newtype`風
コンストラクタでラップされた数値状態である(例えば
`data FNV1a = MkFNV1a Bits64`。あのパッケージの`HashAlgorithm`
インスタンスすべてが使うパターン)。ここでは、ループ自身のトップ
レベルパラメータは*コンストラクタ*であり、ネイティブな値はループ
本体内の明示的なdestructureの後にしか現れない。`nativeArgType`は
そのdestructureの先を見通してネイティブな使用をトップレベル
パラメータへ帰属させることは一切ないので、そのようなパラメータは
常に`RBoxed`のまま -- 正しく保守的である(何も壊れてはいない)が、
本来ありうるほどには効果的でない。

考えられる拡張: 「ループパラメータ`p`の構造的な使用がすべて同じ
単一フィールドコンストラクタの`case p of MkX v => ...`という形の
destructureであり、`v`自身がネイティブ対応である」ことを認識し、
*フィールド*をshadow昇格し、Boxedコンテキストでの使用があれば
そのつど再ラップ(`con MkX [shadow]`)する。ここでは試みていない --
スコープと正しさ(コンストラクタ自身のタグ/形状が、依然「一度だけ
実行される」-- 入口 -- の側で表現される必要があり、これは裸の
スカラーの入口一度きりのunboxとは根本的に異なる形の書き換えである。
「この値がすべてのパスに沿ってどこでも正確にこのコンストラクタ
として存在するか」という、答える必要のある問いは、本書自身の
`nativeArgType`が現在行っていることよりも、`Compiler.RC2.Reuse`
自身の適格性解析の精神に近い)は、現行のものの小さな拡張ではなく、
独自の専用の設計パスを必要とするだろう。

同じベンチマークの支配的なコストが依然として影響を受けない、無関係
な理由がもう2つある。上記だけを修正すれば、その特定のベンチマークで
大きく針が動くと決めつける前に、心に留めておく価値がある:

- インターフェース経由でディスパッチされる比較(`Ord`の`<=`など)は
  決して`RCmpCase`に融合されない -- その融合は直接の`PrimFn`比較
  だけを認識し、型クラスメソッド経由の呼び出しは認識しない
  (`doc/native-type-inference.md`の「比較は別の、より狭い仕組み」
  節参照)。ネイティブshadow化されたループカウンタも、そのような
  比較へ渡すためだけに依然再box化される。
- `IOHashMap`自身のwrite/read経路は、数値アキュムレータループでは
  一切なく、`IORef`/配列アクセスとコンストラクタのリストの
  バケット走査が支配的である -- ネイティブshadow化は、どれだけ拡張
  してもそのどちらにも一切届かなかっただろう。これはむしろ完全に
  `TODO.md`の「デュアル呼び出し規約」のギャップ(ネイティブ表現が
  通常の、ループでない呼び出し境界を一切越えない)の領分である。

## 検証方法

1. `cd rc2 && source ../env.sh && nix-shell -p idris2 gmp pkg-config --run 'idris2 --build rc2.ipkg'`
2. `cd tests/refc-suite && nix-shell -p gcc gmp pkg-config --run './run.sh'` -- 19/19を期待する。
3. `tests/Test9SelfTailLoop.idr` -- 自己末尾呼び出し変換自身の専用
   カバレッジ: パラメータの入れ替え(同時代入の一時スナップショット
   にとってのエイリアシングの危険)、1つの関数内の複数の異なる
   再帰分岐、変更なしでそのまま渡される引数(「move」であって
   再計算ではない)、そして単純な相互再帰がこのパス単独では手つかず
   のままであることの確認。またネイティブshadow昇格後は、ネイティブ
   対応/非対応の型が混在するループの典型例(`countDown`の`Int`
   カウンタとその`String`のパススルー)、および`ROp`/`RCmpCase`
   ではなく`RConstCase`での使用経由で昇格されたループパラメータの
   例でもある(「発見したバグ」#3参照)。
4. `tests/Test10MutualLoop.idr` -- 相互ループ変換自身の専用
   カバレッジ: アリティの異なるグループメンバー(スロットパディング
   -- 「発見したバグ」#4を捕らえた具体的な形)、3方向サイクル(単純
   なペア以上のSCC)、合成グループ内の同一メンバー内遷移(メンバー間
   だけでなく)、グループの外から非末尾およびファーストクラスの
   クロージャ値として両方呼ばれるグループメンバー、そして
   300,000〜500,000段の深さの相互再帰でCスタックが一切増加しない
   こと(`goto`変換が実際に発火していることの直接的な証拠であって、
   単に型検査を通っているだけではないことの証拠)。
5. `tests/BenchLoop.idr`/`tests/BenchMutual.idr` -- 生成されたCの
   検査(`grep -n "^IDRIS2RC2_Value \*Main_sumTo$" -A20 build/exec/*.c`
   など)で、ネイティブshadow昇格がループ内蓄積パラメータすべてに
   適用された場合、ループ本体に`idris2rc2_mk*`/`idris2rc2_dup`/
   `idris2rc2_drop`呼び出しがゼロであることを直接確認する。
   結果として得られる、`idris2 --cg refc`との壁時計比較
   (それぞれ概ね60倍/11倍)は`rc2/BENCHMARKS.md`の2026-08-14付の
   エントリ参照。
6. `--directive dumprcexp`(`doc/reading-the-ir.md`参照)を候補の
   関数に対して使うのが、生成Cを一切見る*前に*、ある定義の本体が
   `loop [...]`で始まっているか(変換された)、そしてその自身の
   パラメータのどれがその行で`Native <ty>`を示しているか(昇格
   された)を確認する最速の方法である -- `doc/reading-the-ir.md`
   自身の第7/8節がまさにこれを歩いて説明している。
