# 末尾呼び出しのループ変換(`Compiler.RC2.Loop`、`Compiler.RC2.MutualLoop`)

(原文: `doc/loop-conversion.md`。内容が乖離した場合は原文を正とする。)

rc2が末尾再帰を`goto`に変換する仕組みの実装ノートである。対象は、自己末尾呼び出し、2つ以上の関数にまたがる相互末尾再帰、およびその両方の上に重ねたネイティブ表現への昇格である。将来のセッションや将来の自分が、設計を一から導き直したり、すでに見つけて直したバグを再び踏んだりせずに全体像を取り戻せることを目的としている。`doc/reuse-analysis.md`(Phase 1+2の後に動くもう1つのIR書き換えパス)と、`doc/native-type-inference.md`(本書のネイティブシャドウ昇格が前提にしているネイティブ/Boxedの`Rep`機構)が姉妹文書にあたる。

本書は、以前`TODO.md`にあった「(implemented)」付きの3項目と、「Native-shadow eligibility stops at bare top-level scalars」の注記をそのまま取り込んだものである。これらはいずれも完成した設計と実装の記録であり、未解決の課題ではないため、全文をここに移した。`TODO.md`には短い参照だけが残っている。

## この最適化群と、それぞれが存在する理由

Idris2自身がコンパイルして得るIRは、あらゆる呼び出しを一様に扱う。クロージャを構築し、トランポリンを経由して呼び出すのである。再帰関数では、反復のたびにクロージャを1つ確保し、引数スロットを埋め、汎用のディスパッチループを通って戻ることになる。ところが末尾再帰関数の「次の反復」は、意味の上では「パラメータを再代入して先頭へ戻る」ことにすぎない。

この無駄を減らす最適化は2段あり、作られた順に次のとおりである。

1. **末尾呼び出し -> `goto`**(本書の主題)。自己再帰の末尾呼び出しと、2つ以上の関数が互いに末尾呼び出しし合う循環の中の末尾呼び出しを、Cのパラメータ変数への再代入と、関数先頭への単純な`goto`にコンパイルする。反復ごとのクロージャ確保も、トランポリンによるディスパッチも発生しない。
2. **ループ内で持ち回るパラメータのネイティブ表現化**((1)の上に構築しており、専用の節で述べる)。ループ本体のどこかでネイティブコンテキストの数値オペランドとして読まれるループパラメータは、ループ突入時に一度だけunbox化する。この最適化がなければ、`goto`のたびに新しいヒープ値へbox化し直し、次の反復の先頭でまたunbox化することになる。

どちらも、コードの形と値の表現を変えるだけの最適化であり、独自の所有権判断は一切下さない。変換前の元の呼び出しについて`Compiler.RC2.RC`の`annotate`(Phase 2)がすでに決めた内容を、そのまま使う。両パスが小さく済んでいるのはこのためである。所有権を正しく決める問題は上流で一度解決されており、ここでの仕事は、呼び出しの形を変えるときにその決定を乱さないことに尽きる。

## パイプライン上の位置

```
Lifted (Compiler.LambdaLift)
  -> Compiler.RC2.InlineCExp       (whole-program inlining, before lambda lifting)
  -> Compiler.RC2.RC.normalize     (Phase 1: ANF-style, native type inference)
  -> Compiler.RC2.RC.annotate      (Phase 2: ownership -- RDup/RDrop/RFree)
  -> Compiler.RC2.Reuse            (constructor-reuse-in-place)
  -> Compiler.RC2.ConAltNative     (native-shadow field caching)
  -> Compiler.RC2.MutualLoop       (mutual tail recursion -> one merged function -- this document)
  -> Compiler.RC2.Loop             (self-tail-call, incl. MutualLoop's own
                                     merged functions -> RLoop/RLoopContinue,
                                     plus native-shadow promotion -- this document)
  -> Compiler.RC2.Sink             (branch-local sinking, see doc/branch-sinking.md)
  -> Compiler.RC2.DualABI          (worker/wrapper synthesis, call-site rewrite)
  -> Compiler.RC2.Emit             (purely mechanical RCExp -> C)
```

`MutualLoop`は`Loop`の後ではなく前に動く。この順序が`MutualLoop`の設計の要である(詳細は後述の専用の節を参照)。`MutualLoop`が合成した関数が`Loop`に渡される時点で、その内部の遷移は、自己呼び出しもメンバー間の呼び出しも、すべて自分自身への通常の末尾呼び出しになっている。`Loop`から見れば、手で書いた自己再帰関数と区別がつかない。そのため、`Loop`は`MutualLoop`の出力を変換するための特別扱いを必要としない。これは偶然ではなく、`MutualLoop`がまさにこの性質を持つ出力を作るように設計されているからである。

## IRの形: `RLoop` / `RLoopContinue`

```idris
RLoop         : FC -> (loopParams : List (Int, Rep)) -> (initial : List RCLocal) -> (prologueDrop : List RCLocal) -> RCExp -> RCExp
RLoopContinue : FC -> List RCLocal -> (postDrop : List RCLocal) -> RCExp
```

`RLoop`は、末尾再帰ループ全体を包むノードである。`loopParams`はこのループ自身が持ち回るローカル変数であり、それぞれが**独自の**`Rep`を持つ。外側の関数のトップレベルパラメータが使う表現(外部呼び出し規約によって常にBoxed)とは無関係である。`initial`は各パラメータの初期値を同じ順序、同じ長さで与える。これらの値は、ループが走り出す前に、**外側の**スコープで一度だけ評価される。`body`は繰り返し評価される。その末尾位置から到達できる`RLoopContinue`は、次の反復の値を与えて先頭へ戻る。それ以外の値が末尾位置に来ると、ループを抜け、その値が`RLoop`ノード全体の結果になる。両ノードを生成するのは`Compiler.RC2.Loop`だけで、`RC.idr`のPhase 1/2はどちらも作らない。

`RLoop`の`prologueDrop`は、このループでネイティブシャドウを得た外側関数のトップレベル引数のうち、シャドウの宣言が実行された後は元のBoxed形式が確実に不要になるものの一覧である。`applyLoop`がこれを一度だけ計算し、データとして持ち回る。これは`Compiler.RC2.Reuse`の`dupOnShared`と同じやり方であり、判断をIRの構築時に一度だけ下して、emit時に導き直さない。ただし、シャドウ化したパラメータすべての元の値が入るとは限らない。後から`Compiler.RC2.DualABI`がワーカーのシグネチャ上でそのパラメータもネイティブに昇格させた場合、そのワーカーの中には、Boxedの値は最初から存在しない。このため`prologueDrop`は、`initial`や`loopParams`と違って、後述の`stripOwnership`の対象の1つになる。`synthesizeWorker`は、通常の`RDrop`の変数リストと同じ要領で、昇格済みのidをここから取り除かなければならない。取り除かないと、シグネチャ上すでにBoxedではない値を二重にdropするか、ネイティブ値をdropしてしまう。

`RLoopContinue`の`postDrop`は、シャドウ昇格したループパラメータの位置に渡すためにネイティブとして読む必要のある、Boxedの引数すべてを保持する。このフィールドは、これがなかったために起きたリークを契機に追加された。詳細は後述の「発見・修正したバグ」の5番で述べる。

### なぜ単純な形ではないのか

初期の設計は、`MkRCFun`上のフラットな`isLoop : Bool`フィールドと、変換した各呼び出しの代わりに置く`RSelfTailCall`ノードを組み合わせたものだった。ループの境界を示す明示的な表現はなく、関数に付けたフラグと、各ジャンプ元に置いた目印があるだけである。この設計で表せるのは、「関数本体全体がBoxedであり、一部の末尾呼び出しが`goto`になる」という状況に限られた。「*このループパラメータ*だけが、関数の呼び出し規約とは別の独自の表現を持つ」と言う手段がなかった。IRに、外側の関数から独立した固有の存在としての「ループ」という概念がなかったからである。

ネイティブシャドウへの昇格(次の節)は、まさにその区別を必要とする。ループ内で持ち回るパラメータのネイティブ表現は、制御がループの中にある間だけ成り立つ。関数の入口(外部からの呼び出し)と出口(ループの最終値)では、通常のBoxed値が引き続き必要になる。`RLoop`/`RLoopContinue`に落ち着くまでに、これを表現する方法として2つの設計を検討した。

1. **関数の入口で一度だけunbox化し、以降はネイティブのまま持ち回って、シャドウ化した変数のidをそれが使われるすべての箇所で付け替える。** これは却下した。関数本体全体で`RCLoc p -> RCLoc shadowId`と機械的に置換するだけで他に何も手を加えないと、`annotate`が`p`についてすでに計算した所有権注釈が壊れる。具体的には、`p`の`postDrop`エントリや、単独で置かれた`RDrop`/`RDup`ノードである。これらはすべて、値が複数のBoxedコンテキストから読まれることを前提にして数と位置が決められており、置換だけではこの前提を直せない。しかも壊れ方が目立たない。型検査は通り、多くの場合は実行もできるが、特定の入力でリークや二重解放が起きる。(これは仮定上の懸念ではなく、実際に起きた問題である。後述の「発見・修正したバグ」を参照。本書が述べる、スコープを絞った正しい形の書き換えでさえ、正しくするには所有権を剥がす専用の手順が必要だった。)
2. **box/unboxを明示的なIRノードにし、`ROp`のような、オペランドを消費して値を生むごく普通のノードとして扱って、その所有権は、他のすべてと同様にPhase 2の既存の`annotate`機構に決めさせる。** 所有権のロジックを新たに一切必要としないので、設計としては魅力的である。しかしこの判断を、`annotate`が走る前のPhase 1の最中に下さなければならない。ところがPhase 1には「ループ」という概念がまったくない。ループの検出は末尾位置の構造的な性質に基づいており、ANF正規化とは意図的に切り離した、後段の専用パスが行う。これを正しく実現するには、ループ検出をPhase 1に組み込むことになり、本作業の他の部分よりずっと大きな再構成になる。今回の範囲外として見送った(`TODO.md`の「Dual calling convention」を参照。ネイティブ表現を任意の呼び出し境界の向こうへ渡すという一般化された版が未実装のままなのも、同じ種類の理由による)。

`RLoop`/`RLoopContinue`に分ける設計は、どちらの代償も払わずに済ませる。「一度だけ実行される部分」(`initial`。外側のスコープで評価され、元のBoxedパラメータを参照する)と、「繰り返される部分」(`body`。ループ自身のパラメータを参照し、それぞれが独自の`Rep`を持つ)が、IRの中で構造的に別の位置になる。後段のパス(本書で述べるパス)は、`annotate`が走り終えた後で昇格を判断できる。正しさは、木全体のリネームと、狙いを絞った所有権の剥がしという、範囲の明確な機械的手順2つに帰着する。Phase 1がループを知る必要はない。この2つの手順の仕組みと、それで十分である理由は、後述の「ネイティブシャドウへの昇格」を参照。

## `Compiler.RC2.Loop`: 自己末尾呼び出しの変換

### `mapTailAppNames` -- 共有される末尾位置の走査

```idris
mapTailAppNames : (FC -> Name -> List RCLocal -> Maybe RCExp) -> RCExp -> (Bool, RCExp)
```

末尾位置にあり、lazyではない`RAppName fc Nothing n args`の葉のうち、`f fc n args`が`Just e'`を返すものをすべて`e'`に置き換える。ここでいう「末尾位置」とは、`Compiler.RC2.Emit`自身の`TailPositionStatus`(`Compiler.RC2.Emit.Util`)がC生成時にすでにたどっている構造的な位置の集合と、まったく同じものである。具体的には、`RLet`の本体、`RDup`/`RDrop`/`RFree`/`RReleaseReuse`/`RReuseOffer`の継続、`RCmpCase`の2つの枝、`RConCase`/`RConstCase`の各alt及びdefaultである。オペランド位置(`RCon`の引数、`ROp`のオペランド、`RApp`のcalleeや引数、`RAppName`*自身の*引数など)は一切走査しない。そこにある呼び出しは末尾位置にないので、`f`が何を返そうと、通常の呼び出し規約を使い続けなければならない。

この関数は`Loop.idr`で一度だけ定義し、`Compiler.RC2.Loop`自身(`f`は外側の関数自身の名前にだけ一致する)と`Compiler.RC2.MutualLoop`(`f`は相互再帰グループの任意のメンバーに一致する)が共有する。これは重複排除のためだけではなく、正しさの要件である。2つのパスが「末尾位置」について別々の定義を持つと、一方が変換した(あるいは見送った)呼び出しを、`TailPositionStatus`に基づくもう一方のemit処理が末尾位置とは認めない事態が起こりうる。その場合、誤コンパイルが気づかれないまま残る。

### `applyLoop` -- ループで包むかどうかの判断

```idris
applyLoop : Name -> RCDef -> RCDef
```

引数は定義自身の名前である。`RC.idr`はPhase 1/2を通して定義自身の名前を持ち回らないため、`RC2.idr`の`toRCDefs`が明示的に渡す。`applyLoop`は`mapTailAppNames`を実行し、`self`を対象とする呼び出しだけに一致させて、それぞれを`RLoopContinue fc args'`に置き換える。1つも見つからなければ、本体はそのまま通す。見つかった場合は、書き換えた本体全体を1つの`RLoop`で包む。ネイティブシャドウへの昇格もここで行う。これは次に述べる。

適用範囲は、`mapTailAppNames`自身の制限と同じである。自己再帰だけが対象であり(相互再帰は`MutualLoop`の仕事で、後述する)、`LazyReason`の下にある呼び出しは除外する(保守的な扱いであり、これ以上は調べていない)。ループで*包む*こと自体は、所有権に一切影響しない。`RAppName`自身の引数について何をdupし何をmoveするかは、このパスが動く前に`annotate`が、他の関数を呼ぶ場合とまったく同じように決めている。呼び出しの*形*を変えても、そのオペランドに起こるべきことは変わらない。`RAppName`を包んでいる`RDup`/`RDrop`/`RFree`/`RReleaseReuse`には手を触れずに残し、置き換えるのは末端の`RAppName`ノードだけである。

### ネイティブシャドウへの昇格

`applyLoop`の後半である。関数自身のトップレベルパラメータそれぞれについて、`RBoxed`から新しいネイティブシャドウへ昇格させる価値があるかどうかを判断する。価値があれば、それに合わせてループ本体を書き換える。

**適格性(`nativeArgType`/`nativeArgTypes`)**: パラメータ`p`が適格になるのは、(末尾呼び出しの書き換え済みの)本体が、`p`をネイティブコンテキストのオペランドとして、*1つの`PrimType`で一貫して*読む場合である。具体的には、融合された`RCmpCase`のオペランド(コンテキストに関係なく常にネイティブ)として読む場合か、`RLet`に束縛された`ROp`のオペランドとして読む場合である。後者は、その`ROp`*自身の*`Rep`が`RNative`/`RInlineNative`のときに限る。結果がBoxedの`ROp`のオペランドは、`emitRC`の`ROp`の場合分けによりBoxedとして読まれるので、数えない。`Compiler.RC2.Emit`が、オペランドを`rcVarToBoxedC`ではなく`Compiler.RC2.Emit.Util`の`rcVarToNativeC`で読むのは、実はこの2か所だけである。適格性の走査は、Emitの実際の動作と食い違うことがないよう、意図的にこの2か所の言葉で定義している。`nativeArgTypes`は(末尾位置だけでなく)木全体を走査する。オペランドはどこにでも現れうるからである。見つけた型をすべて`SortedSet`に集める。`nativeArgType`が受け入れるのは、要素がちょうど1つの結果だけである。ネイティブとして一度も読まれない場合と、互いに食い違う型で読まれる場合は、どちらも保守的にそのパラメータを`RBoxed`のままにする。

`opNativeUsesThrough`が必要なのは、`RLet`の`value`が、裸の`ROp`であるとは限らないからである。`annotate`(Phase 2)は、複数回使われるオペランドの値を、先頭の`RDup`(あまり多くないが`RDrop`/`RFree`/`RReleaseReuse`の場合もある)で包むのが普通である。`Emit.idr`の`emitNativeValue`も、実際の演算にたどり着くまでに、まったく同じ形を剥がさなければならない。**これは開発中に実際に起きたバグであり、仮定上の話ではない。** 適格性の走査の初期版は、`value`を直接`ROp`にパターンマッチさせていた。このため、算術演算で使われる前に`dup`されたパラメータ、つまり2回以上使われるパラメータをすべて見逃していた。どう診断したかは、後述の「発見・修正したバグ」を参照。

**適格な`(p, ty)`の組が決まった後の書き換え手順は、次のとおりである。**

1. `assignShadowIds`が、適格なパラメータ1つにつき新しいidを1つ割り当てる。起点は、定義内ですでに使われている最大のidの次の値である(`args`と、書き換え後の本体にある`RLet`/`RConAlt`が束縛するすべてのid。`collectBoundIds`で集める)。`Core`を通して持ち回るカウンタではなく、単なる算術上の最大値を使う。このパスは全体として、一度に1つの定義だけを入力とする純粋関数に保たれているためである(`MutualLoop`の`FreshId`は対照的で、プログラム全体にわたって持ち回る必要がある)。
2. `renameRCExp`(後述)が、昇格した各パラメータの元のidのすべての出現を、新しいシャドウidで本体全体にわたって一律に置換する。ネイティブコンテキストの読み取りの中だけではなく、**すべての**出現が対象である。Boxedコンテキストでの使用(コンストラクタのフィールド、呼び出しの引数、ループ自身の最終的な戻り値)も向け直されるが、これで正しい。ネイティブな`Rep`を持つローカルに`rcVarToBoxedC`を適用すると、その場で新たにbox化するので、向け直されたBoxedコンテキストの読み取りも正しい*値*を生む。違いは、元のオブジェクトの同一性を共有せず、新しいアロケーションを経由する点だけである(実在するコストだが許容範囲のトレードオフであり、正しさの問題ではない)。この一括リネームが適用されるのは、現在はループ内で持ち回られるパラメータだけである。ループ不変のパラメータは、ネイティブコンテキストの読み取りだけが向け直される(後述の「生き残ったBoxedコンテキストの読み取りに元のBoxed値を再利用する」を参照)。
3. `stripOwnership`(後述)が、`annotate`が*元の*パラメータについて計算した、もう不要な所有権の記録を取り除く。キーにするのは、リネーム後の*シャドウ*idである。
4. `loopParams`は、関数自身の`args`を走査して作る。適格なパラメータは`(shadowId, RNative ty)`を出す。それ以外のパラメータは、`(p, RBoxed)`をそのまま出す(自分自身のidを再利用する。これによって、`Compiler.RC2.Emit`の`declareLoopParam`が宣言を丸ごと省ける。後述)。`initial`は常に`map RCLoc args`である。どのループパラメータの初期値も、実際には、元の常にBoxedなパラメータから読み取る値だからである。`Compiler.RC2.Emit`の`declareLoopParam`が、unbox化の変換を行う(変更のない`RBoxed`パラメータでは省かれる)。

### ループ不変パラメータの除去

外部パッケージ自身のホットループについて`--directive dumprcexpr`の出力を読んでいたときに見つかった問題である(`rc2/BENCHMARKS.md`の2026-08-18の項を参照)。どの反復でも実際には変化しない、ループ内で持ち回るパラメータが、`loopParams`、`initial`、およびすべての`continue`の`args`に残っており、本当に変化するパラメータとダンプ上で区別がつかなかった。動機は速度ではなくIRの*正確さ*である。(`Compiler.RC2.Emit`の`zip`ベースの変換が、その結果として小さくなることもあるが、副次的な効果にすぎず、目的ではない。)`.rcexpr`ダンプの読み手は、`loopParams`に、ループが実際に再代入する値だけが並んでいると信頼できるべきである。

**検出**: 最初に作ったときは、`applyLoop`のネイティブシャドウ昇格(上の手順1〜4)の後で実行していた。現在はリネームより*前*に、末尾呼び出し変換済みの本体に対して実行する。理由と、それで答えが変わらない理由は、後述の「生き残ったBoxedコンテキストの読み取りに元のBoxed値を再利用する」を参照。どちらの場合も、`collectContinueArgs`が本体を走査し、すべての`RLoopContinue`の`args`リストを集める。走査する木の形は、`fillLoopContinuePostDrop`がすでに走査しているものと同じである。構造上、1つの関数に`RLoop`は1つしかなく、入れ子の`RLoop`を気にする必要はない。`invariantLoopParamIds`は、集めたリストすべてにわたって畳み込む。出発点は「すべての位置が不変」であり、集めた`args`リストごとに、「この`continue`は、この位置に*まったく同じローカル*を渡しているか」という条件をANDで重ねる。ここでの「同じローカル」とは、ループパラメータ自身のidの`RCLoc`である。位置が生き残るのは、すべての`continue`が文字どおり一致する場合だけである。Boxedの位置とネイティブシャドウ化された位置は、同じように検査する。ここでは両者を区別しない。

**書き換え**: 生き残った位置は、`loopParams`と`initial`から取り除かれ(`elideInvariantContinueArgs`による。木の走査の形はこれも同じで、すべての`RLoopContinue`の`args`から該当するスロットを落とす)、ネイティブシャドウ化されていたかどうかで、次の2通りのどちらかに処理される。

- **Boxedのままだった場合**: それ以上すべきことはない。そのidは、すでに外側関数自身のトップレベル引数であり、今後もそうであり続ける。ループ本体のどこからでも、宣言なしで直接読める。`Compiler.RC2.Emit`の`declareLoopParam`が、変更のない通常の`RBoxed`ループパラメータについてすでに特別扱いしている「再宣言が不要」というケースと同じである(後述の「Emit」の節を参照)。除去されたBoxedパラメータは、形式上でもループパラメータではなくなるが、その特別扱いの適用対象に入る、というだけのことである。
- **ネイティブシャドウ化されていた場合**: `RLoop`の*全体*を包む、1回限りの`RLet`の組に巻き上げる(`RLet emptyFC sid (RNative ty) (RV emptyFC (RCLoc p)) ...`)。これは、このパスのために考案した新しいIRの形ではない。`Compiler.RC2.ConAltNative`の`shadowAltFields`が使うイディオム(そのモジュール自身のドキュメントと、`doc/reading-the-ir.md`の実例を参照)をそのまま再利用している。Boxed値のネイティブでの読み取りを、ちょうど一度だけキャッシュするための形である。違いは、包む対象が`case`の1つのaltの本体ではなく、ループ全体であることだけである。`prologueDrop`は、これらのidを含まない。これらのidのdropは、この包み込みが担当する。`Compiler.RC2.Emit`の`emitLoopInto`が残りのシャドウ化パラメータ(実際に変化するもの)についてまとめて処理する`prologueDrop`のリストとは、別扱いになる。ここで`p`を読んだ直後に来るのが、無条件の`RDrop`なのか、もっと込み入った処理なのかは、ループ内のどこかで`p`がBoxedコンテキストでも読まれるかどうかで決まる。後述の「生き残ったBoxedコンテキストの読み取りに元のBoxed値を再利用する」を参照。

ここでは、MutualLoopのアリティ調整によるNULLの危険は生じない(これに対し、`Compiler.RC2.Emit`の`declareLoopParam`は、まさにこの理由で明示的なNULLガードを必要とする。そのドキュメントコメントを参照)。`invariantLoopParamIds`は、*すべての*`continue`が同じ実在のローカルを渡す位置だけを受け入れる。したがって、`Compiler.RC2.MutualLoop`が末尾のスロットを埋めるために渡す`RCNull`/`[__]`(後述のそのモジュールの節を参照)が、1回でも遷移で渡された位置は、検査にそもそも通らず、除去の候補にならない。

**DualABIとの相互作用**: `Compiler.RC2.DualABI`の`paramEligibility`は、以前は本体の先頭にある`RLoop`を直接パターンマッチし、`argIds`と`loopParams`を位置で`zip`していた。この処理は、両者の長さが常に等しいことに依存していた。除去によって両者の長さが一致しなくなるので、`paramEligibility`は現在、入れ子の`RLoop`を調べる前に、先頭の`RLet`の連鎖を剥がし(`findLoopThroughLets`)、各パラメータを位置ではなくid(`SortedMap`)で引く。剥がした`RLet`にも`loopParams`にも現れないidは、正しく「ネイティブではない」と判定される(除去されたBoxedパラメータは、もともとネイティブではなかった)。`DualABI`の他の2つの`RLoop`対応関数(`tailValueReps`/`applyCallSiteRewriteBody`)は、変更が一切不要だった。どちらも、中身にたどり着くまで、任意の`RLet`/`RDrop`の接頭辞を汎用的に再帰して通り抜けるので、新しい包み込みの形は、そのまま想定内である。

#### `renameRCExp` -- 木全体のリネーム

```idris
public export
Renaming : Type
Renaming = SortedMap Int Int

export
renameRCExp : Renaming -> RCExp -> RCExp
```

木に現れる*すべての*`RCLocal`の出現と、すべての束縛idを置換する。意味を変えない純粋な置換である(`mapTailAppNames`と違い、末尾位置に限らない。束縛idや読み取りは、どこにでも現れうる)。`RDup`/`RDrop`/`RFree`/`RReleaseReuse`や再利用関連のノードを足したり消したりはしない。それらのノード(とすべての読み取り)が指す先の名前を付け替えるだけであり、既存の所有権ノードは、形を変えずに、対象とともに新しいidへ移る。`Renaming`を`public export`にしているのは、別のモジュールの呼び出し側が、`SortedMap Int Int`の値を、その基底の型のまま直接書けるようにするためである。そうしないと、不透明な型の単一化に失敗する(実際に踏んだ問題で、`export`だけでは足りなかった。出たコンパイルエラーは、後述の「発見・修正したバグ」を参照)。

もともとは、`Compiler.RC2.MutualLoop`の内部だけで使っていた(メンバーごとのidのリネームに必要である。後述)。それを、`MutualLoop`と本モジュール自身のネイティブシャドウの書き換えが、手作業で同期する2つのコピーではなく1つの定義を共有できるように、ここへ移した。`MutualLoop.idr`は、すでに`Compiler.RC2.Loop`を(`mapTailAppNames`のために)importしているので、新しいモジュール依存は生じていない。すでにあった依存の向きに沿って、既存のコードを移動しただけである。

`collectBoundIds : RCExp -> List Int`も、同じ理由で`renameRCExp`の隣に置いてある。`MutualLoop`の`buildGroup`は、メンバー自身のトップレベルパラメータに加えて、内部のどのidに新しい名前が必要かを知るために、「本体でローカルに束縛されているすべてのid」を必要とする。本モジュールの`applyLoop`は、スコープ内にすでにあるどのidとも衝突しない、新しいシャドウidの開始点を選ぶために必要とする。

#### `stripOwnership` -- 昇格したパラメータの古い所有権記録の除去

```idris
stripOwnership : SortedSet Int -> RCExp -> RCExp
```

`ids`のいずれかを対象とする`RDup`/`RDrop`/`RFree`のターゲットと、`ROp`/`RCmpCase`の`postDrop`のエントリをすべて取り除く。`ids`はリネーム後の*シャドウ*idであり、元のパラメータのidではない。これが走る時点で、値を読み取る出現はすべてシャドウに向け直し済みだからである。ネイティブの値には、参照カウントの記録が一切要らない。生のCスカラーには参照カウントのヘッダがなく、`idris2rc2_dup`/`idris2rc2_drop`/`idris2rc2_free`に渡しようがないからである。`annotate`が、*元の*まだBoxedだったパラメータのdup/dropの寿命について決めた内容(ループ本体の複数のBoxedコンテキストの箇所から読まれていた時点の判断)は、もう当てはまらない。そのまま残すのではなく、完全に取り除く必要がある。

**これが安全な理由**: 昇格したパラメータの*他の*出現が、すべて先に実行した`renameRCExp`の呼び出しでシャドウに向け直されているからである。取り除くdropを今も必要とするBoxedの読み取りは、木のどこにも残っていない。もし残っていたら、この手順は不健全になる。リネームを先に、剥がしを後に行い、どちらも同じシャドウidの集合をキーにするという順序が、2つの手順を組み合わせて正しい全体にしている。

**`RCon`のフィールド引数、`RConCase`/`RConstCase`のscrutinee、`RReuseOffer`の`sc`/`dupOnShared`を、意図的に*触らない*理由**: ここでも`renameRCExp`は、他の場所と同じようにこれらのidを置換する。この関数が扱うのは、それらの*所有権の*記録だけであり、それは別の問題である。ネイティブシャドウの適格性を持つパラメータ(`ROp`/`RCmpCase`のオペランド、つまり数値型)と、コンストラクタとしてパターンマッチされる、あるいは再利用検査されるパラメータは、*Idrisの型のレベルで*両立しない。Idrisの1つの値が、ネイティブ適格なスカラーであると同時に、コンストラクタ分岐の対象となるADTであることはできない。したがって、シャドウ化されたidは、そもそもそれらのいずれでもない。コンストラクタのフィールドに格納されるシャドウidは、`rcVarToBoxedC`がその場で新たにbox化するだけで、正しく動く。剥がすべき独自の記録用ノードもない。

ただし、`RConstCase`のscrutineeは見直す価値がある。`RConCase`はコンストラクタ/ADTの形にしか一致しないが、`RConstCase`のscrutineeは、ネイティブ適格な数値型であることがありうる。ループカウンタをリテラルとパターンマッチする場合(`case n of 0 => ...`)がまさにこの形であり、`BenchLoop.idr`の`sumTo`が当たるのもこのケースである。`stripOwnership`はここを正しく放置している(scrutinee位置そのものには、剥がすべき所有権ノードが付いていない)。しかしこれこそが、emit側の実際のバグを生んだ隙間である。後述の「発見・修正したバグ」を参照。

#### 生き残ったBoxedコンテキストの読み取りに元のBoxed値を再利用する

以前は、不変パラメータを昇格させると、`renameRCExp`が*すべての*出現をシャドウに向け直していた。ネイティブコンテキストの読み取りも、Boxedコンテキストの読み取りも区別しない。そのため、昇格後に残ったBoxedコンテキストの読み取りには、`dup`できる元の値への参照がなく、`Emit.idr`の`rcVarToBoxedC`が毎回`nativeMk`で新しく確保し直すことになっていた(`TODO.md`の「reboxing a native-shadowed value always allocates fresh」の項を参照)。この問題は、`Compiler.RC2.ConAltNative`が分解済みフィールドについて同じ問題を直した方法(`rc2/doc/con-alt-native.md`の「Reusing the original Boxed field」の節を参照)と同じやり方で直した。ただし所有権の規則には、1つ意図的な違いがある。ConAltNativeには現れない形が実際にあるためである。

**検出を、リネームより前に移した。** 前述の`invariantLoopParamIds`/`collectContinueArgs`が問うているのは、実は純粋に*構造的な*問いである。「すべての`continue`が、この位置に同じidをそのまま渡しているか」という問いであり、そのidがその後シャドウにリネームされたかどうかには依存しない。末尾呼び出しの変換の直後、`renameRCExp`が一切触れる前の`body'`に対して実行しても、答えは変わらない。これが重要なのは、書き換えを始める前に、適格なパラメータを互いに素な2つのグループに分けられるからである。1つは、ループ内で本当に*持ち回られる*パラメータである。これには従来どおり、`renameRCExp`と`stripOwnership`による一括処理を行う(持ち回られるシャドウのBoxedコンテキストでの再利用を試みない理由は、`TODO.md`の注記を参照)。もう1つが*不変の*パラメータで、こちらはネイティブコンテキストでの出現だけを向け直す(`markInvariantNative`。`Loop.idr`の`nativeArgTypes`/`opNativeUsesThrough`の走査を、そのまま踏襲しつつ、集めるのではなく書き換える)。残ったBoxedコンテキストの出現は、元のパラメータidのままにしておき、次の処理に任せる。

**`dup`だけを使い、`move`を使わない理由。** `ConAltNative`の`reannotateFieldOwnership`は、`RC.idr`の`annotate`と同じ「最初の出現がmoveし、以降はdupする」規則を使う。分解されたフィールドを使うaltの本体は、外側の呼び出し1回につき高々1回しか実行されないので、そこでは安全である。ところが、ループ不変パラメータで残ったBoxedコンテキストの読み取りは、ループの*continue*経路上にありうる。つまり、テキスト上の同じ出現が、反復ごとに再実行される。最初の(テキスト上で先の)反復の使用でmoveすると、パラメータの唯一の生きた参照を手放すことになる。後の反復が同じローカルをまた読むと、moveを受け取った呼び出し先がすでにdropしている場合に、use-after-freeになる。そこで、残ったBoxedコンテキストの出現はすべて無条件に`dup`する(`dupInvariantBoxed`。`RC.idr`の`splitBorrows`のような引数リストの走査だが、参照すべき`owned`の状態はない。moveしてよい唯一の「最初の」出現というものがないからである)。パラメータ自身の解放は、ループの残り全体の評価が終わるまで遅らせて、1回だけ行う。具体的には、`withHoistedExprs`の結果を、まず新しい`resultVar`に束縛する(`RC.idr`の`dropDeadLet`が、不要になった通常のBoxedローカルに使うのと同じ、束縛してからdropして返す形である)。こうすれば、`p`のdropは、それを読む枝が何回実行されたかに関係なく、ちょうど1回だけ走る。残ったBoxedコンテキストの出現が全くないパラメータは、元の単純な形(シャドウの読み取りの直後に無条件の`RDrop`)のままで、`resultVar`は要らない。

**この変更の導入時に見つかった正しさのバグ(1つ目)。** このコードベースで`RCExp`を走査するすべての関数がいつかは遭遇する種類のバグであり、同じ方法で見つかった。`RCExp.idr`の`countUsesR`は、パラメータに残った出現が1つでもあるかを調べるのに使っていたが、`RLoop`/`RLoopContinue`のケースを持たない。この関数はPhase 2(`RC.idr`の`annotate`)のために設計されており、`annotate`は`RLoop`を目にしない(`Compiler.RC2.Loop`が最初に生成するのは、その後だからである)。そのため、`RLoop`を含む木に対しては、包括的なケースが気づかれないままゼロを返す。`wrapInvariantShadows`が渡すのはまさにそのような木である(そこでの`acc`は、ほぼ必ず`RLoop`そのもの、または`RLoop`を包む`RLet`の連鎖である)。ループ本体の*中に*実在する、生きたBoxedコンテキストの読み取りを持つパラメータは、すべてこの検査から見えなくなり、直後にdropされてしまった。`valgrind`で確認した実際のクラッシュ(`malloc(): unaligned tcache chunk detected`)であり、開発中に`tests/Test110Loop/LoopInvariantParam.idr`の`sumWithBoxedContinuePath`/`sumWithBoxedExitOnly`で捕捉した。修正は、専用の`usesInvariant`を作ることで行った(`countUsesR`のロジックを`Loop.idr`の内部にコピーし、`RLoop`/`RLoopContinue`のケースを加えたもの)。`countUsesR`自体を拡張しなかったのは、共有関数の契約を広げず、ローカルに再宣言するという`assignShadowIds`がすでに採っている方針に合わせたためである。

**2つ目のバグ。** 1つ目と同時に見つかった別のバグである。`dupInvariantBoxed`にも、`RLoop`/`RLoopContinue`のケースがなかった。そのコメントは、このパスが「`Compiler.RC2.MutualLoop`/`Compiler.RC2.DualABI`が`RLoop`を生成するより厳密に前に動く」と述べていたが、これは事実であっても的外れだった。`dupInvariantBoxed`が`acc`に対して走る時点では、`applyLoop`自身がすでに`RLoop`を作っているからである。ケースがないため、ループ本体の中にあるBoxedコンテキストの出現には、そもそも到達できなかった。その出現は`dup`されないまま残るのに、パラメータの解放はループの後で無条件に走る。その枝を実際に通った反復で、use-after-freeになる。修正では、2つのケースを追加し、ループ自身の`body`へ再帰させた(念のため、`initial`/`prologueDrop`/`continue`の`args`も再帰の対象にしたが、実際にはそこに`p`が現れることは想定していない。`p`が不変である場所では、`markInvariantNative`がすでにそれらをシャドウidに向け直している)。

### ループ不変な式の巻き上げ

パラメータの除去ができるようになると、自然に次の疑問が出る。トップレベルのパラメータだけでなく、ループ本体の中の*式*にも、反復を通して値が変わらないものがあるのではないか。Idris2は正格な言語である。`ROp`(算術)と`RCon`(コンストラクタの構築)は、観測可能な副作用を持ちえない`RCExp`の形のうち、ほぼ唯一の2つである(本物の副作用は必ず`RExtPrim`を通り、`%World`トークンを持ち回る)。したがって原理的には、どちらの形も、そのオペランドがすべてループ不変であれば、ループの外へ完全に巻き上げられるはずである。

**対象範囲: ループ本体の無条件の接頭辞だけ。** 走査するのは、ループの先頭から、最初の分岐(`RConCase`/`RConstCase`/`RCmpCase`)に当たる*前*までの、直線的な`RLet`の連鎖だけである。分岐の1つの枝の中にある候補は、完全に放置する(`TODO.md`が追跡している、未解決の「single-branch case hoisting」/`RCmpCase`の課題がこれに当たり、ここでは意図的に扱わない)。この制限は恣意的なものではない。ある反復がどの枝に進むかを考えなくても、パス全体の安全性を証明できるようにする制限である。この接頭辞にあるものはすべて、`loop:;`を通るたびに実行される。最初の通過も含まれる(ラベルは、ループの繰り返し領域の一番上にあり、どの終了判定よりも前にある)。つまり、そこにある式は、関数が呼ばれた時点で、少なくとも1回は実行されることがすでに保証されている。これをループの前に1回だけ実行する形に巻き上げても、実行回数は反復ごとに1回の場合より、*減ることはあっても*増えることはない。「到達しない」実行が「到達する」実行に変わることはない。1つの枝の中にある式には、この保証がない。ループが最初の判定で終了すれば、1回も実行されないかもしれない。

**検出(`isInvariantExpr`)**: `variant`は、除去を終えた*最終的な*`loopParams`のidの集合である。`RLet`の`value`が適格になるのは、裸の`ROp`/`RCon`であり、かつそのすべての`RCLocal`オペランドが`variant`の要素*ではない*場合である。`value`は、`opNativeUsesThrough`が剥がすのと同じ先頭の`RDup`/`RDrop`/`RFree`/`RReleaseReuse`を剥がしてから判定する。これ以外に計算すべきことはない。除去の後では、`loopParams`にないものは、構造上すでにループの外の値である。トップレベルの通常の引数か、このパス(またはその前の除去パス)がすでに巻き上げたものである。したがって、*最終的な*`loopParams`に対する所属の検査1回だけで、不変かどうかの判定が完結する。別途、不動点のデータフロー解析を行う必要はない。さらに、保守的な理由で2つの除外条件を置く。`ROp`の`lazy`フィールドは`Nothing`でなければならない(遅延された`Lazy`演算は、評価の*タイミング*自体が観測可能であり、上記の「正格な評価では位置が関係ない」という議論の外にある)。`RCon`の`reuseFrom`も`Nothing`でなければならない(再利用の候補は、特定の`RReuseOffer`が反復ごとに行う実行時の一意性検査に結びついており、このパスが移動してよいものではない)。

**3つ目の除外条件は、痛い目に遭って分かったもので、健全性に不可欠である。** 巻き上げが安全なのは、束縛が宣言する`Rep`が`RNative`/`RInlineNative`であるときだけであり、`RBoxed`では決して安全でない。オペランドについての上記の議論(元の位置を越えて読み続けても安全である)は、巻き上げる束縛自身の*結果*について何も述べていない。`Boxed`の結果には、*ループ本体の内部*に、それ独自の生存期間の事情がある。最初の分岐で止まる走査からは、それが見えない。たとえば、接頭辞の直後の分岐で、その結果が一方の枝(ループの終了値)でしか使われず、ループを続ける枝では使われないとする。すると、`Compiler.RC2.RC`の`annotate`は、使わない*もう一方の*枝の先頭に`drop`を置いている。「分岐の入口ごとに`RDrop`は高々1つ」というのが、所有権の仕組み全体の変わらない規約だからである。このdropは、このパスの走査境界の向こう側にある。その下から構築を巻き上げると、このdropは古くなる。反復ごとに新しく確保した値を解放していたものが、使わない枝を通るすべての反復で、巻き上げた*1つの*共有された値を二重に解放することになる。これは、このパスを実装している最中に直接再現できた。`Boxed`の`Rep`を持つ不変な`RCon`が、ループの終了側の枝でだけ使われていると、`malloc(): unaligned tcache chunk detected`でクラッシュした。`valgrind`で、本物の二重解放であることを確認している。これは`isNativeRep`のガードを入れる前の話である(`tests/Test110Loop/LoopInvariantParam.idr`に取り込んだ、元の`Test21BoxedInvariantNotHoisted.idr`のケースを参照。まさにこの形に対する、恒久的な回帰テストである)。ネイティブの結果なら、この問題を構造的に回避できる。このランタイムでは、ネイティブの値はどこでもdup/dropされないので、どの分岐にも、その値についての古いdropは存在しえない。現在の型システムでは、`RCon`の巻き上げは、実装され正しく動作するものの、実際にはほぼ発動しない(一般のADTの構築は常に`Boxed`である)。恩恵が得られるケースに到達するには、前述の未解決のsingle-branch case hoistingの課題と同じく、「それを使わない枝を調べて調整する」仕組みが必要になる。これは今回扱っていない。

**書き換え(`hoistInvariantPrefix`)**: 接頭辞を一度だけ走査しながら、`variant`を前へ引き継ぐ。巻き上げなかった`RLet`の`var`は`variant`に追加する(保守的な扱いである。巻き上げなかった束縛に依存するものは、その束縛の計算がまだループの中でしか起こらない以上、自身も動かせない)。巻き上げた`RLet`の`var`は、意図的に追加しない。その`var`だけに依存する後続の接頭辞の束縛も、同じ1回の走査で適格のままになる(不動点の反復は要らない。1段上のパラメータ除去の考え方と同じである)。結果として、巻き上げた`(id, Rep, value)`の三つ組を、元の相対順序のまま、書き換え後の残りの部分とともに返す。`applyLoop`は、最終的な`RLoop`を、巻き上げた三つ組1つにつき1つの`RLet`で包む。これには通常の`RLet`ノードをそのまま使い、新しいIRの形は作らない。包みは、前の節で述べた不変シャドウパラメータの`RLet`よりも*内側*に入れ子にする。巻き上げた式が、そのシャドウの1つを読むことがあるからである(たとえば、ネイティブシャドウ化された不変パラメータのシャドウid。`tests/Test110Loop/LoopInvariantParam.idr`の実例にある`bound = limit * 2`がちょうどそれである。ループ不変式の巻き上げのテストは、このファイルの末尾に統合してある)。

## `Compiler.RC2.MutualLoop`: 相互末尾再帰

### `RLoop`/`RLoopContinue`だけでは解決できない問題

`Compiler.RC2.Loop`が認識するのは、*外側の関数自身*を対象とする末尾呼び出しだけである。2つ(以上)の関数が循環して互いを末尾呼び出しする場合、典型例は`isEven`/`isOdd`だが、どの関数にも自己呼び出しがない。それぞれの末尾呼び出しの対象は、*別の*関数である。`RLoop`/`RLoopContinue`を複数の名前付き関数にまたがるように拡張する案は、核となるIRの形に対する変更として大きすぎると判断した。これはコード生成時の変換にすぎず、新しいランタイムの概念ではないからである。

### 設計: 循環を1つの関数に統合する

新しいIRを作る代わりに、このパスは、互いを末尾呼び出しする`>= 2`個の関数のグループごとに、統合した新しい関数を1つ合成する。その本体は、小さな整数のタグで分岐する素直な`RConstCase`で、グループのメンバー1つにつきaltが1つある。そして、グループ内のすべての末尾呼び出し(自己呼び出しもメンバー間の呼び出しも)を、統合した関数自身への通常の末尾呼び出しに書き換える。この呼び出しは、対象のタグと(パディングした)引数を運ぶ。統合した関数から見ると、これらはすべて単なる自己末尾呼び出しである。その直後に走る`Compiler.RC2.Loop`が、すでに`goto`に変換できる形である。`MutualLoop`が`Loop`の後や`Loop`の一部ではなく、*前*に動く理由は、これに尽きる。`Loop`は、統合された相互再帰を扱うために、新しいロジックを**一切**必要としない。統合された関数を目にした時点で、解くべき問題がすでに解いている問題と同じだからである。

元のメンバーのトップレベルの名前は、それぞれ、通常の独立して呼び出せる関数のまま使える(外部の呼び出し元のため、および末尾呼び出し*ではない*使い方のためである。たとえばクロージャとして渡し回す場合で、`Test110Loop/SelfTailLoop.idr`がこれを具体的に検証している)。各メンバーは薄いラッパーになり、自分のタグと引数で統合した関数を1回呼び、その結果をそのまま返す。

rc2の呼び出し規約はすべて一様に`Value*`なので、統合した関数のパラメータは、`tag`と複数のスロットだけである。どれも通常の`RCLocal`であり、バックエンド固有のものはない。メンバーの各パラメータは、`Compiler.RC2.Loop`がそのメンバー単体で昇格させるネイティブ型(`callArgOrOpNativeType`。統合の前に作った呼び出し先テーブルを参照する)か、`Nothing`のどちらかに分類する。パラメータがスロットを共有するのは、同じ分類の内側で、位置が同じ場合だけである。分類ごとのスロット数は、そのメンバーのうち、その分類のパラメータが最も多いものに合わせる。メンバーは自分のスロットしか読まず、すべての呼び出し元(ラッパーでも、グループ内の遷移でも)が、他のすべてのスロットを`RCNull`で埋める。ネイティブの分類の値はすべて同じ型なので、そのスロットを昇格させるのは健全である。`Nothing`のスロットには、異なる型の値が入りうるので、`applyMutualLoop`はLoopに対して、そのスロットを昇格させないよう指示して渡す。(これが置き換えたスロットの共有方式については、「発見・修正したバグ」の8番を参照。)

### サイクルの検出: 直接の対だけでなく、TarjanのSCCを使う

`tailCallTargets`は、`Loop.idr`の`mapTailAppNames`の読み取り専用の兄弟であり、末尾位置について*同じ*構造的な定義を使う(正しさの要件も前述のとおりで、両者は決して食い違ってはならない)。1つの定義について、末尾呼び出しの対象となる名前の集合を集める。`buildGraph`はこれを、`Graph = SortedMap Name (SortedSet Name)`に変換する。グラフは、このパス自身が検討対象とする定義(`MkRCFun`だけ)の間の辺に限る。`tarjanSCCs`は、そのグラフに対するTarjanの強連結成分アルゴリズムの実装である。素朴な再帰版のTarjanではなく、明示的な状態(`TState`)を持つ反復版にしてあり、Idris2の全域性とスタックの制約に収まるようにしている。直接の対だけでなくSCCを使うので、`applyMutualLoop`は*間接的な*サイクル(`A -> B -> A`だけでなく`A -> B -> C -> A`)も見つけられる。`Test110Loop/SelfTailLoop.idr`の`cycleA`/`cycleB`/`cycleC`のグループが、これを具体的に検証している。統合するのはサイズ`>= 2`の成分だけである。サイズ1の成分は、(自己再帰しているかもしれない)通常の関数であり、すでに`Compiler.RC2.Loop`の担当なので、このパスはまったく触れない。

### `buildGroup` -- 統合した関数1つの合成

1つのSCC(`groupNames`)について、次の手順を踏む。

1. メンバーを決定的な順序に並べる(`SortedSet.toList`で、`Ord Name`の順に並ぶ)。タグの割り当てがSCCの走査順序に依存しないようにするためである。出力を再現可能にするための安定性であり、正しさのためではない。
2. メンバーの各パラメータを、`Compiler.RC2.Loop`がそのメンバー単独で昇格させるネイティブ型(`callArgOrOpNativeType`)、または`Nothing`に分類する。`slotCount`は、クラスごとに、1つのメンバーが持つそのクラスのパラメータ数の最大値を足し合わせた数である(「見つかったバグ」の8)。`tagOf : SortedMap Name (Int, List Nat)`が、各メンバーに小さな整数のタグ`0..length members - 1`と、各パラメータのスロット位置(そのクラスの先頭オフセットに、同じクラスの先行パラメータの数を足したもの)を割り当てる。
3. 統合した関数の新しい名前を作り(`freshName`。プログラム全体で使用済みのすべての名前との衝突を避ける)、タグパラメータ(`tagId`)と、共有する各引数スロット(`slotIds`、`slotCount`個)に、新しいidを割り当てる。
4. メンバーごとに、そのメンバーの`RConstAlt`を作る。
   - `collectBoundIds`が、メンバーの本体が内部で束縛するid(メンバー自身のトップレベルパラメータは別に扱うので除く)をすべて見つける。`freshId`が、そのidごとに新しい代替のidを1つ作る。
   - `Renaming`が、メンバー自身のトップレベルパラメータを、上の位置にある*共有された*`slotIds`に対応づけ、すべての内部idを、それぞれの新しい代替idに対応づける。共有された`slotIds`は任意の新しいidではない。それらは、いまや統合した関数の実際のパラメータだからである。
   - `renameRCExp`が、このリネームをメンバー自身の本体に適用する。
   - `rewriteGroupTailCalls`が、*リネーム済みの*本体の末尾位置を(共有の`mapTailAppNames`で)走査し、グループの*どの*メンバーを対象とする末尾呼び出しも(`tagOf`で引く。対象が同じメンバーか別のメンバーかは問わない)、統合した関数自身への通常の末尾呼び出しに置き換える。そのとき、対象のタグを先頭に付け、引数を対象自身のスロット位置に置き、それ以外のスロットはすべて`RCNull`で埋める。
5. 統合した本体は`RConstCase EmptyFC (RCLoc tagId) alts (Just crash)`である。クラッシュするdefaultは、実際には到達しない(`tagId`が持つのは、`alts`のどれかが生成した値だけである)。検査のない部分的なマッチにせず、防御的な`RCrash`として残している。
6. 元のメンバーはそれぞれ薄いラッパーになる: `MkRCFun args_i (RAppName ... mergedName (tag :: padded args))`。

### 所有権: 新しい判断ではなく、純粋なリネーム

`Compiler.RC2.RC`の`annotate`(Phase 2)は、このパスが走る*前*に、各メンバーの元の引数とローカル変数について、dup/drop/moveの扱いをすでにすべて決めている。統合は、そのどれも変えず、末尾呼び出しの*行き先*だけを変える。`renameRCExp`は純粋な置換であり、既存の`RDup`/`RDrop`/`RFree`ノードは、対象とともに新しいidへ移るだけである。この保証があるので、このパスは所有権について自分で考えることなく、前述の手順4を健全に実行できる。

このパスが自力で正しくしなければならない点が1つある。このパスは、`annotate`を一度も通っていない、まったく新しい木の形を構築しているからである。それはパディングの不変条件である。ある遷移がメンバー`j`に入るとき、`j`のスロットには`j`のために新たに渡された実際の値が入り、他のすべてのスロットは常に`RCNull`になっている。*すべての*遷移(ラッパーの呼び出しも、グループ内の末尾呼び出しも)が他のすべてのスロットを`RCNull`で埋めていれば、この不変条件は帰納的に成り立つ。`rewriteGroupTailCalls`とラッパーの構築は、常にそうしている。この不変条件のもとでは、メンバーの本体は、自分のスロットだけを、従来とまったく同じように扱えばよい(それが、`annotate`が統合前の元の引数リストについてすでに決めた内容である)。それ以外は一切読まれないので、このパスが追加のdropを新たに考え出す必要はない。リテラルの`NULL`に対する`idris2rc2_drop`/`idris2rc2_dup`/`idris2rc2_free`は、どれもランタイムでno-opである(この作業中に`support/rc2/memory.c`で確認した)。したがって、パディングスロットを対象とする防御的なdropがあっても無害だったはずだが、この不変条件のおかげで、そのようなdropは生成すらされない。

**この不変条件には、本書で扱う*もう1つの*パスとの間に、実際に確認され文書化されている相互作用が1つある。** 直後に`Compiler.RC2.Loop`で実行されるネイティブシャドウへの昇格は、どのスロットが「一部の呼び出し元では常に`RCNull`」であるかを知る手段を持たない。このパスから見えているのは、統合した関数のトップレベルパラメータであり、他の関数のものと変わらない。*別の*グループメンバーが、同じ位置の自分のスロットをネイティブとして読む場合、そのスロット全体がグループ全体で昇格される。`RCNull`が入っている場合も含めてである。これによって実際にクラッシュが起きた。詳細は後述の「発見・修正したバグ」を参照。

## Emit(`Compiler.RC2.Emit`)

ここまでの2つのパスは、判断を下すだけである。`RLoop`/`RLoopContinue`をCに落とす処理はすべて機械的であり、`Emit.idr`にある。

- **`declareLoopParam`**: ループパラメータ1つを宣言(して初期化)する。変更のない`RBoxed`パラメータで、`initVal`がそのパラメータ自身のidそのものである場合は、`Rep`を記録するほかには何もしない。これが最も一般的なケースで、昇格されなかったすべてのパラメータと、`MutualLoop`が統合した関数の共有スロットのうち一般的な経路のものが該当する。`var_N`は、Cの関数パラメータとしてすでに存在し、すでにこの値を持っている。再宣言すれば、無駄な処理になるだけでなく、Cの再宣言エラーになる。本当に新しいパラメータの場合(ネイティブシャドウ、またはidの異なるBoxedパラメータ。後者は、現在はどちらのパスも生成しないが、全域性のために扱えるようにしてある)は、`declareLet`/`declareNative`を経由せず、`initVal`を`rcVarToNativeC`/`rcVarToBoxedC`で直接読む。`declareLet`/`declareNative`が前提にするのは、評価すべきANF形の計算の記述(`ROp`/`RPrimVal`/...)であり、`emitNativeValue`には、既存のローカルを読むだけの裸の読み取り(`RV`)を扱うケースがそもそもない。この関数の初期の実装は`declareLet`を経由していて、まさにこの隙間に当たり、`InternalError`になった。そのため、`RV`を`emitNativeValue`が汎用的に理解する新しいケースにするのではなく、この仕組み全体を迂回している。そこで汎用的な修正をするのが不適切だった理由は、「発見・修正したバグ」を参照。「この読み取りにdropが必要か」という問いは、`emitNativeValue`の既存のケースでは`postDrop`や所有権のコンテキストで答えているが、裸の`RV`にはそのための情報がない。

  ネイティブシャドウの宣言は、このループパラメータにとって、元のまだBoxedなパラメータを関数全体で使う*最後の*場所でもある(`Compiler.RC2.Loop`の書き換えが、他のすべての参照をすでに新しいシャドウに向け直している)。そのため、この時点で`initVal`がまだBoxedなら、ここでちょうど1回dropする。このdropと、その直前のunbox化の読み取りは、どちらも実行時の`NULL`検査(`(initValName == NULL) ? 0 : (...)`)で守られている。この検査がある理由と、`MutualLoop`が統合した関数にだけ必要だと証明しようとせず、無条件に適用してもコストが小さい理由は、「発見・修正したバグ」を参照。

- **`emitLoopInto`**: `RLoop`そのものを変換する。すべてのループパラメータを宣言し(`declareLoopParam`。上記の一般的なケースではno-op)、新しい番号のラベル`loop_N:;`を出力し、`(label, params)`を`Ref LoopParams (List (String, List (Int, Rep)))`にpushする。これはスタックで、ループに実際に入るまでは空である。そして、このモジュールの他のすべての構文が通るのと同じ、`Sink`/`TailPositionStatus`を考慮する`emitInto`で、`body`へ再帰する。戻る前にスタックをpopして元に戻す。

- **`tryEmitLoopContinue`**: `RLoopContinue`を変換する。新しい値それぞれについて、まず一時変数に退避する。これは、エイリアシング(たとえば`f x y = f y x`)に対する、並行代入の単純な安全策である。ここに所有権の判断はない。各引数のdup/moveは、`Compiler.RC2.Loop`が走る前に`annotate`がすでに決めている。値の出力は、*そのループパラメータ自身の*`Rep`(`LoopParams`の先頭のエントリから読み戻す)に従い、`rcVarToBoxedC`または`rcVarToNativeC ty`で行う。これは最初から、`RBoxed`/`RNative`/`RInlineNative`について完全に汎用的になっている。ネイティブシャドウ化のために後付けしたものではなく、当初からそのように書かれていた。その後、各ループパラメータ変数に、対応する一時変数の値を再代入し、同じラベルへの`goto loop_N;`を出力する。

### 1つの関数に複数のループがある場合

パイプラインは、1つの関数に複数の`RLoop`を作ることがまだない(`applyLoop`が包むのは、定義1つ全体の自己再帰だけである)。しかし`Emit.idr`は、それを前提にもしていない。将来のパス(たとえば、すでにループ変換された呼び出し先をinlineするパス)が、複数のループを生むかもしれないからである。`LoopParams`は単一のスロットではなくスタックである。`emitLoopInto`は、自分の`body`への再帰の前後でpushとpopを行う。このため、このループが終わった後に出力される兄弟のループは、スタックが以前と完全に同じ状態であることを見る。本当に入れ子になったループは、その期間だけこのエントリを隠す。これが正しく動くために、IR上の`RLoop`/`RLoopContinue`にidを持たせる必要はない。`RLoopContinue`は、構造上、対応する`RLoop`が包むまさにその本体の内側にしか生成されない(他のループから「借りた」呼び出し元ではない)。したがって「スタック上で最も内側のエントリへの`goto`」が、同じ関数のどこに他のループがいくつあろうと、常に正しい意味になる。各ラベルの番号は、`tmp_N`/`closure_N`の番号付けと同じ`ArgCounter`から取る。Cはラベルと通常の識別子の名前空間が別なので、問題ない。

`emitInto`は、これ以前から`RLoop`について完全に汎用だった。ディスパッチテーブルは、末尾の戻りに限らず、*任意の*`sink`/`TailPositionStatus`について`RLoop`を`emitLoopInto`に振り分ける。`declareLet`も、`RLet`の`value`を、すでにその汎用の`emitInto`に通している。将来のinlinerが、ループを含む呼び出し先を、呼び出し元にletで束縛された通常の値としてつなぎ込むには、まさにこの形が必要になる。この経路は、ここでの変更なしで、すでに動いていた。単一のループを前提にしないように変える必要があったのは、前述のラベルとスタックだけである。

## 発見・修正したバグ(時系列)

1. **`Renaming`の可視性(`export`と`public export`)。** `Renaming`/`renameRCExp`/`collectBoundIds`を、`MutualLoop.idr`(単一モジュール内でprivateな定義)から`Loop.idr`へ、モジュールをまたいで*共有する*ユーティリティとして移した際、最初は単なる`export`を使った。`MutualLoop.idr`の`buildGroup`(`let ren : Renaming = SortedMap.fromList (...)`)が、`Can't solve constraint between: SortedMap Int Int and Renaming`で型検査に失敗した。`export`は、モジュールの境界を越えて名前の*型シグネチャ*を公開するが、*定義*は公開しない。そのため、`Renaming`は単なる型エイリアスであるにもかかわらず、`Loop.idr`の外では単一化に対して不透明だった。エイリアスを`public export`にして修正した。
2. **`RDup`で包まれた`ROp`を、適格性の走査が見逃した問題。** 前述の「ネイティブシャドウへの昇格」で述べたとおりである。適格性の走査の初版は、`RLet`の`value`を直接`ROp`にパターンマッチさせており、2回以上使われるパラメータをすべて見逃していた(`annotate`が、共有されるオペランドの値を、先頭の`RDup`で包むため)。診断には、`applyLoop`の適格性の検査の直前に、候補となるループ本体を出力する一時的な`Debug.Trace.trace`を追加した(整形には、一時的にexportした`Compiler.RC2.Pretty.prettyExp`を使った。`doc/reading-the-ir.md`を参照)。`BenchLoop.idr`の`sumTo`について、走査が*見つけるべき*ものと実際に見つけたものを比較すると、その食い違いから、処理されていない`RDup`の包みがすぐに分かった。修正は`opNativeUsesThrough`で、`ROp`を調べる前に`RDup`/`RDrop`/`RFree`/`RReleaseReuse`を剥がす。`Emit.idr`の`emitNativeValue`の剥がし方を、そのまま踏襲している。
3. **`RConstCase`のscrutineeが常にBoxedだと仮定していた問題。** `emitConstCaseInto`は、整数のswitchの高速経路(`idris2rc2_extractInt`風の取り出しを使う)でも、文字列/doubleの等値チェーンの経路(`Db`/`Str`のaltのために、Boxedな`IDRIS2RC2_Double`/`IDRIS2RC2_String`構造体のフィールドを参照する)でも、scrutinee `sc`を裸の`varName sc`で読んでいた。つまり、`sc`が常に本物の`IDRIS2RC2_Value*`であると仮定していた。`RC.idr`のPhase 1/2が生成するケースでは、これはすべて正しかった。caseのscrutineeは、通常の関数引数かBoxedな中間値以外のものではなかったからである。しかし、リテラル定数とパターンマッチされるループパラメータ(カウントダウンの`0`の判定。まさに`BenchLoop.idr`の`sumTo`)がネイティブシャドウになりうるようになったとき、この仮定が崩れた。生成されたCは、`idris2rc2_extractInt`が`IDRIS2RC2_Value *`を期待する場所に、生の`int64_t`を渡そうとした。`-Wint-conversion`のコンパイルエラーになり、ネイティブシャドウへの昇格を入れた直後の最初のエンドツーエンドのテストで、すぐに見つかった。修正では、2つの経路の両方を`Rep`対応にした。`scRep <- repOfLocal sc`で`Rep`を取得し、裸の`varName`ではなく、状況に応じて`rcVarToNativeC`/`rcVarToBoxedC`で`sc`を読む。
4. **`MutualLoop`の`RCNull`によるアリティのパディングが、ネイティブシャドウ化されたスロットに達した問題(クラッシュ箇所は2つあり、修正も2つ)。** `MutualLoop`の節で述べたとおり、統合した関数の共有スロットは、*一部の*グループメンバーがそれをネイティブとして読むという理由で、`RNative`に昇格されうる。*他の*メンバーは(アリティが小さいので)、そこで`RCNull`しか受け取らないにもかかわらずである。`Test110Loop/SelfTailLoop.idr`の、アリティの異なる`stepA`/`stepB`のグループ(`stepA : Nat -> Int -> Int -> Int`、`stepB : Nat -> Int -> Int`)で見つかった。ネイティブシャドウへの昇格を入れた後、他のテストはすべて通っていたのに、このグループだけがsegfaultした。
   - **箇所1: ループの途中、`RLoopContinue`経由。** `tryEmitLoopContinue`は、ネイティブな`Rep`を持つループパラメータの新しい値に対して、無条件に`rcVarToNativeC ty v`を呼ぶ。`rcVarToNativeC`の`RBoxed`の枝(`nativeUnbox ty (varName l)`)は、`RCNull`を特別扱いしない。リテラルの`NULL`に対しては、`idris2rc2_to_i64(NULL)`が生成され、ランタイムのアクセサの内部でヌルポインタを参照した。修正として、一般のケースの前に、専用の`rcVarToNativeC _ RCNull = pure "0"`の節を追加した。ここでの`RCNull`は、実際に読まれる値ではない。アリティの小さいメンバーは、使わない末尾のスロットを決して参照しない、という`MutualLoop`の不変条件があるので、この値を受け取る経路ではこの値は使われない。したがって*どんな*値でも安全であり、`"0"`は、ここに来うるすべてのネイティブのC型(`int64_t`、`double`、符号なしの各幅)で有効なリテラルである。
   - **箇所2: ループの入口、`declareLoopParam`経由。** 最初の修正(箇所1だけ)では、クラッシュは完全には解消しなかった。`Test110Loop/SelfTailLoop.idr`は、まだsegfaultした。実際のクラッシュは、1段手前にあった。`declareLoopParam`が、`initial`の値(統合した関数のトップレベルパラメータ。関数の本当の入口であり、ループのタグ分岐が走る*前*)をunbox化する処理は、無条件である。`Main.stepB`の薄いラッパーが、使わない末尾のスロットをリテラルの`NULL`でパディングして統合した関数を呼ぶと、どのタグが渡されたかに関係なく、その`NULL`が`declareLoopParam`の`RNative`の枝に達する。(すでにパッチした)`rcVarToNativeC`の`RCNull`の節は、ここには当てはまらない。IRのレベルでは、これは通常の`RCLoc`であり、その*実行時*の値がたまたま`NULL`なだけで、静的に分かっている`RCNull`の定数ではないからである。`Compiler.RC2.Loop`は、`MutualLoop`のパディングの仕組みを一切知らない(設計どおりである。前述のパイプライン上の位置の議論を参照)。このため、このケースを適格性の段階で除外することができない。修正は、それが本当に必要な1か所に実行時のガードを置くことだった。`declareLoopParam`のunbox化(とその直後のdrop)を`(initValName == NULL) ? 0 : (...)`で包んだ。コストは比較1回で、関数の*入口*で1回(反復ごとではない)である。したがって、`MutualLoop`が統合した関数にだけ必要だと証明しようとせず、無条件に適用しても、実質的な退行にならない。ガードが不要だと証明できる大多数の呼び出しでも、同様である。

   2つの修正は、フルマトリクスで再び検証した。refcスイート19/19、すべてのスモークテスト(`Test111Basics/Basics.idr`から`Test110Loop/SelfTailLoop.idr`まで)、すべてのベンチマークで、`idris2 --cg refc`とバイト単位で一致し、クラッシュもなかった。
5. **`RLoopContinue`が、ネイティブとして読まれたBoxedの継続引数をdropしなかった問題と、`ROp`のBoxed結果のemitにあった、別の独立したリーク。** `valgrind`で検出したリークの調査中に見つかった。このリークは、(最終的に取り消した、`TODO.md`を参照)プログラム全体のinliningパスを通じて表面化したものだが、実際の原因は、そのパスとは無関係で、以前から存在していた。2つのバグがあり、どちらも同じ一般的な形をしている。`Types.repOf`が全体の`Rep`をNativeに昇格させない、`case`/`if`を値とする`RLet`が、ネイティブシャドウ化されたループパラメータの次の値に渡される、という形である。
   - **`RLoopContinue`**: Boxedの値をネイティブとして読む他のすべての`RCExp`の構文(`ROp`、`RCmpCase`、`RAppNameRep`。いずれも`postDrop`フィールドを持つ)と違い、`RLoopContinue`(`applyLoop`が作る自己末尾ループの継続ノード)には、`postDrop`フィールドがまったくなかった。`tryEmitLoopContinue`は、まだBoxedの継続引数を`rcVarToNativeC`で読んで次の反復のネイティブシャドウを作るが、Boxedの元の値は決してdropしなかった。修正は、`RLoopContinue`自体に`postDrop : List RCLocal`を追加することだった。これは`applyLoop`の新しい`fillLoopContinuePostDrop`パスで埋める(`loopParams`が分かった後で一度実行し、`SortedMap Int Rep`を持ち回る。`Compiler.RC2.DualABI`の`applyCallSiteRewriteBody`と同じ方式だが、`Loop.idr`は`DualABI.idr`をimportできないため、新たに書いた)。
   - **`ROp`のBoxed結果のemit(`Compiler.RC2.Emit`)**: 完全に別のバグで、たまたま同じテストの形の上にあったために見つかった。`Types.repOf`が`ROp`自身の結果をBoxedのままにするが、その*オペランド*の1つが個別にNativeである場合が該当する(たとえば、全体のlet束縛がBoxedであるcaseの枝の中の、連鎖した`(acc * 3) + 1`)。`Emit.idr`の`rcVarToBoxedC`は、BoxedなCのプリミティブに渡すために、新しい無名のboxをインラインで作る(`idris2rc2_mkInt64(...)`)。その一時的なboxに名前を付ける場所がなく、解放されなかった。`RLoopContinue`のケースと違い、これはループとは関係がない。Boxedな結果を持つ演算が、Nativeなオペランドを読むところならどこでも起こりうる、`ROp`のemitの一般的な漏れである。修正は`boxOpArg`で、新しく作ったboxに名前を付け、演算がそれを読み終えた直後にdropする。

   2つのバグを合わせると、`rc2/tests/Test110Loop/LoopContinuePostDrop.idr`の挙動が説明できる。これは、最初にこれらのバグを表面化させたinliningパスに一切依存せず、これらを検証するためだけに作った再現テストである。`RLoopContinue`の修正だけでは、リークが*半分*にしかならず、`ROp`の修正も入れて初めて完全にクリーンになった。正確な形は、そのテストのドキュメントコメントを参照。フルマトリクスで再び検証した。refcスイート19/19、すべてのスモークテスト、リークに敏感なすべてのテストで`valgrind`がクリーンだった。例外は、当時すでに存在していた`Test111Basics/Basics.idr`のリーク(その後修正済み)だけである。
6. **`markInvariantNative`が、`RLoopContinue`の`args`の中にあるループ不変パラメータの出現を見逃し、すべての`continue`で不要なdropが生じた問題。** `fillLoopContinuePostDrop`(上の5番で追加した)は、すべての`continue`引数の`Rep`を、シャドウidをキーとする`fullLoopParams`のマップでidから引く。その位置にある、リネームされていない元のパラメータid `p`は、マップにまったく見つからず、その引き当てのデフォルトによって`RBoxed`として読まれた。その結果、すべての`continue`に不要なdropが追加され、反復ごとに1回実行された。`valgrind`で確認した、実際の二重解放とクラッシュであり、開発中に`tests/Test110Loop/LoopInvariantParam.idr`で見つかった。修正では、`markInvariantNative`がすでに書き換えている他のすべての出現と並べて、`continue`の`args`にある`p`の出現も、シャドウid `sid`に向け直した。これで、`fillLoopContinuePostDrop`の引き当ては、不変性について何も知らなくても、シャドウのすでにネイティブな`Rep`を正しく見つけられる。

7. **大規模な実プログラム(`idris2-lsp`)をプロファイリングして見つかった、アルゴリズムの計算量に関する2つの実際のバグ。** このプログラムでは、`rc2: Mutual loop`が約16.7秒、`rc2: Loop conversion`が約41.4秒と報告されていた。どちらも、ノードごとにO(n)の処理を繰り返しており、一度だけ計算するようになっていなかったことが支配的な原因だった。

   - **`Compiler.RC2.MutualLoop`のTarjan SCC(`tarjanSCCs`)。** `strongConnect`は、新しく発見したノードのindexを`length (SortedMap.toList (index st0))`で求めていた。訪問するノードごとに、`index`マップ全体を最初からたどって数え直しており、Tarjanの線形時間という性質を、末尾呼び出しグラフ全体でO(n^2)にしていた。修正では、`TState`に単純な`nextIndex : Nat`カウンタを持たせ、ノードごとに1回だけインクリメントする(代入あたりO(1)という標準的な方法である)。同じ実プログラムで確認したところ、16.740秒から0.574秒になり、見つかるSCCは変わらなかった(87/87の回帰スイートも引き続き通った)。
   - **`Compiler.RC2.Loop`の`buildCalleeTable`/`calleeNativeParams`。** `calleeNativeParams`は、トップレベルパラメータごとに`nativeArgType`を1回ずつ呼んでおり、その呼び出しのたびに、*1つの*定義の本体を`nativeArgTypes`で最初から最後まで走査し直していた。1定義あたりO(パラメータ数 x 本体の大きさ)であり、テーブルを作るためにプログラム中の全定義で合算される。修正は`nativeArgTypeBatch`(`Compiler.RC2.Loop`の「Batched, multi-id native-type analysis」の節)で、同じ問いを、idの集合全体について、1回の共有された走査で答える。専用の`--timing 3`のサブフェーズ(`rc2: Loop conversion (build callee table)`)で切り分けたところ、同じ実プログラムで、修正後は単独で高速(0.109秒)であることを確認した。

   **`applyLoop`自身の関連する修正(`eligible`/`eligibleWithCallArgs`の計算を、同じ方法でバッチ化する)は、試した後に取り消した。** 直接のA/B測定で、改善ではなく悪化することが分かったためである。`rc2: Loop conversion (apply)`は、バッチ化した版(`SortedMap Int (SortedSet PrimType)`ベース)で約41.4秒から約74.5秒に増え、その1つの変更だけを元に戻すと約41.7秒に戻った。当初の仮説は、`applyLoop`がトップレベルパラメータごとに`nativeArgType`/`callArgOrOpNativeType`を1回ずつ呼ぶこと自体が、上の`calleeNativeParams`のバグと同じ形のO(パラメータ数 x 本体の大きさ)の主要なコストだ、というものだった。この呼び出し箇所については、その仮説が誤りだった。`applyLoop`がこの計算を行うのは、それ自身が自己末尾再帰になっている定義だけであり、`calleeNativeParams`のような「プログラム中のすべての定義」に比べて、はるかに少ない。バッチ化した版が、ノードごとの`SortedMap`のマージに要するオーバーヘッドは、この規模では、本体の走査回数が減る分の節約を上回ったらしい。

   **本当に残っているコストは、`applyLoop`自身に定義単位の`logTimeOver`を追加して見つけた。** (`toRCDefs`の`slowApplyLoopThresholdNs`、500msで、`--timing`の指定にかかわらず常に有効である。この段階のコストは、全体に均等に分散しておらず、少数の個別の本体に集中していることが分かったので、さらにもう1つ集計値を出すより、*どの*定義が遅いかの名前を挙げるほうが有用だからである。)この項で一貫して使っている実プログラムでは、しきい値を超えた名前は、上流のIdris2コンパイラの内部関数(`Core.Unify.unifyApp`、`TTImp.Elab.App.checkAppWith'`、単独で8.6秒かかる`TTImp.PartialEval.mkRHSargs`、`TTImp.ProcessRecord.elabGetters`、`Core.Case.CaseBuilder.addGroup`など)か、`Compiler.RC2.MutualLoop`がそのような内部関数をいくつか統合した`{rc2_mutualLoop:N}`ディスパッチャのどちらかだった。この実プログラム(`idris2-lsp`)は、`idris2`パッケージ自体をライブラリとして使っている(LSPサーバーは、コンパイラ自身のelaboratorの内部を必要とする)。そのため、rc2がコンパイルしていたコードの規模は、おおよそ「Idris2コンパイラがコンパイラ自身をコンパイルする」規模だった。ありふれた大きさの多数の関数に均等に分散しているのではなく、手書きの、巨大な複数節の関数(単一化、elaboration、case木の構築)が相手だった。これは、前述の`eligible`/`eligibleWithCallArgs`のバッチ化の試みが、改善ではなく悪化を招いた理由も説明する。これらの本体は、B(本体の大きさ)が非常に大きいが、P(トップレベルのパラメータ数)が特別に大きいわけではない。あの修正が最適化した軸は、この形には的外れだった。

パラメータ数が支配的な要因でないなら、効果が見込めるのは、`applyLoop`が定義ごとに行う*別々の*本体全体の走査の回数を、そもそも減らすことだろう。現在は10回を超えている。`mapTailAppNames`、`collectBoundIds`、`invariantLoopParamIds`/`collectContinueArgs`、`renameRCExp`、`stripOwnership`(変化するパラメータすべてについてまとめて1回、さらに不変パラメータごとにもう1回)、`markInvariantNative`(不変パラメータごと)、`fillLoopContinuePostDrop`、`hoistInvariantPrefix`、`wrapInvariantShadows`の`usesInvariant`/`dupInvariantBoxed`(それぞれ不変パラメータごと)である。これらのうちいくつかを、同じ本体に対する少数の統合したパスにまとめる。ここでは試していない。上の2つの修正より、はるかに大きく、リスクも高い再構成になるからである(既存の各パスは、それぞれ慎重に検討した不変条件を持ち、この文書に詳しく書いてある)。後続の課題として残した。`logTimeOver`の診断自体は、取り消さずに残した。同種の問題を再び見つけるための、コストの低い常設の仕組みである。

**後日の追記: 上の「Bが大きい」という説明は不完全だった。** 同じ`logTimeOver`の診断を拡張して、警告対象の各定義のパラメータ数(P)と大まかな本体のノード数(B)も出力するようにしたところ、Pは*大きい*のにBは*小さい*定義がいくつも見つかった。たとえば、`TTImp.ProcessRecord.elabGetters`はP=26、B=110で、それでも約2.0秒かかる。`Idris.Elab.Implementation.methName`はP=21、B=39で約0.66秒、`Core.Case.CaseBuilder.addGroup`はP=18、B=57で約0.85秒である。これらは、すでに知られていた本当にBが大きいもの(`TTImp.PartialEval.mkRHSargs`はP=14だがB=6433で、約8.5〜9.0秒)と並んでいる。わずか数十ノードの本体が1秒近くかかるというのは、Pが数十の、純粋にメモリ内の`Int`/`SortedSet`/`SortedMap`の操作として、このモジュールにある、O(P)、O(B)、O(P x B)、O(P^2)のどの形でも額面どおりには説明できない。

これを追いかける途中で、本物のO(P^2)が1つ見つかったので直した。`fullLoopParams`は、`argIds`のパラメータ`p`ごとに、`shadowedVariant ++ shadowedInvariant`(それ自体が最大でP個)に対して`Data.List.find`(線形走査)を呼んでおり、O(P)の検索をO(P)回行っていた。これを`shadowedById`に置き換えた。`SortedMap Int (Int, PrimType)`を一度だけ(O(P log P))作り、パラメータごとに(合計O(P log P))引く。正しく、計算量も厳密に改善されているので、そのまま残した。ただし、**再測定しても、警告対象の定義の時間は一切変わらなかった**(`elabGetters`は約2.0秒、`addGroup`は約0.85秒のままである)。P=18〜26は、実際の定数係数のもとでO(P^2)の差が効くほど大きくない。したがって、この修正は正当ではあっても、これも原因ではなかった。

**この項の執筆時点では、原因は未解明だった。** コード上の修正で検証した2つの仮説(ネイティブ引数型の解析のバッチ化と、`fullLoopParams`の2乗の解消)は、いずれもこれらの具体的な数値を動かさなかった。このことから、このモジュールのソースを読んで見つけられる計算量のクラスは、すべて除外される。残る原因は、次のいずれかの可能性が高い。1つは、`applyLoop`が(小さな)不変パラメータの集合ごとに1回ずつ呼ぶ、多数の小さなヘルパー関数のどれかにある、呼び出しごとの固定的なオーバーヘッドである。深く入れ子になったelaboratorのクロージャが捕捉する多数のパラメータの大半が、ループ不変であるなら、ありうる話で、その場合、ここでのPは、前の項の用語でいう「P_invariant」である。もう1つは、ランタイムレベルの要因(周囲のパイプラインに由来するGCの負荷や、`mutual`ブロックを多用するこれらのコンパイラ内部の定義に特有のアロケーションパターン)で、`Compiler.RC2.Loop`のソースを読むだけでは決着がつかない。見つけるには、仮説と再測定のサイクルを重ねるよりも、`idris2-rc2`バイナリ自体に実際のプロファイラ(たとえばChez Schemeのサンプリングプロファイラ)を使う必要がある。この項でこれまで使ったものとは別の道具を必要とする後続の課題として残した。

**3つ目の修正も、測定可能な効果がなく、原因の範囲をさらに絞り込んだ。** `rewritten`の計算は、もともと不変パラメータごとに`foldr`の中で`stripOwnership (SortedSet.singleton p)`を1回ずつ呼んでいた。`stripOwnership`のフィルタリングは、ノードごとの純粋な集合の所属検査であり、異なるid同士の相互作用はない(場合分けをすべて読んで確認した)。したがって、不変パラメータのidの集合*全体*を1回の呼び出しで剥がすことは、1つずつ順に剥がすことと完全に等価であり、パラメータごとに本体の大きさ分の走査を繰り返さずに済む。そのように変更した(`invariantIdsAll`で、`stripOwnership`の呼び出しを最大P_invariant回から1回にした)。正しく、不変パラメータが複数ある定義では、本体の走査が実際に減る。しかし、同じ実プログラムで再測定すると、警告対象の定義の時間は**やはりまったく変わらなかった**(`elabGetters`は約2.06秒、`methName`は約0.68秒のままである)。

互いに独立した、それぞれ安全性を確認済みの3つの修正は、ネイティブ引数型の解析のバッチ化、`fullLoopParams`の2乗の解消、そしてこの`stripOwnership`の統合である。これらはそれぞれ、不変パラメータごと、または引数ごとに繰り返される処理の、別々のもっともらしい原因を狙った。しかし、これらの具体的な数値を*まったく*動かさなかった。これは、それ自体が1つの情報である。残っているコストは、`Compiler.RC2.Loop`のソースから確認できるどの形でも、単に「冗長なO(何か)の走査が多すぎる」のではない、ということを意味する。走査の回数や計算量を減らす3種類の変更を、1つずつ適用し、そのたびに回帰スイート全体が壊れないことを確認した。それでも観測できる変化はまったくなかった。ソースを読んで`applyLoop`を「単純化」する同種の試みは、時間が実際にどこで使われているかのプロファイルを先に取らない限り、これ以上うまくいきそうにない。その道具がない状況では、この調査はここで打ち切るのが妥当である。

**それでも見つかった。本当の原因は、これらの計算量のクラスのどれでもなかった。** `applyLoop`の`let`束縛は、全体にわたって、Idris2の2行形式の`name : Ty` / `name = value`で書かれていた。この形式は、単純な共有された`let`束縛ではない。`Idris.Parser.idr`の`letBlock`(`letBinder <||> letDecl`)によれば、宣言と定義が2つの別々の行にある束縛は、`letDecl`の選択肢でしか構文解析できない。それは本物の*ローカル関数*の宣言であり(`where`節の定義が通るのと同じ仕組みである)、`letBinder`の単一節の形式`name [: Ty] (= | := ) value`ではない(文法を直接読んで確認した。そこでは`=`と`:=`は同じように構文解析される)。複数回参照される0引数のローカル関数は、ちょうど1回だけ評価されて共有されるとは限らず、参照のたびに再度呼び出されうる。`applyLoop`には、このような束縛が約24個あり、そのうちのいくつか(`shadowedVariant`、`shadowedInvariant`、`fullLoopParams`、`invariantIds`など)は、下流の複数の箇所から参照されている。Idris2(またはこのコンパイラ自身がブートストラップされるChezバックエンド)がこれらをメモ化しないなら、参照のたびに、その1つの束縛だけでなく、それが依存するすべてのものが推移的に再計算される。これが連鎖全体で積み重なる。`P`や`B`には関係がない。この形が、正しく考えられた3つの独立した計算量の修正(バッチ化、`fullLoopParams`のO(P^2)、`stripOwnership`の統合)が、すべて*まったく変化なし*と測定された理由である。どれも、計算される*値*にあった実在の非効率を直したが、それが*何回計算されるか*には触れていなかった。

**修正**: 2行形式を、単一の`name : Ty := value`の節(`letBinder`の形式)に書き換える。この形式は、ローカル関数の宣言と取り違えられることがない。`applyLoop`で最も多く参照される束縛を、この方法で変換した。`nextId0`、`eligibleVariant`、`eligibleInvariant`、`hoistResult`である。(`letBinder`は、末尾に`where`節を付けられない。`wrapInvariantShadows`の`wrapOneInvariant`ヘルパーは、本物の複数引数のパターンマッチ関数であり、単純な値の束縛ではもともとないので、通常のローカル関数の形のままにした。これは正しい扱いである。)

同じ実プログラムで検証した結果、`rc2: Loop conversion`は約44秒から約0.65秒に下がった。この調査の途中で追加した定義単位の`logTimeOver`の診断も、*どの*定義も警告しなくなった。`elabGetters`も、`mkRHSargs`も、`{rc2_mutualLoop:N}`ディスパッチャのどれも警告されない。評価モデルに関する修正1つで、それまでの計算量を狙った3つの試みが手を付けられなかった不可解なケースが、すべて解消した。

**これと並行して分かった注意点(多数の束縛を一度に変換した経験から)**: Idris2自身のelaborator(`Compiler.RC2.Loop`をコンパイルする「フロントエンド」であり、`Compiler.RC2.Loop`が出力するものではない)には、1つの`let`ブロックにある`:=`束縛の数や形に結びついた、実在する性能上の断崖があるようである。約24個の束縛を1回で変換したところ、`idris2 --build`のelaborationの段階自体が、RSS 14GB以上に膨れ上がり、強制終了する必要があった。上の修正が変換するのは、実際に複数回参照される少数の束縛だけである(共有の問題の解決に必要なのも、もともとそれだけだった)。1回だけ参照される残りの束縛は、まとめて変換せず、意図的に元の2行形式のまま残した。これをさらに進める場合は、一度にではなく、少数ずつ変換し、そのたびにビルドし直すべきである。

8. **共有スロットが、メンバーごとに異なる型を持っていた問題(2026-09-26)。** 以前は、メンバーは位置によって`slot_0 .. slot_k`を共有していた。そのため、1つのスロットが、あるメンバーのクロージャと別のメンバーの`Int`を保持することがあった。ネイティブシャドウへの昇格は、*一部の*メンバーがそのスロットをネイティブとして読むと、スロット全体を昇格させる(4番と同じ、グループ全体への影響である)。その結果、クロージャが`Int`としてunbox化された。world arity raising(`world-arity-raising.md`)によって、`BenchArityRaise.idr`の`run`と、クロージャを適用する継続が相互末尾再帰になった後で、継続の`apply`が、クロージャの代わりにboxed `Int`を受け取った(`malloc(): corrupted top size`。valgrindでは、`idris2rc2_tailcallApplyClosure`での不正な書き込みとして出た)。IRには、パラメータがどの型を持つかは書かれておらず、どう読まれるかだけが書かれている。そこで最初は、各メンバーに専用のスロットのブロックを与え、1つのスロットが、1つのメンバーの1つのパラメータだけを保持するようにした。しかしそれでは、idris2-lspの統合した関数のパラメータが合計1,567個になり(28メンバーのうちの1つで330個)、Loop conversionが0.5秒から4.4秒に増えた。しかも、すべての遷移が、他のすべてのメンバーのブロックに`RCNull`を書き込むことになった。現在のメンバーは、再び位置によってスロットを共有するが、共有するのは同じ分類のパラメータの間だけである(前述)。`Nothing`の分類のスロットは、決して昇格させない。これによって、パラメータは合計383個、最大でも20個になり、Loop conversionは0.5秒になった。主ループがそのような統合したグループである`BenchArityRaise`は、1.02秒から0.75秒になった。

## 既知の制限: ネイティブシャドウの適格性が、トップレベルの裸のスカラーで止まる

実際のサードパーティパッケージ(`idris2-missing-containers`のハッシュアルゴリズム。数値の全体は`rc2/BENCHMARKS.md`の2026-08-14の項を参照)で測定した結果である。ループパラメータが昇格されるのは、そのパラメータ*自身*が、ネイティブ適格な型を持つローカルであり、かつ`ROp`/`RCmpCase`のオペランドとして直接読まれる場合に限られる。

**この問題は、当初`newtype`の分解の漏れだと誤診していた。** 以前の記述は、次のように主張していた。単一フィールドの`newtype`風のコンストラクタに包まれた数値の状態(たとえば`data FNV1a = MkFNV1a Bits64`。このパッケージのすべての`HashAlgorithm`インスタンスが使う形)が見逃されるのは、ループ自身のトップレベルパラメータが「コンストラクタ」であり、ネイティブの値は、明示的な分解の後にしか現れず、`nativeArgType`はその先を見なかったからだ、という説明である。**これは誤りだった。** 最小の再現例について、`--directive dumprcexpr`の出力で直接確認した。`newtype`として適格な本物のコンストラクタは、構築もマッチも、rc2が`Lifted` IRを目にするより前に、Idris2自身のフロントエンドによって*完全に*消去されている(上流の`Compiler/LambdaLift.idr`の、`MkLCon`の`nt`フィールドに関するドキュメントコメントを参照: 「backend implementations needs not make use of this argument, as newtype unboxing is managed by the Idris 2 compiler」)。rc2側の解析が分解すべきコンストラクタは、そもそも残っていなかった。rc2の`RCDef`の`newtype=`メタデータ(`Compiler.RC2.Pretty`のダンプのフィールド)は、表示のためだけに引き継がれており、`Compiler.RC2.Loop`/`DualABI`が参照することは一切ない。

本当の原因は、コンストラクタが一切ない素の`Bits64`パラメータで、*同一の*症状を再現して確認した。複数の演算からなるANFの連鎖(たとえば、ハッシュのステップの形をした`(v \`xor\` cast b) * k`)は、トップレベルパラメータのネイティブコンテキストでの読み取りを、外側のネイティブ型の`RLet`の`value`に直接置かず、*内側の*`RLet`の`body`(その内側のletの最後の演算)に置く。`nativeArgTypes`の`opNativeUsesThrough`ヘルパーは、前者の形しか見ていなかった。

修正として、`opNativeUsesThrough`が、入れ子の`RLet`の`body`にも再帰するようにした。外側ですでに決まっている*同じ*ネイティブの`Rep`を、連鎖の最後にある裸の`ROp`まで伝える。保守性は以前と同じである(入れ子の`RLet`自身の別の`value`には、ここでは特別な扱いをしない。`nativeArgTypes`の既存の無条件の再帰が、それを独立してすでにカバーしており、*そのlet*自身の`Rep`で制御されている)。これより前の、より広い修正の試みでは、*どんな*裸の`ROp`も、その上に囲むネイティブの`RLet`が一切なくても、ネイティブとして扱っていた。根拠は、その演算自身の`opResultRep`だけで、これは`Compiler.RC2.DualABI`の`tailValueReps`が、*戻り値*の適格性にすでに使っているのと同じ、信頼できる情報源である。この版は、`Test110Loop/SelfTailLoop.idr`で、`valgrind`が検出する実際のリークを起こした。`tailValueReps`は、まったく同じ演算についての戻り値の適格性を、組にして同時に計算するので、両者が食い違うことは決してない。これと違って、`nativeArgTypes`の結果は、`Compiler.RC2.Loop`自身のループパラメータの昇格にも使われる。その昇格は、どの関数の戻り値の適格性が決まるよりも*前*に走る。そのため、裸の末尾は、その時点ではまだBoxedとして描画されることがありえて、実際にそうなった。推測したネイティブ性に基づいて、まだBoxedな読み取りの所有権の記録を剥がしたため、新たにre-boxされた値には、それをdropするものが何も残らなかった。`rc2/tests/Test13NativeArgChain.idr`を参照(`chain`が修正対象の形である。`flat`は、囲む`let`が一切ない、保護されていない単一の`ROp`で、意図的に`RBoxed`のままにしてある。対照として、同じテストファイルに入れている)。

この修正は、*ループではない*関数のパラメータについても、同じ問題を解消する。同様に、`Compiler.RC2.DualABI`のワーカーパラメータの適格性も解消する(たとえば、ループの内側から、ループのアキュムレータを引数にして呼ばれる、要素ごとのヘルパー`step`)。`--directive dumprcexpr`で確認したところ、そのようなヘルパーのワーカーは、このパラメータを、`Boxed`ではなく`Native`と正しく宣言するようになった。

**一般的なケースについては、解消済みである。** 上記の`step`のようなヘルパーへの呼び出しだけを通じて持ち回られる、ループ内のパラメータが、`ROp`/`RCmpCase`のオペランドとして直接読まれる場合と同じ、ネイティブシャドウへの昇格を受けるようになった。`Compiler.RC2.Loop`の`calleeNativeParams`/`buildCalleeTable`は、`MutualLoop`の後、`Loop`の前の定義リストから、プログラム全体のテーブルを一度だけ作る。各エントリは、その1つの定義自身の(変更のない)`nativeArgType`の判定をパラメータごとに記録するだけで、他のエントリを参照することはない。そのため、不動点や循環の処理は必要ない(`MutualLoop`が統合したディスパッチャは、`isMutualLoopMerged`で除外する。これは`Compiler.RC2.DualABI`の中にだけあったのを、`Compiler.RC2.Util`に移して共有している)。次に`callArgNativeTypes`/`callArgOrOpNativeType`が、トップレベルパラメータ`p`について、テーブルが示す、その位置で独立にネイティブ適格になっている呼び出し先に、直接かつ飽和した引数として渡されているかどうかを問う。`applyLoop`は、この結果を`eligibleVariant`に合併する(`RC2.idr`の`toRCDefs`から引き回す、新しい`calleeTable`引数を使う)。

2つの範囲の制限が残っているが、これは意図的であり、見落としではない。

- **呼び出しの1段までしか追わない。** 多段の委譲の連鎖(`loop`の`acc`が`mid`に渡され、`mid`はそれを`step`に転送するだけ)は対象外である。`mid`のパラメータが、*それ自体で*すでに`nativeArgType`適格(`mid`の中で、演算や比較のオペランドとして直接読まれる)である必要があるが、単なる素通しのパラメータは、決してそうならない。
- **変化するループパラメータだけが対象。** ループ*不変*パラメータ(すべての`RLoopContinue`で変化しない)は、意図的に除外している。不変パラメータのネイティブな出現を、そのシャドウに向け直す唯一の場所は`markInvariantNative`だが、これには`RAppName`のケースがない。呼び出し引数としての出現だけを根拠に昇格させると、何からも読まれないシャドウが作られる。無駄にはなるが、安全ではある(`dupInvariantBoxed`の汎用の`RAppName`のケースが、向け直されていない出現を、通常のdupと遅延されたdropによって、どのみち正しく処理する)。`markInvariantNative`に`RAppName`のケースを教える作業とあわせて、後続の課題として残した。

これにより、box化とunbox化の往復(ループで持ち回るアキュムレータを、`step`に渡すためにbox化し、`step`のワーカーが再びunbox化する)のうち、*引数*を渡す側が解消した(`rc2/tests/Test110Loop/LoopCallArgNativeShadow.idr`の`--directive dumprcexpr`と生成されたCの差分で確認した。`step`のワーカーへの呼び出しは、ループ内で持ち回るアキュムレータを、ネイティブの`int64_t`として直接読み、呼び出し地点での`idris2rc2_to_i64`の変換はもうない)。

**そのような呼び出しから次の反復の持ち回る値へ戻る*結果*の側も、解消した。** 以前は、呼び出し先のワーカーがすでにネイティブを返しているのに、結果は`idris2rc2_mkInt64`でbox化された後、次の反復のシャドウのために、すぐに`idris2rc2_to_i64`でunbox化されていた。`Compiler.RC2.DualABI`の呼び出し地点の書き換え(`nativePromotionFor`)に、`RLoopContinue`の引数位置を、直前の`RLet`の値を受け取るネイティブコンテキストの消費者として認識するケースがなかったためである。修正は、`Compiler.RC2.DualABI`に新しく加えた`loopContinueNativeReads`で行った。これを`nativePromotionFor`の適格性の判定に、`nativeArgTypes`/`bareTailNativeReads`/`callArgNativeReads`と並べて合併する。この関数は、`fillLoopContinuePostDrop`と同じ、末尾を保つ骨格を走査し、`RLet`が束縛した値が、囲む`RLoop`の`RLoopContinue`の、`loopParams`がすでにネイティブとしている位置に直接渡されているかどうかを問う。`rc2/tests/Test110Loop/LoopCallArgNativeShadow.idr`に取り込んだ、元の`Test58LoopContinueNativePromotion.idr`のケース(同じファイルの`step`/`loop`の形をそのまま再利用している)で確認した。`step`の呼び出し結果を束縛する`RLet`は`Native Int`と表示される。生成されたCは、そのローカルをワーカーの呼び出しから直接宣言し(`int64_t var_4 = idris2rc2_worker_...`)、`goto loop;`の再代入までの間に、boxやunboxの呼び出しはない。

動機となったベンチマークの支配的なコストは、上記とは無関係な、別の2つの理由で、そのまま変わらない。このベンチマークについて、上記の修正だけで大きく改善すると考える前に、念頭に置いておく価値がある。

- インターフェース経由で呼び出される比較(`Ord`の`<=`など)は、`RCmpCase`に融合されない。この融合が認識するのは、直接の`PrimFn`による比較だけで、型クラスのメソッドを通した呼び出しは認識しない(`doc/native-type-inference.md`の「Comparisons are a separate, narrower mechanism」の節を参照)。ネイティブシャドウ化されたループカウンタは、そのような比較に渡すためだけに、再びboxされる。
- `IOHashMap`の書き込み/読み出しの経路で支配的なのは、`IORef`と配列へのアクセス、およびコンストラクタのリストによるバケットの走査であり、数値のアキュムレータのループではまったくない。ネイティブシャドウ化は、どれほど拡張しても、そのどちらにも届かない。

## 検証の方法

1. ビルドと回帰テストのベースライン: `CLAUDE.md`の「Build & test」の節を参照(`idris2 --build rc2.ipkg`、続いて`tests/refc-suite/run.sh`を実行し、19/19になることを確認する)。
2. `tests/Test110Loop/SelfTailLoop.idr` -- 自己末尾呼び出しの変換に特化したテストである。パラメータの入れ替え(並行代入のための一時変数への退避が必要になる、エイリアシングの危険)、1つの関数内にある複数の異なる再帰の枝、そのまま素通しされる引数(再計算ではなく「move」)を扱う。また、このパスだけでは単純な相互再帰に手を付けないことも確認する。さらに、ネイティブシャドウへの昇格の後は、ネイティブ適格な型と適格でない型が混在するループの標準的な例(`countDown`の`Int`のカウンタと、素通しされる`String`)と、`ROp`/`RCmpCase`ではなく`RConstCase`の使用によって昇格するループパラメータの例になっている(「発見・修正したバグ」の3番を参照)。
3. `tests/Test110Loop/SelfTailLoop.idr`(上の2番と同じファイルで、以前の`Test10MutualLoop.idr`を取り込んでいる) -- 相互ループの変換に特化したテストである。アリティの異なるグループメンバー(スロットのパディング。「発見・修正したバグ」の4番を見つけた、まさにその形)、3者のサイクル(単純な2者の対を超えるSCC)、統合したグループ内の同一メンバーへの遷移(メンバー間だけではない)、グループの外から、末尾ではない呼び出しとファーストクラスのクロージャの値の両方で呼ばれるグループのメンバー、および、Cスタックが伸びない30万〜50万段の相互再帰(`goto`への変換が実際に働いていることの、型検査が通っただけではない直接の証拠)を扱う。
4. `tests/BenchLoop.idr`/`tests/BenchMutual.idr` -- 生成されたCを調べる(`grep -n "^IDRIS2RC2_Value \*Main_sumTo$" -A20 build/exec/*.c`など)。すべてのループ内で持ち回るパラメータにネイティブシャドウへの昇格が適用された後は、ループ本体に`idris2rc2_mk*`/`idris2rc2_dup`/`idris2rc2_drop`の呼び出しが1つもないことを、直接確認する。`idris2 --cg refc`との実時間の比較結果(それぞれおよそ60倍/11倍)は、`rc2/BENCHMARKS.md`の2026-08-14の項を参照。
5. 候補となる関数に対する`--directive dumprcexpr`(`doc/reading-the-ir.md`を参照)は、生成されたCを見る*前*に、ある定義の本体が`loop [...]`で始まっているか(変換されたか)、その行でどのパラメータが`Native <ty>`と表示されているか(昇格されたか)を確認する、最も速い方法である。`doc/reading-the-ir.md`の7節と8節が、まさにこの手順を説明している。
6. `tests/Test110Loop/LoopInvariantParam.idr` -- ループ不変パラメータの除去に特化したテストである。Boxedなパラメータ(`tag`)とネイティブシャドウ適格なパラメータ(`limit`)を1つずつ、実際に変化するアキュムレータとカウンタの組と並べて、すべての再帰呼び出しでそのまま持ち回る。これによって、2種類の除去(とその、大きく異なる所有権の扱い。巻き上げたネイティブのものには明示的な`RDrop`があり、Boxedのものには何もない)を、`valgrind`で確認する。`.rcexpr`ダンプの全体は、`doc/reading-the-ir.md`の8.5節を参照。同ファイルの`sumWithBoxedContinuePath`/`sumWithBoxedExitOnly`は、前述の「生き残ったBoxedコンテキストの読み取りに元のBoxed値を再利用する」を特に対象にしている。不変でネイティブシャドウ適格なパラメータが、ループの継続経路でもBoxedコンテキストで読まれる場合(反復のたびに再び`dup`される)と、終了側の枝でだけ読まれる場合(1回だけ`dup`される)を扱い、どちらも`valgrind`でクリーンである。`tests/BenchLoopInvariantBoxed.idr`は、継続経路の形を300万回の反復で実行する。反復ごとのリークを見紛いようにするためと、その結果の実時間の差を測るためである(この形では、修正前の毎回re-boxしていた挙動より約25%高速になった。`rc2/tests/bench.sh`)。
7. `tests/Test110Loop/LoopInvariantParam.idr`(同じファイルのさらに後ろ) -- ループ不変な式の巻き上げの、肯定的なケースである。`bound = limit * 2`は、ループ本体の無条件の接頭辞にある`Native Int`の`ROp`であり、すでに巻き上げられたネイティブシャドウのパラメータにだけ依存する。`--directive dumprcexpr`で、`loop [...]`の完全に外側、そのパラメータの`RLet`の内側に入れ子になって配置されることを確認した。
8. `tests/Test110Loop/LoopInvariantParam.idr`の`sumOrCtx`(同じファイルのさらに後ろ。以前の`Test21BoxedInvariantNotHoisted.idr`を取り込んでいる) -- 否定的なケースであり、この節の作業が生んだ回帰テストのうち、最も重要なものである。ループの終了側の枝でだけ使われる、`Boxed`の`Rep`を持つ不変な`RCon`が、`loop [...]`の*内側*にとどまり、`valgrind`をクリーンに通ることを確認する。`hoistInvariantPrefix`の`isNativeRep`のガードがなければ、まさにこの形で二重解放が起きる。開発中に直接再現した(`malloc(): unaligned tcache chunk detected`。`valgrind`で、本物の二重解放であることを確認した)。詳しい説明は、前述の「ループ不変な式の巻き上げ」の節を参照。
