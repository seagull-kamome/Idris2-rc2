# 投機的・採否判定付きクロージャ引数特殊化: 調査・設計はしたが未実装

(原文: `doc/speculative-closure-specialization.md`。内容が乖離した場合は原文を正とする。)

本書は、`rc2/doc/loop-in-case-sinking.md`自身の「関連する、より大きなアイデア」節が最初に提起した、クロージャ特殊化アイデアの「段階1」(高階関数自身のクロージャ引数の`apply`を、必ずしも対象の本体をインライン展開せずに、直接の名前付き`call`へ解決する)として検討した設計を記録する。合わせて、upstream Idris2自身の`%spec`機構がこれをタダで提供できるかどうかを完全に調査し、この調査のきっかけとなった具体的なケースに対してなぜそれができないのかも記録する。**ステータス: 紙の上で設計しただけで、未実装。** 本コミットにコード変更は一切含まれない。

## 動機

`idris2-missing-containers`の`Main.idr`は、自前の小さな`foldl`型の走査を持つ:

```idris
go : List String -> (String -> IO ()) -> IO ()
go [] _ = pure ()
go (x::xs) f = f x >> go xs f
```

`--directive dumprcexpr`で確認すると、`Compiler.RC2.Loop`はこれを正しく本物の`RLoop`に変換しており、`go`が`benchmarkHashMap`の`write`フェーズと`read`フェーズ両方を実際に駆動していることも確認できる——この2フェーズは、本プロジェクト自身のプロファイリング(`rc2/BENCHMARKS.md`)が既にこのベンチマークの壁時計時間を支配していると突き止めていたものそのものである。`go`自身のloopの毎回の反復は、1要素を処理するために`apply v1 v3`——boxedで間接的なクロージャディスパッチ(`idris2rc2_applyClosure`)——を行っているが、`go`自身のこのプログラム中の実際の2箇所の呼び出し元それぞれでは、`go`に渡されるクロージャは*任意の実行時の値ではない*: 常にただ1つの、特定のトップレベルコールバック(`write`フェーズでは`IOHashMap.write`を駆動する方、`read`フェーズでは別の`IOHashMap.read`を駆動する方)である。

もし`go`を、実際に観測された別個のクロージャ対象ごとに1回だけ複製し、その複製自身の`apply v1 v3`を既知の対象への直接の名前付き`call`へ解決できれば、本セッション自身の先の調査がboxedクロージャ/interface辞書ディスパッチに帰した1反復あたりのディスパッチオーバーヘッド(`TODO.md`の「Performance: interface-dictionary method dispatch stays boxed...」項目、および本セッション自身の`HasIO`多相性に関する発見)は、interfaceメソッドに限らず、普通の高階関数引数に対してもここに当てはまることになる。

## なぜupstreamの`%spec`をそのまま使わないのか: 完全な調査

Idris2自身の部分評価器(`TTImp.PartialEval`、`%spec`プラグマ)を、rc2側を一切変更せずフロントエンドレベルでこれをタダで得る手段として調査した。実測(最小限の再現コードを`--log specialise:5`で確認し、生成Cも確認)で2つの本物の前提条件が見つかった。うち1つは本調査の最初の通過時には見落としており、セッション途中で訂正している:

1. **特殊化対象の引数は、定義節だけでなく型シグネチャ自身で明示的に名前を付けなければならない。** `apply1 : (Int -> Int) -> Int -> Int`(シグネチャでは引数が無名のまま、節`apply1 f x = f x`でのみ`f`と名付けられている)に対する`%spec f`は、*一行もログを出さず*、複製も*一切生成せずに*沈黙する——ログに記録された失敗ではなく、完全な沈黙である。これは`specArgs gdef`(`%spec`が実際に印を付ける位置の集合)が、シグネチャ上で無名の位置に対しては一切populateされないためである。全く同じ`%spec f`の行のまま、`apply1 : (f : Int -> Int) -> Int -> Int`と名前を付け直すと即座に動作し、`--log specialise:5`は`New RHS: (prim__add_Int x[0] 1)`——特殊化された複製の本体全体が、対象関数を含めて、残存する間接性ゼロの生のプリミティブ演算まで完全に展開された——を示した。これは`%spec`の本物の、確認済みの能力である: interface辞書やプレーンなデータ値だけでなく、普通の関数型(クロージャ)引数を通しても特殊化*できる*——本調査の最初の通過時の結論(「関数型引数は非対応」)は誤りであり、ここで訂正する。
2. **呼び出し箇所で渡される値は、それでもなお真に閉じた項でなければならない**(`PartialEval.idr`自身の`concrete = shrink tm none`、すなわち自由変数が一切無いこと)——上記の命名修正とは無関係で、これが`go`自身の実際の呼び出し箇所を救えない本当の理由である。2つ目の再現コードで確認した: `test base = ...`という関数の中で`apply1 (addBase base) 5`とした場合、`addBase base`は*ローカル*パラメータ`base`を捕捉した部分適用であり——シグネチャの命名修正を適用してもなお、全く同じ、ログ出力ゼロの無反応が発生した。`go`自身の`idris2-missing-containers`における実際の2箇所の呼び出しは、まさにこの形である: `go words $ ignore . pure . hash h`(`h`は`benchmarkHash`自身の引数)と`go dict $ \x => do ... hm ...` / `go words $ ignore . read hm`(`hm`は`benchmarkHashMap`内のローカルな`let`束縛値)——どちらも閉じた項ではない、たとえ各々が最終的に実行するコード自体は各呼び出し箇所で固定・既知であっても。`%spec`自身の閉鎖性要求には、「このクロージャの背後にあるコードポインタは、捕捉する環境が違っても不変である」という、プレーンな閉鎖性より厳密には弱いが、それでも活用可能な性質を表現する手段が無い。

**上記2つの前提条件とは別に、直交する話として**: upstream自身の`mkSpecDef`には採否判定が一切無い。唯一のフォールバック経路は、特殊化中の*本物の elaboration エラー*(`handleUnify`自身のエラーハンドラ、`logC "specialise.fail"`、試みを捨てて元の呼び出しを再利用する)だけであり——「特殊化は成功した(本物の複製を生成した)が、汎用版より小さくも間接性が少なくもならなかった」場合を検出する仕組みはどこにも無い。特殊化対象の引数がたまたま閉じている呼び出し箇所は全て、無条件に完全な複製を得る。これは実際に過去に起きた問題と一致する: 無制限の特殊化がコードサイズの爆発を実際に引き起こしたことがあり、それを食い止める組み込みの仕組みは無かった。これが本書自身の動機の後半であり、そもそも`%spec`が`go`自身の呼び出し箇所に到達できるかどうかとは独立の話である。

## 提案するrc2独自の設計

`%spec`が動機となったケースに到達できず(閉鎖性のため)、到達できる場合でも採否判定を持たない以上、本節では`Compiler.RC2.ConstFold`が既に走った後の`RCExp`に対して動作するrc2側の機構を設計する。「このクロージャ引数はコンパイル時定数か」という既存の`RCConstClosure`(`rc2/doc/const-closure-fold.md`)による検出をそのまま再利用する——これはまさに`%spec`自身の閉鎖性チェックには捉えられない「コードポインタは不変、環境は違ってよい」という性質を捉える。`ConstFold`/`Inline`自身の推論は既にラムダリフト後、リフトされたクロージャ値自身(`partial Main.{benchmarkHashMap:19} missing=2 [v85, v80]`)に対して動作しており、自由変数の捕捉を伴うリフト前の表層項に対してではないからである。

### 1. 候補の検出

ある関数`g`(動機付けの例では`go`)の呼び出し箇所ごとに、`g`自身のパラメータの1つが`g`自身の本体の中で`apply`経由でしか使われていない場合、この呼び出し箇所で供給される*引数*が——`ConstFold`後に——どの自由変数を捕捉しているかに関わらず、常に同じ名前付きトップレベル関数であると証明できるかを確認する。これは完全な閉鎖性より弱い条件である: `partial Main.{benchmarkHashMap:19} missing=2 [v85, v80]`と`partial Main.{benchmarkHashMap:19} missing=2 [v200, v201]`(異なるローカルを捕捉するが同じ対象関数を名指す、2つの異なる呼び出し箇所)は、`%spec`自身の意味では閉じた項ではないにも関わらず、この目的では両方とも「同じ対象」として数える。`g`が実際に呼ばれる対象の*集合*を、プログラム全体にわたって収集する。

### 2. 投機的な複製+再畳み込み、対象ごとに1回だけ試みる

手順1で見つかった別個の対象ごとに(メモ化する——ある`(g, target)`の組は、いくつの呼び出し箇所がそれを共有していようと1回しか試みない。これにより複製の総数は呼び出し箇所の数ではなく、実際に観測された*別個の*対象の数によって抑えられる):

- `g`自身の本体を複製し、特殊化対象パラメータへの全ての`apply`を、直接の`call target [...]`(`target`自身の捕捉された/自由な引数を、`Compiler.RC2.Inline`自身の既存のスプライシング機構が普通のcall-freeな呼び出し先に対して既に行っているのと同じ形で、複製の追加パラメータとして通す)へ書き換える。
- 複製*だけ*に対して`ConstFold`/`Inline`を再度走らせ(プログラム全体に対してではなく)、この直接呼び出しが新たに露出させるであろう更なる畳み込みを実際に起こす——例えば`target`自身が小さくcall-freeなら、呼び出しがもはや`apply`の裏に隠れていないため、`Inline`の既存のCriterion Aが今度はそこへ届く。

### 3. 採否判定 -- 実際のゲート

畳み込んだ後の複製自身の本体を歩き、確認する: 特殊化対象パラメータへの`apply`ノード(あるいは、推移的に、特殊化が除去しようとしていたのと同じ種類のboxedディスパッチ)がまだ残っているか?

- **その種の`apply`が残っていない** -- 特殊化は狙い通りのことを実際に達成した(`apply1`/`inc`の再現コード自身の`New RHS: (prim__add_Int x[0] 1)`が、間接性の痕跡が全て消えた理想的な実例である)。**複製を採用する**; この`(g, target)`の組を共有する呼び出し箇所を全てこの複製へ差し替える。
- **まだ残っている** -- クロージャは畳み込みが届かない場所へ逃げた(データ構造に格納された、返り値になった、畳み込みが解決しなかった分岐の中で適用された等)——複製は汎用版に対して何も得をせず、同じ間接性の2つ目のコピーを持っただけである。**複製を破棄する**; 全ての呼び出し箇所は元の汎用な`g`を呼び続ける。

これは意図的に**構造的な**チェックであり、サイズ閾値のチェックではない——「狙っていた間接性を実際に除去できたか」に答えるのであって、より曖昧な「結果として小さくなったか」ではない。後者だと、本物には良いがテキスト上は大きくなった結果を誤って却下したり、小さいが役に立たない結果を誤って採用したりする恐れがある。計算コストも安い: 既に畳み込んだ複製を1回線形に歩くだけで、別途コストモデルを用意する必要も無い。

## なぜこれはrc2にとって設計上新しいか

既存のrc2の各パス(`Inline`のCriterion A、`ConAltNative`、`ConstFold`自身、`loop-in-case-sinking.md`の沈め込み変換)は全て、未変換の入力自身の形から、変換する**前に**適格性を判定する——純粋で一方向的な「まずチェックしてから書き換える」パイプライン段階である。本設計はこれに対し、まず**投機的に**変換を行い、**結果に基づいて**判断する——`Compiler.RC2`にこれまで前例の無い「試してから、採用するか破棄するかを決める」形である。健全性上の懸念ではない(破棄された複製は単に何からも参照されなくなるだけなので、実行時コストはゼロであり、他の未参照定義と同じく`Compiler.RC2.DeadCode`によって落とされる)——ただし、これを構築する前に、既存パスの小さな拡張ではなく新種のパスアーキテクチャであると明示的に名指しておく価値がある。

## `loop-in-case-sinking.md`との関係

同書自身の「関連する、より大きなアイデア」節は、loop専用の小さな関数を、それ自身既にloopしている呼び出し元へインライン展開することを検討し、特殊化・インライン展開された対象自身がloopである(あるいはloopを含む)場合には本物の入れ子loop対応(`Compiler.RC2.DualABI`の`loopContinueNativeReads`がスタックになる必要がある)が要ることを見つけていた。本書自身の設計は意図的にそれより狭く、その依存を完全に回避する: 上記手順2は`apply`を直接の`call`へ解決し、`Inline`自身の既存の(変更していない)Criterion Aを介して日和見的に再畳み込みするだけである——Criterion A自身が拒否するであろう対象(例えば対象自身が更なる呼び出しを含む、あるいは対象自身がloopである等)のインライン展開を強制することは一度も無い。たまたまloopである対象は、手順2の後も単に直接の`call`のままであり(もはや`apply`ではない、それ自体既に本物の勝ちである)、呼び出し元自身のloop本体へ差し込まれることは無い——つまり上記手順3の採否判定は(もう`apply`が無いという)自分自身の条件で合格し、対象の本体をインライン展開したり入れ子の`RLoop`ノードを生成したりする必要が一度も無い。**この設計は入れ子loop対応を一切必要としない**、それが生まれてきた元の「関連する、より大きなアイデア」とは違って。

## 未解決の懸念・リスク

- **1関数上に複数の特殊化対象パラメータがある場合**: `go`はクロージャパラメータを1個しか持たないが、複数持つ関数では手順1の候補集合が(パラメータごとに1つの対象からなる)*タプル*の集合になる必要があり、試みる別個の`(g, targets...)`複製の数が掛け算で増える——それでも(各パラメータ自身の別個の対象数の積で)抑えられる、通常は小さいはずだが、ここでは詳細設計していない。
- **パイプラインのどこで走らせるか**: `ConstFold`の後(`RCConstClosure`で畳み込まれた対象が見えるように)で走る必要があるが、`Compiler.RC2.Inline`自身の既存パスと相互作用する——これはその間の新しいステップになるのか、それとも(スプライシングやCriterion Aの再適用など、どれだけ機構を再利用しているかを考えると)`Inline`自身の改良になるのか? 未決定。
- **複製自身の所有権の再annotate**: 複製・書き換えされた`g`は、`Compiler.RC2.RC`の`annotate`(そして場合によっては`Reuse`/`ConAltNative`)を、その複製だけに対してもう一度走らせる必要がある——`Compiler.RC2.Inline`自身の既存のスプライシングが、差し込んだコードの所有権を再導出する際に既に扱わなければならないのと同じ形である——新しい問題ではないが、既存の機構が*トップレベル定義丸ごとの複製*(call-freeな呼び出し先の本体を差し込むだけではなく)をカバーしているか確認する価値がある。
- **`DupMerge`/`Loop`との相互作用**: これらより前に走る想定なので(`RC2.idr`自身の`toRCDefs`の順序に合わせる、`Inline`自身が既に早い段階で走っているのと同様)、衝突は無いと予想されるが、実際のパイプライン順序に対して検証していない。
- **これを(対象ごとにメモ化して)抑えることが実際に実世界の爆発を避けられるという計測済みの根拠はまだ無い** -- 上記の設計は、ユーザー自身の無制限な特殊化に関する過去の経験から推論したものであり、新しい計測からではない。実装前に、(多数の別個のクロージャ対象から呼ばれる関数という)合成的なストレスケースで、メモ化による上限が期待通りに振る舞うことを確認する価値がある。
