# 投機的なクロージャ引数の特殊化(採算判定付き): 調査・設計・実装

(原文: `doc/speculative-closure-specialization.md`。内容が乖離した場合は原文を正とする。)

本書は、クロージャ特殊化の「レベル1」にあたる設計を記録する。このアイデアは`rc2/doc/loop-in-case-sinking.md`の「関連する、より大きなアイデア」の節で最初に提起されたもので、高階関数が自分のクロージャ引数に行う`apply`を、対象の本体を必ずしもインライン展開せずに、名前付きの直接`call`へ解決する。あわせて、upstream Idris2の`%spec`機構でこれを追加の実装なしに実現できるかを調べた結果と、この設計のきっかけになった具体例で実現できない理由も記録する。**ステータス: `Compiler.RC2.SpecClosure`として実装済み**(`--directive nospecclosure`で無効化できる)。実際に出荷した内容、本書が今も正確に述べている紙上の設計との相違点、検証で分かったことは、後述の「実装メモ」にまとめた。

## 動機

`idris2-missing-containers`の`Main.idr`には、`foldl`に似た小さな走査関数がある。

```idris
go : List String -> (String -> IO ()) -> IO ()
go [] _ = pure ()
go (x::xs) f = f x >> go xs f
```

`--directive dumprcexpr`で確認すると、`Compiler.RC2.Loop`はこの関数を正しく本物の`RLoop`に変換している。`go`は`benchmarkHashMap`の`write`と`read`の両フェーズを実際に駆動している。この2フェーズは、本プロジェクト自身のプロファイリング(`rc2/BENCHMARKS.md`)が、このベンチマークの実行時間(ウォールクロック)の大半を占めると突き止めたものである。

`go`のループは、1要素を処理するたびに`apply v1 v3`を実行する。これはボックス化された間接的なクロージャディスパッチ(`idris2rc2_applyClosure`)である。ところが、このプログラムで`go`を呼ぶ2箇所のどちらでも、渡されるクロージャは任意の実行時の値ではない。`write`フェーズでは`IOHashMap.write`を駆動するトップレベルのコールバック、`read`フェーズでは`IOHashMap.read`を駆動する別のコールバックと、それぞれ常に特定の1つである。

そこで、実際に観測されたクロージャの対象ごとに`go`を1回ずつ複製し、複製の中の`apply v1 v3`を既知の対象への直接の名前付き`call`に解決する。こうすれば、先の調査がボックス化されたクロージャやインターフェース辞書のディスパッチに帰した1反復あたりのオーバーヘッドを、interfaceのメソッドに限らず、ふつうの高階関数の引数でも取り除ける。ここでいう先の調査とは、`TODO.md`の「Performance: interface-dictionary method dispatch stays boxed...」の項目と、同じセッションで得た`HasIO`の多相性に関する知見である。

## なぜupstreamの`%spec`をそのまま使わないのか

Idris2自身の部分評価器(`TTImp.PartialEval`、`%spec`プラグマ)を使えば、rc2に手を入れずにフロントエンドの段階でこの特殊化が済むのではないかと考え、詳しく調べた。最小の再現コードを`--log specialise:5`で確認し、生成されたCも確認したところ、`%spec`が働くための前提条件が実際に2つ見つかった。調査の初回の通過では片方を見落としており、セッションの途中で訂正している。

1. **特殊化する引数には、定義の節ではなく型シグネチャ自体で名前を付けておく必要がある。**たとえば`apply1 : (Int -> Int) -> Int -> Int`では、引数がシグネチャで無名のままで、節`apply1 f x = f x`の中でだけ`f`と名付けられている。この関数への`%spec f`は、ログを1行も出さず、複製も作らずに黙って終わる。失敗がログに残るのではなく、完全に無反応になる。`%spec`が実際に印を付ける位置の集合`specArgs gdef`に、シグネチャ上で無名の位置が一切入らないためである。`%spec f`の行をそのままにして`apply1 : (f : Int -> Int) -> Int -> Int`と名前を付け直すと、すぐに動作した。`--log specialise:5`には`New RHS: (prim__add_Int x[0] 1)`と出る。特殊化された複製の本体が、対象の関数まで含めて、間接呼び出しの残らない生のプリミティブ演算にまで展開されたのである。つまり`%spec`は、interface辞書やふつうのデータ値だけでなく、ふつうの関数型(クロージャ)の引数についても特殊化できる。調査の初回に出した「関数型の引数は対象外」という結論は誤りであり、ここで訂正する。
2. **呼び出し箇所で渡す値は、完全に閉じた項でなければならない。** `PartialEval.idr`の`concrete = shrink tm none`が、自由変数が1つもないことを要求する。前項の命名の修正とは無関係に、この制約が残る。これこそ、`%spec`が`go`の実際の呼び出し箇所を救えない本当の理由である。別の再現コードで確認した。関数`test base = ...`の中で`apply1 (addBase base) 5`と書くと、`addBase base`はローカルのパラメータ`base`を捕捉する部分適用になる。シグネチャに名前を付けても、やはりログが1行も出ず、特殊化は試行すらされない。`idris2-missing-containers`で`go`を呼ぶ2箇所は、まさにこの形をしている。`go words $ ignore . pure . hash h`(`h`は`benchmarkHash`のパラメータ)と、`go dict $ \x => do ... hm ...`および`go words $ ignore . read hm`(`hm`は`benchmarkHashMap`の中で`let`束縛したローカルの値)である。どちらも閉じた項ではない。各呼び出し箇所で最終的に実行されるコードそのものは固定で、既知であるにもかかわらずである。`%spec`の閉鎖性の要求には、「このクロージャが指すコードポインタは、捕捉する環境が違っても変わらない」という性質を表す手段がない。この性質は閉鎖性より弱いが、特殊化に使える。

上の2つの前提条件とは独立に、もう1つ問題がある。upstreamの`mkSpecDef`には、採算判定がまったくない。フォールバックの経路は、特殊化の途中で本物のelaborationエラーが出た場合に限られる(`handleUnify`のエラーハンドラが`logC "specialise.fail"`を記録し、試行を捨てて元の呼び出しを使う)。特殊化自体は成功して複製ができたものの、汎用版より小さくも間接呼び出しが少なくもならなかった、という場合を検出する仕組みはどこにもない。特殊化する引数がたまたま閉じている呼び出し箇所は、すべて無条件で完全な複製を受け取る。実際、制限のない特殊化がコードサイズの爆発を起こしたことが過去にあり、それを抑える仕組みも組み込まれていない。これが本書の動機の後半であり、`%spec`が`go`の呼び出し箇所に届くかどうかとは関係がない。

## rc2独自の設計

`%spec`は、動機となった例には閉鎖性のために届かない。届く場合でも、採算判定を持たない。そこで本節では、`Compiler.RC2.ConstFold`の実行後の`RCExp`を対象にする、rc2側の仕組みを設計する。「このクロージャ引数はコンパイル時の定数か」を調べる既存の`RCConstClosure`(`rc2/doc/const-closure-fold.md`)による検出を、そのまま再利用する。`%spec`の閉鎖性の検査が捉えられない「コードポインタは不変で、環境は違ってよい」という性質を、この検出なら捉えられる。`ConstFold`と`InlineCExp`の推論は、ラムダリフトの後、リフトされたクロージャ値(`partial Main.{benchmarkHashMap:19} missing=2 [v85, v80]`)に対して行われる。自由変数を捕捉したままのリフト前の表層の項は見ない。

### 1. 候補の検出

関数`g`(動機の例では`go`)の呼び出し箇所ごとに、次の2つを確認する。`g`のパラメータのうち1つが`g`の本体の中で`apply`を通してしか使われていないこと。その呼び出し箇所で渡される引数が、`ConstFold`の後に、捕捉する自由変数とは無関係に、常に同じ名前付きトップレベル関数だと証明できること。これは完全な閉鎖性より弱い条件である。`partial Main.{benchmarkHashMap:19} missing=2 [v85, v80]`と`partial Main.{benchmarkHashMap:19} missing=2 [v200, v201]`を考える。この2つは、別々の呼び出し箇所が別のローカル変数を捕捉しているが、指している関数は同じである。`%spec`の意味では、どちらも閉じた項ではない。しかしこの目的では、両者を「同じ対象」と数える。`g`が呼ばれる対象の*集合*を、プログラム全体で集める。

### 2. 投機的な複製と再畳み込み(対象ごとに1回だけ試行する)

手順1で見つけた対象ごとに、次を行う。`(g, target)`の組は、いくつの呼び出し箇所が共有していても1回しか試さない(メモ化する)。複製の総数は、呼び出し箇所の数ではなく、実際に観測された*異なる*対象の数で抑えられる。

- `g`の本体を複製し、特殊化するパラメータへの`apply`を、すべて直接の`call target [...]`に書き換える。`target`の捕捉値や自由引数は、複製の追加パラメータとして渡す。これは`Compiler.RC2.InlineCExp`が、呼び出しを含まない普通の呼び出し先を差し込むときの既存の仕組みと同じ形である。
- この複製*だけ*に(プログラム全体ではなく)`ConstFold`と`InlineCExp`をもう一度かける。直接呼び出しになったことで新しく見えるようになる畳み込みを、実際に行わせるためである。たとえば`target`自身が小さく、呼び出しを含まなければ、呼び出しがもう`apply`の陰に隠れていないので、`InlineCExp`の既存の基準Aが`target`に届くようになる。

### 3. 採算の判定(実際の関門)

畳み込み済みの複製の本体を走査して、特殊化したパラメータを対象とする`apply`ノードがまだ残っていないかを調べる。取り除こうとしたのと同種のボックス化されたディスパッチが、間接的に残っている場合も、残っているものとして扱う。

- **その種の`apply`が残っていない場合**、特殊化は狙いを達成している。`apply1`/`inc`の再現コードの`New RHS: (prim__add_Int x[0] 1)`が、間接呼び出しの痕跡が完全に消えた理想的な例である。**複製を残し**、この`(g, target)`の組を共有するすべての呼び出し箇所を複製に向ける。
- **残っている場合**、クロージャは畳み込みの届かない場所に逃げている。データ構造に格納された、関数から返された、畳み込みが解決できなかった分岐の中で適用された、などである。複製は汎用版に対して何も得をしておらず、同じ間接呼び出しのコピーが1つ増えただけである。**複製を捨て**、すべての呼び出し箇所は元の汎用の`g`を呼び続ける。

この判定は、サイズの閾値ではなく、構造に基づく。見るのは「作ろうとした間接呼び出しを実際に取り除けたか」であり、「小さくなったか」ではない。サイズで見ると、実際には効果があるのにテキストとしては大きくなった結果を捨てたり、小さいが役に立たない結果を採用したりするおそれがある。計算も安い。畳み込み済みの複製を1回線形に走査するだけで済み、別のコストモデルは要らない。

## rc2にとってのアーキテクチャ上の新しさ

rc2の既存のパスはどれも、変換の前に、変換前の入力の形から適格性を判定している。`InlineCExp`の基準A、`ConAltNative`、`ConstFold`自身、`loop-in-case-sinking.md`の沈め込み変換のいずれも同じである。パイプラインの段階としては、「検査してから書き換える」一方向の処理である。本設計は逆に、先に投機的に変換し、その*結果*を見て判断する。「試してから、採用するか捨てるかを決める」この形には、`Compiler.RC2`に前例がない。健全性の問題ではない。捨てた複製はどこからも参照されないので実行時のコストはなく、参照されない他の定義と同じように`Compiler.RC2.DeadCode`が落とす。それでも、既存のパスを少し拡張するものではなく、新しい種類のパスだという点は、実装に入る前に明記しておく価値がある。

## `loop-in-case-sinking.md`との関係

`loop-in-case-sinking.md`の「関連する、より大きなアイデア」の節は、ループだけでできた小さな関数を、すでにループしている呼び出し元へインライン展開することを検討していた。そして、特殊化してインライン展開した対象自身がループである(またはループを含む)場合は、ネストしたループへの本格的な対応が必要になると結論している。具体的には、`Compiler.RC2.DualABI`の`loopContinueNativeReads`をスタックにする必要がある。

本設計は、意図的に範囲を狭めて、この依存を完全に避けている。上の手順2は`apply`を直接の`call`に解決し、`InlineCExp`の既存の(変更しない)基準Aを通して、機会があれば再畳み込みをするだけである。基準A自身が拒否するはずの対象を、強制的にインライン展開することはない。たとえば、対象自身がさらに呼び出しを含む場合や、対象自身がループである場合である。たまたまループである対象は、手順2のあとも直接の`call`のままになる。`apply`はもうなくなっており、それだけで十分に効果がある。この対象が呼び出し元のループ本体に差し込まれることはない。したがって手順3の採算判定は、対象の本体をインライン展開することも、ネストした`RLoop`ノードを作ることもなく、`apply`が残っていないという自身の条件で合格する。**この設計はネストしたループへの対応をまったく必要としない。**この点で、設計の出発点になった「関連する、より大きなアイデア」とは異なる。

## 実装メモ: 出荷した内容と、設計からの相違点

`Compiler.RC2.SpecClosure`は、上の手順1から3を、ほぼ設計どおりに実装している(モジュール自身のドキュメントコメントに、より詳しい説明がある)。実行位置は、`Compiler.RC2.RC2`の`foldConstProgram`と`insertMemoize`のあいだで、1回だけ走る。実装中に2つの実際の問題が見つかった。どちらも、本書の動機である`go`を特殊化するために必須であり、なくてもよい仕上げではない。

- **`missing > 1`には、連鎖をたどる専用の検出と書き換えが必要だった。** `RApp`の2つのオペランドは裸の`RCLocal`であり、ネストした`RApp`ではない。そのためカリー化された`f a1 a2`(あと2つ引数が要る)は、ANF正規化で1つのノードにならず、`RLet tmp (RApp f a1) (RApp tmp a2)`になる。これは見かけ以上に重要である。`go`と同じ形のふつうの`String -> IO ()`のコールバックは、ここでは`missing = 1`ではなく`missing = 2`に下ろされる。1つ目が本来の引数で、2つ目がIOの呼び出し規約が裏で渡す`%World`トークンである。最初の試作は`missing == 1`だけを扱っており、コンパイルは通り、どのプログラムも正しく動いたが、`go`に対してだけは一度も働かなかった。この連鎖をたどる処理は`SpecClosure.idr`の`chainArgs`と`chainCount`が担う。認識するのは、各`apply`の結果がすぐ次の`apply`に渡り、間に何も挟まらない形だけである。ほかのものが割り込んだ連鎖には、保守的に手を付けない。
- **自己再帰呼び出しにそのまま渡されるパラメータを、明示的に扱う必要があった。** `go`の末尾の`go xs f`がまさにこの形である。クロージャのパラメータは適用されるだけでなく、変更されないまま次の反復にも渡される。構造的再帰による走査では普通の形であり、例外的な場合ではない。この再帰呼び出しも複製のほうへ向け直さない(`rewriteSelfCall`と`selfPassthroughOccurrences`)と、特殊化されるのはリストの先頭要素だけになる。2要素目以降の反復では、毎回、複製されていない汎用の`g`へ再帰してしまうからである。

**実装していないもの**: 複製に対する`InlineCExp`の再実行。手順2の後半にあたる。`Compiler.RC2.InlineCExp`は、`NamedCExp`から`NamedCExp`へ変換するプログラム全体のパスであり、このパイプラインの段階より前の、`RCExp`になる前の段階ですでに1回走っている。構築済みの`RCExp`の複製1つに対して再び呼び出すことは、現在の構造では支えられない。後述の「未解決の問いとリスク」にある「パイプラインのどこで走らせるか」の問いが、この形で解決済みである。複製に対して再実行しているのは、`Compiler.RC2.ConstFold`の`foldConstDef`だけである。したがって、小さく呼び出しを含まない`target`も、複製の中へ日和見的にインライン展開されることはなく、直接呼び出しのまま残る。手順3が確かめる効果は得られるが、紙上の設計の手順2が述べていた追加の効果は得られない。

**検証**: 手書きで作った`go`型の再現コード(呼び出し箇所が2つ、捕捉クロージャの対象が2種類、すべて`missing = 2`)は、`--directive noloop`でも、デフォルトのパイプラインでも、正しく特殊化された。`apply`は直接呼び出しに完全に解決され、自己再帰呼び出しは複製に向き直り、汎用の`go`はデッドコード除去で完全に消え、プログラムの出力は正しかった。`rc2/tests/verify.sh`のスイート全体(85テストとvalgrind)も通っている。`refc-suite`の`callingConvention`テストは、生成されたCのゴールデン出力を作り直す必要があった。動作が変わったからではない。このパスが`PrimIO.unsafePerformIO`の定型的な`apply`も(偶然にではあるが、同じ形なので)一律に特殊化し、その結果、生成ファイル内のほかの場所の`tmp_N`の番号がずれたためである。実際のワークロードである`idris2-missing-containers`の`benchmarkHashMap`(本書の動機のベンチマーク)では、実行時間に測定可能な改善はなかった(12.04秒に対して12.09秒。ノイズの範囲内)。これは、このパスが存在する前に別の調査で出ていた`rc2/BENCHMARKS.md`の結論と整合する。このワークロードで支配的なコストは、interfaceを介したハッシュ計算と、`IOHashMap`の`IORef`およびリスト走査による`write`フェーズであり、どちらも、このパスが狙う「ふつうの関数引数として渡されるクロージャ」の形ではない。設計の考え方も、狙った効果も正しい。`go`自身は設計どおりに特殊化されている。ただ、この外部ワークロードは、そこで時間を使っていないだけである。

## 内部構造(`SpecClosure.idr`)

モジュール自身のドキュメントコメントは、意図的に短くしてあり、この節への参照になっている。推論の根拠を書いてあるのは、ここだけである。

**レコード。** `KnownClosure`(`target`/`missing`/`capturedArgs`)は、`RUnderApp` 1つの3つのフィールドをそのまま写したものである。`target`と`missing`は、2つの呼び出し箇所が「同じ対象」であるために一致しなければならない部分である。`capturedArgs`は呼び出し箇所ごとの値で、自由に異なってよい(上述の`[v85,v80]`と`[v200,v201]`の例)。`Opportunity`は、1つの呼び出し箇所の`(callee, argPos, KnownClosure)`を記録する。`Bound`は、有効な`RCLocal`の`Int`のidを、それが保持していると分かっている`KnownClosure`に対応づける。定義の本体を前向きに走査しながら作り、要素を取り除くことはしない。`normalizeDef`が1つの定義の中でidを単調に1回ずつ割り当てるので、1つの定義の本体の中ではidが再束縛されることがない。したがって、どこで挿入した項目も、ネストしたcaseの分岐を含め、その本体の残りの部分で正しいままである。

**使用箇所で既知のクロージャを見つける(`lookupKnown`)。**見つける経路は2つある。1つは、`RCLoc i`を`Bound`でたどって、外側にある`RUnderApp`に行き着く経路で、これが一般の、捕捉が1つ以上ある場合である。もう1つは、引数の位置にそのまま現れる裸の`RCConstClosure n missing`で、この場合は`Bound`を引かない。捕捉がゼロの`RUnderApp`は、このパスが走る時点では、この形になっている。`ConstFold`自身の、より限定的な定数クロージャの畳み込み(`rc2/doc/const-closure-fold.md`)が、使用箇所ごとにすでに置換を済ませており、たどり直すための`Bound`の項目が残らないからである。これは痛い目に遭って分かったことである。このモジュール自身の動機となった再現コード(`mkTarget prefix`、`prefix`は文字列リテラル)がまさにこの経路を通る。リテラルが先に畳み込まれて消える。`Bound`しか調べない初期版の`lookupKnown`は、これを完全に見逃した。

**連鎖の検出(`chainArgs`/`chainCount`)。** `RApp`の2つのオペランドは裸の`RCLocal`で、ネストした`RApp`にはならない。このため、カリー化された`v a1 a2`(あと2つ引数が要る)は、ANF正規化で1つのノードではなく`RLet t (RApp v a1) (RApp t a2)`になる。`chainArgs`は、この形を1段ずつたどる。最初の`apply`では`v`を、次の段では新しく作られた中間値を追う。最後の`apply`だけは、`RLet`をもう1つ重ねず、裸の末尾の式であってもよい。連鎖の中で最終結果に名前を付ける必要はないからである。一致するのは正確な形だけである。何かが割り込めば(関係のない`RLet`、case分岐など)、連鎖全体を特殊化しない。部分点は与えないという方針による。`chainCount`は、下りながらすべてのノードで`chainArgs`を試す。連鎖の根はどの部分式にもなりうるからである。`go`の実際の本体では、関係のない外側の`RLet`の*値*の中に、連鎖の根がある。

**自己再帰への素通し(`selfPassthroughOccurrences`、`rewriteSelfCall`)。**これが必要な理由は、上の「実装メモ」にある。`paramUses`は、パラメータがちょうど1回出現することを要求するのではなく、素通しの出現を`countUsesR`の合計から差し引いて数える。`rewriteSelfCall`は、そのような再帰呼び出しを、構築した複製の中で複製自身へ向け直す。このとき、元のクロージャ引数があった位置に`capturedParams`を差し込む。

**安全な新しいid(`maxVarInBody`、`freshIdsFrom`)。**複製が新しく持つ、捕捉値のパラメータのidは、`g`の本体がすでに使っているidと衝突してはならない。このモジュール自身の`FreshId`のrefから割り当てる方法は使えない。`FreshId`は、どの定義の番号付けとも無関係だからである。定義ごとの番号付けは、`normalizeDef`の`nextVarId`により、定義のたびに0から始まる。実際に衝突し、最初に試したときには「redeclared with a different kind of symbol」というCのコンパイルエラーが出て確認できた。そこで`maxVarInBody`が、`g`の本体の中のどこかで束縛されている最大の`Int`と、引数のidを調べ、`freshIdsFrom`がそこから数え上げる。落とし穴が2つあり、どちらもレビューで見つけたのではなく、実際のコンパイル失敗で分かった。

- `maxVarInBody`は、`RLet`のidだけでなく、`RConAlt`と`RConstAlt`のパターン束縛のidも数えなければならない。`RConCase`と`RConstCase`の場合は、後述の共有コンビネータ`foldSubExprs`を、意図的に通さない。この汎用の子要素ごとの再帰には、コンストラクタaltの束縛リストに処理を差し込む場所がない。それらのidを黙って落とすと、上の段落で述べた種類のidの衝突が、まったく同じ形で再発した。
- `freshIdsFrom n`は、意図的に`[1 .. n]`という範囲構文で書かない。Idris2の`Enum Nat`では`[1 .. 0] = [1, 0]`となり、`[]`ではなく2要素のリストになる。そのため、実際の捕捉数が0のときは、余計な捕捉パラメータが2つ、黙って作られていた。呼び出し箇所が渡すどの数よりも多いパラメータを持つ複製が宣言されて、実際のCのコンパイル失敗が起きるまで、見つからなかった。

**共有の構造再帰(`mapSubExprs`、`foldSubExprs`)。** `maxVarInBody`以外のこのモジュールの走査は、ノード固有の場合に一致しなかったとき、すべて`RLet`、`RCmpCase`、`RConCase`、`RConstCase`の中へ、同じ方法で再帰する。このパスの入力は厳密にPhase 2より前の形なので、ネストした`RCExp`を持てるコンストラクタはこの4つだけである。`RDup`、`RDrop`、`RFree`、`RReleaseReuse`、`RReuseOffer`、`RLoop`、`RLoopContinue`、`RAppNameRep`、`RAppFFIInline`、`RMemoize`は、ここには現れない。`mapSubExprs f`は、各子要素に`f`を適用して節点を作り直す(`RCExp -> RCExp`の書き換え)。`foldSubExprs op z f`は、各子要素の`f`の結果を`op`で結合する(`RCExp -> a`の走査)。子要素のない葉には`z`を使う。ほぼ同じ手書きのコピーが6つあったが、この2つのコンビネータにまとめた。`maxVarInBody`だけは、上の落とし穴のとおり`foldSubExprs`を使えない。

**採算判定と呼び出し箇所の向け直し(`stillAppliesParam`、`redirectCallSites`、`buildClone`)。** `stillAppliesParam`は手順3の関門そのものである。畳み込み済みの複製に対して素の`countUsesR`で調べれば足りる(`paramUses`の連鎖を考慮した数え方は要らない)。`rewriteApply`が、そのパラメータのただ1つの出現を取り除こうとした後にもパラメータが残っているなら、特殊化は完全には成功していないからである。`redirectCallSites`は、`collectOpportunities`と同じ方法で`Bound`をたどり直す。これによって、残すことにした複製が作られた*その対象*を、どの呼び出し箇所が共有しているかが分かる。同じ`(callee, argPos)`に別の対象を渡す呼び出し箇所は、対象ごとのメモ化の設計に従い、汎用の`g`を呼び続ける。`buildClone`の`capturedCount`は、根拠となる呼び出し箇所を1つ取って決める。同じ`(callee, argPos, target, missing)`のキーを共有するすべての呼び出し箇所で、この値は一致すると仮定している。この仮定は構成上成り立つ。どこで参照しても、同じ`target`の名前とアリティだからである。

## 未解決の問いとリスク

- **1つの関数で複数のパラメータを特殊化する場合**: 未解決のままで、実装していない。`go`のクロージャのパラメータは1つしかない。複数ある関数では、手順1の候補集合を、パラメータごとに対象を1つ選んだ*組*の集合にする必要がある。試みる異なる`(g, targets...)`の複製の数は増えるが、それでも上限はある(各パラメータの異なる対象の数の積で、通常は小さい)。ただし、詳しい設計はしていない。`SpecClosure.idr`の実装も、一度に特殊化するパラメータの位置は1つだけである。
- **パイプラインのどこで走らせるか**: 解決済み。新しい段階として、`foldConstProgram`の直後、`insertMemoize`より厳密に前に置いた。`InlineCExp`自身の改良ではない(`InlineCExp`にはまったく手を入れていない。複製に対して再実行しない理由は、上の「実装メモ」を参照)。
- **複製自身の所有権の再注釈**: 解決済み。予想より簡単だった。残した複製は、`toRCDefs`が後続の`annotate`/`Reuse`/`ConAltNative`/`Loop`などへ通している`List (Name, RCDef)`に挿入される。したがって、ほかの定義とまったく同じ扱いを受け、特別な処理は一切要らない。`SpecClosure`自身は`annotate`を呼ばない。
- **`DupMerge`や`Loop`との相互作用**: 解決済み。`rc2/tests/verify.sh`のスイート全体が通り(85テストとvalgrind、リークは0)、実際のパイプラインの順序で衝突は観測されなかった。
- **対象ごとにメモ化して数を抑えれば、現実のプログラムでコード量の爆発を避けられるという、プロファイル上の証拠はまだない**: 部分的に対処済み。`idris2-missing-containers`の`benchmarkHashMap`は、このパスを有効にしてもコンパイルでき、正しく動作し、コードサイズや正しさの問題は観測されていない。ただし、このワークロードは、多数の異なるクロージャの対象から呼ばれる関数を含んでいない。メモ化による上限が現実の負荷でどう振る舞うかは、まだ測定していない。この項目が当初求めていた合成ストレステスト(多数の異なるクロージャの対象から呼ばれる関数)は、作っていない。
- **不動点まで反復せず、コンパイル1回につき1回だけ適用する**(実装中に、明示的な依頼で見つかった): 残した複製の本体が、それ自体として新しい特殊化の機会を露出させる可能性は原理的にある。`foldConstProgram`が`ConstFold`を不動点まで再実行するのも、1つのCAFの畳み込みが別のCAFの畳み込みを可能にするからで、これと同じ理屈である。まだ試していない。`SpecClosure.idr`の`applySpecClosure`のドキュメントコメントに、理由と、将来の不動点のラッパーがとる(ごく単純な)形が書いてある。

## 推移的な特殊化(2026-09-26設計、2026-09-27実装)

ステータス: 実装済み。設計との相違点は「結果」にまとめた。動機は`TODO.md`の「`sort` against Chez」にある。特殊化されていない比較関数は、100万要素の`sort`の4.18秒のうち約0.6秒を占める。これは2番目に大きい原因である。

### 現状の限界

`Data.List.sortBy cmp xs`は、`cmp`を自分では適用しない。`cmp`を次の2つに渡すだけである。

- `cmp`を適用する`mergeBy cmp`。
- 自己再帰呼び出しとしての`sortBy`(素通し)。

`paramLooksSpecializable`(現在の`paramUses`)は、適用の連鎖がちょうど1つであることを要求した。そのため`sortBy`の`cmp`は適格にならない。`mergeBy`は、既知のクロージャではなく`sortBy`のパラメータだけを渡されて呼ばれるので、こちらにも機会がない。`main`に`sortBy compare xs`と直接書いても、汎用のままになる。その結果、比較のたびに`idris2rc2_applyClosureN`のディスパッチ、クロージャとその引数への参照カウント操作、ボックス化された`Ordering`が発生する。

### 使い方の3つ目の種類としての転送

`g`のクロージャのパラメータ`v`の使い方は、次の3種類になる。

1. **適用:**長さ`missing`の`apply`の連鎖。従来と同じで、多くとも1回まで(「結果」を参照)。
2. **自己再帰への素通し:**自分自身の呼び出しの同じ引数位置に渡す。従来と同じ。
3. **転送(新規):**別の関数`h`の呼び出しの位置`q`に渡す。

適格性は、`(関数, argPos, missing)`の三つ組に関する、プログラム全体の性質になる。三つ組が*閉じている*とは、そのパラメータのすべての使い方が上の3種類のいずれかであり、かつ、すべての転送先`(h, q, missing)`自身も閉じていることをいう。

これは最大不動点である。まず、使い方が上の3種類だけである三つ組をすべて候補にする。そのうえで、取り除かれた三つ組へ転送している三つ組を、繰り返し取り除く。相互に転送する場合(`g`から`h`、`h`から`g`)は残る。

### 複製の構築

キーは、従来どおり`(callee, argPos, target, missing)`のままである。ワークリストは、現行の特殊化の機会から始める。

キー`(g, p, target, missing)`の複製を作る処理は、現在の`buildClone`と同じことを行う。

- パラメータは、捕捉値のパラメータに置き換わる。
- 適用の連鎖は、`target`への直接呼び出しになる。
- 自己再帰呼び出しは、複製を呼ぶ。

これに加えて、複製の中のすべての転送箇所`h [.. v@q ..]`が、キー`(h, q, target, missing)`の特殊化の機会になる。既知のクロージャは、その複製自身の捕捉値のパラメータである。キーがまだワークリストになければ追加する。

向け直しの処理が転送された値を認識できるように、複製は入口で`v`を束縛し直す。これは、転送箇所がある場合に限る。

- 捕捉がない場合(`compare`のような定数クロージャ)、`v`はそのまま定数`RCConstClosure target missing`になる。
- 捕捉がある場合、`v`は`let v = partial target missing [captured..]`になる。

`redirectCallSitesTable`は、転送箇所を、既知のクロージャを持つほかの呼び出し箇所と同じように扱う。すべての転送箇所が向け直されると、`v`を読むものはなくなる。定数の場合は何も残らない。`partial`の場合は不要な`let`が残る。RCの前に、これを削除する必要がある(複製に対する`ConstFold`の後続のラウンドか、不要な純粋`let`を掃除するパスで行う)。

### 採用の判定

複製が採用されるのは、転送箇所が*採用された*複製へ向け直された後に、パラメータがもう参照されていない場合である。これもまた、このラウンドで構築した複製に関する最大不動点である。

- 適用の連鎖が畳み込まれて消えた複製をすべて候補にして始める。
- 転送箇所の転送先の複製が落とされた複製を、落とす。
- 変化がなくなるまで繰り返す。

向け直しの表には、採用された集合が入る。この表は、元の定義と採用された複製に対して、従来どおり1回だけ適用する。

### パイプライン上の位置: 変更なし

`SpecClosure`が走る時点で、`sort`の比較関数はすでに定数になっている。`Compiler.RC2.InlineCExp`が名前付きcase tree上で`sort`を呼び出し元へ差し込み、ConstFoldが定数の`Ord Int`辞書から`compare`を畳み込むからである。`--directive noearlyinline --directive nolateinline`を付けてダンプすると、`main`の中に`call Data.List.sortBy [#{{csegen:25}:2}/2~closure, ..]`が見える。

したがって、推移的な拡張だけで、`sort`と、直接書いた`sortBy compare`の両方が対象になる。SpecConstConの後に2回目のラウンドを置く必要があるのは、SpecConstConだけで定数になる辞書の場合に限られる。これは、前述の「不動点まで反復せず、コンパイル1回につき1回だけ適用する」の問いに属する。

### 上限

- **新しいキー**は、既知のクロージャを呼び出しの連鎖に沿って転送する場合にのみ生じる。各キーは多くとも1回しか構築されない(キーでメモ化する)ので、このラウンドは必ず終了する。
- **コードサイズ:**連鎖に沿って、`(関数, target)`ごとに複製が1つできる。注目する数値は、idris2-lspの複製の数とビルド時間である(`--timing 3`と、このパス自身の`--directive timing`の件数)。

### 結果(2026-09-27)

**実装。**変更箇所は`SpecClosure.idr`である。

- `paramUses`が`paramLooksSpecializable`を置き換え、転送箇所を返す。
- `buildClone`が、転送箇所を、既知のクロージャを渡す形に書き換える。
- ワークリスト(`buildAll`)が、各複製の転送のキーを追加する。
- `acceptClosed`が、すべての転送箇所が採用された複製を見つけられる、最大の部分集合を残す。
- `dropDeadEntryClosure`が、向け直しで使い終えた、入口で束縛したクロージャを取り除く。

適格性は、プログラム全体の不動点として事前には計算しない。呼び出し先が、そのパラメータをほかの方法で使っているキーは、複製が作られないだけである。採用の判定が、そこへ転送しているものをすべて落とす。

**適用の連鎖は多くとも1つまで。**設計では、連鎖はいくつあってもよいとしていた。idris2-lspで試すと、約6,300ではなく8,860の複製が採用された。うち987件はクロージャを2回以上適用し、1,605件は転送しており、最終的なRCExpは18%大きくなった。`sort`に2つ目の連鎖は要らない(`mergeBy`が`cmp`を適用するのは1回である)。そこで、規則は1つのままにしている。

| idris2-lsp、最終RCExp | 変更前 | 連鎖の数に制限なし | 多くとも1つ |
|---|---|---|---|
| 定義の数 | 19,528 | 19,807 | 19,149 |
| `rc2_specClosure_*`の定義の数 | 740 | 1,606 | 906 |
| 行数 | 668,914 | 792,159 (+18%) | 694,148 (+3.8%) |

連鎖を多くとも1つとすると、採用される複製は7,299件で、そのうち1,086件が転送を含む。このパスの所要時間は、idris2-lspで約1.1秒である。`rcexpr-lint`は異常を検出していない。

**速度。** 100万個の`Int`の`sort`は、1.49秒から1.11秒になった(Chezは1.23秒)。`mergeBy`の複製の中の比較関数が、直接のワーカー呼び出しになったためである。

**実行ファイルのサイズ**(text、単位はバイト)は次のとおりである。

| | 変更前 | 変更後 |
|---|---|---|
| `sort` | 87,588 | 91,316 (+4.3%) |
| map/filter | 70,835 | 70,595 |
| closures | 66,035 | 65,787 |
| `missing-containers` | 114,573 | 114,573 |
| 他の69個のスモークテストの合計 | 4,007,625 | 4,004,761 |

大きくなったのは`sort`だけで、特殊化された`sortBy`と`mergeBy`を持つようになったことによる。複製が汎用のコードをそっくり置き換える場合は、汎用版がデッドコードとして落とされるので、小さくなるプログラムもある。

**テスト。** `Test106TransitiveSpec`を、Chezと比較する。

- `sortBy compare`、`sort`、降順の`sortBy`。
- `k`を捕捉するクロージャを、`twice`を通して`applyAll`へ転送する例。`--directive nolateinline`を付けたダンプには、両方の複製が現れ、捕捉値がそのまま渡されて、`partial`は残っていない。
- 互いに転送し合う`evens`と`odds`。
- クロージャを保存もするので汎用のままになる`stash`。

これらのヘルパーは、InlineCExpの閾値より大きく、`twice`は呼び出し元が2つあるので、このパスより前にインライン展開されるものはない。

- `rc2/doc/const-closure-fold.md` -- `RCConstClosure`。手順1が、捕捉のない場合に再利用する、「このクロージャはコンパイル時定数か」の既存の検出である。捕捉のある場合は、`SpecClosure.idr`自身の`lookupKnown`が、`Bound`と`RUnderApp`をたどって扱う。`RCConstClosure`だけでは対応できない(その関数のドキュメントコメントを参照)。
- `rc2/src/Compiler/RC2/InlineCExp.idr` -- 基準Aと既存の差し込みの仕組み。手順2の「再畳み込み」の後半に使えないかを調べたが、結局再利用していない。名前付きcase tree上で動く、`RCExp`になる前のパスで、このパスが走る時点ではすでに1回走り終えているからである(上の「実装メモ」を参照)。それでも、上の「ネストしたループへの依存がない」という議論には、直接関係する。
- `idris2-src/src/TTImp/PartialEval.idr` -- upstreamの`%spec`機構。ここで詳しく調べた。`specArgs`/`getSpecArgs`が要求する命名と閉鎖性、`mkSpecDef`の、エラーのときにしか働かない(採算判定のない)フォールバック。
- `idris2-missing-containers`の`test/src/Main.idr` -- 本書の動機となった、実際のコードの`go`。このパスが`go`自身を正しく特殊化しても同パッケージの`benchmarkHashMap`が速くならない理由は、先に行った調査を記録した`rc2/BENCHMARKS.md`にある。
