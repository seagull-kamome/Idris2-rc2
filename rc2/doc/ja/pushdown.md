# Dup/dropのプッシュダウン(`Compiler.RC2.PushDown`)

(原文: `doc/pushdown.md`。内容が乖離した場合は原文を正とする。)

## このパスの役割

`case`(`RConCase`、`RConstCase`、または`postDrop`のない`RCmpCase`)の直前に連続して並ぶ`dup`/`drop`ノードを、すべての枝の先頭へ移す。そのうえで、同じ枝の中で`dup v`が`drop v`に出会えば、両者を相殺する。変換前は次のとおりである。

```
case v525 of
  CONS [..] args= [v524, _] ->
    dup v524
    drop [v525]
    case v524 of
      CONS [..] args= [v522, _] ->
        dup v522
        drop [v524]
        v522
      _ ->
        drop [v524]
        "none"
```

変換後は次のようになる。

```
case v525 of
  CONS [..] args= [v524, _] ->
    case v524 of
      CONS [..] args= [v522, _] ->
        dup v522
        drop [v525]
        v522
      _ ->
        drop [v525]
        "none"
```

フィールド`v524`は、親の`v525`から借りたものである。`Reuse.resolveAlt`は、親を枝の先頭でdropできるように、残るフィールドをすべて所有にする(`dup v524`)。内側の`case`は、続く各枝で`v524`をもう一度dropする。そこで、この並びを枝の中へ押し込む。すると、親のdropは枝に入るまで待てるようになり、その経路ではフィールドの`dup`/`drop`の対がなくなる。`--directive nopushdown`で無効にできる。

この形は、`tools/rcexpr-lint --pushdown-stats`(パターンA。`tools/rcexpr-lint/README.md`を参照)で見つかった。`RC.annotate`はdupを消費箇所にしか置かないので、発生源ではない。idris2-lspには、`case`との間に`dup`/`drop`ノードしかない箇所が8,535個ある。このうち6,161個はcaseのフィールドで、`Reuse.resolveAlt`が`dupOnSurvive`と枝の`outerDrop`によって作る形である。残る2,374個はそうではない。コードを読んだ限りでは、呼び出し元が引数を`dup`した後で`LateInline`が呼び出し先を埋め込んだもの、`Loop`、`ConAltNative`が原因である。パスを切って確かめたわけではない。このパスを`annotate`の内側ではなく最終的なIR(デッドコード除去の直後、`DupMerge`の前)で走らせるのは、そのためである。こうすれば、すべての生成元の出力を見られる。lintが測るのも、このIRである。

## アルゴリズム

`pushDownExp`は木を走査する。`RDup`/`RDrop`ノードが最大限に連続した並び`R`の後に`case` `K`が続いているとき、次の手順をとる。

1. `normalize R`を求める。まず、すべての`dup`を(ローカル変数ごとに回数をまとめて)置く。続いて、対応する`dup`/`drop`の対を相殺した残りを、1つの`drop`にする。
2. 先頭の並びが`Q_i`である各枝`i`について、`normalize (R ++ Q_i)`を求める。相殺された対の数が、その枝での削減量になる。
3. 書き換えるのは、いずれかの枝で対が相殺され、かつ`dup`/`drop`操作の静的な個数が増えない場合だけである。条件は`sum_i |normalize (R ++ Q_i)| <= |R| + sum_i |Q_i|`で、これは`(arms - 1) * |R| <= 2 * cancelled pairs`と同じである。どの経路が実行する操作も、書き換え前以下になる。これはこの静的条件とは無関係に成り立つ。静的条件が防ぐのは、コード(および`dup`/`drop`の行数)の増加だけである。
4. 新しい枝に再帰する。枝の先頭にある並びが、次の`case`の直前に来て、さらに先へ進めることがある。上の入れ子パターンの例では、並びがすべての階層を降りていく。

`reuseOffer`、`free`、`releaseReuse`、およびふつうの`dup`/`drop`以外の操作は、並びを終わらせる。そのため、一意性の検査が、変わった参照カウントを見ることはない。

## 健全性

並びの中では、何も束縛されず、カウントを観測するものもない。したがって並びは、ローカル変数に対する`+1`/`-1`の多重集合と、順序の制約からなる。順序の制約とは、フィールドの`dup`は、何かがまだそのフィールドを生かしている間に行わなければならない、というものである。

- `dup`を前に動かしても安全である。死んでいるオブジェクトが減るからである。`drop`を後ろに動かしても安全である。オブジェクトの寿命が延びるだけだからである。そのため、`dups ++ drops`という正準形は、何かを早すぎる時点で解放することがない。この形では、`dup v`と`drop v`の間に何があっても、両者は相殺される。`v`を所有する親の`drop`が間にあっても同じである。
- 並び全体を、`K`のディスパッチより後ろへ遅らせても安全である。ディスパッチはカウントを変えないし、`dup`が実行される時点でdropはまだ1つも走っていない。並びは1つの単位として遅らせるので、`dup`が、そのフィールドが依存するdropから切り離されることはない。
- ディスパッチが読むもの(スクルティニーや、比較されるオペランド)の`drop`は、遅らせない。そのような場合、このパスは働かない。`postDrop`が空でない`RCmpCase`でも働かない。そのdropは枝より前に走るからである。
- 相殺される対は、`dup v`と、その枝が自身の先頭の並びの中で最初に行う`drop v`である。`v`の`reuseOffer`をまたぐことはない(`reuseOffer`は並びを終わらせる)。そのため、`reuseOffer v`の枝は自分の`dup`を保ち、親が一意のときの再利用の経路は変わらない。

意図的にまたがないものが2つある。1つは`let`である。並びと`case`の間にある呼び出しが、フィールドの親を消費するかもしれず、一意性を前提にした呼び出しをまたいで親を生かしておくかもしれない。親のdropを遅らせると、インプレースの更新が、黙ってコピーに変わってしまう。もう1つは、先頭の並びより枝の奥にある、相殺できる`drop`である。

## 計測(idris2-lsp、最終的なIR、静的な個数)

同じコンパイラで、`--directive nopushdown`とデフォルトを比べた。

| | nopushdown | default |
|---|---|---|
| `dup`の行数 / `drop`の行数 | 78,483 / 71,191 | 74,835 / 64,999 |
| IRの行数 | 670,479 | 660,639 |
| dup/dropの操作の合計 | 269,416 | 255,574 (-5.1%) |
| パターンA(lint)の箇所数 / 操作数 | 12,277 / 19,255 | 5,065 / 5,057 |
| パターンD(フィールドをdupしてから親をdrop)の箇所数 / 操作数 | 19,410 / 29,584 | 13,421 / 20,827 |
| `rcexpr-lint`の異常 | 0 | 0 |

このパスは、idris2-lspで約0.13秒かかる。パターンAの残りは、ほぼすべてがこのパスの拒む形である。一つは、並びと`case`の間に`let`か`cmp`があるもので、5,065箇所のうち4,755箇所を占める。多くは、呼び出しの結果をそのままマッチする形である。もう一つは、先頭の並びより奥で相殺される枝である。

## パターンD: フィールドのdup、続いて親のdrop(設計のみ)

`dup f; ...; drop [P]`の形で、`f`がcaseでマッチした`P`のフィールドであるもの(lintのパターンD)は、プッシュダウンの後もidris2-lspに13,421箇所、20,827操作(8.1%)残っている。そのうち9,914操作はループの中にある。`P`が実行時に一意であれば、両方の操作が不要になる。殻は解放され、フィールドへの参照は、新しい所有者にそのまま渡るからである。静的なパスには、一意かどうかが分からない。

必要な仕組みはすでにある。`reuseOffer P dupOnShared=[fields] dropOnUnique=[]`に`releaseReuse P`を続けると、`if (isUnique(P)) { /* keep the shell */ } else { dup fields; drop P }`が出力される。`Reuse.resolveAlt`がこれを作るのは、枝がこの後、同じ名前のコンストラクタを構築する場合だけである。残るDの箇所についてこの条件を外すのが、最も手軽な選択肢である。新しいIRノードも`Emit`の変更も要らない。一意性の検査が箇所ごとに1回増える代わりに、一意の経路では`2k`個の参照カウント操作が減る。ただしコードサイズは増える。`resolveAlt`には、逆向きの計測結果が記録されている(死んだofferを共有の経路にまとめると、参照カウントの操作が増えた)。そのため、静的な個数ではなく、実行時の計測(`bench.sh`)が必要である。別の案は、フィールドを親から借りたままにすることで、保留にしている(TODO.md)。型付き定数のフィールド(`noboolfield`)には`dup`/`drop`がなく、Dには含まれない。
