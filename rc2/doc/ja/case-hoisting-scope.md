# ループ不変なコンストラクタフィールドのホイスティング: 調査したが見送り

(原文: `doc/case-hoisting-scope.md`。内容が乖離した場合は原文を正とする。)

本書は、ループ本体の中にある「ループ不変かつ枝が1つだけの `RConCase` の
destructure」をループの外へホイストする案を調査し、見送った経緯を記録する。
将来この案を再び検討するときに、同じ調査をやり直さずに済ませるためである。
本書はもう1件の案も扱う。`Compiler.RC2.ConAltNative` をループ境界やデュアルABI
境界をまたぐように拡張する計画がかつてあり(後述の「関連する未解決の問題」を参照)、
これは同じ問題を別の名前で呼んだものにすぎなかった。こちらも同じ理由で見送った。

## 動機

きっかけは、`idris2-missing-containers` の
`Data.Hash.Algorithm.Internal.feedCharOfString.go` に対する
`--directive dumprcexpr` のダンプを読んでいて見つけた無駄である
(`rc2/BENCHMARKS.md` の 2026-08-18 付「クロージャの in-place 拡張」の項を参照。
この変更の動機になったのが、まさにこのループである)。このループの本体は、
`case v0 of HashAlgorithm ... args=[..., v20, ...]` を毎回の反復で実行している。
目的は、インターフェース辞書のメソッドクロージャを1つ取り出すことだけである。
`HashAlgorithm` はレコードで、このマッチの枝は1つしかなく、デフォルト枝も要らない。
したがって、どの枝が実行されるかはループに入る前から分かっている。

`Compiler.RC2.Loop` のループ不変パラメータの除去は、`v0` 自体をループのパラメータから
すでに取り除いている。どの continue でも `v0` は変更されずに渡されるからである。
しかし、ループ本体の中の `case` はこのパスの対象外であり、`v20` の冗長な
再マッチと再 `dup` は、毎回の反復でそのまま残っている。

## 調査で分かったこと

**`Emit.idr` は、分岐条件そのものをすでに消している。** `emitAltChain`
(`rc2/src/Compiler/RC2/Emit.idr`。定義部分のドキュメントコメントを参照)は、
デフォルトのない単一枝の `RConCase` を特別扱いする。コメントの言葉を借りれば、
「デフォルトのない単一枝の case は(取りうるコンストラクタがそもそも1つしかない)、
さらに縮退して `if` がまったく出力されなくなる」。枝が0個でデフォルトだけの場合も
同様である。つまり、当初このエントリが懸念していた `if` / `switch` による
ディスパッチのコストは、C を出力する時点でとうに消えている。これは推測ではなく、
`emitAltChain` の `chained` / `condAlts` / `tailAlt` のロジックを読んで確認した。
毎回の反復で残っているのは、destructure そのもの(`sc->args[k]` を新しい
ローカル変数に読み込む処理)と、そのフィールド自身の `RDup` である。
コストは実在するが、当初の見積もりより小さい。

この残りのコストをホイストする方法として、次の2案を検討した。

1. **単一枝 case の一般的な平坦化。** 単一枝(または枝なしでデフォルトのみ)の
   `RConCase` を、平坦な `RLet` の連鎖に書き換える。destructure するフィールドごとに
   `RLet` を1つ置き、その後ろに枝の本体を続け、`RConCase` ノードは取り除く。
   こうすれば、ループ不変であることは `Compiler.RC2.Loop` の既存の
   `isInvariantExpr` / `hoistInvariantPrefix` の仕組みがそのまま判定してくれる。
   ループ専用のパスを新設する必要はない。

   ただし、この案は先に新しい IR ノードを導入しないと成立しない。
   `RConAlt.args : List Int`(`RCExp.idr`)は、独立した式ではない。意味を持つのは、
   これを囲む `RConCase` 自身の `sc` との関係においてだけである。
   「コンストラクタ `sc` のフィールド `k` を読む」という式は存在しないため、
   `RLet` の `value` に置けるものがない。これを新設する(たとえば `RGetField`
   ノード)と、次の箇所すべてに手が入る。

   - `RCExp.idr` の構造解析関数(`freeLocalsR` / `countUsesR` / `usedConstructorsR`)
   - `Compiler.RC2.Reuse`(`dupOnShared` の計算、`RReuseOffer` との相互作用)
   - `Emit.idr`(新しい lowering のケース)
   - `Compiler.RC2.Loop` の不変性の検査

   これは局所的な小変更ではなく、IR に新しいプリミティブを加えることになる。
   しかも、上で述べたとおり、対象の問題は当初の想定より狭いことが分かっている。

2. **ループ専用の再構成(新しいノードなし)。** 平坦化はせず、`RConCase` 全体を
   ループの外に出し、残った枝の本体の*内側*にループを包む。つまり、
   `RLoop ... (RConCase sc [...] Nothing)` を
   `RConCase sc [MkRConAlt ... (RLoop ...)] Nothing` に書き換える。
   既存の `RConCase` と `RLoop` だけで書けるので新しいノードは要らない。
   一方で、適用できるのは「ループの中に単一枝の case がある」という形だけである。
   ループの外にある単一枝の case には一般化できず、どのみち専用のパスが必要になる。

## どちらも見送った理由

`if` が消えているという上記の事実を踏まえると、残る利得は、すでに狭い形に対する
「1反復あたり destructure と dup を1回ずつ省く」ことだけである。その形とは、
単一枝の case で、スクルティニーがループ不変なのに、それでも毎回実行される場合である。
この利得は、どちらの案のコストも正当化しない。

案1は、当初考えていたより小さい利益のために、影響範囲の広い新しい IR プリミティブを
要求する。案2は新しいプリミティブこそ避けられるが、得られるのは狭いループ専用の
特殊ケースだけである。`Compiler.RC2.Loop` や `Compiler.RC2.Sink` と並ぶ、
単一目的のパスがもう1つ増えるにすぎない。しかも、その対価として省けるのは、
「1反復あたり1回の分岐ディスパッチ」ではなく「1反復あたり1回の dup」だと分かっている。

決定: **見送り。現時点では計画していない。** プロファイリングで、この反復ごとの
dup のコスト(すでに消えている分岐ディスパッチのコストではない)が実際に問題になる
具体例が見つかった場合に限り、見直す。

## 関連する未解決の問題: `ConAltNative` のループ境界・デュアルABI境界をまたぐ拡張

`Compiler.RC2.ConAltNative`(`rc2/doc/con-alt-native.md` を参照)は、
destructure したコンストラクタのフィールドをネイティブ値として何度も読む場合に、
その値をキャッシュする。ただし、キャッシュが効くのは単一の case の枝の本体の中だけである。
かつて `TODO.md` には、このキャッシュをループの反復境界やデュアルABIの呼び出し境界を
またぐように拡張する提案が、別の項目として載っていた。つまり、
**ループを通して持ち回されるコンストラクタ**のフィールドについて、ネイティブの
shadow を反復をまたいで保持する。そうしなければ、ループ本体が `case` に入り直す
たびに、destructure とキャッシュをやり直すことになる。

これは、前述の単一枝 case のホイスティングと同じ問題であり、ループではなく
`ConAltNative` の側から眺めているだけである。「動機」で挙げた
`feedCharOfString.go` の `v0` / `v20` は、まさに「ループを通して持ち回される
コンストラクタ」の例である。反復をまたいで残る `v20` のネイティブ shadow は、
この拡張が生み出すはずだったものそのものである。

実装するには、まず案2が一般のケースですでに解いている問題を解く必要がある。
`case` をループの外で1回だけ実行し、ループを残った枝の本体の内側に入れ子にする
再構成である。その上に `ConAltNative` の既存の枝ごとの shadow キャッシュを重ねる。
キャッシュの実行は、反復ごとではなく1回で済む。案1と違って新しい IR ノードは要らない。
`ConAltNative` の shadow-and-rename の仕組み(`doc/con-alt-native.md` の「設計」を参照)は、
既存のノードの上で動くからである。ただし、案2の狭さは引き継ぐ。依然として特定の1つの形の
ための専用パスであって汎用的な仕組みではなく、本書がすでに「得られる利得が想定より
小さい」として作らないと決めたループ再構成の仕組みを前提にしている。

元の提案のうち、デュアルABI境界をまたぐ側(ループの反復だけでなく、*関数呼び出しを
またいで*ネイティブ shadow を残すこと)は、ここまで詳しく検討したことがない。
実現には、`ConAltNative` が呼び出し箇所でコンストラクタのフィールドの shadow の状態を
推論できなければならない。つまり、`Compiler.RC2.DualABI` の引数・戻り値の Rep の
ネゴシエーションを拡張する必要があるが、その設計はこれまで一度も行われていない。
これは上記のすべてに加えて必要になる。

決定: **見送り。現時点では計画していない。** 理由は、ループ不変な case の
ホイスティングの項と同じである。この拡張を価値あるものにするはずだった部分
(ループ再構成の変換)は、それ自体の費用対効果の判断ですでに見送っている。

## ファイル

- `rc2/src/Compiler/RC2/Emit.idr` -- `emitAltChain` のドキュメントコメント。
  デフォルトなしの単一枝 case が縮退して「`if` がまったく出力されなくなる」という、
  本書の調査結果の根拠である。
- `rc2/src/Compiler/RC2/RCExp.idr` -- `RConAlt` / `RConCase`、`RLet`。
  `RGetField` のようなノードを仮に導入する場合、ここに追加することになる。
- `rc2/src/Compiler/RC2/Loop.idr` -- `isInvariantExpr` / `hoistInvariantPrefix`。
  平坦化した `RLet` の連鎖が利用するはずだった、既存のループ不変式のホイスティングの仕組み。
- `rc2/BENCHMARKS.md` -- 2026-08-18 付「クロージャの in-place 拡張」の項。
  このループの形が最初に見つかった場所。

  shadow キャッシュ」。
