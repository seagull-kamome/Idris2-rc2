# プログラムがマルチスレッドになるまでは通常の参照カウントを使う

(原文: `doc/hybrid-refcount.md`。内容が乖離した場合は原文を正とする。)

ステータス: 実装済み(2026-09-27)。末尾のエスケープ解析は、計測の結果、見送った。元の動機は`TODO.md`(「thread-local-awareなdup/dop」)にある。

## 問題

`dup`/`drop`は、スレッドを一度も起動しないプログラムでも、すべてアトミックなread-modify-writeになっている(`concurrency.md`の「atomic refcount」)。参照カウントの操作をすべて通常の(非アトミックな)操作にすると、参照カウントを多用するコードは25〜30%速くなる。

- `idris2-missing-containers`: 8.07秒から6.16秒
- `sort`: 3.19秒から2.37秒

## 設計

### プロセス全体で1つのフラグ

`bool idris2rc2_threaded`は、起動時はfalseである。これは、プログラムが2つ以上のスレッドでIdrisのコードを実行しうることを表す。

- **falseの間**、参照カウントの操作はすべて通常の操作になる。
- **trueになると**、従来どおりすべてアトミックになる。
- **セットするだけで、クリアすることはない。**

フラグをセットするのは、次の場所に限られる。

1. **ランタイム自身によるスレッドの起動時。** `refc_fork`、rc2baseの`forkJoin`、およびそれらの上に作られたもの(`TaskWorker`)である。いずれも`pthread_create`の前にセットする。
2. **ランタイムが関知しないスレッドの場合は、手動で。** たとえば、スレッドを起動してIdrisのクロージャを適用するCライブラリが該当する。プログラムは、そのスレッドがIdrisの値に触れる前に、`System.GC.RC2.enableMultiThreading`、あるいはCから`idris2rc2_enableMultiThreading()`を1回呼ぶ。
3. **起動時から。** `%cg rc2 multithreaded`または`--directive multithreaded`を指定する。外部ライブラリが初期化中にスレッドを起動するプログラムや、この問題をいっさい考えたくないプログラム向けである。

オブジェクトごとの印も、関数ごとのアノテーションもない。スイッチは1つだけで、プログラムに課される義務は、上の2だけである。ランタイムから見えない最初のスレッドの前に、1回宣言すればよい。

### 実行時に切り替えても安全な理由

フラグがセットされる前は、Idrisのコードを実行するスレッドは1つだけなので、通常の操作でも競合は起きない。フラグは2つ目のスレッドが起動する前に、そのスレッドの上でセットされる。`pthread_create`と、Cライブラリが自前のスレッドを起動するために使う受け渡しは、2つのスレッドを同期させる。このため、新しいスレッドは、セット済みのフラグを見る。それ以前に書き込まれたすべてのカウントも同様に見える。これ以降は、すべての操作がアトミックになる。

フラグはただの`bool`である。他のスレッドが存在する前に1回だけ書き込まれ、その後は読まれるだけなので、読み取りにアトミック操作は要らない。

### ヘッダ: union

カウントは1つの16ビットのフィールドのままで、2通りの方法でアクセスできる。

```c
typedef struct {
  union {
    _Atomic uint16_t refCount; // once idris2rc2_threaded
    uint16_t rc;               // before: plain loads and stores
  };
  uint8_t tag;
  uint8_t reserved;
} IDRIS2RC2_Header;
```

通常のアクセスは、`REFCOUNT_MAX`の検査や、switchの前の`isUnique`も含めて、すべて`rc`を通す。これは重要である。最初の試作では、フィールドを`_Atomic`のままにして、通常の経路にはrelaxedなloadとstoreを使った。しかし、得られた効果は半分だけだった。`missing-containers`は8.07秒から7.08秒になったが、完全に通常の操作にした場合は6.16秒である。GCCは、`_Atomic`なオブジェクトへのアクセスを、relaxedであっても、結合も並べ替えもしない。

### ランタイムの操作

`idris2rc2_datatypes.h`の2つのヘルパが、フラグの検査を担う。どちらもフラグを1回だけ検査し、`REFCOUNT_MAX`の検査を含む更新全体を、通常の操作またはアトミックな操作のどちらかで行う。

| ヘルパ | フラグが立っているとき |
|---|---|
| `idris2rc2_rc_retain(h)` | relaxed load、relaxed add |
| `idris2rc2_rc_release(h)` | relaxed load、release subtract、0になったらacquire load。最後の参照だったならtrueを返す |

ランタイムの参照カウントの更新は、`rt.c`のものも含めて、すべてこの2つを通る。

- `dup`、`drop`、`releaseLast`
- クロージャの`trampoline`、`tailcallApplyClosure`、`dropReuseConstructor`

最初の版はヘルパを4つ(load、add、subtract、acquire)持っていた。そのため`dup`と`drop`はフラグを2回検査しており、1回は`REFCOUNT_MAX`の検査、もう1回は更新のためだった。このせいで`missing-containers`の改善が1.5ポイント失われた(-16.4%ではなく-14.9%)。

`dup_n`自身のフラグが下りている経路を除くと、`rc`に直接触れる箇所は3つだけで、いずれも他のスレッドから到達できないオブジェクトを対象にしている。

- 新規のアロケーション
- 小さい整数のキャッシュの、1回限りの初期化
- すでに一意だと証明された値に対する`VERIFY`

`dup_n`のCASループは、フラグが立っているときだけ走る。`isUnique`は、フラグが立っていればacquire loadを行い、立っていなければ通常のloadを行う。

**解体の前のacquireは、フェンスではなくloadである。** 以前は`atomic_thread_fence(memory_order_acquire)`だった。ThreadSanitizerはフェンスをモデル化しないので、別のスレッドのrelease-decrementの後に続くすべての解体を競合として報告した。この変更前のランタイムでは45回の実行のうち6回、この変更の版では50回の実行で186件の警告が出た。同じカウントに対するacquire loadは、同等の効果を持ち、すでにキャッシュにある行に対するloadが1回増えるだけで済み、TSanも理解できる。50回の実行で警告は0件だった。

**`REFCOUNT_MAX`の検査は、ヘルパの一部である。** 最初の版では、そこで`rc`を直接読んでいた。他のスレッドが走り出すと、その通常の読み取りがアトミックな更新と競合した。rc2baseの`TestMVar`を1回実行しただけで、TSanは1,289件の競合を報告した。

## 計測(2026-09-27)

各プログラムの生成Cを、次の3つとリンクして計測した。

- この変更の前のランタイム(アトミック)
- 参照カウントの操作をすべて通常の操作にしたランタイム
- 実装したランタイム

数値は、3回実行した中で最良のものである。

| | アトミック(変更前) | すべて通常 | 実装版 |
|---|---|---|---|
| `idris2-missing-containers` | 8.11s | 6.18s (-24%) | 6.78s (-16%) |
| `sort`、1M個の`Int` | 3.17s | 2.38s (-25%) | 2.45s (-23%) |
| クロージャ、1M x 20 | 3.66s | 2.60s (-29%) | 2.69s (-27%) |
| map/filter、300k x 50 | 7.31s | 6.69s (-8%) | 6.71s (-8%) |
| BenchKnownCon | 0.76s | 0.57s | 0.57s |
| BenchClosureChain | 0.17s | 0.10s | 0.10s |
| BenchPushCon | 0.31s | 0.22s | 0.24s |

- マイクロベンチマークでは、効果のほとんどが保たれている。
- `missing-containers`では、フラグのために、すべて通常にした場合より命令数が7%、サイクル数が8%多くなる。これは、生成された本体が大きいプログラムで、参照カウントの操作ごとにloadと検査が1回ずつ増えた分である。
- map/filterを律速しているのは、カウントではなく、入力リストのキャッシュミスと`malloc`である。

次の2つの変種は、効果がなかった。

- 更新だけをフラグで切り替え、フェンスと`dup_n`は無条件のままにする。
- アトミックな経路をインラインから外す(`noinline, cold`)。マイクロベンチマークでは、わずかに遅くなった。

## エスケープ解析: 通常の操作に固定する(後回し)

残っているコストは、検査そのものである。他のスレッドから到達可能になることが決してないと証明できる値は、フラグがどうであっても、検査なしで通常の`dup`/`drop`にできる。そのような値とは、次のものである。

- その関数が構築するセル(`RCon`、クロージャ)
- 関数の内側で、フィールドの読み取りと`case`にだけ使われる
- 呼び出しに渡されず、他のオブジェクトに格納されず、返されない

このようなオブジェクトに到達するのは常に1つのスレッドだけである。途中でフラグが立ったとしても、そのカウントを更新するのはそのスレッドだけなので、正しさは保たれる。Emitは、これに対して`idris2rc2_dup_local`/`idris2rc2_drop_local`を出力する。

`TODO.md`には、すでに問題点が書かれている。そのような値のほとんどは、アンボックス化されているか、既存のコンストラクタのエスケープ解析(`constructor-escape-analysis.md`)で除去されている。得られる効果の上限は、上の表の最後の2列の差、つまり`missing-containers`で8ポイントである。解析を作る前に、そのうちどれだけに届くかを計測しておくべきである。

**計測(2026-09-27): 手続き内の解析は、作る価値がない。** 最終的なRCExp上で、すべての`dup`、`drop`、`postDrop`を数えた。

| | 箇所の数 | 同じ関数で構築されたセルに対するもの | そのうち、関数の外へ出ないもの |
|---|---|---|---|
| idris2-lsp | 297,911 | 4,063 | 57 |
| `missing-containers` | 806 | 10 | 0 |

ここで「出る」とは、呼び出しに渡される、フィールドに格納される、返される、ループで引き回される、エイリアスされる、のいずれかである。そのようなセルは、すでにアンボックス化されているか、コンストラクタのエスケープ解析で畳み込まれていて、残っていない。ほぼすべての`dup`/`drop`は、関数がパラメータとして受け取った値か、その値から読み出した値に対するものである。たとえば`map`がdropするリストのセルがそうである。これらを通常の操作に固定するには、次の2つが必要になる。

- ランタイムのエスケープ点(`fork`、`Channel`、共有された`IORef`、FFI、CAF)のどれかに到達しうる値の、プログラム全体にわたる解析
- 引数がスレッドローカルだと分かっている呼び出し元のための、呼び出し先ごとの複製

**計測(2026-09-27): パラメータを通した連鎖も、作る価値がない。** プログラム全体にわたる大まかな見積もりは、次のとおりである。

- 互いにエイリアスしうる、あるいは含みうる値は、同じグループにまとめる。対象は、エイリアス、コンストラクタのフィールド、`case`の束縛、引数とパラメータ、結果、ループのパラメータである。
- FFI、クロージャ適用、CAF、プリミティブに触れるグループ、またはクロージャとしても使われる関数に触れるグループは、共有されうるものとする。
- 複製はしない。

この見積もりでは、idris2-lspの297,911箇所のうち15,768箇所(5.3%)が見つかる。idris2-lspの17,870個の関数のうち7,737個は部分適用もされるので、そのパラメータは呼び出し元が不明である。`missing-containers`では、806箇所のうち283箇所が見つかる。そのうち生成Cの中で位置を特定できた236箇所を、手作業で通常の操作にした。

| `missing-containers` | 時間 |
|---|---|
| 実装版 | 6.48s |
| それらの箇所を通常の操作に | 6.37s (-1.7%) |
| すべての参照カウント操作を通常に | 5.95s |

これで埋まるのは、差の5分の1である。しかも、健全な実装なら見送らざるをえない分は、まだ引かれていない。見送りとする。残るコストのうち大きいのは、アロケータである。

## API

rc2baseの`System.GC.RC2`にあり、`unsafeGCDup`/`unsafeGCDrop`の隣に置かれている。

```idris
||| Switches rc2's reference counting to atomic operations, for good.
||| Call it once before starting a thread the runtime does not know
||| about, one that will touch Idris values (a C library's thread
||| running an Idris callback). `fork`/`forkJoin` already do it.
export enableMultiThreading : IO ()

||| Whether reference counting is atomic yet.
export isMultiThreaded : IO Bool
```

Cのコードからは、`idris2rc2_memory.h`の`idris2rc2_enableMultiThreading()`と`idris2rc2_threaded`が使える。

## テスト

- `Test102MultiThreadSwitch`: フラグは起動時に下りていて、`fork`の後に立っていることを確認する。valgrindの下でも実行する。
- `Test103MultiThreadedDirective`: `%cg rc2 multithreaded`の下では、起動時にフラグが立っていることを確認する。
- rc2baseの`TestMultiThreadRC2`: `enableMultiThreading`の後にフラグが立っており、その後の`forkJoin`も動くことを確認する。
- `Test104ThreadStress`: 8本の`forkJoin`スレッドが、共有された2,000要素のリストを1つmapして新しいリストを返し、それをメインスレッドでdropする。

**ThreadSanitizer: `tests/tsan.sh`。** `verify.sh`の最後のフェーズとして走る(`--no-tsan`でスキップできる)。ランタイムとrc2baseのCを`-fsanitize=thread`でビルドし、次のプログラムの生成Cとリンクして、TSanの警告が1件でもあれば失敗とする。

- `Test102`と`Test104`
- rc2baseの`TestConcurrency`、`TestMVar`、`TestMultiThreadRC2`

競合は、特定のインターリーブでしか現れないことがあるので、それぞれ`TSAN_RUNS`回(デフォルトは3)実行する。各10回の実行で警告は出なかった。変更前のランタイムでは、45回の実行のうち6回で、フェンスに起因する偽陽性が出ていた(「ランタイムの操作」を参照)。
