# 自己末尾再帰ループを、ループ不変なディスパッチcaseの内側へsinkingする: 調査・設計済み、未実装

(原文: `doc/loop-in-case-sinking.md`。内容が乖離した場合は原文を正とする。)

本書は、`rc2/doc/case-hoisting-scope.md` の続きとして検討した設計を記録する。
`case-hoisting-scope.md` は、その逆向きの変換、すなわちループ不変な `case` をループの
*外へ*ホイストする案を調査し、見送ったものである。将来この案を再び取り上げる(あるいは
やめると判断する)ときに、以下の分析をやり直さずに済ませるために書いている。
**ステータス: 紙の上で設計しただけで、未実装である。**

## 動機

`case-hoisting-scope.md` は、`idris2-missing-containers` の
`Data.Hash.Algorithm.Internal.feedCharOfString.go` で見つかった形のコストを
「1反復あたり dup 1回」と見積もった。そして、検討した2つの実装案のどちらも、これでは
割に合わないと判断した。しかし、この見積もりは実際のコストを小さく見ていた。
**本当の1反復あたりのコストは、dup 1回ではなく、ループ本体で使われ続ける
destructure 済みフィールドの数だけのdupである。** このプロジェクトの
`--directive dumprcexpr` で、`idris2-missing-containers` の `MurMur3` の
`HashAlgorithm` 実装のダンプを取り、直接確認した(`rc2/BENCHMARKS.md` の
idris2-missing-containers の節を参照)。

```
case v1 of
  Data.Hash.Algorithm.MurMur3.MkMurMur3 [record] tag=Just 0 args=[v2, v3, v4] ->
    dup v2 x2
    dup v3 x2
    dup v4 x2
    drop [v1]
    ...
```

フィールドは3つあり、それぞれのdupは `x2` にまとめられている(下流での使用が
2か所ずつある)。つまり、反復のたびに実質6回のインクリメントが発生する。しかも、
この `case` のスクルティニー(`v1`、`HashAlgorithm` の状態)は、実際の呼び出し元で
*外側の*文字ごとのループを何周しても、まったく変化しない。`Compiler.RC2.Loop` の
既存のループ不変パラメータの除去は、`v1` 自体をループのパラメータから外している。
それでも、`v1` を再びマッチする `case` と、そのフィールドを取り出す `dup` は、毎回の
反復で再実行される。

## `case-hoisting-scope.md` との関係

`case-hoisting-scope.md` の案2(「`RConCase` 全体をホイストし、残った枝の本体の*内側*に
ループを包む」)は、本書の変換とまったく同じものを、逆の向きから述べたものである。
あちらは「case をループから引き抜く」と言い、こちらは「ループをcaseの中へ押し込む」と
言う。あちらでは、コストを「dup 合計1回」と見積もっていたため、専用のパスを作るだけの
見返りがないとして見送られた。本書は、「残るフィールドごとに dup 1回」という訂正後の
見積もりのもとで、この案を再検討する。あわせて、あちらが素描するにとどまっていた設計も
仕上げる。

## 変換の内容

対象は、次のような関数である。関数の本体は、先頭の `RDup` / `RDrop` / `RLet` の前置きを
取り除くと、それ自体が `RConCase` / `RConstCase` になる。その `case` のスクルティニーは、
ループ不変なローカル変数である。つまり、トップレベルの引数であり、`mapTailAppNames` が
末尾の自己呼び出しの対象として見つけるどの呼び出しからも、再代入されない。各枝は、
それぞれ独立に、0個以上の末尾再帰の自己呼び出しを含む。

```
-- before
def go(v0, ...params...):
  case v0 of
    Alt1 [tag=0] args=[f1, f2, f3] -> <body1, may tail-call go(v0, ...)>
    Alt2 [tag=1] args=[g1]         -> <body2, may tail-call go(v0, ...)>

-- after
def go(v0, ...params...):
  case v0 of
    Alt1 [tag=0] args=[f1, f2, f3] ->
      loop:  -- RLoop, params now include f1/f2/f3 as loop-invariant captures
        <body1, tail self-calls become RLoopContinue>
    Alt2 [tag=1] args=[g1] ->
      loop:  -- an *independent* RLoop, siblings never nest
        <body2, tail self-calls become RLoopContinue>
```

末尾の自己呼び出しを実際に含む枝は、それぞれ専用の `RLoop` を得る。この `RLoop` は、
`Compiler.RC2.Loop.applyLoop` がすでに持っている仕組みと*同じ*もの(shadow の昇格、
不変式のホイスト、`RLoopContinue` の構築、`fillLoopContinuePostDrop`)で作る。
違いは、関数全体に対して1回ではなく、枝ごとに1回ずつ呼び出す点だけである。
その際、その枝自身がdestructureしたフィールド(`f1` / `f2` / `f3`)を、
`applyLoop` が通常のトップレベル引数に対して行っているのと同じ扱いの対象に加える
(ネイティブshadowへの昇格や、不変パラメータの除去などの対象になる)。`case` 自体は
ちょうど1回しか実行されない。スクルティニーがループ不変なので、仮に再突入したとしても
必ず同じ枝が選ばれる。ただし、もはやループの内側にないので、再突入そのものが起こらない。
そのため、これまで反復のたびに再実行されていたフィールドの `dup` は、ループが始まる
前に1回だけ実行される。

## なぜ、本物の入れ子ループのサポートは不要なのか

これは設計中に気づいた、重要な訂正である。素朴に捉えると、「1つの関数の中に複数の
ループ」を作る話に聞こえる。それなら、`TODO.md` の「Future: nested self-tail-recursive
loops」の項目が警告している作業がすべて必要になりそうに思える。しかし、この特定の形に
ついては、その必要はない。

**この変換が作るループは兄弟関係にあり、入れ子にはならない。** 枝ごとに作られる
`RLoop` は高々1つである。また、ある枝の本体が別の枝のループを含むこともない。それらは
同じ `case` の互いに素な分岐の中にあり、実行時にはそのうちちょうど1つだけが実行される。
生成された木のどの地点でも、それを*囲んでいる*有効なループは高々1つである。このことから
次の2点が導かれる。

- `Compiler.RC2.DualABI` の `loopContinueNativeReads`(現在は、「それを囲むループ自身の
  `loopParams`」を保持する、`Maybe (List (Int, Rep))` 型の単一のスロット)は、スタックに
  する必要が**ない**。スタックが必要になるのは、1つのループの本体をたどっていて見つけた
  `RLoopContinue` が、外側のループと内側のループのどちらのものか曖昧になりうる場合で
  ある。それには、兄弟関係ではなく、本物の入れ子(あるループの本体が別のループを含む
  こと)が必要になる。
- `Loop.idr` の、本体ごとに働く補助関数(`stripOwnership`、`renameRCExp`、
  `hoistInvariantPrefix`、`wrapInvariantShadows`、`markInvariantNative`、
  `dupInvariantBoxed`、`invariantLoopParamIds`、`elideInvariantContinueArgs`、
  `fillLoopContinuePostDrop`)は、「入れ子になったループ自身の境界で止まる」ように
  する必要が**ない**。止まるべき入れ子の境界がないからである。これらはどれも、枝ごと
  に1回ずつ、その枝自身の互いに素な部分木に対して独立に呼び出せる。現在、関数全体の
  本体に対して1回実行されているのと同じである。枝どうしはIRのノードを共有しないので、
  互いに悪影響を及ぼすおそれはない。

したがって、実際の前提条件は、`TODO.md` の既存の項目より狭い。必要なのは、
**「1つの関数が、独立に末尾再帰するcaseの枝ごとに1つずつ、複数の兄弟の `RLoop` を
生成してよい」**ことであり、「ループが入れ子になってよい」ことではない。本物の入れ子が
必要になる形については、後述の「関連する、より大きな案」を参照。

## 実際に必要になる変更

1. **`applyLoop` 内(またはその前段)での、新しい検出ステップ。** 従来の、関数全体を
   単一のループとして走査する処理に進む前に、「関数の本体が(前置きを除けば)、
   ループ不変なスクルティニーに対する `RConCase` / `RConstCase` である」という形を
   認識する。スクルティニー自体のループ不変性の検査が必要になる。考え方は、
   `invariantLoopParamIds` が通常のパラメータに適用しているものと同じ形で、
   「このローカル変数が、どの枝の末尾自己呼び出しをまたいでも再代入されないか」を
   調べればよい。関数の引数に対する `case` という新しいものについては、一般の場合
   よりも簡単な問いになる。本書が対象とする狭い形では、スクルティニーは常に単なる
   トップレベルの引数であり、計算された式にはならない。これは、`case-hoisting-scope.md`
   が意図的に範囲を狭めたのと同じ方針であり、「任意のループ不変な式」という一般の版は
   目指さない。
2. **ドライバの再構成。** `applyLoop` のトップレベルの入口を、次のように変える。
   「まずcaseをsinkingする形を試し、一致すればその枝ごとに、既存の本体単位のコア
   ロジックを独立に再帰適用する(結果として兄弟のループが0個、1個、N個できる)。一致
   しなければ、従来どおり関数全体に対する動作に戻る」。従来は、これを無条件に行って
   いた。
3. **枝自身がdestructureしたフィールドを、既存の引数リストの扱いに組み込む。**
   `applyLoop` のコアロジックは、すでに `argIds`(現状は、関数自身のトップレベルの
   引数)についてパラメータ化されている。枝自身の本体を、その枝専用の小さなループの
   ホストとして処理するときは、その枝の `RConAlt.args` も同じリストに入れる必要が
   ある。
4. **Emit 側。** `emitAltChain` の、単一枝でデフォルトなしの場合の「`if` がまったく出
   力されない」縮退(`case-hoisting-scope.md` の調査結果)が、1つ以上の枝の本体が
   通常の式ではなく `RLoop` ノードになっても、引き続き適用されることを確認する。この
   縮退は分岐のディスパッチそのものに関するもので、枝の本体の内容とは直交するため、
   適用されると予想している。ただし、仮定するだけにせず、実装後に生成された C で確認
   する価値がある。

## 未解決の疑問とリスク

- **`Compiler.RC2.MutualLoop` との相互作用。** このパスも、末尾再帰の形(相互再帰する
  関数を1つにまとめる)を対象にする。パイプラインの順序(`RC2.idr` の `toRCDefs` では
  `MutualLoop` が `Loop` より前に走る)から、直接の衝突はなさそうである。しかし、
  case をsinkingする形の検出を実際に実装したときに、確認が必要である。特に、
  `MutualLoop` がすでにマージした関数が、この変換を適用すべき(あるいは適用すべきで
  ない)形で、case をsinkingする形になる場合があるかどうかを調べる必要がある。
- **`Compiler.RC2.ConAltNative` を上に重ねること。** `case-hoisting-scope.md` の
  「関連する未解決の問題」の節は、これをすでに自然な後続の拡張として挙げていた
  (ネイティブshadowを、毎回キャッシュし直さずに、ループの反復をまたいで残す)。
  これは今回もそのまま当てはまるが、詳細な設計はまだしていない。
- **スクルティニーの不変性の検査を正しく書くこと。** 正しさに関するバグが潜みうる
  のは、ここだけである。ある枝の末尾再帰の継続が、スクルティニーを(直接、あるいは
  ループパラメータの連鎖を通じて)実際には*変更している*のに、ループ不変と誤って
  判定してしまうと、最初の反復のあと、`case` のディスパッチが誤った枝に固定されたまま
  になる。気づかないうちに起こる、本物の挙動上のバグであり、最適化の取りこぼしでは
  済まない。新しい検査をゼロから書くのではなく、`invariantLoopParamIds` が持つ、
  すでにテスト済みの推論を再利用するべきである。

## 関連する、より大きな案(意図的に別扱い): ループだけの関数を、囲むループにインライン化する

この設計が生まれたのと同じ議論で出た案である。関数が複数の `RLoop` を生成できるように
なれば、`Compiler.RC2.InlineCExp` が、本体全体が自己末尾再帰のループになっている小さな
関数を、自身もループしている呼び出し元に展開する道も開けるのだろうか。現状では、これは
できない。`Inline` の基準A(`rc2/doc/inlining.md`)は、呼び出しを含まない呼び出し先を
要求する。自己末尾再帰の関数は、`Inline` が走る時点(`Compiler.RC2.Loop` がその自己
呼び出しを `RLoopContinue` に変換する前)では、少なくとも1つ(自分自身への)呼び出しを
必ず含む。そのため、そのような関数は、サイズにかかわらず、現状ではインライン化の対象
にならない。これは、`rc2/doc/caf-memoization.md` の「Interaction with
Compiler.RC2.InlineCExp」の節が、CAF についてすでに見つけていた、2つの仕組みが重ならな
いという性質と同じである。

これは、上で述べたsinkingの変換とは、まったく異なる形である。呼び出し先自身のループ
を、呼び出し元自身のループ本体の*内側*にある呼び出し箇所に展開すると、`RLoop` が別の
`RLoop` の中に本当に**入れ子**になる。兄弟関係ではない。まさにこれが、`TODO.md` の
「Future: nested self-tail-recursive loops」の項目がすでに警告している形である。必要
になるのは、`Compiler.RC2.DualABI` の `loopContinueNativeReads` を、(最も内側のループ
に対応づけられた)本物のスタックにすることと、上に挙げた `Loop.idr` の本体単位の補助
関数をすべて監査して、入れ子になった内側のループ自身の境界で正しく止まる(その向こう
側までは踏み込まない)ようにすることである。これは、`TODO.md` の既存の項目のうち
*費用の大きい*半分であり、上のsinkingの変換は、これを必要としないように、わざわざ
設計したものである。

**追記**: クロージャの呼び出し*そのもの*を解決して(`apply` を直接の `call` にして)、
呼び出し先の本体は必ずしもインライン化しない、という、より狭い兄弟の仕組みは、
`rc2/doc/speculative-closure-specialization.md` に別途設計してある。この仕組みは、本節
が述べる入れ子ループの仕組みを必要としない。同書は、`go` がクロージャを呼び出すという
この同じ形の*一般の*場合(呼び出し先がループだけの関数に限らない)も扱っており、
採算性を判断する独自の基準を持っている。

**本書自身の設計の一部としては、意図的に追求しない。** この2つ目の案を実現するために、
入れ子ループのための仕組みをすべて作るとしたら、まだまったく測定されていない利益のために、
大きなコストを払うことになる。上記のsinkingの変換が、実際にプロファイルした
フィールドごとの `dup` のコストに基づいているのとは異なる。小さなループだけの関数が、
別のループの本体の中から実際に呼ばれている具体的なプログラムは、まだ見つかっていない。
この案を再検討する場合に最初にやるべきことは、この調査全体が守ってきた方針と同じである。
実際のプログラムに `--directive dumprcexpr` を使って具体例を探す(あるいは作る)。その
形と、そのコストが実際に生じるかどうかを確認してから、実装の範囲を決める。
