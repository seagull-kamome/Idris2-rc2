# ループ不変な分岐caseの中へ、自己末尾再帰loopを沈める: 調査・設計はしたが未実装

(原文: `doc/loop-in-case-sinking.md`。内容が乖離した場合は原文を正とする。)

本書は、`rc2/doc/case-hoisting-scope.md`(「caseをループの外へホイストする」案、既に見送り済み)の裏返しの変換として検討した設計を記録する -- 将来のセッションがこの案を再検討する(あるいは見送る)際に、以下の分析を再導出せずに済むように。**ステータス: 紙の上で設計しただけで、未実装。** 本コミットにコード変更は一切含まれない。

## 動機

`case-hoisting-scope.md`は、`idris2-missing-containers`の
`Data.Hash.Algorithm.Internal.feedCharOfString.go`に見つかった形状のコストを「1回の反復あたりdup1個」と見積もり、それではどちらの実装案も正当化できないと判断していた。この見積もりは実際のコストを過小評価していた: **本当の1反復あたりのコストは「dup1個」ではなく、「ループ本体で使われ続ける、destructureされたフィールド1個につきdup1個」である。** これは本セッションで`idris2-missing-containers`の`MurMur3`の`HashAlgorithm`実装を実際にダンプして確認済みである(`rc2/BENCHMARKS.md`のidris2-missing-containers節参照):

```
case v1 of
  Data.Hash.Algorithm.MurMur3.MkMurMur3 [record] tag=Just 0 args=[v2, v3, v4] ->
    dup v2 x2
    dup v3 x2
    dup v4 x2
    drop [v1]
    ...
```

3フィールド、それぞれバッチ`x2`(下流で2箇所使用)——スクルチニー(`v1`、`HashAlgorithm`の状態)が実際には周回する外側のループを通じて一度も変化しないcaseに対して、毎回の反復で実効6回分の増分が発生している。`Compiler.RC2.Loop`の既存のループ不変パラメータ除去は、`v1`自身を既にループ自身の搬送パラメータから除外しているが——その`v1`を再マッチするcaseと、そのフィールドを読み戻す`dup`群は、それでも毎回の反復で再実行され続ける。

## `case-hoisting-scope.md`との関係

同書のオプション2(「`RConCase`全体をホイストして、生き残った枝の本体の中にループを包み込む」)は、まさにこれと同じ変換を逆方向から説明したもの(あちらは「caseをループの外へ引き抜く」、こちらは「ループをcaseの中へ押し込む」)である。同書ではこの案は「dup合計1個」というコスト見積もりのもとで、専用パスを正当化するだけの見返りが無いとして見送られた。本書は「生き残るフィールドごとにdup1個」という訂正済みの見積もりのもとでこれを再検討し、かつ同書が素描するに留めていた設計を完成させる。

## 変換の中身

ある関数の本体が——先頭の`RDup`/`RDrop`/`RLet`という前置きを剥がした後——それ自体がループ不変なローカル(トップレベルの引数で、`mapTailAppNames`が見つける末尾自己呼び出しのターゲットとして再代入されることがないもの)をスクルチニーとする`RConCase`/`RConstCase`であり、各分岐がそれぞれ独立に0個以上の末尾再帰自己呼び出しを含む場合:

```
-- 変換前
def go(v0, ...params...):
  case v0 of
    Alt1 [tag=0] args=[f1, f2, f3] -> <本体1、go(v0, ...)を末尾呼び出しするかもしれない>
    Alt2 [tag=1] args=[g1]         -> <本体2、go(v0, ...)を末尾呼び出しするかもしれない>

-- 変換後
def go(v0, ...params...):
  case v0 of
    Alt1 [tag=0] args=[f1, f2, f3] ->
      loop:  -- RLoop、パラメータにはf1/f2/f3がループ不変な捕捉値として加わる
        <本体1、末尾自己呼び出しはRLoopContinueになる>
    Alt2 [tag=1] args=[g1] ->
      loop:  -- 独立したRLoop、兄弟同士は決して入れ子にならない
        <本体2、末尾自己呼び出しはRLoopContinueになる>
```

実際に末尾自己呼び出しを含む各枝はそれぞれ自分専用の`RLoop`を得る。使う機構は`Compiler.RC2.Loop.applyLoop`が既に持っているもの(shadow昇格、不変式ホイスト、`RLoopContinue`構築、`fillLoopContinuePostDrop`)そのままで、関数全体に対して1回だけ呼ぶ代わりに枝ごとに1回呼ぶだけである。その枝自身のdestructureされたフィールド(`f1`/`f2`/`f3`)は、`applyLoop`が既に普通のトップレベル引数に与えている扱い(ネイティブshadow昇格やループ不変パラメータ除去の対象になる)にそのまま合流させる。case自体は今やちょうど1回しか実行されない(スクルチニーがループ不変なので、仮に再突入があったとしても常に同じ枝を通る——そして実際には再突入は起きない、そもそもループの外に出たのだから)ため、以前は毎回の反復で再実行されていたフィールドの`dup`群は、ループが始まる前にちょうど1回だけ実行されるようになる。

## なぜ本物の入れ子loop対応が不要か

これは本設計を詰める過程で見つかった重要な訂正点である。素朴な捉え方(「1関数に複数のloop」)は、`TODO.md`の「Future: nested self-tail-recursive loops」項目が警告している事態全部が必要に聞こえる。しかし、この特定の形状に限れば、そうではない。

**この変換が生み出すloopは兄弟同士であり、決して入れ子にはならない。** 各枝は高々1個の`RLoop`を得て、どの枝の本体も他の枝のloopを含むことはない——それらは同じ`case`の互いに排他な分岐に住んでおり、実行時にはそのうちちょうど1つしか実行されない。生成された木のどの地点でも、依然として「現在自分を包んでいるloop」は高々1個である。つまり:

- `Compiler.RC2.DualABI`の`loopContinueNativeReads`(現在は「包んでいるloop自身の`loopParams`」用の単一`Maybe (List (Int, Rep))`スロット)は**スタック化不要**である。スタックが必要になるのは、あるloop本体を歩いている最中に見つけた`RLoopContinue`が外側と内側どちらのloopに属するか曖昧になり得る場合——つまり本物の入れ子(あるloopの本体が別のloopを含む)が必要な場合であり、兄弟関係ではそれは起きない。
- `Loop.idr`自身の本体単位ヘルパー群(`stripOwnership`/`renameRCExp`/`hoistInvariantPrefix`/`wrapInvariantShadows`/`markInvariantNative`/`dupInvariantBoxed`/`invariantLoopParamIds`/`elideInvariantContinueArgs`/`fillLoopContinuePostDrop`)は「入れ子loop自身の境界で止まる」ことを新たに覚える必要が**無い**——そもそも止まるべき入れ子境界が存在しない。どれも枝ごとに独立して、その枝自身の互いに独立した部分木に対して1回ずつ呼び出せる——今日、関数全体の本体に対して1回だけ実行しているのと全く同じ形で。枝同士がIRノードを共有することは無いので、互いに汚染し合うリスクも無い。

つまり実際の前提条件は、`TODO.md`の既存項目より狭い: **「関数はケースの各枝ごとに、独立に末尾再帰であるならば、兄弟の`RLoop`を複数持ってよい」**——「loopが入れ子になってよい」ではない。真に入れ子が必要になる形は下記「関連する、より大きなアイデア」参照。

## 実際に手を入れる必要がある箇所

1. **`applyLoop`内(またはその手前)の新しい検出ステップ**: 「関数本体が(前置きを除けば)ループ不変なスクルチニーを持つ`RConCase`/`RConstCase`そのものである」という形状を、今の関数全体単発ループ走査にフォールバックする前に認識する。スクルチニー自身のループ不変性チェックが要る——`invariantLoopParamIds`が普通のパラメータに対して既に適用している推論と同じ形を、「このローカルがどの枝の末尾自己呼び出しによっても(直接であれ、ループパラメータの連鎖を通じてであれ)再代入されることが無いか」という問いに適用するだけであり、ここでのスクルチニーは常にプレーンなトップレベル引数である(`case-hoisting-scope.md`自身の意図的に狭いスコープに倣い、「任意のループ不変式」という一般形は狙わない)ので、一般の場合より単純な問いになる。
2. **ドライバの組み替え**: `applyLoop`自身のトップレベルの入り口を、「まずcase沈め込み形状を試す。マッチすれば既存の本体単位の中核ロジックを各枝に独立に再帰適用する(結果として0個、1個、あるいはN個の兄弟loopが生まれる)。マッチしなければ今の関数全体の挙動にフォールバックする」という形に変える必要がある。
3. **枝自身のdestructureされたフィールドを既存の引数リスト処理に合流させる**: `applyLoop`の中核ロジックは既に`argIds`(現状は関数自身のトップレベル引数)でパラメータ化されている。ある枝自身の`RConAlt.args`は、その枝の本体をそれ自身のミニloopホストとして処理する際、同じリストに合流させる必要がある。
4. **Emit側**: `emitAltChain`の既存の単一枝・デフォルト無しの「if文自体を出さない」畳み込み(`case-hoisting-scope.md`自身の発見)が、1個以上の枝自身の本体がプレーンな式ではなく`RLoop`ノードそのものになった後もそのまま効くか確認する——効くはずである(この畳み込みは分岐そのものの話であり、枝の本体の中身とは直交する)と予想されるが、実装した際に生成Cで確認すべきで、前提だけで済ませるべきではない。

## 未解決の懸念・リスク

- **`Compiler.RC2.MutualLoop`との相互作用**: このパスも末尾再帰の形状を対象に動作する(相互再帰関数を1つに合成する)。パイプラインの順序(`RC2.idr`の`toRCDefs`: `MutualLoop`は`Loop`より先に走る)からは直接の衝突は無さそうだが、case沈め込みの検出が実際に動くようになった時点で確認が必要——特に、`MutualLoop`が既に合成した関数が、この変換が適用すべき(あるいは適用すべきでない)形でcase沈め込みの形状を呈することがあり得るか。
- **`Compiler.RC2.ConAltNative`の上乗せ**: `case-hoisting-scope.md`自身の「関連する隙間」節が既にこれを自然な追随案として挙げている(ネイティブshadowをループの反復を跨いで生かし続ける、毎回再キャッシュする代わりに)——ここでも変わらず真実だが、まだ詳細設計はしていない。
- **スクルチニーの不変性チェックを正しく行うこと**がバグを隠しやすい唯一の箇所である: スクルチニーをループ不変だと誤って扱ってしまい、実はどこかの枝の末尾再帰の継続が(直接であれ、ループパラメータの連鎖を通じてであれ)それを実際に変化させている場合、caseの分岐先が最初の1回以降静かに固定されてしまう——これは見逃した最適化どころではなく、本物の挙動バグである。ゼロから新しいチェックを書くのではなく、`invariantLoopParamIds`自身の既存の、既にテスト済みの推論を再利用すべきである。

## 関連する、より大きなアイデア(意図的に切り離す): loop専用関数を包み込むloopへインライン展開する

本設計のきっかけとなったのと同じ会話から出てきた話: 関数が複数の`RLoop`を生み出せるようになれば、`Compiler.RC2.Inline`が「本体全体が自己末尾再帰loopそのものである」小さな関数を、それ自身loopしている呼び出し元へ差し込めるようにもなるのではないか? 今日はできない: `Inline`のCriterion A(`rc2/doc/inlining.md`)は呼び出し先がcall-freeであることを要求し、自己末尾再帰関数は`Inline`が走る時点(`Compiler.RC2.Loop`がまだその自己呼び出しを`RLoopContinue`に変えていない時点)で常に少なくとも1個の呼び出し(自分自身への)を含む——なのでそのような関数は、大きさに関わらず今日は一度もInline対象にならない。`rc2/doc/caf-memoization.md`自身の「Interaction with Compiler.RC2.Inline」節が既にCAFについて見つけたのと同じ排他性である。

これは上記の沈め込み変換とは本質的に異なる形状である: 呼び出し元自身のloop本体の**内側**にある呼び出し箇所へ、呼び出し先自身のloopを差し込むと、1個の`RLoop`がもう1個のloopの**中に本当に入れ子になった**ものが生まれる——兄弟ではない。これはまさに`TODO.md`の「Future: nested self-tail-recursive loops」項目が既に警告している形であり、`Compiler.RC2.DualABI`の`loopContinueNativeReads`が(最内周のloopでキー付けした)本物のスタックになる必要があり、加えて上記`Loop.idr`自身の本体単位ヘルパー群全てを、入れ子になった内側loop自身の境界で正しく止まる(踏み越えない)よう監査する必要がある——上記の沈め込み変換がまさに避けるよう設計された、`TODO.md`の既存項目の中でも**高価な方**の半分である。

**更新**: クロージャの**呼び出しそのもの**(`apply`→直接`call`)だけを解決し、必ずしも呼び出し先自身の本体をインライン展開しない——ゆえに本節が説明する入れ子loop対応の機構を一切必要としない——より狭い、兄弟関係の機構を`rc2/doc/speculative-closure-specialization.md`に別途設計した。同書はこの同じ「goがクロージャを呼ぶ」形状の**一般形**(loop専用の対象に限らない)を、独自の採否判定機構込みで扱っている。

**本書自身の設計の一部としては意図的に追求しない**: この2つ目のアイデアを解禁するためだけに完全な入れ子loop基盤を構築するのは、まだ全く計測されていない見返りのために大きい方のコストを払うことを意味する——上記の沈め込み変換(実測済みの、プロファイル済みのフィールドごとの`dup`コストに根ざしている)とは違い、loop専用の小関数がまさに別のloopの本体の内側から呼ばれている、という具体的なプログラムはまだ見つかっていない。これを再検討するなら、正しい最初の一歩は、この調査全体が従ってきたのと同じ規律である: 実プログラムに対して`--directive dumprcexpr`で具体例を見つける(あるいは構築する)、そしてこの形状(とそのコスト)が実際に発生することを確認してから、実装のスコープを決める。
