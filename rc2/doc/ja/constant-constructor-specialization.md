# 定数コンストラクタ引数の特殊化

(原文: `doc/constant-constructor-specialization.md`。内容が乖離した場合は原文を正とする。)

コンパイル時定数の*コンストラクタ*(実際にはinterface辞書)を引数に取る呼び出し先を、その引数について特殊化する。これにより、呼び出し先の中にあるboxedなメソッドディスパッチが、直接呼び出しに変わる。

実装は`rc2/src/Compiler/RC2/SpecClosure.idr`の後半(`applySpecConstCon`)にある。構造を扱うヘルパとパイプライン上の位置は、クロージャ引数を扱う兄弟のパスと共有する。`--directive nospecconstcon`で無効にできる。クロージャ側については`speculative-closure-specialization.md`を参照。3段階の構成と採否の判定の方針は、意図的にそちらにそろえてある。

## 埋めるべき隙間

`SpecClosure`は、*クロージャ*引数、つまり**適用される**パラメータについて呼び出し先を特殊化する。interface辞書のケースは扱えない。辞書の場合、引数は**分解される**レコードだからである。

```
def Prelude.Types.elemBy  (fun args= ["v10077", "v10078", "v10079"] ret= Boxed)
  case v10077 of                                       -- (1) destructure
    Prelude.Interfaces.MkFoldable [record] args= [_, _, _, _, _, v10085] ->
      let v10087 = apply v10078 [v10079]
      apply v10085 [..., v10087]                       -- (2) boxed dispatch
```

`v10077`は`case`のスクルティニーとしてしか使われていない。呼び出し元は、`Compiler.RC2.ConstFold`がすでに1つの`RCConstCon`に畳み込んだ辞書を渡している。その`RCConstCon`のフィールドは`RCConstClosure`である。したがって、ディスパッチを解決するのに必要なものはすべてコンパイル時に分かっている。ただ、それが呼び出し先自身の本体には届いていないだけである。

## 下流に新しい処理が要らない理由

定数を本体に届けることが、書き換えのすべてである。残りは、既存の連鎖が自力で仕上げる。

1. `ConstFold`の`RConCase`のスクルティニー解決が、既知の`RCConstCon`に対して`case`を畳み込み、各altのフィールドを、対応する定数に束縛する(`insertConArgs`)。
2. 各メソッドのフィールドは`RCConstClosure`になっている。そのため`ConstFold`の`RApp`の場合が、`apply`を直接の`RAppName`呼び出し(引数が足りなければ`RUnderApp`)に書き換える。`const-closure-fold.md`を参照。
3. `Inline`/`LateInline`/`DualABI`は、名前が付いた呼び出しを見通せるようになる。`RApp`のままでは見通せなかったものである。

クロージャ側と違って、ここに`rewriteApply`に相当するものがないのは、このためである。置換と既存の畳み込みで、変換のすべてが済む。

## 3つのステップ

1. **候補の検出。** 呼び出し箇所`call g [..., c, ...]`のうち、`c`が`RCConstCon`であるものを探す。そのうえで、`g`のその位置のパラメータが、次の3通りの使われ方*以外*にはどこにも使われていないことを調べる。
   - `RConCase`のスクルティニーとして使われる。
   - `g`自身の再帰呼び出しの同じ引数位置に、そのまま渡される(自己の素通し)。
   - 別の呼び出しのパラメータに渡される(転送箇所。後述の「推移的な特殊化」を参照)。

   スクルティニーか転送箇所が少なくとも1つあれば、三つ組`(g, argPos, c)`を記録する。この関門が`constParamUses`である。クロージャ側の`paramUses`をモデルにしていて、`apply`を「`RConCase`のスクルティニー」に置き換えた。`selfPassthroughOccurrences`と`forwardSites`は、そのまま共有している。

   この時点で`ConstFold`はプログラム全体で不動点まで走り終えている。そのため、定数の引数は呼び出し箇所にそのまま書かれており、`RLet`の向こうに隠れていることはない。クロージャ側と違って、引き回すべき`Bound`環境はない。

   **自己の素通しを許すために、専用の仕組みは要らない**。この点は明記しておく価値がある。再帰する`go`がステップごとに辞書を引き回すのは、現実のinterface辞書がほとんど必ず取る形である。これを拒否すると、機会の大半を捨てることになっていた。許可しても問題なく動く。シード付きの畳み込みは、再帰呼び出しにも定数を代入する。その結果、定数を明示した*汎用の*呼び出し先を呼ぶ形になる。ステップ3のプログラム全体のリダイレクトの走査は、元の関数だけでなく複製にも及ぶ。そのため、この呼び出しはまさにこのキーのリダイレクトのエントリに一致し、引数を落とした、複製自身への呼び出しになる。再帰は、追加の作業なしに、底まで特殊化される。

2. **投機的な複製と再畳み込み。** 異なる三つ組ごとに1回だけ行う(メモ化する)。`g`を複製し、シグネチャから該当のパラメータを落として、そのidを畳み込み自身の`Env`にシードする。そのために追加したのが`ConstFold.foldConstDefWith`である。

3. **採否の判定。** 複製が持つ`RApp`ノードの数が、元の関数より厳密に少ないときだけ、複製を残す。代入の後では、特殊化したパラメータは完全に消えている。したがって、判定の問いは構造に関する素直なものになる。このパスが取り除くために作られたディスパッチは、実際に取り除かれたか。取り除かれていなければ複製を捨て、すべての呼び出し箇所は汎用の`g`を呼び続ける。例外は、次の節の純粋な転送関数だけで、これは到達先で判定する。

パイプライン上の位置は、`applySpecClosure`の直後である。このため、そのパスが作った複製を消費する(その時点で、複製は通常の`MkRCFun`である)。`insertMemoize`/Phase 2の厳密に前でもあり、これらから見たときも、このパスが作った複製は通常の関数になっている。

## 推移的な特殊化

辞書は、受け取った関数が自分でスクルティニーとして調べるのではなく、別の関数に渡すだけのことが非常に多い(`f c x = g c x`で、`case`を行うのは`g`)。厳密な関門は、こうした例をすべて拒否していた。この拡張は、クロージャ側の「推移的な特殊化」(`speculative-closure-specialization.md`)にならっている。

- **転送箇所を3つ目の使い方として認める。** `forwardSites`は、パラメータがそのまま渡される飽和した`RAppName`の引数位置を列挙する(同じ位置への自己の素通しは除く)。ほかの使い方がすべて転送箇所であるパラメータは対象になる。転送が1つ以上あれば、スクルティニーが0個でもよい。値を保存する使い方や、エスケープする使い方が1つでもあれば、対象外のままである。
- **キーごとに1回で終わらせず、ワークリストで処理する。** 構築した各複製の`needs`(`constNeeds`)は、*畳み込み後の*本体から読み取る。対象は、同じ定数をパラメータ位置に明示している呼び出しすべてで、キーにすると`(callee', pos', same constant)`である。`buildConstAll`がこれらをキューに入れ、`seen`集合が、失敗も含めてすべての試行を記憶する。そのため各キーは1回だけ構築され、ループは終了する。キーは`(callee, argPos, constant)`のままである。
- **受理(`acceptConst`)。** 閉じた部分集合のうち最大のものを採る。複製を残すのは、次のどちらかの場合である。
  - 単独で採算が合う(`own`: `RApp`ノードが減る)。転送先の呼び出しは、汎用の呼び出し先を呼ぶままになるが、それで正しい。
  - 純粋な転送関数で、その`needs`がすべて受理されている。

  転送関数は、まず、採算の合う複製に到達するものだけに絞り込む(最小不動点)。何の仕事もしない転送関数の循環が、自分自身を正当化できないようにするためである。そのうえで、`needs`が受理されていないものを落とす。クロージャ側の`acceptClosed`と同じ手順である。
- **転送された呼び出しのために新しい書き換えは要らない。** シード付きの畳み込みが、転送する呼び出しにも定数を代入する。プログラム全体を対象とする`redirectConstCallSites`の走査は、元の関数だけでなく複製にも及ぶので、これが次の複製への呼び出しに変える。自己の素通しと同じ仕組みである。

`rc2/tests/Test128SpecConstConFwd/`は、次の3つを扱う。2段の転送チェーン(`chain2 -> chain1 -> classify`)、再帰する純粋な転送関数(`countAll -> countOne`)、辞書を保存するので汎用のままにしなければならない関数(`stash`)である。その`check.sh`は、転送関数の複製が存在し、boxedなディスパッチも汎用チェーンへの呼び出しも含まないことを検査する。

## 一度取り消された`where`節の罠

このパスは、2026-09-24に設計、実装、計測された後、**不採用**とされた。`TODO.md`には、`idris2-lsp`の全体のビルドに103秒もかかるのに、削れるディスパッチは193個だけ、と記録された。同じ日に再計測したところ、この不採用は誤りだった。コストの原因はこのパスではなかった。

`goKeys`は、各キーの呼び出し先を`defOf : SortedMap Name RCDef`で引いていた。これは`where`節で書かれていた。

```idris
  where
    defOf : SortedMap Name RCDef
    defOf = SortedMap.fromList defs        -- looks like a constant
```

`where`の定義は、それが参照する外側のパターン変数を引数に取る関数にラムダリフトされる。つまりこれは実際には`defOf defs`であり、**使われるたびに毎回再評価される**。`goKeys`はキーごとに1回使うので、約1,600個のキーは、38k要素のマップを約1,600回作り直すことを意味した。これを関数本体で一度だけ束縛し、パラメータとして`goKeys`に渡すようにした(`applySpecClosure`自身の`goKeys`は、すでにそうしていた)。

| | 修正前 | 修正後 |
|---|---|---|
| `goKeys` | 102.9s | **0.010s** |
| `idris2-lsp`全体のビルド | 131s | 27.7s |

原因の特定は、アブレーションで行った。各フェーズを使い捨てのディレクティブの裏に置き、ビルド全体の時間の差を連続して引いていく方法である。これを記録しておく価値があるのは、真犯人にたどり着く前に、もっともらしい2つの容疑者が*無実*と計測されたからである。そのうち1つは、最初の調査で名指しされていたものだった。

| フェーズ | コスト |
|---|---|
| `(Name, Nat, RCLocal)`のキー集合の構築(深い定数の木を`SortedMap`のキーにする) | 0.044s |
| CAFテーブルの再構築 | 0.001s |
| `goKeys` | **102.9s** |
| すべての呼び出し箇所の書き換え(エントリごとに深い`RCLocal`の`==`) | 0.085s |

決め手は、ノード数を数えたことだった。1,598個のキーすべての本体は**合計で23,911ノード**に収まったのに、それをたどるのに104秒かかっていた。1ノードあたり4.3msでは、たどる処理そのものが原因でないことは明らかで、残るのはそのすぐ隣にある`lookup`だけだった。

**パスに`where`で束縛したコレクションを追加するときは、それが何回参照されるかを確認すること。** 1回だけ参照して、パラメータとして先へ渡すなら安全である。何かの要素ごとに1回ずつ参照するのは安全でない。

## 拡張前の効果が約1.8%にとどまった理由

歴史的な記録であり、上の推移的な拡張より前の計測である。理由は2つあり、どちらもバグではなく、厳密な関門に固有のものである。`idris2-lsp`では、1,598個の異なるキーのうち次のとおりになる。

- **903個(57%)が、スクルティニーのみの関門を通らない。** 辞書は、スクルティニーとして調べられ、自分自身の再帰に引き回されるだけでなく、*別の*呼び出し先にも渡されている。これを解決するには、手続き間の特殊化(呼び出しの連鎖に沿って定数を伝播させる)が必要になる。それは別の、はるかに大きな機能である。
- **さらに117個が採否の判定を通らない。** 最初の関門を通るのが695個で、残される複製が578個である。捨てられたものは、`case`は畳み込んだが、畳み込みが届かない場所にディスパッチを残していた。

このパスが残す578個の複製のうち、最終的なIRまで残るのは73個である。残りの505個が無駄になったわけではない。呼び出し元がちょうど1つの複製は、`LateInline`が差し込んで消すものであり、置き換えた呼び出しより良い結果になる。

`--directive timing`の出力には、この内訳が表示される(`N distinct keys`、続いて`N keys past the scrutinee-only gate, M clones kept`)。そのため、コンパイラを再ビルドしなくても、任意のプログラムで再現できる。

## 反復

このパスは、`applySpecRounds`の各ラウンドで、クロージャ側のあとに走る。新しい複製が1つも残らないラウンドが出るまで繰り返す。残された複製の本体から、新しい定数引数が見えるようになることがあり、クロージャの複製から、新しい辞書が見えるようになることもあるからである。仕組みと、`idris2-lsp`での収束の表(ラウンドごとに残るコンストラクタ複製の数: 1429、163、13、1、0)と、ラウンド数の上限を8にした理由は、`speculative-closure-specialization.md`の「Iteration」にある。

## 未解決の課題

- **特殊化するパラメータが複数ある場合**(2つの辞書を取る関数)。計測したところ、`idris2-lsp`には、既知の辞書を2つ以上渡す呼び出し箇所が153個ある。しかし、最終的な本体に対する共同の複製は、そのどれについても成功しなかった。実装する価値はない(詳細は`speculative-closure-specialization.md`の末尾にある)。
- **保存される辞書や、エスケープする辞書。** `idris2-lsp`では、保存だけのキーが320個、そのほかのエスケープが79個、転送と保存が混在するキーが122個あり、汎用のままである。これを解決するには、関門を緩めるのではなく、別の解析が必要になる。

## ラムダリフトの前で試みたが、採用しなかった(2026-09-29)

リフトの前の、名前付きのcase木に対する版を作り、idris2-lspで計測した。やり方は次のとおりである。定数の辞書(閉じたフィールドを持つコンストラクタを値とするCAF)ごとに呼び出し先を複製し、その辞書に対する`case`を畳み込み、メソッドのラムダの呼び出しをそれぞれベータ簡約する。複製は75個残ったが、プログラムは悪くなった。定義が1,031個、構築されるクロージャが43個、`apply`が41個増え、構造体の返り値が594個減った。このパスの代わりにではなく、このパスの前に走らせた場合は、`apply`が3個減る代わりに、定義が232個増えた。

case木には、`RCConstCon`/`RCConstClosure`にあたるものがない。そこでは、辞書を1つの共有された静的な値にすることができない。メソッドのラムダの複製は、1つずつ別々にリフトされ、すぐに適用されない場合はクロージャとして構築される。さらに、別の辞書を経由して到達する辞書(スーパークラスのフィールド)は、`ConstFold`が走るまで定数にならない。このパスがRCExp上の、`ConstFold`の後ろにとどまっているのは、このためである。
