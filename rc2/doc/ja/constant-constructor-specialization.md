# 定数コンストラクタ引数の特殊化

(原文: `doc/constant-constructor-specialization.md`。内容が乖離した場合は原文を正とする。)

コンパイル時定数の*コンストラクタ*(実際にはinterface辞書)を引数に取る呼び出し先を、その引数について特殊化する。これにより、呼び出し先の中にあるboxedなメソッドディスパッチが、直接呼び出しに変わる。

実装は`rc2/src/Compiler/RC2/SpecClosure.idr`の後半(`applySpecConstCon`)にあり、構造を扱うヘルパとパイプライン上の位置を、クロージャ引数を扱う兄弟のパスと共有する。`--directive nospecconstcon`で無効にできる。クロージャ側については`speculative-closure-specialization.md`を参照。3段階の構成と採否の判定の方針は、意図的にそちらにそろえてある。

## 埋めるべき隙間

`SpecClosure`は、*クロージャ*引数、つまり**適用される**パラメータについて呼び出し先を特殊化する。interface辞書のケースは扱えない。辞書の場合、引数は**分解される**レコードだからである。

```
def Prelude.Types.elemBy  (fun args= ["v10077", "v10078", "v10079"] ret= Boxed)
  case v10077 of                                       -- (1) destructure
    Prelude.Interfaces.MkFoldable [record] args= [_, _, _, _, _, v10085] ->
      let v10087 = apply v10078 [v10079]
      apply v10085 [..., v10087]                       -- (2) boxed dispatch
```

`v10077`は`case`のスクラティニーとしてしか使われていない。そして呼び出し元は、`Compiler.RC2.ConstFold`がすでに1つの`RCConstCon`に畳み込んだ辞書を渡している。その`RCConstCon`のフィールドは`RCConstClosure`である。したがって、ディスパッチを解決するのに必要なものはすべてコンパイル時に分かっている。ただ、それが呼び出し先自身の本体には届いていないだけである。

## 下流に新しい処理が要らない理由

定数を本体に届けることが、書き換えのすべてである。残りは、既存の連鎖が自力で仕上げる。

1. `ConstFold`の`RConCase`のスクラティニー解決が、既知の`RCConstCon`に対して`case`を畳み込み、各altのフィールドを、対応する定数に束縛する(`insertConArgs`)。
2. 各メソッドのフィールドは`RCConstClosure`になっている。そのため`ConstFold`の`RApp`の場合が、`apply`を直接の`RAppName`呼び出し(引数が足りなければ`RUnderApp`)に書き換える。`const-closure-fold.md`を参照。
3. `Inline`/`LateInline`/`DualABI`は、名前が付いた呼び出しを見通せるようになる。`RApp`のままでは見通せなかったものである。

クロージャ側と違って、ここに`rewriteApply`に相当するものがないのは、このためである。置換と既存の畳み込みで、変換のすべてが済む。

## 3つのステップ

1. **候補の検出。** `call g [..., c, ...]`という呼び出し箇所のうち、`c`が`RCConstCon`であり、`g`のその位置のパラメータが、少なくとも1回スクラティニーとして調べられ、かつ`RConCase`のスクラティニーか、`g`自身の再帰呼び出しの同じ引数位置への、自分自身の素通し以外には*どこにも*使われていないものを探す。見つかったら、三つ組`(g, argPos, c)`を記録する。この関門が`paramIsScrutineeOnly`である。クロージャ側の`paramUses`をモデルにしており、`apply`を「`RConCase`のスクラティニー」に置き換え、`selfPassthroughOccurrences`はそのまま共有している。

   この時点で`ConstFold`はプログラム全体で不動点まで走り終えている。そのため、定数の引数は呼び出し箇所にそのまま書かれており、`RLet`の向こうに隠れていることはない。クロージャ側と違って、引き回すべき`Bound`環境はない。

   **自己の素通しを許すために、専用の仕組みは要らない。** この点は明記しておく価値がある。再帰する`go`がステップごとに辞書を引き回すのは、現実のinterface辞書がほとんど必ず取る形であり、これを拒否すると、機会の大半を捨てることになっていた。許可しても問題なく動く。シード付きの畳み込みは、再帰呼び出しにも定数を代入する。その結果、定数を明示した*汎用の*呼び出し先を呼ぶ形になる。ステップ3のプログラム全体のリダイレクトの走査は、元の関数だけでなく複製にも及ぶ。そのため、この呼び出しはまさにこのキーのリダイレクトのエントリに一致し、引数を落とした、複製自身への呼び出しになる。再帰は、追加の作業なしに、底まで特殊化される。

2. **投機的な複製と再畳み込み。** 異なる三つ組ごとに1回だけ行う(メモ化する)。`g`を複製し、シグネチャから該当のパラメータを落として、そのidを畳み込み自身の`Env`にシードする。そのために追加したのが`ConstFold.foldConstDefWith`である。

3. **採否の判定。** 複製が持つ`RApp`ノードの数が、元の関数より厳密に少ないときだけ、複製を残す。代入の後では、特殊化したパラメータは完全に消えている。したがって、これは構造に関する正直な問いである。このパスが取り除くために作られたディスパッチは、実際に取り除かれたか。取り除かれていなければ複製を捨て、すべての呼び出し箇所は汎用の`g`を呼び続ける。

パイプライン上の位置は、`applySpecClosure`の直後である。このため、そのパスが作った複製を消費する(その時点で、複製は通常の`MkRCFun`である)。`insertMemoize`/Phase 2の厳密に前でもあり、これらから見たときも、このパスが作った複製は通常の関数になっている。

## 一度取り消された`where`節の罠

このパスは、2026-09-24に設計、実装、計測された後、**不採用**とされた。`TODO.md`には、`idris2-lsp`の全体のビルドに103秒もかかるのに、削れるディスパッチは193個だけ、と記録された。同じ日に再計測したところ、この不採用は誤りだった。コストの原因はこのパスではなかった。

`goKeys`は、各キーの呼び出し先を`defOf : SortedMap Name RCDef`で引いていた。これは`where`節で書かれていた。

```idris
  where
    defOf : SortedMap Name RCDef
    defOf = SortedMap.fromList defs        -- looks like a constant
```

`where`の定義は、それが参照する外側のパターン変数を引数に取る関数にラムダリフトされる。つまりこれは実際には`defOf defs`であり、**使われるたびに毎回再評価される**。`goKeys`はキーごとに1回使うので、約1,600個のキーは、38k要素のマップを約1,600回作り直すことを意味した。これを関数本体で一度だけ束縛し、パラメータとして`goKeys`に渡すようにした(`applySpecClosure`自身の`goKeys`は、すでにそうしていた)。

| | 修正前 | 修正後 |
|---|---|---|
| `goKeys` | 102.9s | **0.010s** |
| `idris2-lsp`全体のビルド | 131s | 27.7s |

原因の特定は、アブレーションで行った。各フェーズを使い捨てのディレクティブの裏に置き、ビルド全体の時間の差を連続して引いていく方法である。これを記録しておく価値があるのは、真犯人にたどり着く前に、もっともらしい2つの容疑者が*無実*と計測され、そのうち1つは最初の調査で名指しされていたものだったからである。

| フェーズ | コスト |
|---|---|
| `(Name, Nat, RCLocal)`のキー集合の構築(深い定数の木を`SortedMap`のキーにする) | 0.044s |
| CAFテーブルの再構築 | 0.001s |
| `goKeys` | **102.9s** |
| すべての呼び出し箇所の書き換え(エントリごとに深い`RCLocal`の`==`) | 0.085s |

決め手は、ノード数を数えたことだった。1,598個のキーすべての本体は**合計で23,911ノード**に収まったのに、それをたどるのに104秒かかっていた。1ノードあたり4.3msでは、たどる処理そのものが原因でないことは明らかで、残るのはそのすぐ隣にある`lookup`だけだった。

**パスに`where`で束縛したコレクションを追加するときは、それが何回参照されるかを確認すること。** 1回だけ参照して、パラメータとして先へ渡すなら安全である。何かの要素ごとに1回ずつ参照するのは安全でない。

## 計測

`idris2-lsp`のビルド全体を、`--directive nospecconstcon`を付けた同じビルドと比べた。

| | off | on |
|---|---|---|
| `apply`ノード | 11,384 | **11,182** (-202) |
| `DeadCode`後の定義 | 26,387 | **25,978** (-409) |
| コンストラクタの再利用の成功(`reuse=`) | 21,829 | **22,195** (+366) |
| ネイティブの`RLet` | 3,349 | 3,422 (+73) |
| IRの行数 | 732,238 | 735,646 (+0.5%) |
| `dup` / `drop` | 93,645 / 77,223 | 94,165 / 77,813 (+0.6%) |
| コンパイル時間(3回の中央値) | 27.49s | 28.59s (+4.0%) |

複製を作っているにもかかわらず、定義の数は*減る*。`DeadCode`が、呼び出し元がなくなった元の関数を、採用された複製より多く刈り取るからである。

実行時の性能は、5回の中央値である。各ベンチマークを、`--directive nospecconstcon`を付けた自分自身とA/B比較した。

| | off | on | |
|---|---|---|---|
| `rc2/tests/BenchSpecConstCon.idr` | 0.48s | **0.37s** | 約23%高速 |
| `rc2/tests/BenchSpecConstConRec.idr` | 0.49s | **0.40s** | 約18%高速 |

それぞれの生成Cにある`idris2rc2_applyClosure`の呼び出し箇所は、4個から0個になる。2つのベンチマークは、関門の2つの側面を覆っている。1つ目は再帰しない呼び出し先に届く場合で、2つ目は辞書を自分自身の再帰に通して引き回す場合である。

**プログラム全体のIRの数は、この効果を過小に見せる。** 自己の素通しを許したことの静的な効果は、`idris2-lsp`では`apply`ノードが9個減るだけである。しかし、辞書を引き回す再帰はループである。除去されるディスパッチのコストは、ノードごとに1回ではなく、反復ごとに1回かかっていた。`BenchSpecConstConRec`は、この形を正直に測る指標であり、この形は普通のIdrisのコードで一般的なものである。

## プログラム全体での効果が約1.8%にとどまる理由

理由は2つあり、どちらもバグではなく、関門に固有のものである。`idris2-lsp`では、1,598個の異なるキーのうち次のとおりになる。

- **903個(57%)が、スクラティニーのみの関門を通らない。** 辞書は、スクラティニーとして調べられ、自分自身の再帰に引き回されるだけでなく、*別の*呼び出し先にも渡されている。これを解決するには、手続き間の特殊化(呼び出しの連鎖に沿って定数を伝播させる)が必要になる。それは別の、はるかに大きな機能である。
- **さらに117個が採否の判定を通らない。** 最初の関門を通るのが695個で、残される複製が578個である。捨てられたものは、`case`は畳み込んだが、畳み込みが届かない場所にディスパッチを残していた。

このパスが残す578個の複製のうち、最終的なIRまで残るのは73個である。残りの505個が無駄になったわけではない。呼び出し元がちょうど1つの複製は、`LateInline`が差し込んで消すものであり、置き換えた呼び出しより良い結果になる。

`--directive timing`の出力には、この内訳が表示される(`N distinct keys`、続いて`N keys past the scrutinee-only gate, M clones kept`)。そのため、コンパイラを再ビルドしなくても、任意のプログラムで再現できる。

## 未解決の課題

- **特殊化するパラメータが複数ある場合**(2つの辞書を取る関数)。クロージャ側にもある同じ未解決の問題で、同じく対象外としている。パラメータ位置は一度に1つだけ扱う。
- **不動点まで繰り返さない。** これもクロージャ側と同じである。残した複製が、さらに別の機会を生むことがある。
- **手続き間の伝播。** 上記の903個のキーは、辞書が別の呼び出し先に渡されるものである。残りの効果はすべてここにある。これはこの関門を緩めれば得られるものではなく、別の解析である。

## ラムダリフトの前で試みたが、採用しなかった(2026-09-29)

リフトの前の、名前付きのcase木に対する版を作り、idris2-lspで計測した。定数の辞書(閉じたフィールドを持つコンストラクタを値とするCAF)ごとに呼び出し先を複製し、その辞書に対する`case`を畳み込み、メソッドのラムダの呼び出しをそれぞれベータ簡約する。複製は75個残ったが、プログラムは悪くなった。定義が1,031個、構築されるクロージャが43個、`apply`が41個増え、構造体の返り値が594個減った。このパスの代わりにではなく、このパスの前に走らせた場合は、`apply`が3個減る代わりに、定義が232個増えた。

case木には、`RCConstCon`/`RCConstClosure`にあたるものがない。そこでは、辞書を1つの共有された静的な値にすることができない。メソッドのラムダの複製は、1つずつ別々にリフトされ、すぐに適用されない場合はクロージャとして構築される。さらに、別の辞書を経由して到達する辞書(スーパークラスのフィールド)は、`ConstFold`が走るまで定数にならない。このパスがRCExp上の、`ConstFold`の後ろにとどまっているのは、このためである。
