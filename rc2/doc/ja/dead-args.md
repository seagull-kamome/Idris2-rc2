# デッド引数の除去 (`Compiler.RC2.DeadArgs`)

(原文: `doc/dead-args.md`。内容が乖離した場合は原文を正とする。)

## 問題

Idris2のエラボレータは、`where`関数をトップレベルに持ち上げるとき、外側の節にある変数をすべて追加引数として渡す。使われているかどうかは問わない。`Data.List.sortBy`では、ラムダリフティングより前の`--dumpcases`の時点で、すでにその結果が見える。

```
Data.List.sortBy   ... (split [!{arg:2}, !{arg:1}, !{arg:2}]) ...     -- xs, cmp, xs
Data.List.split    = [{arg:1}, {arg:2}, {arg:3}]:
                       splitRec [!{arg:1}, !{arg:2}, !{arg:3}, !{arg:3}, id]
Data.List.splitRec = [{arg:1}, {arg:2}, {arg:4}, {arg:5}, {arg:6}]:
                       ... splitRec [!{arg:1}, !{arg:2}, ...] ...
```

`splitRec`は`{arg:1}`(外側の`xs`)も`{arg:2}`(`cmp`)も読まない。自分自身への再帰呼び出しに渡すだけである。

この余計な引数のコストは、レジスタ1本分では済まない。RCは再帰呼び出しの中に使用を見つけるので、外側の`xs`は関数の入口でdropされない。Loop変換の後では、この引数はループが終わるまで保持されるループ不変量になる。リストの先頭を握り続けると、後続のセルがすべて共有されているように見える。その結果、`splitRec`が組み立て直す半分のリストはセルを再利用できない。セルは1個ずつ新規に確保され、古いリストは最後にまとめて解体される。

要素数100万の`sort`では、これが単独で最大のコストだった。
- 所要時間は3.21sではなく4.18s。
- 確保回数は2.36倍(100kでは600,197回のところ1,415,221回)。

同じコードのコピーにこの種の引数を1つ加えるだけで、両方の数値がそのまま再現した(`TODO.md`、「`sort` against Chez」)。

フロントエンド側のこの挙動自体は`KNOWN-BUGS.md`に記録している。

## 書き換え

*スロット*とは、関数とそのパラメータ位置の組である。スロットがデッドであるとは、次の2つがともに成り立つことをいう。
- そのパラメータのすべての使用が、呼び出し先の引数の個数ちょうどで呼ばれた呼び出し(`NmApp (NmRef g) args`)の引数になっている。ラムダの内側の使用も同様に扱う。
- それらの引数位置自体がデッドスロットである。

これは最大不動点であり、相互の転送も扱える。`split`は`{arg:1}`を`splitRec`のデッドスロット 0 に渡し、`hop`と`skip`は互いに1つずつ渡し合う。

デッドなパラメータは、すべて関数から取り除く。同時に、対応する引数もすべての呼び出しから取り除く。捨てる引数が計算を伴う場合は、その呼び出しで計算を伴う引数をすべて、先に`let`で順番どおりに束縛する。これで各引数は、元の位置で一度ずつ評価される。捨てた引数のためだけにあった`let`は、普通のデッド束縛になる。

## シグネチャが保たれる場合

単純な呼び出し以外の参照があり、パラメータを変えるとそれが壊れる場合、関数はパラメータをそのまま保つ。
- **そのような呼び出し以外で参照されている。** 裸の`NmRef`、またはその`Force`がこれにあたる(部分適用は、case tree上では飽和した呼び出しを包むラムダになるので問題ない)。
- **引数の個数が異なる呼び出し**がある。
- **ルート**(エントリポイント、エクスポート)である。
- **インクリメンタルコンパイル**(`doc/incremental-compile.md`)。他のモジュールからの呼び出しが見えないので、パス全体を無効にする。

## パイプライン上の位置

このパスは、名前付きのcase treeに対して、インライン化の直後、ラムダリフティングの前に走る(`Compiler.RC2.DeadArgs`、2026-09-29。それ以前はRCExp上で、「RC normalize」の直後に走っていた)。以降のパスは、ラムダリフティングも含めて、すべて細くなったシグネチャを見る。デッドな値を転送するだけだったラムダは、その値をもうキャプチャしない。

case tree上のほうが多く見つかるのも、同じ理由による。RCExp上では、そのようなラムダは値を保持する持ち上げ済みの定義であり、部分適用から参照されていた。そのためシグネチャが保たれ、値は使用されているとみなされた。

idris2-lspでは、このパスはトップレベル関数のパラメータ19,219個のうち4,718個を除去する。RCExp上では66,385個(持ち上げ済みのラムダを含む)のうち1,875個だった。`rcexpr-lint`は異常を検出せず、`dup`の加算が2,964回、`drop`の減算が16,378回、クロージャが28個減る。パスの所要時間は0.65sから0.87sに増える。

## 結果 (2026-09-26)

- `Data.List.sort`、`Int` 100万個: 4.18sから3.21sに短縮。確保回数も、100kで600,197回に戻った。
- `Test99DeadArgs`は次のケースを扱う。
  - `where`ヘルパー
  - 相互の転送
  - デッド引数を持ちつつ部分適用もされるため、シグネチャが保たれる関数
  - `sort`

  出力はChezと一致し、valgrindでも問題は出ない。
- idris2-lsp: パラメータ66,385個のうち1,875個を除去した。`rcexpr-lint`は異常を検出しない。パスの所要時間は0.82s。
  - 初版は2.07sかかった。全定義にわたる`concatMap`が`++`の左畳み込みになっており、プログラムの規模に対して2乗の計算量だったためである。`foldr (++) []`に変えて解消した。
  - デッドスロットの不動点は、逆向きの転送辺に対するワークリストで計算する。各辺は1回しか訪問しない。
