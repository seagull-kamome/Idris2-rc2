# 転送関数の別名化 (`Compiler.RC2.FwdAlias`)

(原文: `doc/fwd-alias.md`。内容が乖離した場合は原文を正とする。)

`--directive nofwdalias`で無効にできる。

## 問題

本体が、自身のパラメータを順番どおりに渡して別の関数を呼ぶだけの関数

```
f a b c = g a b c
```

には、それ自身の用途がない。アリティの引き上げと特殊化は、このような関数を多く残す。`ArityRaise`が分割した関数のクローンは、その名前のまま、引き上げた版を1行で呼ぶ関数になる。あるいは、引き上げた版のほうが別の関数へ転送するものになる。`f`への呼び出しはインライン化されるかリダイレクトされたが、呼び出し以外の種類の参照が1つ、`f`を生かし続けた。クロージャの対象(`partial f missing [..]`、`delay`、定数クロージャ)である。`Compiler.RC2.DeadCode`は名前を指されているものを残し、クロージャはその関数を名指しする。そのため、この別名はCに残った。呼び出しを返すだけの呼び出しである。

`rc2-norepl`のIRでは、このような関数(boxedで、順番も同じ)が871個あった。これに対して、パラメータを別の順番で渡すものは61個、パラメータのないものは70個だった。

## パス

`applyFwdAlias`は、再利用の再チェックの後、デッドコード除去の前に走る。

- `forwarders`: boxedでワーカーでない関数`f`のうち、パラメータを持ち、本体が、同じ個数のパラメータを持つboxedでワーカーでない関数`g`の`RAppName`1つだけで、`f`のパラメータをちょうど順番どおりに渡し、lazyでないもの。`g`は同じプログラムの関数でなければならない。そのため、インクリメンタルモードでは、別のモジュールへの呼び出しはそのまま残す。
- `resolve`は`f -> g -> h`を終点までたどる。循環はそのまま残す。
- 転送関数への参照は、すべて`FunDedup`の`renameNamesD`でその転送先に名前を付け替える。対象は呼び出し、`partial`、`delay`、定数クロージャである。定数コンストラクタの中にあるクロージャ定数には届かない(そのerasedな証明を作り直せない)ので、そこで名指しされた転送関数は残る。
- 転送関数はここでは取り除かない。どこからも名指しされなくなれば、デッドコード除去が取り除く。ルートは残る。

この名前の付け替えが正しいのは、`f`と`g`が同じパラメータを同じ順番で取るからである。呼び出しも、パラメータのプレフィックスをキャプチャして残りを欠いたクロージャも、どちらの名前を使っても意味は同じである。

## 別の順番のパラメータ

`f a b c = g b a c`: boxedでワーカーでない`f`のうち、本体が、同じアリティのboxedな関数`g`の`RAppName`1つだけで、`f`のすべてのパラメータを1回ずつ、別の順番で渡すもの(`permuters`)。`permRewrite`は、上記の名前の付け替えより前に走る。

- 呼び出し`f xs`は、引数を`g`の順番に並べた`g`の呼び出しになる。
- クロージャ`partial f m caps`は、キャプチャしたパラメータが`g`でも先頭のもの(並べ替えはそれらの間だけ)であり、欠けている`m`個のパラメータが順番どおりに最後に残る場合に、`partial g m caps'`になる。こうすれば、後の`apply`が与える引数は、`f`がそれを置いたはずの位置に収まる。それ以外のクロージャは`f`のまま残す。

`delay`と定数クロージャは変更しない(定数クロージャは何もキャプチャしないので、並べ替えれば必ず欠けたパラメータが動いてしまう)。

## 定数を加えるもの

`MutualLoop`がまとめたグループの各メンバーに残すラッパは、次の形をしている。

```
ping a b = {rc2_mutualLoop:0} #0 a b          -- the selector, then the parameters of the member
eval a b c = {rc2_mutualLoop:155} #1 a b c [__] [__]   -- and the padding of the parameters it lacks
```

これはすべてのパラメータを1回ずつ渡すが、ほかに定数も渡すので、順番どおりの転送関数でも並べ替えでもない。`constForwarders`は、boxedでワーカーでない`f`のうち、本体がboxedな`g`の`RAppName`1つだけで、`f`のすべてのパラメータが1回ずつ渡され、ほかの引数が定数である(少なくとも1つある)ものを取る。`repForwarders`は、任意の種類の関数について同じものを取る。条件は、本体が`postDrop`のない`RAppNameRep`1つだけで、結果がその関数自身の表現であり、すべてのパラメータがそれ自身の表現で渡されることである(ワーカーのラッパ、およびラッパのワーカー)。`constRewrite`は、そのような関数の各呼び出しを転送先の呼び出しにする。引数は、定数も含めて、ラッパが並べたとおりに並べる。転送関数の転送関数もたどれるように、これを数ラウンド繰り返す。クロージャは関数を変えない。後の`apply`が与える引数が、転送先が受け取る位置に収まらないからである。ラッパは、ほかに名指しするものがなくなれば、デッドコード除去が取り除く。

このパスは`LeafTail`より前に走る。そのため、ラッパの末尾呼び出しはまだ`RAppName`のままであり、末尾位置にあるその呼び出しは、転送先の末尾呼び出しのまま残る(クロージャ経由か直接かは、`LeafTail`が決める)。

`Test175FwdAliasConst`: まとめられた`ping`/`pong`のラッパの呼び出しが、まとめた関数の呼び出しになる。出力は`--directive nofwdalias`のときと同じである。

## 未対応のこと

- 途中のパラメータを欠くクロージャ: `f`が残る。
- 別の順番の転送関数に対する、定数上のクロージャ(`RCConstPartial`): `f`のまま残る(付け替えるのは関数と欠けている部分だけなので、順番どおりの転送関数には届く)。
- 並べ替える関数への転送関数は、1段階しかたどらない。すでに`RAppNameRep`になっている呼び出しは、定数を加える転送関数(前述)についてだけ書き換える。
- パラメータを捨てる、または繰り返す転送関数。(定数を渡すものについては前述を参照。)
- `worker`への転送関数: クロージャはboxedな引数を取らなければならないので、それをアンボックス化するスタブが必要である。
- 定数コンストラクタの中の参照(前述)。

## テスト

`Test158FwdAlias`: 別の関数へ転送する関数を、その関数と一緒にクロージャとしてリストに保持する。IR上の転送関数は`--directive nofwdalias`のときより少なく、出力は同じである。

`Test160FwdAliasPermuted`: `mkSwapped`が作る2つのクロージャは、そのラムダがキャプチャしたパラメータを入れ替えて`joined`を呼ぶものであり、`partial Main.joined`になる。`mkRotated`が作るクロージャは途中のパラメータを欠くので、自身のクロージャのまま残る。

## 測定

`TestAsyncHTTPServer`では、定義が902個から889個に、転送関数が16個から3個に減る(残る3個は定数コンストラクタの中で名指しされている)。

`rc2-norepl`では、別の順番の転送関数を名指ししていた214個のクロージャのうち137個が、その転送先を名指しするようになった(残る77個は、並べ替えでない転送関数64個と、途中のパラメータを欠くもの13個である)。定義は13175個から13136個に減る。

`rc2-norepl`(callgrind上での`libs/prelude`のビルド、2026-11-14)では、定数への拡張により、ラッパの呼び出しが約640万回減る(`scan`のワーカーが4.4 M、`eval`が0.8 M、`getFirstMatch`のワーカーが0.7 M、...)。命令数は29.222 Gから29.217 G(-0.02%)、実行ファイルは15,574,448バイトから15,553,016バイト(-0.14%)になる。呼び出し1回あたり約1命令である。Cコンパイラはラッパの`return merged(sel, ...)`をすでにジャンプに変えているので、省いた呼び出しはほとんどコストがなかった。これは整理であって、高速化ではない。
