# コンストラクタを挟んだ末尾再帰 (TRMC)

(原文: `doc/trmc.md`。内容が乖離した場合は原文を正とする。)

状態: フェーズ1から3まで実装済み(2026-09-26と2026-09-27、
`Compiler.RC2.Trmc`)。フェーズ4は測定のうえ見送ったか、別の仕組みで実装済みである(「計画」を
参照)。残る課題は`TODO.md`の「tail recursion modulo constructor」で
管理している。動機は`KNOWN-BUGS.md`の「deep non-tail recursion
overflows the C stack」にある。

## 問題

```idris
mergeBy order (x::xs) (y::ys) = case order x y of
    LT => x :: mergeBy order xs (y::ys)
    _  => y :: mergeBy order (x::xs) ys
```

再帰呼び出しが`::`の下にあるため、これは末尾呼び出しではない。要素1個
ごとにCスタックのフレームを1つ消費する。rc2はCスタック(8 MB)の上で
動くので、`mergeBy`は10万要素でクラッシュする。`[1 .. n]`(`takeUntil`)
も同様で、`sort`は100万要素でクラッシュする。Chezはスタックを伸長する
ため、これらはすべて完走する。

idris2-lspの最終RCExpで測定した結果は次のとおりである(全体の表は
`TODO.md`にある)。
- 再帰フィールドを1つ持つ末尾の`::`が283箇所ある。
- 他のコンストラクタにも365箇所あり、大半は項の走査である。
- 再帰フィールドを2つ以上持つものが151箇所ある。

## 方針: 宛先渡し

再帰呼び出しの前にセルを作っておき、再帰フィールドはホールとして
空けておく。再帰呼び出しは値を返す代わりに、そのホールを埋める。
こうすると再帰呼び出しが末尾呼び出しになり、既存のLoop変換がこれを
ループにする。

どのセルも新しく作られたもの(`RCon`)であり、関数が戻るまでは、組み
立て中のチェーン以外からは到達できない。したがってセルへの書き込みは
外から観測できない。この論拠はPerceus/KokaのTRMCと同じで、本プロ
ジェクト自身の`reuse=`とも同じである。

## 書き換えの形

適格な関数`f`に対して、このパスは2つの関数を出力する。

**`f#`**(`MN "rc2_trmc_<f>"`)は蓄積版である。パラメータは`f`の
パラメータに`res`と`last`の2つを加えたものになる。
- `res`はチェーンの最初のセルで、最後に返される。
- `last`はホールがまだ空いているセルである。

どちらも所有権を持つ通常の`Boxed`ローカルである。`f#`の本体は`f`の
本体の各末尾を次のように書き換えたものになる。

| `f`の末尾 | `f#`での末尾 |
|---|---|
| 再帰箇所: `let v = call f as'; C [.., v, ..]` | `let c = C [.., NULL, ..]; fill last.k := c; call f# as' res c` |
| 単なる自己末尾呼び出し `call f as'` | `call f# as' res last` |
| その他の末尾 `e` | `let r = e; fill last.k := r; drop last; res` |
| `crash` | そのまま |

`k`はホールのフィールド番号で、関数ごとに静的に決まる。

**`f`**は名前もシグネチャも変えないので、呼び出し側の変更は要らない。
本体は`f`の元の本体のまま、再帰箇所だけを次のように書き換える。

```
let c = C [.., NULL, ..]
call f# as' c c
```

`f`の基底ケースは従来どおりに返るため、一度も再帰しない呼び出しに追加
のコストはかからない。

Loop変換を通すと、`f#`は元のパラメータと`res`、`last`を持つループに
なる。1回の反復で行うのは、アロケーション1回(多くは死にかけの入力
セルの`reuse=`)、フィールドへのストア1回、`last`として次へ渡す
セルの参照カウント加算1回である。

### 複数のホール番号(フェーズ3)

項の走査における`Bind`と`App`のように、箇所ごとに埋めるフィールド番号
が異なる場合、`f#`は3つめの追加パラメータ`hk`(`last`のホールの番号)
を受け取る。各箇所は自分の番号を定数として渡す。`fill`は`hk`に対する
`case`になり、番号ごとに静的な`RFill`が1つずつ置かれる。

```
case hk of
  0 -> let _ = fill last . 0 = c; call f# as' res c #1
  _ -> let _ = fill last . 1 = c; call f# as' res c #1
```

`RFill`自体はフィールド番号を静的に持ち続けるので、`RFill`を知って
いるパスは何も変更しなくてよい。`fill`の後に続くコード(末尾呼び出し、
または`res`を返す処理)には`let`がないため、各分岐にそのコピーを
置く。番号が1種類しかない関数には`hk`を付けず、フェーズ1と同じ形に
なる。`hk`は常に小さな値なので、Loopはこれをネイティブのループ
パラメータのまま扱う。

### 複数の再帰フィールド(フェーズ3)

`Node (f l) x (f r)`のような箇所では、最後に評価される再帰呼び出し
だけをホールにする。それより前の呼び出しは`f`(エントリ。エントリは
さらに`f#`を使う)への通常の呼び出しのままにする。そのため、木に
対する`map`は右の背骨をたどるループになり、再帰の深さは木の左枝の
深さまでにとどまる。

### `last`が生のホールアドレスではなく所有参照である理由

生の`Value **`をホールのアドレスとして持つと、参照カウントされない
新しい`Rep`が必要になり、`Rep`を場合分けしているすべてのパスがそれに
対応しなければならない。`last`を通常の所有`Boxed`参照にしておけば、
RC(`annotate`)、Reuse、Loop、DualABI、DeadVarsは変更せずに済む。

最新のセルは2か所から保持される。1つは直前のセルのフィールド、もう
1つは`last`である。`c`は`fill`に消費されると同時に`last`として次へ
渡されるので、RCが`dup`を自分で挿入する。古い`last`は最後の使用、
つまり`fill`の`postDrop`で解放される。結果として、どのセルも最終的に
参照カウント1になる。

代償は、要素ごとに加算1回と減算1回である。ホールアドレス方式なら
これを省けるので、ベンチマークで問題になれば、後からフェーズ4として
導入できる。

## 新しいIRノード: `RFill`

```
RFill : FC -> (cell : RCLocal) -> (field : Nat) -> (value : RCLocal) -> (postDrop : List RCLocal) -> RCExp
```

`RFill`は`RStructSet`と同じくUnitに評価され、常に`let`で束縛される。
- `value`を`cell`のフィールド`field`に格納する。このとき古い内容は
  解放しない。古い内容は`NULL`のホールだからである。
- `value`を消費する。
- `cell`は借用するだけである。これが`cell`の最後の使用なら`postDrop`
  が`cell`を解放する。`RStructSet`の`postDrop`と同じ規約である。

Emitは`((IDRIS2RC2_Constructor *)cell)->args[field] = value;`に
落とす。

`RStructSet`を知っているパスには、すべて対応する`RFill`のケースを
足す。現時点で12ファイルある(`grep -c RStructSet`)。重要なケースは
次のとおり。

- **RC(`annotate`):** `cell`は`postDrop`付きの借用オペランド、
  `value`は消費オペランドである。
- **DeadVars/Sink:** `RFill`は副作用を持つ。死んだ`let`として除去
  してはならず、分岐の中へ沈めてもならず、別の`RFill`を越えて移動
  してもならない。
- **DualABI:** `value`と`cell`は常に`Boxed`なので、`RFill`がネイティブ
  読み出しになることはない。
- **Prettyと、rc2baseのAST/Parser/Lint:** `fill`の行を扱う。

ホール自体は、`RCon`の引数リストに`RCNull`として書く。このパス以降、
`let`束縛された`RCon`からフィールドを射影するパスは存在しないので、
これで安全である。
- `RCConstCon`を作るのはConstFoldだけで、ConstFoldはこのパスより前に
  動く。
- `PushConRC`が使うのはタグだけである。

## 適格条件

関数`f`は、次をすべて満たすときに書き換える。

1. `RCFun`であり、*再帰箇所*を少なくとも1つ持つ。再帰箇所とは、
   次を満たす末尾の`RCon C args`である。
   - `args`のうちちょうど1つが、(`let`の入れ子を何段か介して)正格かつ
     飽和した`RAppName f as'`に束縛されたローカルである。
   - そのローカルは他のどこでも使われていない。
2. (フェーズ1のみ。フェーズ3で解除された。)すべての再帰箇所が同じ
   コンストラクタのフィールド番号`k`を使う。`::`は常にフィールド1
   である。
3. 各箇所の`C`が実際のヒープコンストラクタである。アリティが1以上で、
   newtypeではなく、NULLで表現される引数なしコンストラクタでもない。
4. 再帰呼び出しから`RCon`までの間に評価される`let`が、副作用を
   持たない。副作用とは、`%World`オペランド、`RExtPrim`、foreign呼び
   出し、`RApp`を指す。書き換えではそれらの`let`を再帰呼び出しの前に
   評価することになるが、これは純粋な計算の順序を入れ替えるだけで
   ある。その中でクラッシュや発散が起きる場合、再帰より前に起きる
   ようになるが、結果は同じである。
5. `%foreign`でも、CAFでも、MutualLoopがすでに作ったループ本体でも
   ない。相互再帰はフェーズ2で扱う。

再帰フィールドが2つ以上ある箇所では、最後に評価される呼び出しを書き
換え対象とし、他の呼び出しは通常の呼び出しのままにする(フェーズ3)。
それらはその呼び出しより前に評価されるので、適格条件4が検査する
`let`には含まれない。

## パイプライン上の位置

TRMCは「Arity raise (after early inline)」の後、「CAF memoization」と
「RC annotate」の前に置く。

- **ConstFold、PushCon、SpecClosure、SpecConstCon、Early inlineの後**
  に置くのは、特殊化済みのクローンを見られるようにするためである。
  `Data.Vect.map`の33個のコピーがその例である。また、ホールを持つ
  セルが後のパスで静的な定数に畳み込まれることもなくなる。
- **RC annotateの前**に置くのは、`res`、`last`、新しいセルに対する
  dup/dropをすべてRCに配置させるためである。そうすれば、Reuseが
  死にかけの入力セルを新しい`RCon`に提供でき、`map`のような関数が
  in-placeで動く。
- **Loop変換の前**に置くのは、RCの後に動くLoop変換が
  `call f# ... res c`を`RLoopContinue`に変えるためである。

`notrmc`ディレクティブを指定すると、他の段階と同様にこのパスが無効に
なる。

## コストとリスク

- **コードサイズ:** 書き換えた関数は`f`と`f#`の2つになる。
  idris2-lspでは364関数が該当する。後続のパスが`f`を再び小さくできる。
  LateInlineが`f`を展開し、DeadCodeが使われない`f#`を落とす。
  idris2-lspのビルド時間とCコードのサイズは`--timing 3`で確認する。
- **要素あたりの処理:** Cの呼び出し、return、フレームの代わりに、
  ループ1反復、ストア1回、加算1回、減算1回になる。安全になるだけで
  なく速くなるはずだが、ベンチマークで確認する。
- **評価順序:** 適格条件4を参照。
- **`f#`の結果はstruct returnできない**(`res`がパラメータだから
  である)。これまで再帰の末尾がコンストラクタだった`f`は、struct
  returnを失う可能性がある。測定が必要だが、スタック安全性の利得の
  ほうが大きい。

## フェーズ2の設計: 相互再帰(2026-09-27)

### 形

測定には`--directive nomutualloop`でビルドしたidris2-lspを使った。
MutualLoopがまだ何もマージしていない状態である。末尾コンストラクタ
のうち、最後に評価されるフィールドが別の関数への呼び出しであるものを
取り出す。そのうち65箇所では、呼び出された側が末尾呼び出しとこの種
のフィールドだけをたどって呼び出し元に戻ってくる。ループにできる
のはこれらだけで、次の2種類がある。

- **関数と、その`case block`ヘルパー(`::`が19箇所、他に数箇所)。**
  `buildDoLets`、`collectDefs`、`mergeStrLit`、`compressLefts`、
  `words`、`getOpts`などである。ヘルパーが`x :: f xs`を組み立て、
  `f`がヘルパーを末尾呼び出しする。再帰の深さはリストの長さと同じ
  なので、現状ではスタックがあふれる可能性がある。
- **項の走査と、特殊化された`Maybe`の`map`(38箇所)。** たとえば
  `substEnv`の`CConCase`は`map (substEnv ..) mDef`で終わり、その
  `map`のクローンが`Just (substEnv .. x)`を組み立てる。再帰の深さは
  項の深さまでだが、書き換えの扱いは同じである。

残りの相互再帰90箇所はループにできない。最後に評価される呼び出しが、
末尾呼び出しでない経路を通ってしか戻ってこないからである。たとえば
`substEnv`の`CApp`は、各headについて`substEnv`を呼ぶ`mapAppend`の
クローンで終わる。

### 書き換え

フェーズ1と3では、箇所の対象は「その関数」1つだけだった。フェーズ2
ではこれを関数の集合、すなわち*グループ*に広げる。

1. **辺。** 適格な関数(`RBoxed`を返し、パラメータを持つ`RCFun`)
   ごとに、次を集める。
   - 末尾呼び出し。
   - ホール候補の呼び出し先。ホール候補とは、末尾`RCon`のフィールドに
     束縛され、1回だけ使われ、後ろに順序を入れ替えられない`let`を
     持たない、最後に評価される呼び出しである。規則はフェーズ3と
     同じで、呼び出し先は任意の関数でよい。

   適格な関数どうしの辺だけを数える。
2. **グループ。** グループは、このグラフの強連結成分
   (`MutualLoop.tarjanSCCs`)のうち、箇所を1つ以上含むものである。
   メンバーが1つのグループは、まさにフェーズ1と3の場合になる。
3. **蓄積版。** すべてのメンバー`m`に`m#`を作る。パラメータは`m`自身
   のものに`res`と`last`を加えたもので、グループ内の箇所が複数の
   ホール番号を使うなら`hk`も加える。追加パラメータはすべての
   メンバーで共通にする。ヘルパーパターンの`f`のように、自分では箇所
   を持たないメンバーも同様である。チェーンはそのメンバーも通るから
   である。
4. **本体。** メンバーの`m#`の本体は、`m`の各末尾をフェーズ1と同様に
   書き換えたものである。ただし「`f`」はグループの任意のメンバーを
   指す。
   - メンバー`g`を呼ぶ箇所は、次の形になる。
     `let c = C [.., NULL, ..]; fill last := c; call g# as' res c k`
   - メンバー`g`への末尾呼び出しは、`call g# as' res last hk`になる。
   - その他の末尾は、`last`をそれで埋めて`res`を返す形になる。

   `fill`はグループ内のフィールド番号に対して`hk`で分岐する
   (フェーズ3)。
5. **エントリ。** 各`m`は名前とシグネチャを保つ。変わるのは箇所だけ
   で、`let c = C [..]; call g# as' c c k`になる。他のメンバーへの
   末尾呼び出しは、そのエントリへの呼び出しのまま残すので、呼び出し側
   の変更は要らない。

こうして、`m#`どうしは互いに、またグループ内の他のものを呼ばずに末尾
呼び出しし合う形になる。MutualLoopはRCの後に動き、通常の相互末尾
再帰と同様にこれらを1つの関数にマージする。Loopはそれを1つのループ
にする。これより下流は何も変わらない。`hk`、`res`、`last`は
MutualLoopのスロット共有から見れば通常のパラメータである。

### 関数ごとの書き換えではなくグループにする理由

`f`だけを書き換えても、ヘルパーパターンには効かない。`f`の箇所が呼ぶ
のは`g`であり、`g`には自分自身を呼ぶ箇所がないからである。蓄積版は
*呼び出し先*の蓄積版へ続けなければならないので、サイクル全体に同時に
蓄積版が必要になる。

### コストとリスク

- **コードサイズ。** 19個の`Maybe`の`map`クローンを含め、すべての
  メンバーが複製される。使われなくなったものはフェーズ1と同様に
  LateInlineとDeadCodeが縮める。
- **MutualLoopのグループが大きくなる。** マージされた`m#`のグループ
  には、メンバーごとに1つの選択肢がある。エントリはこれに含まれ
  ない。各エントリは`m#`の1つを一度呼ぶだけである。
- **評価順序。** フェーズ1の適格条件4と同じで、箇所ごとに検査する。
- **すでに互いに末尾呼び出ししているメンバー。** そのエントリは従来の
  グループのままで、MutualLoopがこれまでどおりマージする。`m#`版は
  それとは別の、2つめのグループになる。

### テスト

`Test113DeepRecursion/TrmcMutual.idr`が2つのケースを、それぞれ100万
要素で検証する。
- 関数と、`x :: f xs`を組み立てるヘルパー(ヘルパーパターン)。
- 2つめの型`Node Int Opt`を経由するチェーン。`mapOpt`が`One`、`Two`、
  `Three`の再帰フィールドを、番号0、1、2で埋める。`mapE`自身の
  ホールがフィールド1にあるので、グループのホールは番号0から2を使う。

どちらのヘルパーも、Inlineのしきい値より大きくしてある。小さな
ヘルパーはこのパスより前に呼び出し元へインライン化され、2つの関数
の組は単なる自己再帰になってしまう。`Maybe`自身の`map`も同じ運命を
たどる。インライン化するとフィールドの中に`case`が残り、どのフェーズ
もそれを扱えない。

期待される出力はChezから得る。このテストはvalgrind下でエラーなく
動き、`--directive notrmc`ではCスタックをあふれさせなければならない。

## フェーズ1の結果(2026-09-26)

**正しさ。** `Test113DeepRecursion/Trmc.idr`は、`map`、`filter`、
`zipWith`、数え上げビルダーを使って、100万要素のリストと`Link`/`End`
のチェーンを組み立て、valgrind下でエラーなく動く。
`--directive notrmc`を付けると、同じテストがCスタックをあふれさせる。
`Data.List.mergeBy`も、100万要素のリスト2つをマージできるように

## フェーズ4の測定結果(見送り、2026-09-27)

**所有する`last`の代わりに生のホールアドレスを使う案。** 新しいセル
ごとの`dup`1回と、前のセルの`drop`1回を省ける。実装せずに、節約量を
測定した。
- 100万要素のリストを50回`map`と`filter`するベンチマークの生成Cを
  手で編集し、2つのTRMCループ(エントリ、各箇所、各終端)から`last`
  の`dup`と`drop`をすべて削った。
- 編集したプログラムはvalgrind下でエラーなく動き、終了時に使用中の
  メモリも元のプログラムと同じだった。

実行時間は27.39秒から27.33秒になっただけである(0.3%)。どちらの
カウント操作も、書き込んだばかりでまだキャッシュにあるセルに対して
行うので、安い。これらのループのコストは別のところにある。同じ
ベンチマークがChezでは7.4秒で済む。perfによると、rc2の時間の大半は、
入力セルの参照カウントのロード(キャッシュミス)、そのフィールドの
アトミックな`dup`/`drop`、`malloc`に費やされている。入力のリストが
共有されているため、`map`はセルを再利用できない。

**フィールドの中の`case`の下にあるホール**(`Node x (case m of ..
Just (f e))`。`Maybe`の`map`をインライン化した結果として残る)は、
idris2-lspに3箇所ある。パスを作る価値はない。

## 見つかったバグ

1. **LateInlineが2つのパラメータを呼び出し元の1つのローカルに別名化
   した。** `mergeBy xs xs`は同じローカルを2回渡す。TRMCによって
   `mergeBy`のエントリが再帰を持たなくなると、LateInlineがそれを展開
   できるようになり、`buildSplice`が両方のパラメータをその1つの
   ローカルに別名化した。すると2つの`reuseOffer`が1つの確保領域を
   共有し、同じ記憶域に2つの新しいセルが作られたため、`mergeBy xs
   xs`が途中で切れたリストを返した。`buildSplice`は、同じ呼び出しの
   後ろにも引数が現れるパラメータに対して新しいローカルを束縛する
   ようになった。ループ搬送のパラメータでは、すでにそうしていた。
2. **`applyTrmc`の`where`束縛の集合。** このパスは最初、idris2-lspで
   20秒かかった。newtypeコンストラクタの集合を`where`で束縛していた
   ため、定義のたびに作り直されていたのである
   (`constant-constructor-specialization.md`の「`where`節の罠」)。
   `<- pure`で束縛するようにして、パスは0.1秒になった。
3. **Reuseがフィールドを持たないコンストラクタを提供した。**
   フェーズ3の木のテストが`mapT f Leaf = Leaf`でクラッシュした。
   TRMCの有無とは無関係である。Reuseがスクルーティニーのセルを、その
   分岐で作る`Leaf`に提供したため、Emitがそのセルに対して
   `idris2rc2_isUnique`を呼んだ。ところが畳み込まれた定数は`Leaf`を
   セルではなくタグ付きポインタ(`RCEmptyCon`)として持っており、その
   参照カウントを読んでフォールトした。フィールドのない選択肢には
   再利用する価値がないので、`Reuse.resolveAlt`はそれを提供しなく
   なった。
4. **ConstFoldが、畳み込まれた`Nothing`に対する`case`を残した。**
   フェーズ2のテストがコンパイルに失敗した。TRMCの有無とは無関係で、
   `case v of Nothing -> ..`で宣言されていないCローカルが出ていた。
   Inlineの後、ConstFoldが畳み込んだペアの`Nothing`フィールドを
   `case`が読んでいた。そのフィールドのローカルは`RCNull`に解決され
   たが、`RConCase`のケースにはそれに対する節がなかった。そのため
   `case`は、出力から`let`が消えたローカルの名前を使い続けた。どの
   パスがそれを落としたのかは突き止めていない。現在は、`NULL`の
   スクルーティニーに対して、`case`が持っている`Nil`、`Nothing`、`Z`、
   `MkUnit`のいずれかの選択肢を選ぶ。
